# v0.68.0: Production Native Performance

**Status: active (2026-09-23).** Phases 0 through 2 are complete. Phase 3 is next.

## Goal

Improve the runtime and code-size characteristics of native Nocter applications through one
target-independent optimization authority. The optimizer operates only after executable closure,
ownership, destruction, dispatch, layout, ABI transport, and machine operations are fixed. It
cannot inspect source, syntax, declarations, checking state, or MIR as a fallback.

This milestone optimizes generated programs rather than compiler or editor latency. `check` and LSP
requests therefore do not construct or run the optimizer. Native `build`, `run`, and `test` use the
same optimized `MachineProgram` boundary before target instruction selection.

## Completion Definition

v0.68.0 is complete when all of the following are true:

- every machine body follows one draft, optimization, immutable freeze, and dataflow-validation
  path, including compiler-generated destruction and erased-callable adapters;
- operation effects and trap preservation have one machine-owned legality classification;
- target-independent constant propagation, control-flow simplification, unreachable-code removal,
  dead pure-value removal, and redundant storage/address cleanup operate without source or semantic
  recovery;
- optimization preserves ownership transfer, drop order, recoverable failure, traps, allocation,
  blocking, asynchronous suspension, and cancellation behavior;
- ARM64 consumes the optimized immutable machine product and does not repeat target-independent
  optimization or ABI decisions;
- structural measurements show which transformations changed each representative native program,
  and external measurements compare generated code size and runtime on real standard-library and
  application workloads; and
- complete compiler, native, standard-library, example, documentation, packaging, and installed-home
  gates pass with no regression in deterministic output.

## Authority and Legality

`nocter-machine` owns optimization because it owns the representation being transformed. A separate
crate would either expose mutation of Machine internals or duplicate the representation. Machine
freezes a body only after optimization and derives liveness exactly once from that final body.

An operation may be removed only when Machine's exhaustive effect classification proves that it has
no externally observable action and cannot trap. Calls, stores, ownership transitions, destruction,
allocation-bearing erasure, pack consumption, error operations, region release, suspension, and
explicit safety checks are retained unless a later proof specifically establishes equivalence.
Absence of a known effect is never treated as proof of purity.

Safety checks remain part of program semantics. A check may disappear only when the optimizer
proves its failure condition impossible on the exact path. A statically failing check may become an
unconditional trap, but never undefined behavior.

## Measurement Boundary

Correctness tests assert transformation legality and native behavior. They do not use wall-clock
thresholds. Each optimized body retains a structural transformation report produced during its sole
optimization pass, so tests and milestone evidence do not rediscover changes by diffing private IR.

External performance evidence uses complete compiler-produced executables and records source,
compiler, installed-home, host, input, and sample identity. Compile latency is monitored for
regression but is not improved by moving optimization into `check` or editor paths.

## Phases

### Phase 0 — Contract and Baseline

**Status: complete.** The milestone fixes the optimizer boundary, safety rules, measurement split,
completion gates, and prohibition on source/MIR fallback. The existing pipeline was audited: Machine
already owns the target-independent operations and ARM64 already consumes that closed contract, so
no additional IR or pass-through crate is justified.

### Phase 1 — Canonical Body Freeze and Local Simplification

**Status: complete.** Every ordinary, generated-destruction, and erased-adapter body now enters one
Machine-owned draft-to-freeze path. The exhaustive effect authority conservatively separates pure,
trapping, and observable operations. Boolean constant propagation and constant branch/value-switch
simplification run before immutable tables and the sole dataflow construction, and each body retains
the exact transformation counts without rediscovering an IR diff. Machine, ARM64, and native-session
tests preserve native behavior across the boundary.

### Phase 2 — Reachability and Dead Values

**Status: complete.** Machine now computes the complete execution-resource closure from the entry
block, reachable control-flow edges, retained operations, function parameters, and deferred
execution state. One validated dense remapping authority removes unreachable blocks, unused pure
operations and values, and their unreferenced stack objects, addresses, drop flags, and pack state.
It rewrites every surviving cross-domain reference before immutable freeze; no sparse identity or
reachability decision escapes to ARM64. Operations in reachable code remain removable only when the
Phase 1 effect classification proves them pure and non-trapping.

### Phase 3 — Storage and Check Optimization

**Status: in progress.** Exact whole-stack stores and subsequent loads within one basic block now
share one local-storage proof. A forwarded load is removed through the existing dense pruning
remapper rather than a second IR rewrite. Callable boundaries, indirect stores, distinct types or
representations, and block edges stop the proof; checked address evaluation remains trapping until
a stronger exact-address proof exists. A non-parameter stack object is then removed with all of its
stores and addresses only when no projection, call argument, destruction, deferred-frame field,
cancellation action, region operation, switch, pack iterator, or unforwarded load can observe it.
Within a basic block, repeated drop-flag writes are coalesced only until a callable boundary; the
last state before branch, suspension, return, or exit remains authoritative for cleanup behavior.
General address evaluation remains trapping. Only a direct whole-stack address whose type, size,
and alignment exactly match its stack object receives a local non-trapping proof, allowing an
unused load or address materialization to disappear through the same pruning pass. Borrow
weakening now retains its distinct readonly semantic value while Machine proves that it shares the
mutable borrow's physical storage. ARM64 consumes that explicit identity, assigns the same virtual
register, and emits no copy; it does not infer semantic equivalence itself. ARM64 also plans
lane-complete direct aggregates once before frame placement. Exact register or immediate lanes are
constructed without a zero/store/load stack round trip, while partial-lane writes use the original
zero-initialized memory path. Frame placement and instruction selection consume the same plan, and
multi-lane general assignments use the existing cycle-safe post-allocation parallel-copy authority.

Forward values and copies across safe local regions, remove redundant loads, stores, address
materialization, borrow weakening, aggregate staging, and drop-flag transitions, and remove bounds
or arithmetic checks only from explicit proofs. Aliasing, calls, suspension, and ownership transfer
are optimization barriers unless Machine carries a stronger fact.

### Phase 4 — Native Workload Completion

Exercise the optimized product across synchronous, fallible, allocation-heavy, asynchronous,
cancellation, collection, parsing, compression, filesystem, process, networking, and HTTP programs.
Measure representative generated code size and runtime, attribute remaining dominant costs, and
make only target-specific improvements that belong to ARM64 selection or encoding.

### Phase 5 — Qualification and Review

Run the complete gates and review the full affected boundary for duplicate authority, safety-check
loss, stale pre-optimization dataflow, target-independent ARM64 peepholes, sparse identity leakage,
and benchmark-only production behavior. Release preparation begins only after that review has no
open material finding.

## Non-goals

- changing Nocter source semantics or weakening always-on safety checks;
- adding user-facing optimization attributes or an unstable optimization-level surface;
- moving optimizer work into `check`, LSP, or semantic queries;
- interprocedural source or declaration analysis after executable closure;
- profile-guided optimization, JIT compilation, LLVM integration, or a second native target; and
- accepting compile-time or memory regressions without measured generated-program benefit.
