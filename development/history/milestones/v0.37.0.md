# v0.37.0: Compiler and Editor Performance

**Status: release candidate qualified; publication pending (2026-09-06).**
v0.37.0 improves compiler, editor, and development-verification latency without changing source
semantics, diagnostics, native ABI, generated-program behavior, or LSP meaning. Work begins with
reproducible evidence and optimizes only an attributed dominant cost.

The active measurement boundary belongs to
[`development/design/performance-measurement-design.md`](../../design/performance-measurement-design.md).
Recorded results are non-normative milestone evidence.

## Phase 0: Measurement Authority and Released Baseline

Establish one repeatable runner for process-cold single-file checking, process-cold representative
package checking, and persistent body-edit editor analysis. Record v0.36.0 latency and memory where
the host exposes it. Keep external timing independent from deterministic query execution and reuse
counters.

**Status: complete.** The runner records exact compiler and source identities, host facts,
clean-worktree state, sample configuration, distribution summaries, and Darwin peak resident
memory. It uses only installed CLI and LSP contracts. The compiler's deterministic query counters
remain a separate structural signal.

The released v0.36.0 baseline was measured from clean repository revision
`678d8f75998bc181b1ee03f95d0a55ac0193f7d8` on the recorded Apple M1 host:

| Scenario | Median elapsed | Median peak resident memory |
| --- | ---: | ---: |
| Single-file cold check | 662.652 ms | 196,313,088 bytes |
| Representative package cold check | 717.804 ms | 206,422,016 bytes |
| LSP initialize | 124.647 ms | not measured |
| LSP open plus first checked hover | 535.996 ms | not measured |
| Body edit plus checked hover | 188.280 ms | not measured |
| Fifty measured edits in one session | 9,444.732 ms | not measured |

The complete distribution and input digests are retained in
[`development/benchmarks/baselines/v0.36.0-arm64-darwin.json`](../../benchmarks/baselines/v0.36.0-arm64-darwin.json).
The small difference between the two cold checks suggests a large fixed cost shared by both paths;
the repeated editor cost is independently material. This is an attribution hypothesis, not a
conclusion, and Phase 1 must profile both before selecting a production change.

## Phase 1: Bottleneck Attribution

Profile the slowest user-visible scenario and follow its owned data path. Use existing computation
counters first. Add temporary or permanent instrumentation only through an explicit observation
boundary when the bottleneck cannot otherwise be located. Select one structural cause rather than
optimizing scattered symptoms.

**Status: complete.** Query counters show that declaration preparation and unchanged sibling body
checking are reused. Sampling attributes about 65 percent of the repeated editor request to the
monolithic `ProgramFinalizationQuery`, which canonically replays every body and rebuilds whole-
program provenance, effects, loans, and source projection. The
[Phase 1 review](../reviews/v0.37.0-phase-1.md) records the evidence, root cause, rejected shortcuts,
and selected decomposition boundary.

## Phase 2: Cold Command Path

Remove repeated discovery, source observation, parsing, validation, or materialization from the
dominant cold command path when Phase 1 proves it material. Preserve fresh-process semantics and
the rule that each decision has one owner. A persistent disk compilation cache remains out of
scope.

Begin by replacing the three unindexed body-relation input slices with one checking-owned canonical
catalog. The catalog proves complete unique `BodyId` coverage once and gives provenance, effects,
and loans constant-time access to the same source, checked body, and origin facts. Measure this
prerequisite independently before selecting additional cold work.

**Status: complete.** One dense `BodyRelationCatalog` now replaces the three independently
expressible input slices, and `BodySourceCatalog` uses direct dense identity lookup as well. The
[Phase 2 review](../reviews/v0.37.0-phase-2.md) records verification and an alternating comparison
against v0.36.0. Repeated editor latency improved by 1.4 percent at the individual edit median and
2.1 percent over a fifty-edit session; cold paths remained effectively unchanged. This validates
the boundary cleanup but is far below the milestone target, so Phase 3 must address finalization
reconstruction itself.

## Phase 3: Incremental Editor Path

Reduce work after body-only edits through query keys, fingerprints, retained products, or source
projection boundaries as evidence requires. Editor features continue to consume the same checked
semantic products as commands; no editor-only meaning or source-text recovery may be introduced.

Move source-neutral relation facts and body-local finalization products across the query boundary,
while retaining one canonical program assembly. Solve type and closure identity explicitly; never
reuse a materialized body whose identities belong to an earlier replay branch.

**Status: complete.** Exact-current canonical replay, source-neutral relation analysis, and final
assembly are separate query contracts. Scalar literal edits reuse provenance, effect, and loan
facts while current semantic identities and source projection are rebuilt and rejoined. Immutable
semantic authorities are shared across the query boundary rather than deeply cloned. The
[Phase 3 review](../reviews/v0.37.0-phase-3.md) records the model, regression coverage, and
alternating measurement: median body-edit latency improved by 24.5 percent and the fifty-edit
session by 24.7 percent, while measured cold paths remained below the five-percent regression
limit.

## Phase 4: Backend and Output Path

Enter native lowering or output emission only if Phase 1 identifies it as a dominant user-visible
cost. Any change must preserve target-program, machine-program, ABI, and deterministic-output
boundaries. Otherwise close this phase explicitly as unnecessary.

**Status: closed as unnecessary.** Phase 1 attributed the dominant repeated-editor cost to semantic
finalization, and Phase 3 exceeded the milestone target there. No measured evidence justifies a
backend or output-path change in this milestone.

## Phase 5: Qualification

Compare the qualified candidate against v0.36.0 on the same host, run the complete compiler and
packaging gates, and review the change for duplicated authority, hidden recomputation, changed
diagnostics, editor divergence, and benchmark-specific production behavior.

**Status: complete.** The
compiler gate itself was measured before treating its long duration as unavoidable. Its integration
tests were executing compiler workspace code without optimization,
and the native-session suite compiled the complete public-example corpus a second time after the
stronger command-boundary tests had already compiled and executed it. Workspace-only test
optimization and removal of that subsumed smoke layer reduce a clean complete compiler gate from
569.31 seconds to 305.55 seconds on the recorded Apple M1 host, a 46.3 percent reduction. All
semantic, editor, native, architecture, formatting, feature, and Rustdoc checks still pass. The
[verification-throughput review](../reviews/v0.37.0-verification-throughput.md) records the
attribution, rejected runner shortcut, and retained coverage.

Ordinary command compilation was then measured independently rather than assumed to benefit from
the incremental-editor work. Retaining one immutable compile input, replacing complete type-prefix
maps with persistent cursors, and sharing one body-syntax projection authority reduced the paired
single-file check median by 24.4 percent and package check median by 26.4 percent. LSP open plus
first checked hover improved by 31.5 percent in the same comparison, and cold-check peak memory
fell by about ten percent. The
[ordinary-compilation review](../reviews/v0.37.0-ordinary-compilation.md) records the design,
measurement, and decision not to add speculative lazy transport initialization. Packaging and the
final release review remain.

The complete candidate was then compared directly with v0.36.0 through benchmark schema 2, which
records installed manifest and standard-library identities as well as the exact scenario source
sets. Single-file and package check medians improved by 23.6 percent, first checked hover by 28.0
percent, body-edit hover by 32.7 percent, and the fifty-edit session by 33.2 percent. A fifteen-
session confirmation found no material LSP initialization regression. The
[performance closure review](../reviews/v0.37.0-performance-closure.md) records the measurements
and boundary review. The [release-preparation record](v0.37.0-release-preparation.md) owns the
qualified release-content identity and retained artifact evidence.

## Completion Definition

v0.37.0 is complete when the dominant measured user path improves by at least 15 percent in median
latency without a regression above 5 percent in another measured major path, deterministic query
execution counts stay equal or improve, and complete semantic, editor, native, packaging, and
documentation qualification passes. If profiling finds no structurally sound opportunity capable
of meeting the target, the milestone must report that result instead of forcing a local shortcut.

## Non-goals

- persistent on-disk compilation artifacts
- generated-program runtime optimization without a measured compiler pathology
- changes to source semantics, diagnostics, ABI, or editor meaning
- benchmark-only fast paths in production code
- absolute timing guarantees across machines
- networking or additional standard-library API surface
