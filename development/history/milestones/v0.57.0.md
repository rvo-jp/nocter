# v0.57.0: Constant Generics and Fixed-Capacity Data

## Goal

Add one checked constant-generic model for storage sizes and fixed capacities, then use it for
practical allocation-free data structures. Constant arguments become evaluated semantic values
before type identity, layout, checking, or editor queries consume them; no downstream phase parses
or evaluates their source again.

## Completion Definition

v0.57.0 is complete when all of the following are true:

- declarations distinguish type parameters from `const N: usize` parameters and retain their
  authored order in one parameter schema;
- type applications accept a type or structural constant argument according to that schema and
  diagnose wrong domains, arity, unsupported constant types, and unevaluable values at the
  application site;
- the structural constant evaluator is the sole authority for concrete constant arguments;
- symbolic references to constant parameters can determine fixed-array lengths inside a generic
  declaration, and specialization replaces them with one checked `usize` value;
- normalized constant values participate in nominal type identity, substitution,
  monomorphization, layout, and ABI identity without source text or evaluator state;
- callable constant parameters are inferred from structural type positions such as `[T; N]`, and
  an otherwise unknown constant parameter is rejected rather than guessed;
- construction, instance patterns, interface applications, aliases, requirements, copyability,
  destruction, and overlap checking preserve the same mixed generic argument sequence;
- hover, signatures, completion, navigation, semantic highlighting, formatting, and diagnostics
  present the authored parameter domain and canonical evaluated arguments from semantic data;
- the standard library provides a fixed-capacity byte buffer and a generic stack-resident vector
  whose capacity is part of the type, with allocation-free construction and bounded mutation;
- native tests cover distinct capacities, full-capacity failure, generic calls, layout, and ABI;
  and
- whole-repository review finds no type-only arity shortcut, duplicated constant evaluation,
  downstream syntax reinterpretation, or layout rule that omits constant arguments.

## Semantic Boundary

v0.57.0 supports `usize` constant parameters. This is the storage-size domain required by fixed
arrays and capacities. Other scalar constant types, constant arithmetic predicates, defaults,
variadic generic packs, associated constants, and general dependent typing remain outside the
milestone.

The canonical declaration and application forms are:

```nct
struct Buffer<T, const N: usize> {
    values: [T; N]
}

let page: Buffer<u8, 4096>
```

A generic parameter schema is ordered, so type and constant parameters may be interleaved. A bare
name in an argument position is resolved exactly once against the corresponding parameter domain.
An argument for a constant parameter uses the structural constant-expression language; the syntax
tree retains an argument node, and declaration lowering produces a typed constant term or evaluated
value. Later phases never reinterpret the source spelling.

## Phases

### Phase 0 — Parameter and Argument Authority

Status: complete.

- freeze syntax, supported constant domain, and diagnostic ownership;
- replace type-only parameter metadata with one ordered parameter schema;
- introduce normalized semantic constant arguments and symbolic parameter terms; and
- keep syntax parsing independent of declaration lookup while preventing downstream re-parsing.

### Phase 1 — Type Construction and Substitution

Status: complete.

- lower mixed applications against the selected declaration schema;
- evaluate closed arguments through the structural constant evaluator;
- substitute symbolic parameters in fixed-array lengths and nested generic applications; and
- make equality, interning, aliases, patterns, and requirements preserve mixed arguments.

### Phase 2 — Inference, Selection, and Ownership

Status: complete.

- infer callable constant parameters from structural type positions;
- specialize construction, instances, interface implementations, copyability, and destruction;
- reject ambiguous or overlapping constant-specialized declarations without ranking; and
- prove that one substitution authority serves ordinary calls and interface dispatch.

### Phase 3 — Layout, ABI, and Execution

Status: active.

- include evaluated values in monomorphization and executable-item identity;
- derive fixed-array and nominal layout only after substitution closes every size;
- carry closed capacities through MIR and target lowering without evaluator access; and
- add native ABI and execution coverage for distinct capacities.

### Phase 4 — Fixed-Capacity Standard APIs

Status: planned.

- add a fixed-capacity byte buffer for protocol and I/O staging;
- add a generic stack-resident vector with checked bounded mutation;
- provide allocation-free adapters where existing iterator contracts suffice; and
- document when fixed-capacity and dynamically allocated collections are appropriate.

### Phase 5 — Editor and Qualification

Status: planned.

- expose parameter domains and canonical arguments through semantic presentation;
- complete formatting, navigation, rename, completion, and diagnostics;
- run compiler, editor, standard-library, native, documentation, installation, and packaging
  gates; and
- review every generic consumer for type-only assumptions and repeated constant work.

## Deferred Work

Constant parameters of types other than `usize`, symbolic arithmetic over constant parameters,
constant defaults, constant inequalities and other arithmetic predicates, associated constants,
compile-time owned allocation, general dependent types, and user-defined value domains remain
deferred. Closed constant arguments may still use the structural constant-expression language;
only an expression that remains symbolic after declaration checking is restricted to one bare
constant parameter in v0.57.0.
