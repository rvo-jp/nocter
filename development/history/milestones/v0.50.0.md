# v0.50.0: Local Data and Asynchronous Streaming

## Goal

Complete one coherent local-data pipeline so a Nocter program can discover files, read and write
them without blocking the executor, transform asynchronously produced items with bounded memory,
and connect local storage to the existing network, HTTP, TLS, and process byte-stream contracts.

This milestone is not a collection of asynchronous wrappers. It introduces one owned blocking-job
boundary for target operations that cannot use readiness notification, one canonical asynchronous
filesystem surface, and one asynchronous item-consumption model. Every public facility must compose
through those shared contracts.

## Completion Definition

v0.50.0 is complete when all of the following are true:

- no canonical asynchronous filesystem operation executes a blocking syscall on the executor
  thread;
- queued, running, completed, cancelled, and abandoned blocking jobs have closed ownership and
  cleanup rules;
- the blocking-job service has bounded workers and bounded admission rather than spawning an
  unbounded thread or retaining an unbounded queue;
- `File` and ordinary filesystem operations are executor-safe, while explicitly named blocking
  twins remain available for synchronous programs;
- regular-file streaming, positioning, metadata, links, mutation, directory traversal, and
  recursive traversal have documented error, partial-progress, and cancellation behavior;
- `AsyncIterator` and `for await` provide one language-level item-consumption contract for
  directory entries and other asynchronous producers;
- byte chunks, text lines, directory traversal, process pipes, and existing network transports can
  participate in bounded streaming pipelines without subsystem-specific control loops;
- at least one complete application recursively discovers local input, transforms it, connects it
  to another I/O endpoint, handles cancellation and errors, and remains bounded in memory;
- compiler, LSP, formatter, standard-library, conformance, documentation, and release gates pass;
- a final repository-wide review finds no retained compatibility path, duplicate lifecycle
  authority, target-ABI reconstruction, or caller-dependent cleanup obligation in this area.

## Design Boundaries

### Owned Blocking Jobs

A submitted job owns every byte and operating-system resource that target code may access after
submission. A running syscall never retains a pointer into an abandoned Nocter future or caller
buffer. Read jobs publish owned output only after completion; write and path jobs retain owned input.
Dropping a future either removes a job that has not started or abandons an in-flight result to the
service, whose completion path performs the same close-once cleanup without publishing into caller
storage.

The service exposes typed job and completion roles. Standard-library source selects semantic
operations; it does not know queue records, worker synchronization, native callback layouts, or
completion-channel encoding. The task runtime observes a generation-qualified completion interest;
it cannot inspect filesystem operation state.

Worker and admission capacity are fixed by the runtime contract. Saturation applies backpressure;
it never creates an unbounded thread or queue. Executor shutdown stops admission, detaches waiters,
and drains or safely abandons every accepted job before releasing service storage.

### Canonical and Blocking Surfaces

The unqualified filesystem surface is executor-safe, matching the existing `Reader`, `Writer`,
network, HTTP, TLS, and process conventions. Synchronous operations are explicit through
`BlockingFile`, `BlockingReadDir`, and `_blocking` operation names. The two surfaces share domain
validation, portable result values, descriptor ownership, and public error classification. An
asynchronous implementation does not call a public blocking wrapper, and the blocking surface does
not drive an executor internally.

No compatibility aliases preserve the v0.49.0 spelling. The migration is one authority replacement.

### Asynchronous Items

`AsyncIterator` owns one associated `Item` and one asynchronous mutable `next` operation. `for await`
is syntax for consuming that contract with ordinary loop cleanup and control flow; it is not a
second iteration protocol. Early exit, `return`, failure propagation, and future destruction release
the iterator exactly once.

The initial adapter set may use synchronous closures after an item becomes available. Asynchronous
closures and generator declarations are not prerequisites for the iteration contract and do not
receive ad hoc encodings in this milestone.

### Bounded Streaming

Byte and item adapters own an explicit bounded buffer or obtain bounded storage from their source.
Downstream readiness controls upstream progress. Convenience collection remains available where an
API says it allocates the complete result, but no streaming API silently materializes an unbounded
input.

## Phases

### Phase 0 — Blocking-Job and Completion Model

Status: completed.

- freeze job identity, lifecycle, capacity, admission, completion, abandonment, and shutdown;
- add a target-independent blocking-job owner separate from the task scheduler;
- reuse readable-descriptor readiness as a wake-only channel while retaining exact JobId
  observation in the lifecycle service;
- define the Darwin worker and wakeup boundary without exposing native records to standard source;
- prove stale completion rejection, saturation, cancel-before-start, abandon-while-running,
  completion-without-waiter, and shutdown cleanup with deterministic model tests;
- record dependency direction and prohibit filesystem policy from entering the runtime service.

Phase 0 closed with a target-independent lifecycle authority, a fixed-worker Darwin conformance
adapter, wake-only descriptor integration, deterministic lifecycle tests, and mechanically checked
production dependency boundaries. The implementation review is recorded in
[`development/history/reviews/v0.50.0-phase-0.md`](../reviews/v0.50.0-phase-0.md).

### Phase 1 — File and Local-Storage Surface

Status: completed.

- replace the blocking-only canonical `File` surface with executor-safe `File` and explicit
  `BlockingFile`;
- implement open, create, append, read, write, flush, close, position, seek, truncate, and
  positioned I/O;
- keep descriptor state, portable validation, and public error mapping singular;
- specify and test partial progress, terminal state, cancellation, and drop behavior.

Phase 1 closed with one executor-safe `File`, one explicit `BlockingFile`, asynchronous and
blocking whole-file helpers, cursor and positioned operations, opaque runtime-owned file storage,
and one generated completion ABI. Semantic primitive roles select open modes and seek origins, so
standard source cannot manufacture target tags. Compiler construction checking, formatter-visible
syntax, hover, definition, implementation navigation, generated cancellation, native explicit
close, implicit drop, and process shutdown are qualified. The implementation review is recorded in
[`development/history/reviews/v0.50.0-phase-1.md`](../reviews/v0.50.0-phase-1.md).

### Phase 2 — Filesystem Completion

Status: active.

- provide asynchronous and explicit blocking metadata, link, canonicalization, copy, rename,
  creation, removal, and directory operations;
- add recursive creation, removal, and traversal with explicit non-transactional failure rules;
- keep raw target facts, UTF-8 path policy, traversal policy, and public error policy in separate
  owners;
- prevent recursive helpers from accumulating an unbounded implicit work list.

The completed Phase 2 ranges extend the Phase 1 bounded service with ownerless owned-path jobs for
single-entry removal, rename, single-directory creation, and empty-directory removal. Their
canonical public functions are asynchronous, their synchronous twins carry `_blocking`, both
surfaces consume the same path validation and error policy, and mutation is attempted once rather
than retried after an ambiguous interruption. Metadata and existence queries now use the same
bounded service; the worker decodes target `stat` storage into portable completion facts before
standard source constructs `Metadata`. Directory acquisition and raw record batches now use the
same bounded service and pre-reserved descriptor retirement. The worker owns each output batch and
completion alone copies its initialized prefix into caller storage; asynchronous and blocking
streams share one record decoder and public error policy. Recursive directory construction now has
canonical asynchronous and explicit blocking forms over one shared prefix scanner. Links,
canonicalization, copy, recursive removal, and traversal remain open Phase 2 work.

### Phase 3 — Asynchronous Iteration

Status: planned.

- specify and implement `AsyncIterator` and `for await`;
- integrate parser, declarations, checking, ownership, lowering, cleanup, formatter, diagnostics,
  hover, semantic tokens, completion, and navigation;
- use one checked acquisition and dispatch decision rather than lowering-time lookup;
- prove early-exit, failure, move, borrow, cancellation, and destruction behavior.

### Phase 4 — Streaming Adapters

Status: planned.

- add bounded byte-chunk, text-line, directory-entry, and recursive-walk producers;
- add the useful synchronous-transform subset of map, filter, enumerate, and take;
- connect file, process, network, TLS, and HTTP byte sources through existing `Reader` and `Writer`
  contracts;
- keep framing and decoding policy in adapters rather than the executor or job service.

### Phase 5 — Cross-I/O Composition

Status: planned.

- validate file-to-file, HTTP-to-file, file-to-process, and process-to-file pipelines;
- make timeout, cancellation, downstream failure, and partial-output precedence observable and
  consistent;
- eliminate endpoint-specific copies of generic transfer logic.

### Phase 6 — Complete Application

Status: planned.

- add one runnable asynchronous local-data application exercising recursive discovery, streaming
  transformation, another I/O endpoint, cancellation, and recoverable errors;
- keep the example bounded in memory and free of compiler- or platform-specific escape hatches;
- treat any required application-local lifecycle workaround as an incomplete shared contract.

### Phase 7 — Integration and Release Qualification

Status: planned.

- complete documentation, editor support, conformance, stress, and leak-oriented verification;
- remove superseded names, wrappers, primitive roles, and duplicated target paths;
- review the whole repository for authority duplication, reverse dependencies, recomputation, and
  caller-dependent cleanup;
- run deterministic packaging and installed-toolchain qualification before requesting publication.

## Non-goals

- public threads, arbitrary worker closures, detached tasks, or parallel iterators;
- asynchronous closure bodies or generator declarations;
- filesystem watchers, memory mapping, advisory locking, or target-specific permission APIs;
- shell parsing, implicit executable search, or terminal control;
- targets other than `arm64-darwin`;
- compatibility aliases for the v0.49.0 blocking filesystem surface.
