# v0.65.0: Practical Stateful Services

**Status: active.** v0.65.0 is one vertical application milestone rather than a sequence of
unrelated library additions. It starts from shared state and bounded asynchronous coordination,
then carries those foundations through service lifecycle, typed HTTP application data, routing,
sessions, observability, and one complete server example.

## Goal

Make a long-running Nocter service practical to write and reason about. One process must be able to
share owned state between asynchronous operations, coordinate bounded work without blocking the
executor, stop cleanly, decode common HTTP application data, route requests through shared state,
and expose useful operational context.

The milestone must preserve Nocter's ownership and effect contracts. Shared state is explicit,
bounded queues provide backpressure, cancellation cannot leak a lock or endpoint, and asynchronous
waiting continues to use the executor's existing readiness model rather than a parallel scheduler.

## Completion Definition

v0.65.0 is complete when all of the following are true:

- a page-backed shared-storage authority supports deterministic clone and last-owner destruction
  without permitting a shared value to escape through a region allocation;
- a public synchronization module provides a bounded channel, shared mutual exclusion, and an
  explicit cancellation source/token contract suitable for cooperative asynchronous tasks;
- channel capacity is part of the type, send and receive preserve FIFO order, closure is observable,
  and cancellation or dropped endpoints cannot strand owned values;
- synchronization waits reuse one target-independent notification contract over existing descriptor
  readiness, with no polling timer, spin loop, process-module dependency, or second executor model;
- service code can observe termination requests and perform graceful shutdown through structured
  task ownership;
- HTTP applications can decode query values, forms, media types, and cookies through owned or
  explicitly borrowed representations with bounded parser behavior;
- routers can carry explicit application state without global mutable storage or hidden cloning;
- session and logging APIs compose the stateful router while retaining explicit failure and
  redaction boundaries;
- one complete example runs a concurrent stateful HTTP service and exercises startup, requests,
  shared state, shutdown, and operational output; and
- compiler, editor, native, standard-library, documentation, example, and packaging gates pass.

## Responsibility Boundaries

`std/internal/shared` owns page-backed shared allocation, reference counting, value projection, and
last-owner destruction. It is package-only infrastructure. Public synchronization types cannot
duplicate its pointer arithmetic or release policy.

`std/internal/notify` owns one nonblocking task-notification descriptor pair and its retry and close
rules. Raw descriptor primitives belong to the target OS adapter. Process pipes and synchronization
notifications are separate owners that consume that adapter; neither imports the other's internal
representation.

`std/sync` owns public shared-state and bounded-coordination semantics. It may depend on internal
shared storage, internal notification, fixed-capacity storage, and task readiness contracts. It does
not know scheduler queues, target syscalls, HTTP types, or process-pipe state.

`std/process` owns process lifecycle and standard-stream pipes. Moving generic descriptor
primitives to the OS adapter does not move process ownership or child-I/O policy.

`std/http` owns application-data decoding and stateful routing. It consumes synchronization through
public contracts and cannot inspect shared allocation, wakeup descriptors, or executor state.

The compiler and native backend continue to own future lowering and readiness execution. The
standard library describes synchronization through existing future and descriptor-readiness
contracts; it does not introduce compiler-recognized synchronization type names.

## Core Invariants

- Nocter user tasks currently execute cooperatively on one executor thread. Shared reference counts
  and lock state are therefore non-atomic and are never valid across foreign threads. A future
  multithreaded executor requires a new checked contract rather than silently changing this rule.
- Shared allocations always use the page allocator. Region storage cannot outlive its lexical
  release boundary and is never accepted as shared backing storage.
- Each shared allocation contains exactly one reference count and one initialized value. Cloning
  changes only the count; the final handle drops the value once and releases the mapping once.
- A mutex guard is the sole capability that exposes mutable access. Dropping the guard releases the
  lock and notifies waiters, including during future cancellation.
- A bounded channel never allocates after construction. Endpoint counts and queued values live in
  the same shared state, and the final receiver destroys every value that was not received.
- Notification bytes are wake hints, not semantic state. Every operation rechecks shared state after
  wakeup, so coalesced, stale, or spurious readiness cannot change channel or mutex behavior.

## Phases

### Phase 0 — Shared Ownership and Notification Foundation

**Status: active.** Freeze the ownership and wakeup model, move generic descriptor primitives from
the process surface to the target OS adapter, implement package-only shared storage and notification
owners, and prove their destruction and cancellation invariants independently of public APIs.

### Phase 1 — Bounded Coordination

**Status: planned.** Add `Mutex<T>`, `MutexGuard<T>`, `Sender<T, N>`, `Receiver<T, N>`, and explicit
cancellation source/token values. Establish FIFO, backpressure, close, clone, drop, and cancellation
tests before application adoption.

### Phase 2 — Service Lifecycle

**Status: planned.** Add termination-signal observation and a structured service scope that stops
accepting work, cancels outstanding waits, and joins owned tasks before returning.

### Phase 3 — HTTP Application Data

**Status: planned.** Add strict query/form decoding, media-type handling, and cookie parsing and
rendering. Reuse existing URL, scanning, header, and encoding authorities instead of introducing
HTTP-local text parsers.

### Phase 4 — Stateful Routing

**Status: planned.** Let one router carry explicit shared application state and pass it to handlers
without globals, hidden allocation, or duplicated route selection.

### Phase 5 — Sessions and Observability

**Status: planned.** Build signed or opaque session identifiers from existing randomness and codec
contracts, and add structured operational logging with explicit redaction and request context.

### Phase 6 — Complete Service and Review

**Status: planned.** Replace isolated demonstrations with one complete stateful service, run the full
validation matrix, and review the repository for duplicate ownership, waiting, parsing, routing,
session, or logging authorities before release preparation.

## Non-goals

v0.65.0 does not add a multithreaded executor, lock-free atomics, unbounded queues, distributed
sessions, a database client, HTTP/2, a general web framework, or compiler-recognized synchronization
types. It does not use timer polling as a substitute for readiness notification.
