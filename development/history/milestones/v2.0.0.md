# Nocter v2.0.0: Compile-Time Optimization and Minimal Syntax

## Status and Authority

Planning only. No v2.0.0 compiler implementation or release qualification is claimed. The decisions
below were adopted on 2026-11-07 as direction for the next major language design. The target name
does not imply that an intervening major release exists or that a release date has been selected.

This milestone records adopted direction, pending design questions, work order, and acceptance
criteria. It does not change current language behavior. [`spec/`](../../../spec/README.md) remains
the sole normative source for supported behavior; future changes must update their owning chapters
before compiler implementation. Existing release qualification and publication work remains a
separate boundary.

## Primary Goal

Target faster generated-program execution than Rust through compile-time evaluation, static
analysis, specialization, and optimization. This is the primary performance objective, not a claim
that the current compiler is faster or that every program can outperform every Rust equivalent.
Define representative workloads and comparison conditions before claiming an advantage.

Preserve memory safety and observable program semantics. Keep source syntax to the minimum needed
to express program behavior and supply information the compiler cannot soundly derive. Learning
cost matters: ordinary application authors should not have to describe optimization machinery.
Evaluate complete tasks such as adding a callback or decoding a value, rather than optimizing
keyword count or source length in isolation.

Prefer doing work during compilation when it removes runtime work without changing behavior.
Longer compilation may be an acceptable tradeoff for faster executables, but record compiler time
and memory so pathological specialization or evaluation does not become an unbounded default.

The independent native backend remains an asset for self-contained distribution and optimization
control. LLVM independence alone is not evidence of faster application execution than Rust.
Performance claims require measurements with stated safety and failure semantics.

## Adopted Direction

### Move Work to Compilation and Require a Reason for Syntax

Adopt the following design priorities:

- Evaluate computations whose inputs and effects permit compile-time execution; runtime input
  remains runtime input. Do not require applications to restate facts already available to the
  compiler merely to request optimization.
- Infer ownership, borrowing, provenance, and execution facts where sound. Retain those facts in
  compiler products so optimization can use them without reconstructing source semantics.
- Prefer static specialization and direct calls when concrete targets are known. Investigate
  removing temporary storage, redundant copies, allocation, checks, and abstraction overhead
  before adding source-level optimization controls.
- Require each proposed syntax form to identify the program meaning or otherwise unavailable
  information it expresses. Use inference or a library API when that is sufficient. Fewer tokens
  alone are not a justification for a new form.
- Preserve safety, failure, side-effect, and destruction behavior. Unknown facts require a sound
  conservative result, not unchecked execution. Reordering, speculation, and compile-time
  evaluation must not introduce or hide observable effects.
- Do not introduce implicit copying, reference counting, or tracing collection solely to hide an
  ownership error. A different memory model remains a separate proposal whose semantics and
  runtime costs must be evaluated against the primary performance objective.

These are adopted design criteria. They do not adopt any particular optimizer pass, expand the
current constant-evaluation domain, relax a safety check, or authorize a new memory model. The
current specification and compiler authority boundaries continue to apply until a separately
specified change replaces them.

The adopted capture inference and explicit callable type arguments serve this direction together:
inference removes routine source obligations, while an explicit type argument supplies a concrete
substitution when inference alone cannot determine it. Neither requires dynamic dispatch or an
implicit allocation as part of its language meaning.

### Infer Closure Captures

Ordinary closures should infer captures from references to enclosing local values. A caller should
not need to write a capture list for a simple predicate:

```text
let threshold = 10
let predicate = (value: i32) {
    value >= threshold
}
```

This illustrates planned v2.0.0 behavior, not a program accepted under the current explicit-capture
contract.

The adopted model infers readonly borrowing for reads, readwrite borrowing for mutation, and owned
capture when the body consumes an outer value. Inference must preserve exclusivity, storage
lifetime, callable invocation capability, and exactly-once destruction. It must not silently copy
an owning resource, introduce reference counting, or retry a rejected borrow with a different
ownership policy merely to make the program compile.

Retain a way to request owned capture when a closure must outlive the current scope. Its precise
syntax and interaction with existing explicit capture lists remain design work. Ordinary explicit
`move` expressions outside capture inference have not been changed by this decision.

Before specification adoption, settle:

- whole-binding versus projection-sensitive capture, including overlapping uses;
- precedence when one capture is read, mutated, and consumed on different reachable paths;
- inferred capture initialization and destruction order, including observable cleanup;
- nested closures, copyable captures, and contextual callable requirements;
- escaping closures and the diagnostics or explicit ownership request they require;
- editor presentation of inferred captures without requiring annotations in ordinary source.

Owning chapters: [Callable Values](../../../spec/language/callables.md),
[Ownership](../../../spec/language/ownership.md), and the closure productions in
[Syntactic Grammar](../../../spec/language/syntactic-grammar.md).

### Allow Explicit Callable Type Arguments

Adopt explicit type arguments at call sites, including the following form:

```text
let config = decode<Config>(bytes)?
```

Omitting type arguments continues to request inference. Explicit arguments select generic
substitutions; they do not bypass bounds, ownership, provenance, or execution-contract validation.
This replaces the current rule that a callable's own type arguments can never be written.

The design must distinguish arguments belonging to a type owner, such as
`Container<Item>.make(...)`, from arguments belonging to the selected callable. Apply a coherent
policy to functions, methods, and construction functions rather than adding an isolated special
case for top-level calls.

Before specification adoption, settle:

- complete argument lists and their correspondence to declared generic parameters;
- whether partial lists, placeholders, or mixed type/constant argument lists are supported;
- nested generic delimiters, comparison expressions, whitespace, and newline recognition;
- interaction with contextual result typing and closure parameter/result inference;
- parser recovery and diagnostics for wrong arity, wrong argument kind, and unsatisfied bounds.

Partial arguments, defaults, placeholders, and named arguments are not adopted by this decision.
Parsing must remain independent of name resolution and semantic type information.

Owning chapters: [Generics and Interfaces](../../../spec/language/generics-and-interfaces.md),
[Construction](../../../spec/language/construction.md), and
[Syntactic Grammar](../../../spec/language/syntactic-grammar.md).

### Keep Advanced Contracts out of Ordinary Application Code

Adopt the goal that ordinary application authors should generally be able to write programs
without authoring `noalloc`, `notrap`, `from`, or `region`.

Use implementation inference, suitable library APIs, and existing elision where sound. Keep
explicit contracts available for library guarantees, ambiguous storage relationships, constrained
allocation, and performance-sensitive boundaries. This goal does not remove allocation guarantees,
trap checks, provenance validation, or region escape checking. It does not authorize automatic
strengthening of a public API from its current implementation.

Do not make an ordinary callback or collection operation require users to learn a new effect
parameter system. Any future effect-composition design must demonstrate a reduction in application
annotation burden before adoption. Blocking behavior and asynchronous drive safety remain separate
contracts; this goal does not authorize hiding a blocking operation inside a nonblocking future.

Evaluate API usage separately from authoring specialized libraries: applications may rely on a
library's guarantees without spelling those guarantees themselves.

## Proposals Requiring Further Evaluation

The following suggestions have not been adopted. Do not implement or describe them as v2.0.0
commitments without a separate decision:

- removing `see`, changing same-module visibility, or replacing handwritten contract/body pairs;
- unifying `construct`, `instance`, and `method`;
- making ordinary ownership transfers implicit or changing `&+T` spelling;
- replacing `T!` with a named result type or changing forced unwrap syntax;
- generalized outcome nesting, a storable unit type, and typed errors;
- optimized default layout, niche representations, or explicit fixed-layout contracts;
- allocation-free concrete futures, borrowed callable erasure, and generalized effect composition;
- safe partially initialized buffers, disjoint mutable slice APIs, and later-stage safety proofs;
- SIMD facilities, numeric reordering contracts, or a different shared-memory concurrency model.

Document each candidate's task-level benefit, semantic cost, migration impact, and interaction with
the adopted changes. A list of proposals is not an implementation schedule.

## Investigation: Programming without Ownership Annotations

Investigate how far programmers can write code without reasoning about ownership. This is an open
investigation, not adoption of implicit moves, automatic borrowing, ARC, GC, or copy-on-write.

Distinguish three objectives:

1. Omit capture and lifetime-related syntax in common local code.
2. Avoid ownership-driven restructuring for common application tasks through safe library APIs.
3. Accept arbitrary sharing, escaping references, and mutation without ownership reasoning.

The adopted capture inference directly advances the first objective. The second needs concrete API
and diagnostic evaluation. The third changes the memory-management and aliasing model and cannot
be promised as a consequence of inference alone.

Compare static ownership/borrow inference with restricted accepted programs, automatic reference
counting with a defined cycle policy, tracing collection, and value semantics with explicit copy
or copy-on-write behavior. Record runtime operations, memory retention, allocation failure,
destruction timing, identity, shared mutation, and concurrency consequences. Automatic memory
reclamation does not resolve the intended semantics of shared mutation or resource protocols.

Prioritize static inference under the existing deterministic ownership model. The alternatives
above are comparison subjects, not equally preferred implementation directions: hiding ownership
syntax must be assessed against generated-program speed and the cost of any remaining runtime
memory-management operations.

Research evidence includes
[Perceus: Garbage Free Reference Counting with Reuse](https://doi.org/10.1145/3453483.3454032),
which combines reference counting with reuse for a functional core and establishes its garbage-free
result for cycle-free programs. It is evidence for a possible approach, not proof that arbitrary
Nocter programs can receive the same guarantees or run faster than Rust. Swift's
[ARC discussion](https://developer.apple.com/videos/play/wwdc2021/10216/) also illustrates why
automatic reference counting still needs a policy for strong reference cycles.

Before recommending a memory-model change, compare small programs that retain callbacks, store
views into growing collections, share mutable state, and create cyclic graphs. Explain which
programs compile, what aliasing means, when resources are released, and what runtime costs remain.
Do not silently clone, share, or prolong resource lifetimes as an error-recovery strategy.

## Work Order and Completion Gates

1. **Establish performance evidence.** Select representative application workloads and CPU-bound
   kernels, and record a Nocter baseline and optimized Rust equivalents. Use the existing
   [measurement boundary](../../benchmarks/methodology.md). Record algorithms, inputs, outputs,
   safety and failure semantics, compiler versions and options, CPU, allocation behavior, and
   executable identities. Report ordinary optimized configurations and any settings needed for a
   closer safety comparison separately. Measure runtime distributions, peak memory where available,
   executable size, and compilation cost; no speed advantage is established by this plan alone.
2. **Close the design.** Write minimal examples for each pending capture and explicit-call question;
   obtain decisions where materially different observable behaviors remain. Record the selected
   rules in the owning specification chapters, including grammar, formatting, diagnostics, and
   editor behavior. This phase is pending; the high-level decisions above are already adopted.
3. **Implement capture inference.** Cover readonly, readwrite, and consuming captures; nested and
   escaping closures; conflicting loans; copyability; and normal, failure, and cancellation cleanup.
   Keep inference independent from unadopted changes to ordinary move expressions.
4. **Implement explicit callable arguments.** Cover inferred and explicit calls, owner/callable
   separation, nested generic syntax, contextual closures, bounds, and invalid argument lists.
   Resolve substitutions once and reuse the existing specialization and dispatch authorities.
5. **Investigate measured runtime costs.** Attribute bottlenecks and evaluate compile-time
   computation, specialization, ownership-aware storage transformations, and loop optimization
   against them. Each candidate needs its own design and correctness argument before
   implementation. Compare generated code and runtime evidence, and retain semantic information
   explicitly at the stage that consumes it. A shorter source program or a larger optimizer pass
   count is not evidence of faster execution.
6. **Verify the complete product.** Update formatter, tokens/AST output, diagnostics, completion,
   signature help, hover, navigation, and compiler conformance cases. Exercise both features
   together, including a generic call with a capturing callback. Run authoritative compiler gates
   and documentation generator tests with an out-of-repository site build.
7. **Evaluate learning cost and performance together.** Have learners write a capturing filter,
   specify a decode result type, and repair a borrow error. Record explanations needed, mistakes,
   and successful repairs. Check
   representative application examples for avoidable advanced annotations; do not remove a
   necessary contract merely to improve a count. Confirm that inference and source simplification
   do not introduce hidden allocation, copying, dispatch, or memory-management costs. Use the
   recorded workloads to evaluate the runtime-speed objective and document regressions as well as
   improvements; report any remaining gap to Rust without claiming the objective has been met.

Implementation is incomplete until code generation and destruction preserve the selected semantics,
tooling presents the same decisions, and current documentation no longer contradicts the adopted
rules. Publication requires its own future release qualification and authorization.
