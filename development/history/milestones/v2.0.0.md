# Nocter v2.0.0: Compile-Time Optimization and Minimal Syntax

## Status and Authority

Planning only. No v2.0.0 compiler implementation or release qualification is claimed. Initial
direction was adopted on 2026-11-07; subsequent source decisions are recorded in the linked review.
These define direction for the next major language design. The target name
does not imply that an intervening major release exists or that a release date has been selected.

This milestone records adopted direction, pending design questions, work order, and acceptance
criteria. It does not change current language behavior. [`spec/`](../../../spec/README.md) remains
the sole normative source for supported behavior; future changes must update their owning chapters
before compiler implementation. Existing release qualification and publication work remains a
separate boundary.

The subsequent [implementation-readiness review](../reviews/v2.0.0-implementation-readiness.md)
records autonomous semantic closure, a bounded reservation/ownership model check, conservative
optimization conditions, and the specification/implementation entry gates. Human-facing source
choices are isolated in the [source-design review](../reviews/v2.0.0-source-design-decisions.md).
These records advance design; they do not claim v2.0.0 compiler support.

The later S8/S9 source decisions adopt type-side ordinary input/results, operation-directed
local inference, explicit standalone transfer, canonical receiver abbreviations, and
`func`/`mut`/`once` invocation types. A bare existing place supplies I; `^place` supplies X; calls
supply their declared result permission. Earlier result/binding-prefix examples in historical
reviews are not alternate source styles. S10 adopts qualifier scope through outcome wrappers
and retains complete implementation signatures: body readers must not need a second source
merely to recover the signature. Remaining full composition/module migration and validation
still require closure.

The [typing/migration review](../reviews/v2.0.0-access-typing.md) records the first partial
specification migration. The explicitly future [Value Access Model](../../../spec/language/value-access.md)
and linked owning sections now define the operation/Copy/binding/return foundation, origin
relationships, callable modes, storable unit, and access-syntax fragments. Current released
rules remain active. Outcome/async composition, captures, full grammar, and other adopted
contracts still need coherent migration; no implementation-ready or full-soundness claim follows.

## Primary Goal

Choose coherent source semantics and give the compiler the freedom and information to produce the
best execution it can justify for those semantics, inputs, and target. Use compile-time evaluation,
static analysis, specialization, and optimization to remove unnecessary runtime work. Exceeding
Rust may be a consequence; a Rust comparison, relative-speed threshold, or near-term competitive
result is not a design requirement or completion gate.

Implementation effort and short-term delivery are not criteria for rejecting a better model.
Consider replacing existing ownership, type-checking, representation, and standard-library designs
when that produces a clearer and more optimizable language. Current implementation boundaries
remain authoritative for current behavior, not permanent limits on v2.0.0 design. There is no
requirement to preserve a design merely to reuse existing compiler work.

Preserve memory safety and observable program semantics. Keep source syntax to the minimum needed
to express program behavior and supply information the compiler cannot soundly derive. Learning
cost matters: ordinary application authors should not have to describe optimization machinery.
Evaluate complete tasks such as adding a callback or decoding a value, rather than optimizing
keyword count or source length in isolation.

Prefer doing work during compilation when it removes runtime work without changing behavior.
Longer compilation may be an acceptable tradeoff for faster executables, but record compiler time
and memory so pathological specialization or evaluation does not become an unbounded default.

The independent native backend remains an asset for self-contained distribution and optimization
control. Correctness proofs, inspection of generated operations, and measurements of Nocter
workloads assess whether a transformation helps; comparative marketing claims are not the reason
to select the semantics. A universal globally optimal executable is not promised: resource use,
latency, throughput, and compilation work require explicit objectives and assumptions.

The [runtime performance research review](../reviews/v2.0.0-runtime-performance-research.md)
examines selected 2024–2026 results and foundational value-semantics work. Its earlier proposals for
mandatory Rust comparisons and relative-speed goals are superseded by this direction; published
research observations remain evidence with their original limits. It does not adopt new language
semantics or establish measured Nocter speedups.

The redesign must reduce three costs together: the source a person must read to work on a task,
the code they must write and maintain, and the decisions they must make about compiler machinery.
The physical organization is part of that goal. Directory modules reveal structure, `index.nct`
collects the public contract, and direct `see` edges identify relevant private sources. These
boundaries reduce the human working set; they are not restrictions on the compiler's whole-program
analysis or optimization.

Required semantic information is different from required notation. Preserve information needed
for safety, intended behavior, and efficient execution, but do not require authors to repeat it
when the compiler can soundly derive it from an authoritative contract or checked implementation.
No amount of extra source text establishes a speed advantage by itself. Two spellings that select
the same checked operations can have the same execution cost. Retain explicit choices where
different meanings remain possible, and evaluate necessary runtime costs against measured programs.

## Adopted Direction

### Move Work to Compilation and Require a Reason for Syntax

Adopt the following design priorities:

- Evaluate computations whose inputs and effects permit compile-time execution; runtime input
  remains runtime input. Do not require applications to restate facts already available to the
  compiler merely to request optimization.
- Infer ownership, borrowing, provenance, and execution facts where sound. Retain those facts in
  compiler products so optimization can use them without reconstructing source semantics.
- Prefer static specialization and direct calls when concrete targets are known. Investigate
  removing temporary storage, redundant copies, allocation, checks, and abstraction overhead
  before adding source-level optimization controls.
- Require each proposed syntax form to identify the program meaning or otherwise unavailable
  information it expresses. Use inference or a library API when that is sufficient. Fewer tokens
  alone are not a justification for a new form.
- Preserve safety, failure, side-effect, and destruction behavior. Unknown facts require a sound
  conservative result, not unchecked execution. Reordering, speculation, and compile-time
  evaluation must not introduce or hide observable effects.
- Do not introduce implicit copying, reference counting, or tracing collection solely to hide an
  ownership error. A different memory model remains a separate proposal whose semantics and
  runtime costs must be evaluated against the primary performance objective.

These are design criteria rather than adoption of a particular optimizer pass, safety-check
relaxation, or new memory model. Specific adopted extensions are recorded separately below. The
current specification and compiler authority boundaries continue to apply until a separately
specified change replaces them.

The adopted capture inference and explicit callable type arguments serve this direction together:
inference removes routine source obligations, while an explicit type argument supplies a concrete
substitution when inference alone cannot determine it. Neither requires dynamic dispatch or an
implicit allocation as part of its language meaning.

### Reduce the Human Working Set and Unnecessary Decisions

Adopt the user's broader redesign goal: ordinary code should state application behavior while the
compiler supplies provable ownership, effect, placement, and optimization facts. Judge the complete
workflow rather than replacing a keyword with a similarly demanding type, wrapper, or directive.
Keep advanced control where a real semantic choice remains, but do not make ordinary code describe
the current implementation of memory management or code generation.

Retain directory-defined module identity, contract-only roots, and the adopted direct `see`
semantics. A reader should normally be able to use a module from its contract and edit an
implementation from the relevant source, its contract, and directly identified dependencies. Count
the files and declarations a task actually requires; moving obligations into distant helpers does
not reduce that burden. Inferred effects must be available through tooling without making the
caller inspect every private callee body. Compiler reachability and analysis remain independent
of the human reading boundary.

For every retained or proposed source obligation:

- State the user-visible meaning and the error or ambiguity it prevents.
- Identify why authoritative signatures, expected types, resolved operation identities, data flow,
  specialization, or a suitable ordinary API cannot supply the information.
- Compare explicit and inferred forms at the checked-operation and runtime levels. If they can
  preserve the same behavior and cost, prefer the form with less routine writing and reasoning.
- Expose a real choice when inference would otherwise choose between sharing and independence,
  ownership transfer and continued use, different failure policies, or resource-completion times.
  Do not select a different meaning merely because it is cheaper.
- Report failed safety proofs and optimization opportunities in terms of the affected data and
  operation. A diagnostic should not force a user to reconstruct the compiler's internal stages.

Do not target a particular language's token count or assume a short source language must produce
slower code. Likewise, do not trade away static specialization, safety, or defined resource
behavior merely to shorten an example. A simpler spelling is useful when its semantics and cost
remain clear; a compiler limitation alone does not justify making it a permanent source obligation.

Record proactive improvement proposals with benefits, counterexamples, migration cost, and their
interactions with adopted decisions. This authorizes investigation and proposals, not automatic
adoption of every simplification. Qualify the redesign using both realistic authoring tasks and
generated-program measurements before claiming that it achieves the performance objective.

### Define Values through Input, Update, and Transfer Operations

Adopt the conceptual model detailed in
[Value Access Model](../reviews/v2.0.0-values-and-access-operations.md), the adopted name for this
design. Replace ordinary first-class borrow types as the user-facing foundation with values and
three explicit operation contracts: input, update, and transfer. An unmarked parameter supplies read access
while the caller retains ownership. Updating the caller's original place and transferring its
ownership require distinct declared modes; invocation derives each mode from the selected contract.

An input cannot consume or mutate its supplied place or retain access beyond its permitted
operation. An update grants exclusive temporary access to a writable place and must preserve
valid initialization and cleanup on return, failure, and cancellation. A transfer grants ownership
to the recipient and makes the previous owned place unavailable until valid reinitialization.
These are program meanings, not requests for physical copying, pointer passing, or an optimizer.
Input permission does not imply purity or absence of other externally visible effects.

Treat fields, elements, and subranges as parts on which input/update operations can act, rather
than making every temporary access an ordinary storable `&T` or `&+T` value. Keep lifetime,
provenance, non-conflict, identity, and destruction facts in the compiler. Do not make a dangling
result compile by inserting an owning clone, reference counting, or resource-lifetime extension.

The conceptual model and mode symbols are adopted: input is unmarked, `&` requests update, and `^`
requests ownership. S8 moves declaration qualifiers to types: `buffer: &Buffer`, `job: ^Job`,
and `func open(id: u64): ^File!`. This placement does not itself remove the separate explicit
source-transfer operation in returns or storage. Retire equivalent `edit`/`move` keyword aliases
and the former readonly-borrow meaning of `&` at the coherent v2.0.0 migration boundary. Detailed
grammar and acceptance rules remain open. Adopt uniformly declaration-driven receivers and
arguments (source-review S1): select one callable contract and derive all operand modes from it.
Remove call-side `.&`/`.^` and direct argument-mode prefixes; do not retain optional marker aliases.
This supersedes the earlier matching argument-marker requirement and receiver-only recommendation.
Standalone transfers into owned storage and results remain explicit operations.

S2's [earlier result-placement decision](../reviews/v2.0.0-source-design-decisions.md#s2-declare-result-permission-before-the-callable-name)
is superseded by S8: write `func open(...): ^File!`, with the successful result's permission
beside its type. Unqualified T offers read/input; `&T` update and `^T` ownership. Calls still derive
their result permission from that contract; callee assertions such as `^open(...)` remain rejected.
Result mode is part of the contract, not the lookup name or an overload discriminator. Interfaces,
function values, origins, outcome layers, and async wrappers still require coherent specification
and conformance before compiler implementation.

Keep [S7's semantic permissions and var removal](../reviews/v2.0.0-source-design-decisions.md#s7-declare-local-permissions-and-remove-var),
with S8's type-side spelling and [S9's operation-directed inference](../reviews/v2.0.0-source-design-decisions.md#s9-infer-local-permission-from-the-initialization-operation).
I reads, U updates the original place, and X owns writable/replaceable/transferable storage.
`let next = ^previous` infers X and transfers the owner; `let inspect = next` infers I and leaves
next's ownership intact. A U-returning call infers U, while reading that U variable supplies I.
An explicitly X local may request a checked Copy, but its destination annotation cannot replace
a missing source move. Copy and later uses do not change an inferred local mode.

Retain only `self`, `&self`, and `^self` receiver abbreviations, not expanded typed aliases.
Adopt `func`, `mut`, and `once` as structural invocation kinds, independently of outer
callable-value permission and result permission. Keep forced capture `(^buffer; ...)` as the
same explicit transfer operation; withdraw the unadopted typed-capture alternative.
Apply qualifiers before outcome suffixes, with parentheses for a larger scope. Retain complete
root/body signatures and canonical agreement; reject inherited abbreviated implementation heads.
This deliberately preserves source-local readability even when it repeats header text. C2's general destination-directed transfer is not adopted; standalone transfer remains
explicit. Do not add `with`, optional name-side binding/result markers, or hidden owners behind I/U.

Adopt the delegated [result contract decisions](../reviews/v2.0.0-result-access-contracts.md):
separate payload mode from carrier ownership, outside access, and allocator/region constraints;
preserve those facts through abstraction. Ordinary I/U `return` selects surviving caller storage,
finishes ordinary callee cleanup, and hands off delegated access without hidden suspension or
local-resource lifetime extension. Return an owned guard when a guard must survive. Failure and
absence retain only active-branch dependencies; an owned future/closure can still depend on an
outside owner. Ready futures retain output dependencies through await or output cleanup.
These are internal model decisions, not compiler support or a completed formal proof. Structural
callable result-mode spelling is adopted separately below.

Adopt the model's [six semantic decisions](../reviews/v2.0.0-values-and-access-operations.md#adopted-semantic-decisions):

1. Ordinary owned bindings/results contain independent values, not hidden aliases. Implicit copies
   require a permitted type; noncopyable values require explicit transfer or construction/copy.
   Explicit transfer invalidates the source for both copyable and noncopyable types. Do not insert
   cloning, copy-on-write, or shared ownership to repair invalid ownership code.
2. A transferred parameter grants read, update, and further-transfer permission without an
   intermediate mutable local. An update must leave valid initialization on failure but does not
   automatically roll back completed changes. A consuming operation remains responsible for owned
   cleanup on failure. Resource-specific restrictions still apply.
3. Evaluate operands exactly once, left to right. Reserve existing source places during preparation;
   activate transfers and exclusive updates when all arguments are ready, at invocation. A later
   argument's preparation failure does not consume an earlier reserved source. Earlier expression
   side effects and temporary cleanup are not rolled back. Prevent invalidation of reserved places
   and conflicting live access; allow completed temporary reads before exclusive activation.
4. Exposing a field, element, or range uses a distinct projection contract with a defined owner
   dependency. Do not choose projection versus owning copy from the caller's later use. Persistent
   access forms and their invalidation rules require explicit closure.
5. Deferred operations retain required input/update access from construction through completion or
   cancellation and required cleanup, unless an explicitly dependent result retains it longer.
   Transfer parameters become owned by the pending operation at construction under the same
   preparation rules, not at first execution or `await`. Captures follow the same permissions and
   retention rules without hidden copying, sharing, or resource-lifetime extension.
6. Preserve parameter, receiver, and captured-state invocation permissions through generics,
   interfaces, function values, and erased callbacks. Do not infer a call's public mode from a body,
   copyability, or the caller's last use. Input-only wrappers cannot forward ownership they lack;
   mode strengthening is an API contract change.

These decisions use the adopted call-marker omission. Adopt the subsequent delegated
[semantic closure](../reviews/v2.0.0-value-access-semantics.md) for the structural opt-in Copy
policy, writable X parameter slots, read-like preparation reservations, atomic invocation transfer,
projection dependencies and cleanup, capture demand/order, and deferred cancellation. It includes
distinguishing valid/conflicting/failure cases and contract evidence requirements. Final source
forms, owning specification chapters, and implementation conformance remain gates; optimization
does not choose source ownership semantics.

Completion of the Value Access Model's semantics, analysis, and optimization design is delegated
to the agent, including remaining decisions with observable consequences within this model.
Resolve those questions without requesting approval, respecting the adopted contracts and
safety/resource requirements. Consult the user only on source-language design requiring human
evaluation of writing, reading, or learning code. Call omission, ordinary projection returns,
public construction, owned-capture/environment invocation forms, and structural callable result-mode
spelling have selected rules. Follow the model's
[design responsibility and closure rules](../reviews/v2.0.0-values-and-access-operations.md#design-responsibility-and-closure):
record evidence, alternatives, exact decisions, proof obligations, and distinguishing cases;
separate resolved model rules, pending syntax, and implemented behavior. Do not leave internal
questions pending solely to await approval or a final source spelling.

Earlier v2.0.0 sketches that use `&self`, `&T`, or `&+T` describe superseded source forms, not a
second retained access model. The current specification continues to define the implemented
language until the owning chapters are migrated. The earlier type-driven automatic-borrow
abbreviation remains deferred; unmarked parameter declarations mean input, while each selected
contract explicitly declares updates/transfers and supplies their modes to unmarked calls.

Owning chapters include [Ownership](../../../spec/language/ownership.md),
[Callables](../../../spec/language/callables.md),
[Generics and Interfaces](../../../spec/language/generics-and-interfaces.md),
[Sequences](../../../spec/language/sequences-and-text.md),
[Asynchronous Computations](../../../spec/language/asynchronous-computations.md), and
[Syntactic Grammar](../../../spec/language/syntactic-grammar.md).

### Unify Compile-Time Constants across Value and Type Positions

Adopt the direction that a supported `usize` value computed at compile time can also determine a
fixed-array length or a constant generic argument. Calling a `const` function must not by itself
disqualify an otherwise valid closed constant from those type positions:

```text
const func width(): usize {
    return 64
}

const WIDTH: usize = width()
type Block = [u8; WIDTH]
```

This is planned v2.0.0 behavior. The current specification permits the value constant but excludes
function-derived constants from its call-free structural length/argument domain. Replace that
source-visible staging distinction with one coherent constant-eligibility rule. Preserve exact
target arithmetic, type/range validation, and canonical identity from the evaluated value.

Type construction and evaluation must share explicit dependency management and diagnose cycles and
deterministic work/depth limit exhaustion. Evaluation consumes resolved, checked callable decisions
and must not re-resolve source in a later stage. Settle the dependency protocol before changing the
existing stage boundary. Unknown runtime values remain invalid in a constant-required position.

This decision does not make ordinary functions implicitly `const`, admit arbitrary effects during
constant evaluation, or add symbolic generic arithmetic such as unresolved `N + 1`. The separate
adopted evaluator expansion below adds supported aggregate values. Owning chapters are
[Compile-Time Constants](../../../spec/language/constants.md),
[Generics](../../../spec/language/generics-and-interfaces.md), and
[Arrays](../../../spec/language/sequences-and-text.md).

### Expand Compile-Time Evaluation through Ordinary Computation

Adopt finding 1 of the [language design review](../reviews/v2.0.0-language-design-independence.md):
extend the evaluator instead of requiring another source language for generated data. Support
local mutation, loops subject to deterministic evaluator limits, fixed-array repetition, and
serializable aggregate results, including nominal records and floating-point static tables.
Remove the scalar-only constant domain and unrelated static-initializer exclusions as coherent
parts of this expansion; retain the semantic distinction between a storage-independent constant
and an addressable immutable static.

Retain `const` as an explicit compile-time capability, using the same resolved and checked body
as runtime execution. It is a staging contract, not a request for an optimizer pass. Ordinary
runtime code may still be evaluated or folded when the compiler proves that transformation valid.
Separate values and operations allowed temporarily inside evaluation from values that may survive
in a constant or be serialized into static storage. This adoption does not implicitly admit
compile-time I/O, nondeterministic input, arbitrary owned allocation, escaping evaluator addresses,
or every possible nominal constructor and destructor. Close eligible aggregate construction,
temporary mutation/borrows, static references, final-value validation, and target serialization
together, including rejection of values with unsupported retained resources.

Preserve target arithmetic, ordinary type and ownership checks, dependency-cycle diagnostics,
and deterministic work, memory, and call-depth budgets. A required constant that exceeds a budget
must be diagnosed; it must not silently become runtime initialization. Compilation cost remains
part of qualification even when generated execution becomes faster.

Acceptance examples include a loop-generated checksum table, a repeated static array, a nominal
parser-table entry, and a floating-point static table. Verify emitted data and absence of runtime
initialization, not merely acceptance of the syntax. Owning chapters are
[Compile-Time Constants](../../../spec/language/constants.md),
[Values and Types](../../../spec/language/values-and-types.md), and
[ABI and Layout](../../../spec/platform/abi-and-layout.md).

### Separate Opaque Return Contracts from Their Bodies

Adopt finding 2 of the [language design review](../reviews/v2.0.0-language-design-independence.md):
permit an ordinary bodyless public callable to declare a `some Interface` result while its matched
implementation supplies the body and hidden concrete witness. Contract-only `index.nct` must not
force an author to publish an adapter's concrete type or inline its factory implementation.

The public declaration and matched implementation share one opaque result identity. Determine and
validate the witness from the implementation, use its actual layout and cleanup internally, and
expose only the declared interface, associated bindings, and storage relationships to callers.
Keep one witness per callable specialization and preserve distinct opaque identities for distinct
callables. Hidden copyability and unrelated inherent methods do not silently become public
capabilities. Contract/body joining must consume resolved identities, not compare rendered type
names or independently invent a second opaque type.

Close matching syntax, target-specific bodies, missing or duplicate definitions, generic witness
selection, recursion/dependency cycles, provenance inference, and tooling navigation before
implementation. This decision does not itself permit opaque interface requirements, heterogeneous
return witnesses, or general dynamic interface objects. Owning chapters are
[Static Opaque Results](../../../spec/language/generics-and-interfaces.md#static-opaque-results),
[Modules](../../../spec/language/modules.md), and
[ABI and Layout](../../../spec/platform/abi-and-layout.md).

### Remove Authored Execution-Effect Modifiers

Remove `noalloc`, `notrap`, and `blocking` from v2.0.0 source contracts. This includes callable
declarations, destructors, operators, coercions, interface requirements, generic predicates, structural callable
types, erased callable types, and primitive declarations. Do not replace them with equivalent
attributes, effect parameters, or renamed keywords. This supersedes the earlier direction of
retaining these modifiers for advanced library authors and the review's proposal to strengthen an
authored `noalloc` guarantee.

Removing the modifiers does not remove the facts. Infer allocation, possible traps, termination,
blocking, observable effects, storage origins, and cleanup effects as separate compiler-owned
summaries. Include runtime-owned error storage and frame/environment allocation when classifying
dynamic managed storage. Do not mistake absence of Nocter-allocator requests for absence of all
runtime-managed allocation, or mistake process termination for a pure operation. Trusted bodyless
operations retain facts certified by exact declaration roles; ordinary source cannot grant itself
trusted guarantees through spelling.

Compose generic and cleanup effects conditionally on concrete type arguments and callable
witnesses, independently of copyability. Specialization may discharge those conditions without
extra application annotations. Unknown indirect targets require a sound conservative summary;
erasure cannot erase an effect and then let the compiler assume its absence. Preserve one
authority for selected operations and carry their facts forward rather than re-resolving names
or dispatch in later passes.

When trap freedom cannot be proven, retain the runtime check. Failure to prove an optimization is
not by itself a source error. Memory safety, initialization, borrow validity, deterministic cleanup,
and asynchronous drive safety remain validity conditions. Infer synchronous waiting through direct
calls, callbacks, interface dispatch, primitive operations, and implicit cleanup. Every future must
remain safe to drive without synchronous external waiting. If the compiler cannot establish that
property for a selected operation, reject that asynchronous use with the effect's origin and call
path; never silently block the executor, insert a worker thread, or assume an unknown callback is
nonblocking. Conservative rejection is distinct from retaining an ordinary runtime safety check.

Carry conditional blocking summaries through generic bodies and validate their concrete witnesses.
For erased callbacks and bodyless boundaries, define the available target/effect evidence before
accepting a nonblocking use; removing source annotations must not create a proof gap. Do not require
ordinary code to recreate the removed distinction through a new effect keyword. `async` and the
retained `const` capability describe staging behavior and are not removed by this decision. The
nonblocking rule still does not imply a bound on CPU work, allocation latency, or execution time.

Expose inferred properties and their uncertainty through compiler/editor reports, separately from
authored signatures; the formatter must not manufacture removed qualifiers. Removing an authored
guarantee also removes its explicit API compatibility promise. A body change may change inferred
performance facts or invalidate a safety-sensitive use, so report those consequences at the
affected operation. Exact build-policy tooling for users needing a hard allocation/trap budget
remains pending; it must not recreate mandatory function annotations under another name.

Owning chapters are [Callables](../../../spec/language/callables.md),
[Memory](../../../spec/language/memory-and-regions.md),
[Asynchronous Computations](../../../spec/language/asynchronous-computations.md),
[Control Flow](../../../spec/language/control-flow.md), and
[Primitive Boundaries](../../../spec/platform/primitives-and-os.md).

### Leave Physical Representation and Proof Placement Open to Optimization

Adopt removal of constraints whose sole purpose is to freeze the current implementation rather
than express source behavior or a necessary external contract. In particular, ordinary source
types must not universally require declaration-order field layout, a separate byte tag without
niches, a 256-variant enum limit caused only by that tag, one heap mapping per erased environment,
or a heap-backed frame for every asynchronous producer. Permit compact layouts, scalar replacement,
allocation elimination, frame placement, reuse, and direct specialization where sound. This is
permission to choose a representation, not a promise of allocation-free heterogeneous storage or
of a particular optimizer algorithm.

Separate abstract source semantics from materialized layout and ABI. Any layout observable through
a supported size/alignment/address operation or external boundary needs a coherent selected
contract; use one authoritative representation decision for all consumers. Do not let individual
passes disagree about storage layout. A fixed-layout or interoperation facility, if needed, must
justify its explicit contract; no Rust-style representation attribute is adopted automatically.

Permit additional safety proofs after specialization, inlining, or loop transformation without
repeating source name/type/dispatch selection. Carry semantic operation identities, check
obligations, and proof evidence forward through the acyclic compiler pipeline. A source-stage
failure to prove a check redundant must not permanently forbid a valid later proof; an outstanding
obligation must still produce equivalent checked behavior before code generation completes.

Retain the behavioral constraints that give a program its meaning: side-effect and callback
execution, permitted evaluation order, aliasing and identity observations, recoverable failure,
resource completion, cleanup order, checked integer semantics, and floating-point semantics.
Removing representation restrictions does not authorize fast-math reassociation, unchecked memory
access, or arbitrary resource-lifetime extension. Settle the observability of allocation failure,
allocator operations, and addresses before adopting transformations that would change them.

Require measured examples for optional views, mixed-alignment records, large enums, nonescaping
erased callbacks, asynchronous pipelines, and checks discharged only after specialization. Record
runtime, allocation count, memory, executable size, and compilation costs alongside correctness.
Owning chapters include [ABI and Layout](../../../spec/platform/abi-and-layout.md),
[Memory](../../../spec/language/memory-and-regions.md),
[Asynchronous Computations](../../../spec/language/asynchronous-computations.md), and
[Control Flow](../../../spec/language/control-flow.md).

### Separate Physical Backing from Observable Resource Operations

The delegated [storage-optimization closure](../reviews/v2.0.0-storage-optimization.md) selects
a checked distinction between logical values/resources and their physical backing. R/D/S access,
payload dependencies, and semantic allocator origins remain authoritative; placement P records
register/stack/frame/heap choices without becoming new source syntax.

Optional private frame/environment/transport backing may be eliminated with its implementation-only
OOM termination when a checked language/library contract permits that representation. Do not
retain a dummy allocation probe. Exposed resource requests, recoverable/required failures, budgets,
callbacks, capacity guarantees, address/ABI observations, and cleanup still require preservation.
A factory name, X result, or removed effect modifier supplies no elision certificate by itself.

Materialize required storage by capacity/ABI/ownership-commit deadlines; do not move allocation or
waiting into reserved operations or future drive/cancellation. Reuse needs compatible backing
and no remaining byte use through accesses, dependencies, addresses, or cleanup. Fusion preserves
callback order, first failure, and destruction, including failures from otherwise I/O-free stages.
Retain one selected semantic operation graph and revalidate actual physical effects without new
source lookup. These are internal semantic decisions under delegation, not human-selected syntax.

The owning future memory, callable/async, and standard-library behavior sections now state the
boundary. Its finite trace exploration accepts narrow private elision and simple reuse/streaming
cases and rejects counterexamples; it does not infer real summaries, implement an optimizer, prove
general soundness, or establish a native speedup. Continue the full certificate and compilation
work before claiming these transformations for generated Nocter programs.

### Preserve One Recoverable Failure Payload

Retain one built-in `error` payload for every `T!` failure channel. The design deliberately avoids
making application authors reconcile independently chosen library error types through enclosing
error enums, per-boundary conversions, or lossy replacements needed only for signature
compatibility. Ordinary propagation carries the failure without such adapters. Classification,
causes, and context belong to the unified error information.

This is a retained design constraint. Per-API typed failure payloads and a typed-error parameter
system are excluded from v2.0.0 exploration. Domain data may still use ordinary enums, but
applications must not be required to convert a different failure type at every fallible boundary.

Prefer unchanged propagation or context that preserves the root failure in normal documentation
and APIs. Deliberate reclassification, recovery, and suppression remain explicit application
policies. The adopted unhandled-failure diagnostics must preserve that distinction rather than
forcing users to manufacture a new error type or discard information to satisfy the checker.

The outcome changes below distinguish success from failure construction; returning `error`
information as successful data does not introduce another failure payload type. Owning contracts
remain [Errors and Optionals](../../../spec/language/errors-and-optionals.md),
[Design Principles](../../../spec/principles.md), and the
[Recoverable Errors guide](../../../std/error/README.md).

### Separate Outcome Branch Selection from Payload Type

Adopt an explicit distinction between returning a value and completing a computation with failure.
A payload's type being `error` must not by itself select the failure branch. Permit error
information as successful data, including an `error!` result with distinct success and failure
branches. Retain `T!` as the fallible type spelling with the fixed `error` failure payload above;
a named replacement result type has not been adopted.

Adopt `throw` as the explicit current-callable failure exit (source-review S4). It evaluates an
error operand and transfers that owned built-in error into the declared failure layer, with
ordinary recoverable scope cleanup. It does not dynamically search for a handler, exit an enclosing
closure, unwind callers, or propagate through an ordinary call without `?`. A callable without a
fallible result layer cannot use it. An async producer fails its output when driven, not when its
future is constructed. Ordinary success return and exact whole-outcome forwarding retain their
distinct rules; type `error` alone never selects failure.

Adopt the separately reviewed `throw reason` spelling for an existing owned error. `throw`
itself supplies the fixed transfer meaning; reject redundant `throw ^reason` as an alternative.
An input-only error cannot be thrown, and no implicit copy supplies ownership.
A helper can construct stored failure data
using `throw`; no separate magic failure constructor is required. Close success injection,
whole-outcome forwarding, branch construction, and propagation without flattening or payload-type
reinterpretation. Preserve exactly-once evaluation, ownership transfer, and cleanup.
The [source follow-ups](../reviews/v2.0.0-source-design-decisions.md#outcome-and-unit-source-decisions)
record the separately adopted `throw` operand, optional-presence, and unit-literal spellings.

Also permit nested optional layers while preserving their independent meanings. An iterator of
optional items must distinguish termination from a yielded absent item; no automatic flattening
may erase that distinction. Define construction and elimination for each layer before extending
the current one-optional-layer limit. This decision does not independently adopt arbitrary repeated
fallible layers or a new `match` pattern language.

Adopt an ordinary generic prelude function for explicit presence:

```text
func some<T>(value: ^T): ^T?

let a: i32? = 10
let absent: i32?? = none
let present_absent: ^i32?? = some<i32?>(none)
let present_value: ^i32?? = some(some(42))
```

`some` transfers its argument into exactly one new present layer; ordinary call arguments omit
mode markers under S1. Retain unambiguous contextual presence injection in bindings and returns,
including `let a: i32? = 10`, without requiring a wrapper at every optional boundary. `some` is
an ordinary expression identifier, not new reserved syntax or an intrinsic recognized by name.
Close generic construction versus exact forwarding without flattening nested states.

Owning chapters are [Errors and Optionals](../../../spec/language/errors-and-optionals.md),
[Values and Types](../../../spec/language/values-and-types.md), and
[Ownership](../../../spec/language/ownership.md). Close the grammar and tooling contracts alongside
those semantics before implementation.

### Treat void as a Storable Unit Value

Adopt `void` as the type with exactly one information-free value, usable in ordinary generic and
stored-value positions. A normal completion or bare `return` supplies that value. Permit
containers, generic task results, and optional values to use it without introducing a nominal
empty-struct wrapper. An optional unit distinguishes absence from presence of normal completion.

The value needs no data bytes, but it remains a logical initialized value with ordinary control
flow and type identity. Keep `never` distinct: it describes a path that does not return a value,
not successful completion. This adoption does not by itself extend `never` to every type position
or introduce zero-element tuples.

Adopt `()` as the sole explicit literal of type `void`. For example, `let complete: void = ()`
stores unit, and `some(())` produces a present `void?`, distinct from `none`. Normal completion
and bare `return` still supply unit implicitly; do not require a new literal at every successful
exit or add a separate unit/zero-element-tuple type or named constructor alias.

Before implementation, close unit/closure grammar recognition, implicit completion contexts,
generic substitution, optional/fallible composition, constant-evaluation eligibility, zero-size
layout and transport, and the existing opaque `*void` boundary. Do not infer that a zero-size result
allows its producing operation's side effects to be deleted.

Owning chapters are [Values and Types](../../../spec/language/values-and-types.md),
[Control Flow](../../../spec/language/control-flow.md),
[Errors and Optionals](../../../spec/language/errors-and-optionals.md), and
[ABI and Layout](../../../spec/platform/abi-and-layout.md).

### Keep Comparison Semantics Independent of Views

Adopt comparison selection from the type's own explicit operation contract or the applicable
built-in operation. A declared projection exposing a common view does not by itself inherit that
view's equality or ordering. In particular, two distinct domain types exposing text must not
become comparable solely because both expose text.

Callers may explicitly select the text projections and compare those projected inputs. Exact
projection spelling follows the source-design review; the earlier `&str` coercion sketch is
superseded. Preserve declared input-shape adaptation where selected by the operation contract,
without retaining ordinary first-class borrow types. Remove comparison fallback through a view,
including for derived comparison operators and the relevant generic evidence. Any allowed
cross-domain comparison requires its own explicit contract; it cannot arise merely from
compatible view representations.

Update the equality/ordering selection authority, interface evidence, primitive cases, and
standard comparison implementations together. Preserve source operand evaluation order and
partial-order behavior such as floating-point NaN. Method and indexing fallback policies remain
separate questions rather than being changed incidentally.

Owning chapters are [Equality and Indexing](../../../spec/language/equality-and-indexing.md),

### Distinguish Discard, Failure Acceptance, and Resource Completion

Adopt diagnostics for discarding an unhandled fallible outcome. Ordinary value discard does not
substitute for the decision to accept an operation's failure. Use explicit handling such as
`catch _` to express intentional failure suppression, and propagation when the failure should
reach the caller. An unchecked `let _ = save()` must not silently serve both decisions.

Close diagnostic severity and control-flow rules before implementation. Cover stored and nested
outcomes, scope-end destruction, explicit drop, aggregates, and asynchronous composition; merely
assigning an outcome to an unused named local must not evade the intended check. Do not diagnose
an outcome while it is still retained for later handling or transfer.

Keep resource release distinct from successful completion of a protocol. `drop` safely releases
owned resources; fallible `flush`, `finish`, and `close` operations report their own documented
results. Destruction cannot silently claim that buffered output was delivered, a transaction was
committed, or data became durable. A flush to another writer is not automatically durable storage.

Prefer consuming `finish`/`close` APIs when completion permanently ends a uniquely owned resource's
usable state. Preserve borrowed `flush` for continued use. This is a library/API design direction,
not a requirement that every close operation consume a value: shared handles and externally
controlled resources may still need runtime state checks. Define failure, partial progress, and
cancellation ownership for consuming operations; cancellation or drop does not mean success.

Owning chapters are [Bindings](../../../spec/language/bindings-and-initialization.md),
[Errors and Optionals](../../../spec/language/errors-and-optionals.md),
[Ownership](../../../spec/language/ownership.md), and
[Diagnostics](../../../spec/tooling/diagnostics.md). Exact resource operations remain owned by
their standard-library declarations and assigned behavior guides, including
[I/O](../../../std/io/README.md), [Filesystems](../../../std/fs/README.md), and
[Tasks](../../../std/task/README.md).

### Reuse Tuple Destructuring at Binding Positions

Adopt tuple destructuring for function parameters, closure parameters, and `for` bindings, reusing
the existing local-binding pattern model rather than requiring a temporary local at each position.
Illustrative planned forms are:

```text
for (key, value) in ^entries {
    process(key, value)
}

let add = ((left, right): (i32, i32)) {
    left + right
}
```

The source value is acquired once. Tuple shape, nested patterns, and one-slot `_` discard leaves
follow the common binding rules. Destructuring must preserve moves, copies, loans, partial
initialization, and destruction obligations; it cannot insert implicit cloning or automatically
change an owned input into a borrow. Existing explicit loop ownership selection is unchanged.

Before implementation, close grammar and contextual typing at each position, writable parameter
and loop binding rules, contract/body parameter matching, and decomposition of borrowed tuples.
Verify name collisions, arity/type errors, capture interaction, and cleanup on early return,
failure, loop exit, and cancellation where applicable. This adopts tuple binding patterns, not
general enum/record patterns or new `match` patterns. Owning chapters are
[Tuples](../../../spec/language/tuples.md), [Callables](../../../spec/language/callables.md),
[Ownership](../../../spec/language/ownership.md),
[Control Flow](../../../spec/language/control-flow.md), and
[Syntactic Grammar](../../../spec/language/syntactic-grammar.md).

### Group Item Directives under One Attachment Rule

Adopt one attachment rule for item-prefix directives such as `#visibility` and `#target`: a group

appear in either order, and the formatter emits one canonical order:

```text
#visibility: "/"
#target: "arm64-darwin"
func platform_operation(): void
```

Reject duplicate occurrences of the same item directive and groups with no following declaration.
Validate each directive's admitted target kinds independently; grouping does not authorize target
gates or visibility restrictions on previously unadmitted declaration forms. No group establishes
a continuing file-wide mode or affects a later sibling declaration.

The remaining grammar must define comments and blank-line handling, member positions, error
recovery, and canonical ordering. Package metadata directives retain their own schemas and
repetition rules; this decision does not prohibit repeated executable or test target records.

### Infer Closure Captures

Ordinary closures should infer captures from references to enclosing local values. A caller should
not need to write a capture list for a simple predicate:

```text
let threshold = 10
let predicate = (value: i32) {
    value >= threshold
}
```

This illustrates planned v2.0.0 behavior, not a program accepted under the current explicit-capture
contract.

The adopted model infers input access for reads, update access for mutation, and owned capture
when the body consumes an outer value. Inference must preserve exclusivity, storage
lifetime, callable invocation capability, and exactly-once destruction. It must not silently copy
an owning resource, introduce reference counting, or retry a rejected borrow with a different
ownership policy merely to make the program compile.

Retain the owned-capture segment `(^buffer; value: u8) { ... }` to move a source when body use
alone would only require read/update access. The prefix is a source-transfer operation, not an
identifier-side type declaration. Infer other captures. Do not add redundant read/update capture
lists, a typed-capture alias, or an equivalent `move` keyword.

Use `func(...)`, `mut(...)`, and `once(...)` for read/update/consuming invocation. In particular
`^func(u64): ^File!` owns a repeatedly read-invoked callable with owned successful output;
`^once(u64): ^File!` independently consumes its environment on invocation. `once` means at most
one invocation per owned instance, not a requirement to invoke it. Copying requires separate
Copy evidence and creates a separate instance. Preserve all nine invocation/result mode pairs,
parameter passing, and outside dependencies through abstraction.

Before specification adoption, settle:

- whole-binding versus projection-sensitive capture, including overlapping uses;
- precedence when one capture is read, mutated, and consumed on different reachable paths;
- inferred capture initialization and destruction order, including observable cleanup;
- nested closures, copyable captures, and contextual callable requirements;
- escaping closures and the diagnostics or explicit ownership request they require;
- editor presentation of inferred captures without requiring annotations in ordinary source.

Owning chapters: [Callable Values](../../../spec/language/callables.md),
[Ownership](../../../spec/language/ownership.md), and the closure productions in
[Syntactic Grammar](../../../spec/language/syntactic-grammar.md).

### Allow Explicit Callable Type Arguments

Adopt explicit type arguments at call sites, including the following form:

```text
let config = decode<Config>(bytes)?
```

Omitting type arguments continues to request inference. Explicit arguments select generic
substitutions; they do not bypass bounds, ownership, provenance, or execution-contract validation.
This replaces the current rule that a callable's own type arguments can never be written.

The design must distinguish arguments belonging to a type owner, such as
`Container<Item>.make(...)`, from arguments belonging to the selected callable. Apply a coherent
policy to functions, methods, and construction functions rather than adding an isolated special
case for top-level calls.

Before specification adoption, settle:

- complete argument lists and their correspondence to declared generic parameters;
- whether partial lists, placeholders, or mixed type/constant argument lists are supported;
- nested generic delimiters, comparison expressions, whitespace, and newline recognition;
- interaction with contextual result typing and closure parameter/result inference;
- parser recovery and diagnostics for wrong arity, wrong argument kind, and unsatisfied bounds.

Partial arguments, defaults, placeholders, and named arguments are not adopted by this decision.
Parsing must remain independent of name resolution and semantic type information.

Owning chapters: [Generics and Interfaces](../../../spec/language/generics-and-interfaces.md),

### Define Interfaces as Explicit Static Operation Contracts

Adopt interfaces as explicit nominal contracts for operations and the conditions under which those
operations may be used. Distinguish three responsibilities: required operation signatures and
associated types; the concrete operation implementations selected for a type; and documented
semantic laws. Signature compatibility alone does not establish interface conformance.

Retain explicit conformance, associated types, statically selected calls, and specialization. An
interface bound does not introduce a runtime interface object, allocation, vtable, or name search.
Preserve deterministic implementation selection rather than using declaration/import order or
overlap ranking. Static target selection enables optimization but does not itself promise inlining
or a runtime-speed advantage.

Allow interfaces to require supported operators as well as receiver methods and the construction
functions specified below. Begin with the existing closed operator families; this does not adopt
arbitrary operator declarations. A comparison capability can state its equality operation directly
instead of requiring a separate expression-predicate form solely because equality is an operator.
Close operator requirement grammar, conformance, and interaction with existing predicates before
implementation.

Identify an interface operation by its owning interface and member identity, independently of an
inherent method's name. Explicit implementation mappings must allow two interfaces with same-name
operations and different meanings or signatures to be implemented by the same type. Unambiguous
same-name matching may supply a shorthand, but ambiguous calls require explicit interface
selection. Adopt source-review S5: use `impl Interface { member = inherent_member }` for a
genuinely different implementation name, collision resolution, or explicit default replacement.
The map binds the operation body; it does not rename the public interface member or require the
helper to be public. Do not retain redundant maps for already unique same-name conformance.
Use ordinary member calls when lookup is unique and `value.(Interface.member)(...)` when an
interface-operation collision requires selection; redundant qualification is not an optional
style. Bind and validate implementations once before specialization/lowering; no runtime adapter
search or general UFCS is implied.

Retain defaults as standard implementations derived only from required operations, explicit
prerequisites, and ordinary accessible APIs. Defaults add no fields or access to private concrete
representation. Keep `default` explicit in the contract even when the body is in an implementation
source. Replacing a default must be an explicit interface implementation decision;
adding an unrelated same-name inherent method must not silently replace it.

An interface prerequisite supplies a required capability, not stored inheritance. A stronger bound
makes its prerequisite operations available, but the concrete type must have a unique valid base
implementation with its associated bindings. Do not synthesize missing bodies or associated types
from a stronger interface name. Settle operation and associated-type collisions using their
interface identities rather than textual coincidence.

Distinguish compiler-checked type, borrow, provenance, and effect facts from semantic promises such
as total ordering, equality/hash consistency, and exact remaining length. Such laws are documented
implementation obligations unless separately proven. Conformance alone cannot justify removing
safety checks, observable callbacks, or destruction; inferred allocation/trap freedom is not a
purity proof. A false semantic-law claim must not by itself authorize memory-unsafe generated code. Define each
law's behavioral consequences and verification strategy in the owning contract before using it
as an optimization premise.

These directions and S5's named mapping/qualification forms are adopted. Complete recognition,
operator requirement forms, and generic/default boundary cases remain specification work.
They do not adopt the separate proposal to change generic constraint
spelling. Owning chapters are [Interfaces](../../../spec/language/generics-and-interfaces.md),
[Default Methods](../../../spec/language/callables.md),
[Operators](../../../spec/language/equality-and-indexing.md), and
[Ordering](../../../spec/language/ordering.md). Standard interfaces retain declaration and behavior
ownership under [`std/`](../../../std/README.md).

### Allow Interfaces to Require Construction Functions

Adopt receiverless interface requirements specifically for functions that construct the
implementing type. These are the operations currently owned by `construct` and moved into the
unified type-behavior container below, producing `Self` or its supported outcome/deferred output.
They are not methods invoked without a receiver:

```text
interface Parseable {
    func parse(text: str): ^Self!
}

func load<T>(text: str): ^T! where T impl Parseable {
    return T.parse(text)
}
```

This is planned v2.0.0 syntax. A concrete implementation must explicitly satisfy the interface and
provide a compatible type-owned construction function. Specialization selects that function
statically. Calls remain `Type.function(...)` for construction functions and
`value.method(...)` for methods; this decision does not add UFCS, a runtime type object, or general
type-owned utility functions whose results do not construct the owner.

Close requirement grammar, concrete function binding, associated-result substitution, guarantees,
provenance, asynchronous outputs, and contract/body placement before implementation. Use the
interface-owned operation identities and implementation mapping model adopted above. Owning
chapters are
[Construction](../../../spec/language/construction.md),
[Interfaces](../../../spec/language/generics-and-interfaces.md), and
[Syntactic Grammar](../../../spec/language/syntactic-grammar.md).

### Group Type-Owned Behavior in impl

Adopt `impl Type` as the common container for construction functions, receiver methods,
literals, operators, coercions, interface implementation facts, and destruction. Remove the
`instance` declaration spelling, separate `construct Type` container, and top-level
`drop Type(...)` declaration form. Do not retain `instance` as an alternative v2.0.0 spelling,
nest the old containers inside a new outer wrapper, or merge the callable kinds.

Keep `impl Interface` as the conformance declaration inside the type's `impl` block. The outer
`impl Type { ... }` defines the type's implementation; the inner `impl Interface` explicitly
commits that type to an interface contract. The two roles are distinguished by their syntactic
positions, not by runtime interpretation or name-based guessing. Existing `T impl Interface`
generic requirements also retain their spelling. An operation's presence alone still does not
establish conformance.

```text
impl Buffer {
    impl Reader
    ...
}
```

The following illustrates the adopted implementation-side shape, not current compiler support:

```text
impl Buffer {
    func new(capacity: usize): ^Self {
        ...
    }

    method self.len(): usize {
        ...
    }

    drop {
        ...
    }
}
```

`func` remains a type-owned construction operation producing `Self` or its supported wrapped or
deferred result. `method` retains an explicit receiver and ordinary value-member invocation.
`drop` is automatic lifecycle behavior with exclusive update access to complete `Self` and
completion without a result;
its declaration omits the redundant receiver/result signature. It is not a normally callable
public method. Receiverless utilities that do not construct the owner remain module functions,
and general UFCS remains excluded.

Unify the container form, not the physical source file. `index.nct` contains public operation
contracts and interface implementation facts; directly linked implementation sources contain
their bodies, private operations, and destruction in the same `impl Type` form. The drop body need
not appear in the outward-facing contract. Source fragments must retain one operation identity,
exact contract/body correspondence, and deterministic uniqueness rather than source-order merging.

Destruction remains unique per eligible move-only nominal family, covers the complete unrefined
generic family, and is incompatible with `copy struct`. A conditional operation block cannot create
a conditional destructor. Preserve complete-self destruction, infallible/nonblocking cleanup,
field cleanup order, and initialized-parent requirements at user destructor entry. Grouping does not change stored
layout, runtime dispatch, or ownership semantics.

Before implementation, close generic headers, conditional member availability, literal uniqueness,
inferred drop effects and directive applicability, implementation mappings, and migration from
separate containers. Verify construction, methods, interface requirements, and destruction together across
contract/implementation fragments. Owning chapters are
[Construction](../../../spec/language/construction.md),
[Current Type-Owned Operations](../../../spec/language/generics-and-interfaces.md),
[Ownership and Drop](../../../spec/language/ownership.md), and
[Syntactic Grammar](../../../spec/language/syntactic-grammar.md).

### Publish Construction Availability Explicitly

Adopt source-review S6: use the existing `func` and `literal` vocabulary inside `impl Type` to
publish construction entries. A public field list exposes those fields; it does not claim a
complete private representation or automatically grant public named-field initialization.

Named construction functions, such as `func open(id: u64): ^Self!`, can initialize hidden state
without announcing its presence. An explicit structural literal grant publishes field construction:

```text
struct Point {
    x: i32
    y: i32
}
impl Point {
    literal { x, y }
}

let point = Point { x: 1, y: 2 }
```

Grant names resolve to public field identities and use their declared types. The one synthesized
structural initializer must cover all required semantic fields, satisfy visibility/generic rules,
and preserve initialization/cleanup obligations. A private representation change cannot silently
withdraw that public promise: incompatibility is diagnosed at its implementation. Factories remain
the construction mechanism for hidden state or invariants requiring additional initialization.
Arbitrary custom record-literal bodies/defaults are not adopted.

Do not automatically generate equivalent named `new` and field-literal entries or infer public
construction from implementation helpers. `...` is not a hidden-representation marker, and `pub`
and the separate `construct` container are not reintroduced. Complete grammar and standard-library
migration are still required. Owning chapters include [Construction](../../../spec/language/construction.md),
[Modules](../../../spec/language/modules.md), and [Literal Definitions](../../../spec/language/literals-and-packs.md).

### Make index.nct a Contract-Only Source

Adopt `index.nct` as the module's outward-facing contract source. API declarations authored there
are externally visible by default; implementation-only helpers and dependencies belong in ordinary
implementation sources. Remove `pub` without introducing a second export keyword. Restricted
visibility uses the adopted path-based directive described below.

Every explicitly authored `use` in `index.nct` both introduces a local binding and re-exports it.
An ordinary implementation source's `use` remains a local reference. Signature dependencies are
therefore deliberate parts of the outward-facing contract: importing a type for a signature also
commits to its re-exported name. Removing that name is an API change even if its original use in a
signature has disappeared. Re-exporting retains the original declaration/type identity.

The synthetic prelude is not an authored `use` and does not become a module's re-exported surface.
A re-export must not widen its target's visibility. An unrestricted re-export of a package-only
target is an error, not an implicit permission upgrade.

Retain direct, non-transitive `see` to limit the implementation sources a reader needs to inspect
for a source's private dependencies. A `see` from `index.nct` connects contracts to implementation;
it does not re-export the target's helpers. Source inventory and whole-program optimization remain
separate from source-local visibility: retaining `see` does not promise fewer compiler input files
or a separate-compilation barrier.

Contract-only does not mean that dependency declarations, documentation, and package metadata are
exported API declarations. Resolve the exact admissible item forms before implementation, including
opaque types, record fields, implementation bodies, tests, and executable entry placement. Existing
private declarations in module roots require an explicit migration decision rather than automatic
publication. Namespace aliases, collisions, and restricted re-exports also require complete rules.

`internal.nct` has no adopted special filename or contract-file role. The explicit visibility
directive keeps the restriction visible at the affected declaration instead.

Owning chapters: [Modules and Visibility](../../../spec/language/modules.md),
[Packages](../../../spec/language/packages.md),
[Syntactic Grammar](../../../spec/language/syntactic-grammar.md), and
[Source Style](../../../spec/tooling/formatting.md).

### Restrict Visibility with a Path-Based Directive

Adopt `#visibility` with the same module-boundary path forms as current `pub(...)`. The directive
attaches to exactly one following API declaration or member in `index.nct`, optionally grouped with
other item-prefix directives under the shared attachment rule above. The
following illustrates adopted v2.0.0 direction, not syntax supported by the current compiler:

```text
#visibility: "/"
func internal_operation(): void

func public_operation(): void
```

Only `internal_operation` is package-restricted. The next unqualified declaration has ordinary
external visibility. There is no file-wide mode switch or reset convention.

| Directive value | Intended audience |
| --- | --- |
| Omitted directive | All packages |
| `"/"` | Every module in the declaring package |
| `"./"` | The declaring module and its descendants |
| `"../"` | The parent module and its descendants |
| Repeated `"../"`, such as `"../../"` | The selected ancestor module and its descendants |

The boundary is interpreted from the declaring module, never the importing source, process working
directory, or implementation body's location. Package identity is exact. These strings select
source-access audiences; they do not load files or modules. Accept only `/`, `./`, and one or more
complete `../` components. Arbitrary module names, dependency aliases, filesystem paths, and
traversal above the package root are invalid. `"package"` is not an alternative spelling.

`"./"` includes descendant modules and does not mean implementation-private. Keep private helpers
in ordinary implementation sources, with direct `see` where needed. The directive cannot publish
new API from an ordinary implementation source.

A type's audience bounds the audience of its members. A restricted type does not acquire wider
access through an otherwise unqualified member. Exported signatures must not expose types that
their intended callers cannot access. A restricted `use` narrows a re-export without widening the
target's audience. Implementation bodies inherit their matched contract's audience rather than
repeating the directive.

The directive spelling, allowed paths, default external visibility, and one-item attachment are
adopted. Before implementation, close the detailed grammar for fields and other members, `use`,
aliases, interface facts, and grouped target directives; diagnostics and formatting follow the
shared directive rules. Do not infer a continuing default for a multi-member `impl Type` block from
one-item attachment. Audit current restricted APIs and private module-root
declarations for migration, and cover each path boundary with valid and invalid conformance cases.

Tooling must show the effective audience at definitions, completion, hover, and API listings. This
directive controls source access only; it cannot grant primitive/trusted authority or alter runtime
dispatch, calling convention, or optimizer access to implementation bodies.

### Keep Advanced Contracts out of Ordinary Application Code

Adopt the goal that ordinary application authors should generally be able to write programs
without authoring lifetime or allocator machinery. `noalloc`, `notrap`, and `blocking` are removed
under the adopted execution-effect decision; ordinary applications should also avoid needing
`from` or `region`.

Use implementation inference, suitable library APIs, and existing elision where sound. Keep
explicit storage relationships and allocation-selection APIs available where their meaning cannot
be inferred. The adopted removal of execution-effect modifiers above replaces the earlier plan to
retain those source guarantees for advanced users. Allocation and trap facts remain inferred; runtime
checks, provenance validation, and region escape checking remain required. Inferred implementation
properties are not silently promoted into authored API promises.

Do not make an ordinary callback or collection operation require users to learn a new effect
parameter system. Any future effect-composition design must demonstrate a reduction in application
annotation burden before adoption. Blocking behavior and asynchronous drive safety remain separate
contracts; this goal does not authorize hiding a blocking operation inside a nonblocking future.

Evaluate API usage separately from authoring specialized libraries: applications may rely on a
library's guarantees without spelling those guarantees themselves.

## Proposals Requiring Further Evaluation

The [language design independence review](../reviews/v2.0.0-language-design-independence.md)
evaluates current restrictions against Nocter's own goals. Its compile-time evaluation and opaque
contract/body recommendations are adopted above. The decisions on inferred effects and
representation freedom replace or advance parts of its other recommendations. The review records
their status; recommendations not covered by an adopted decision remain pending.

The following suggestions have not been adopted. Do not implement or describe them as v2.0.0
commitments without a separate decision:

- changing the retained direct `see` semantics or replacing handwritten contract/body pairs;
- unifying generic requirement spelling, such as replacing `T impl Reader` and `copy T` with
  colon-based capability requirements;
- making ownership transfers outside callable-directed calls implicit; the call-policy question
  is evaluated separately below;
- completing the grammar of the adopted declaration-driven calls, owned-capture/callable forms,
  and standalone input/update/transfer operations; do not reopen optional call-marker aliases;
- replacing `T!` with a named result type or changing forced unwrap syntax;
- broader repeated-fallible composition beyond the adopted optional nesting;
- exact optimized layout policies and any explicit fixed-layout contract syntax;
- concrete future/frame representations, borrowed callable erasure, and exact effect-summary design
  under the adopted freedom and inference rules;
- safe partially initialized buffers and disjoint mutable slice APIs;
- SIMD facilities, numeric reordering contracts, or a different shared-memory concurrency model.

Document each candidate's task-level benefit, semantic cost, migration impact, and interaction with
the adopted changes. A list of proposals is not an implementation schedule.

### Deferred Borrow and Transfer Abbreviations

The user deferred type-driven automatic readonly borrowing at ordinary call arguments and omission
of explicit transfer when returning an existing owned move-only value. Do not add those shortcuts
to the old model. The later adopted input/update/transfer model changes plain-parameter semantics
uniformly, rather than conditionally eliding a required borrow marker. It retains explicit transfer;
its `^` transfer marker is adopted. Calls omit receiver markers; complete standalone-transfer
precedence remains specification work rather than a choice of receiver-marker placement.

The reason is potential misunderstanding of whether an expression borrows, copies, or transfers
ownership. Sound compilation and identical generated operations alone do not establish that a
shorter form reduces the reader's work. Evaluate how much context a person needs to identify the
operation, not only how much syntax the author can omit.

Continue strengthening compiler inference for access ranges, provenance, effects, disjointness,
placement, reuse, and redundant checks while retaining the selected source operations. Integrate
capture, receiver, and `await` rules with the adopted model; do not infer that every previous
abbreviation or unchanged receiver spelling follows from that adoption.

### Prioritized Candidates for Less Application Work

These remaining candidates are not adopted. Prefer proof and maintenance improvements that
preserve readable ownership operations.

- **Prove disjoint access instead of requiring manual restructuring.** Start with distinct fixed
   array indices and bounded slice ranges that existing facts can prove disjoint. Retain conflicts
   when paths may overlap, and invalidate facts when their inputs can change. Compare the direct
   algorithm with helper-based alternatives, including index evaluation and error paths. This
   advances the pending disjoint-access work without adding unsafe operations or requiring users
   to learn proof annotations.
- **Reduce contract/implementation repetition.** First evaluate generating and updating private
   signatures from their matched contracts through tooling, preserving comments, direct `see`
   dependencies, and stable declaration identity. This reduces manual editing, although it does
   not reduce authored source size. Separately investigate inheriting redundant implementation
   signature information from one exact contract. Any source shorthand must avoid accidental
   name matches, ambiguous generics, hidden dependencies, and extra files needed for an ordinary
   edit. It is not adoption of a replacement contract/body language or generated public contracts.

Evaluate these on disjoint-buffer processing and an API signature change. Compare source size,
manual edits, explanations needed, files read, allocations, copied bytes, remaining checks, and
runtime. Optional cost reports should
identify why an allocation/copy/check remains and the relevant call or data path; report unknown
facts honestly. Such reports explain the adopted inference machinery rather than adding mandatory
source annotations.

## Follow-up Audit: Derived Ordering Selection

The current [Ordering chapter](../../../spec/language/ordering.md) has a textual inconsistency to
audit independently of the v2.0.0 comparison-policy change. Its Derived Comparisons section defines
`left <= right` using `less(left, right)` and `left >= right` using `less(right, left)`. Its
Selection section instead assigns the source right operand as the semantic left for `<=` and the
source left operand for `>=`.

Following the derivation would select from the source left for `<`/`<=` and the source right for
`>`/`>=`. Audit the owning chapter, cross-references, production selector, and distinguishing
conformance cases before recording a correction. This finding is about specification text; it is
not evidence that a released executable is miscompiled. No current specification, published
artifact, or qualified release candidate is changed by this planning record.

## Investigation: Programming without Ownership Annotations

Investigate remaining ownership and lifetime obligations within the adopted input/update/transfer
model. Its detailed access/dependency rules are recorded in the delegated semantic closure;
source notation, specification migration, and implementation verification remain open. General implicit transfers, ARC, GC, and
copy-on-write are not adopted by this investigation.

Distinguish three objectives:

1. Omit capture and lifetime-related syntax in common local code.
2. Avoid ownership-driven restructuring for common application tasks through safe library APIs.
3. Accept arbitrary sharing, escaping references, and mutation without ownership reasoning.

The adopted capture inference directly advances the first objective. The second needs concrete API
and diagnostic evaluation. The third changes the memory-management and aliasing model and cannot
be promised as a consequence of inference alone.

Compare static ownership/borrow inference with restricted accepted programs, automatic reference
counting with a defined cycle policy, tracing collection, and value semantics with explicit copy
or copy-on-write behavior. Record runtime operations, memory retention, allocation failure,
destruction timing, identity, shared mutation, and concurrency consequences. Automatic memory
reclamation does not resolve the intended semantics of shared mutation or resource protocols.

Evaluate detailed designs on their own semantic merits. The existing borrow-type implementation
is not a required foundation or a preferred choice because it is already implemented. Preserve
safety and a defined resource lifecycle while completing
[Value Access Model](../reviews/v2.0.0-values-and-access-operations.md), whose conceptual
replacement of ordinary first-class borrow types and `&`/`^` contract modes are adopted. Receiver
and argument calls uniformly omit markers; complete standalone expression grammar remains open.

Research evidence includes
[Perceus: Garbage Free Reference Counting with Reuse](https://doi.org/10.1145/3453483.3454032),
which combines reference counting with reuse for a functional core and establishes its garbage-free
result for cycle-free programs. It is evidence for a possible approach, not proof that arbitrary
Nocter programs can receive the same guarantees or universally optimal execution. Swift's
[ARC discussion](https://developer.apple.com/videos/play/wwdc2021/10216/) also illustrates why
automatic reference counting still needs a policy for strong reference cycles.

Automatic region inference is also a concrete research direction. The constraint-based placement
in [Better Static Memory Management](https://www.microsoft.com/en-us/research/publication/better-static-memory-management-improving-region-based-analysis-of-higher-order-languages/)
allows non-lexical region lifetimes and inserts allocation/release operations. This supports
investigating inferred placement; it does not establish an optimal layout or lifetime for arbitrary
Nocter programs.

Distinguish feasible automation from a universal optimality promise:

- Propagate origins and loans through calls, infer their ordinary elisions, specialize concrete
  operations, and select storage when escape and alias information proves the choice valid.
  These can remove annotations and runtime work for an accepted program without changing its
  meaning. Return a caller-owned value directly rather than inventing a dangling borrowed result.
- Do not promise an exact, terminating static analysis for every program with unrestricted dynamic
  sharing. [The Undecidability of Aliasing](https://web.cs.ucla.edu/~palsberg/course/cs232/papers/ramalingam-toplas94.pdf)
  establishes a relevant limit for languages with conditionals, loops, dynamic storage, and recursive
  structures. This is not a proof that lifetime annotations are necessary: a restricted ownership
  discipline, conservative rejection, or defined runtime management can avoid needing exact analysis.
- Define whether keeping an original value and mutating a second value means independent values,
  shared identity, or invalid ownership use. The compiler cannot choose between those observable
  meanings merely because one is cheaper. A chosen value model may require additional state or
  runtime work when both versions remain live.
- Keep storage reclamation separate from semantic resource completion. A file close, lock release,
  callback, or user destructor cannot be delayed or advanced solely to simplify inferred storage.
  Storage may be moved, reused, or retained only where the defined identity, cleanup, and failure
  behavior is preserved.
- Specify the optimization objective and compilation budget. Minimum peak memory, fewest
  allocations, lowest latency, and fastest throughput need not select the same strategy; runtime
  inputs can also change which strategy wins. Longer compilation does not remove these limits.

For every candidate, investigate strong static ownership/provenance inference, whole-program
specialization, inferred regions, and storage reuse where appropriate. Give diagnostics in terms of
the conflicting operation and data that must remain available. Do not require an ordinary author
to choose an implementation lifetime merely because an optimizer did not find its best placement.
The fallback for an unproven ownership relationship remains a design question: conservative
rejection, an explicit ownership API, and runtime-managed sharing have different costs. Runtime
management, automatic cloning, general implicit moves, and automatic lifetime extension are not
adopted by this investigation.

Before closing the remaining model details, compare small programs that retain callbacks, store
views into growing collections, share mutable state, and create cyclic graphs. Explain which
programs compile, what aliasing means, when resources are released, and what runtime costs remain.
Do not silently clone, share, or prolong resource lifetimes as an error-recovery strategy.

## Work Order and Completion Gates

These are dependency gates, not a requirement to obtain native workload measurements or close the
entire language before starting any front-end work. The
[first access validation slice](../reviews/v2.0.0-first-access-slice.md) now specifies a bounded
private-function fragment, including S11 `&place`, RHS-first assignment, joins/backedges, and
the expanded 50-case source corpus. Production syntax parses 44 and rejects six; declaration
processing rejects six headers and produces metadata for 38, with stable data/permission/input
identities and exact-current source rebinding. Structural body typing now rejects eight cases and
produces typed-only selected operations for thirty. Eleven of those still require flow rejection;
initialization/liveness/escape/conflict and conditional cleanup remain pending. Continue integration
under the slice's entry/completion gates; retain complete implementation signatures and the
single declaration-driven call spelling. No human source choice blocks that task. Full v2.0.0
closure, module/std migration, native execution and performance qualification remain separate.

1. **Establish semantic examples and execution evidence.** Select representative application
   workloads and CPU-bound kernels, specify their intended behavior, and record Nocter execution
   and generated-operation evidence. Use the existing
   [measurement boundary](../../benchmarks/methodology.md). Record algorithms, inputs, outputs,
   safety/failure behavior, compiler options, target, allocation behavior, executable identities,
   runtime distributions, memory, code size, and compilation resources. Use transformation ablations
   and Nocter baselines where useful. Rust implementations and relative-speed thresholds are not
   prerequisites for design or implementation.
2. **Close the design.** Write minimal examples for input/update/transfer semantics and notation,
   projections, retained access and asynchronous duration, pending constant-evaluation, opaque-return
   contract/body separation, effect inference and qualifier removal, representation freedom,
   tuple-binding, capture, explicit-call, outcome branch selection/nesting, unit values, comparison selection,
   unhandled outcomes, resource completion, interface-operation mapping, unified type-behavior, and
   contract-only module-root questions, including grouped directives and visibility;
   apply the delegated Value Access Model decision scope above, consulting the user only on its
   human-facing source-design alternatives. Outside that scope, obtain decisions where materially
   different observable behaviors remain. Record the selected
   rules in the owning specification chapters, including grammar, formatting, diagnostics, and
   editor behavior. This phase is pending; the high-level decisions above are already adopted.
3. **Implement input/update/transfer as one model after closure.** Migrate parameter and receiver
   contracts, argument operations, callable invocation/capture, generic/interface evidence,
   projection access, and deferred lifetime dependencies coherently. Verify that ordinary input
   cannot consume or update the original place, update permission is exclusive and preserves
   initialized state, and transfer invalidates the previous owned place. Preserve initialization,
   cleanup, and effect facts internally without retaining a parallel first-class borrow syntax.
   Implement only the separately selected spelling, including any single-symbol operators and
   their precedence, formatting, diagnostics, and editor behavior.
4. **Implement unit values and explicit outcomes.** Support one-value `void` across generics,
   stored layout, calls, and futures; explicit outcome branches including successful error payloads;
   and nested optional state distinctions. Preserve the single `error` failure payload and verify
   construction, forwarding, propagation, ownership, and cleanup end to end, including constant
   evaluation where separately admitted.
5. **Expand and unify constant evaluation.** Support function-derived closed `usize` constants in
   array lengths and constant arguments, local mutation and loops, repetition, and serializable
   aggregate/static results through one checked evaluation authority. Verify equal-value type
   identity, target-width arithmetic, invalid retained resources or runtime inputs, dependency
   cycles, deterministic budgets, emitted tables, and absence of runtime initialization.
6. **Infer execution effects and remove their source modifiers.** Replace `noalloc`, `notrap`, and
   `blocking` across declarations, callable types, generic/interface requirements, destructors, and
   primitive wrappers. Verify conditional generic and cleanup summaries, indirect/erased targets,
   allocation of error storage, recursive call groups, and inferred nonblocking future safety.
   Unknown facts must not become false guarantees. Keep runtime checks where needed and update
   diagnostics/editor reports without synthetic source qualifiers. Exercise a body change that
   makes a formerly safe asynchronous callback blocking.
7. **Extend tuple bindings.** Implement common patterns in function and closure parameters and
   `for` bindings. Verify nested/discard patterns, contextual inference, ownership, and cleanup
   without new allocation or implicit copies.
8. **Unify item directive attachment.** Accept independent directive order, reject duplicates and
   unattached groups, validate target kinds, and format canonically while preserving comments and
   the distinct package-metadata rules.
9. **Implement capture inference.** Cover readonly, readwrite, and consuming captures; nested and
   escaping closures; conflicting loans; copyability; and normal, failure, and cancellation cleanup.
   Keep capture inference consistent with selected explicit transfers and independent of later optimization.
10. **Implement explicit callable arguments.** Cover inferred and explicit calls, owner/callable
    separation, nested generic syntax, contextual closures, bounds, and invalid argument lists.
    Resolve substitutions once and reuse the existing specialization and dispatch authorities.
11. **Unify type-owned behavior.** Move construction and destruction into `impl Type` while keeping
    callable kinds, contract/body identity, private source fragments, and generic applicability
    explicit. Verify single destruction, lifecycle effects, cleanup order, and copy/partial-move
    restrictions. Retain inner `impl Interface` conformance and distinguish it from the outer
    implementation block in syntax and tooling. Remove superseded declaration forms at the coherent
    migration boundary.
12. **Implement interface operation contracts.** Cover methods, construction functions, and supported
    operators; associated bindings; same-name operations with distinct interface identities;
    explicit default replacement; prerequisites; and missing, conflicting, or incompatible mappings.
    Verify generic `T.function` construction calls and static target selection without UFCS or
    implicit boxing. Preserve semantic-law versus compiler-proof boundaries through optimization.
13. **Implement contract-only roots after specification closure.** Migrate private helpers and
    implementation-only imports out of roots, remove `pub`, and implement root `use` re-exports and
    the adopted path-based visibility directive. Verify API names, signature dependency visibility,
    prelude isolation, opaque representation access, unchanged direct `see` behavior, and
    contract/body identity. Include bodyless opaque return contracts with hidden witnesses in
    directly seen bodies, generic/target-specific implementations, and missing/duplicate body
    diagnostics. Keep unadopted directive alternatives out of the grammar.
14. **Implement direct comparison contracts.** Remove comparison fallback through views and cover
    distinct domain wrappers, explicit view comparisons, generic/interface evidence, derived
    operators, and primitive cases. Track the separate Ordering chapter audit without treating its
    correction as already resolved.
15. **Implement outcome diagnostics and resource completion APIs.** Cover intentional failure
    suppression, named/aggregate outcomes, partial progress, failure cleanup, and cancellation.
    Scope consuming-finalization migrations to the actual resource contract rather than changing
    all close methods. Verify that release and cancellation never masquerade as successful finish.
16. **Use representation freedom to address measured runtime costs.** Attribute bottlenecks and
    evaluate compile-time computation, specialization, ownership-aware storage transformations, and loop optimization
    against them. Each candidate needs its own design and correctness argument before
    implementation. Compare generated code and runtime evidence, and retain semantic information
    explicitly at the stage that consumes it. A shorter source program or a larger optimizer pass
    count is not evidence of faster execution. Cover compact layouts, removed representation-only
    variant limits, frame/environment allocation elimination, and later-stage safety proofs while
    preserving layout observations, check obligations, identity, and resource cleanup.
17. **Verify the complete product.** Update formatter, tokens/AST output, diagnostics, completion,
    signature help, hover, navigation, and compiler conformance cases. Exercise the adopted changes
    together, including a generic call with a destructuring, capturing callback and grouped contract
    directives. Run authoritative compiler gates and documentation generator tests with an
    out-of-repository site build.
18. **Evaluate learning cost and performance together.** Have learners write a capturing filter,
    specify a decode result type, and repair a borrow error. Record explanations needed, mistakes,
    and successful repairs. Check representative application examples for avoidable advanced
    annotations; do not remove a necessary contract merely to improve a count. Confirm that
    inference and source simplification do not introduce hidden allocation, copying, dispatch, or
    memory-management costs. Use the recorded workloads to evaluate execution quality and document
    regressions as well as improvements. Judge the selected semantics and demonstrated removal of
    unnecessary work, without a Rust-relative acceptance gate or a short-term delivery target.

Include complete authoring tasks that exercise the physical design: locate a module API from the
directory tree, change an implementation using its root contract and direct `see` dependencies,
and update one public signature across its implementation and callers. Record files/declarations
read, source size, manual edits, explanations needed, and runtime costs separately. Use existing
[JSON normalization](../../../examples/json-normalize/index.nct) and
[HTTP service](../../../examples/http-service/index.nct) packages as workload starting points;
add a view/buffer-processing case that exposes ownership and disjoint-access costs. Preserve the
original workload, input, output, safety, and failure conditions when comparing redesign variants.

Update formatter, editor, and standard-library contracts alongside each compiler boundary. Do not
leave a newer semantic rule implemented behind an older source-acceptance or diagnostic path.

Implementation is incomplete until code generation and destruction preserve the selected semantics,
tooling presents the same decisions, and current documentation no longer contradicts the adopted
rules. Publication requires its own future release qualification and authorization.
