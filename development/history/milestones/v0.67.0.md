# v0.67.0: Operational Local Applications

**Status: active.** Phase 0 fixes the responsibility and failure contracts for the complete
milestone before implementation changes begin.

## Goal

Let one Nocter program run as a configurable local service without assembling its own configuration,
reload, storage-ownership, and persistence policies. A complete application can combine defaults,
one JSON file, the process environment, and command-line arguments; validate the resulting immutable
configuration; hold exclusive process ownership of durable local state; reload configuration without
publishing invalid state; and shut down with a final durable commit.

This is one application milestone rather than a collection of unrelated conveniences. Configuration
produces the immutable policy used by the service and store, the service lifecycle controls when a
new policy becomes visible, and the store provides the single-writer state boundary required by a
restartable process.

## Completion Definition

v0.67.0 is complete when all of the following are true:

- opening a `Store` acquires operating-system-enforced exclusive ownership that rejects a second
  same-process or cross-process owner and is released by close or process termination;
- store lookup, replacement, and removal use one in-memory hash index while deterministic retained
  entry order remains the sole persistence authority;
- one commit writes only its bounded mutation batch, supports multiple staged changes atomically,
  and compaction writes a deterministic complete checkpoint;
- recovery accepts the published v0.66.0 journal format through one explicit migration boundary and
  thereafter normalizes the file to the new format without changing committed data or sequence;
- `std/config` builds one immutable configuration from explicit caller-ordered sources, validates
  required and constrained values, rejects unknown or duplicate input, records source provenance,
  and redacts secrets from diagnostics and presentation;
- JSON objects, process environment values, structured CLI arguments, and authored defaults feed the
  same configuration builder without a hidden precedence order or process-global configuration;
- the service lifecycle distinguishes termination from reload, publishes a reloaded configuration
  only after complete validation, and retains the previous valid configuration after reload failure;
- the complete HTTP service example demonstrates configuration overlay, redacted logging,
  process-exclusive durable state, incremental commits, reload, graceful shutdown, and restart
  recovery; and
- compiler, editor, native, standard-library, documentation, example, migration, crash-tail, and
  installed-home gates pass.

## Responsibility Boundaries

`std/io` owns descriptor lifetime and the portable meaning of acquiring exclusive ownership on an
already-open file. The target adapter owns the operating-system operation and target error
classification. Neither layer chooses a store path or persistence format.

`std/store` owns the stable lock-file derivation, retained entry order, transient hash index,
transaction staging, journal format, migration, recovery bounds, commit sequence, and compaction.
Only retained entries are authoritative application state. The index is rebuilt from them once and
is never serialized.

`std/config` owns schema declarations, source-neutral input values, overlay application, validation,
provenance, secret classification, and the immutable finalized result. Source adapters translate
JSON, environment, and CLI data into that input vocabulary; they do not independently validate or
choose precedence.

`std/service` owns process lifecycle observations and delivery. Application code owns when to read a
replacement configuration, when to attempt publication, and how a successfully published value is
shared with handlers. The signal adapter cannot mutate application configuration.

Application code owns its configuration schema, authored source order, domain decoding above byte
values, request synchronization, and the policy for committing or rejecting one application-level
operation.

## Core Invariants

- The lock identity is derived from the authored store path, not the replaceable journal inode, so
  compaction cannot release or redirect ownership.
- Lock acquisition is non-waiting. Contention is an ordinary explicit error rather than an implicit
  block or a retry loop.
- Closing or dropping the lock descriptor releases ownership; stale filesystem bytes never represent
  ownership after a process exits.
- The hash index stores only hashes and retained-entry positions. Equal-hash candidates are always
  confirmed by exact key bytes. Persistence order never depends on randomized hash placement.
- A successful incremental commit publishes its complete mutation batch at one sequence. Recovery
  applies either the complete batch or none of it.
- Recovery never guesses a record version. Each version has one decoder, and migration produces the
  new version through the ordinary durable replacement authority.
- Configuration source order is the order in which the caller applies sources. No source kind has a
  privileged hard-coded precedence.
- A finalized configuration is immutable. Reload constructs and validates a separate candidate,
  then replaces the published value once; failed candidates remain observable only as redacted
  diagnostics.
- Secret values cannot be recovered from formatter output, validation errors, structured logs, or
  source provenance. Secret names and source kinds remain available for diagnosis.

## Phases

### Phase 0 — Contracts and Authority Map

**Status: complete.** This record fixes the completion boundary, authority flow, migration rule,
failure behavior, and phase order before implementation begins. Existing APIs were inspected to
ensure the design composes with the file service, deterministic ordered storage, structured CLI,
JSON, environment, and service lifecycle rather than creating parallel mechanisms.

### Phase 1 — Enforced Store Ownership

**Status: complete.** One typed file-owner operation now carries non-waiting exclusive acquisition
through the standard profile, runtime contract, host conformance service, generated ARM64 Darwin
service, and package-visible `std/io` policy. `Store` retains a locked stable `.lock` sibling across
journal compaction and releases it on close or owner destruction. Same-process and cross-process
contention, explicit retirement, process-exit release, native duplicate open, recovery, and reopen
behavior are covered without a process-local ownership table or persistent ownership marker.

### Phase 2 — Indexed State and Lending Traversal

**Status: complete.** `StoreState` is the sole retained-state authority: reusable slots carry one
intrusive insertion-order chain, while one seeded hash index stores only hashes and candidate slot
positions. Lookup, replacement, removal, snapshot decoding, and duplicate rejection share that
representation. `Store.entries()` lends ordered key/value views without copying or allocation, and
the ownership checker prevents mutation while the traversal is live. The index is never serialized
or reconstructed by an ordinary operation.

### Phase 3 — Incremental Journal and Migration

**Status: complete.** Journal version `2` distinguishes deterministic checkpoints from bounded
atomic mutation batches through one framing authority. Ordinary commits append only staged
operations; staging or journal-bound overflow replaces history with a checkpoint. Recovery replays
complete batches in order, rejects mixed formats, and treats only an incomplete final record as an
interrupted commit. The explicit version `1` reader validates the published v0.66.0 snapshot format,
retains its last committed state, and immediately normalizes it through the ordinary durable
replacement path without changing data or sequence.

### Phase 4 — Source-Neutral Configuration Core

**Status: complete.** `Schema` owns ordered, uniquely named text, Boolean, signed, and unsigned field
declarations with composable presence, secrecy, and inclusive constraints. Named `Source` values
remain representation-neutral; `Builder.apply` validates and normalizes a complete source before
publishing any replacement, so every recoverable failure leaves prior state unchanged. Caller order
alone defines precedence. `finish` consumes the builder into an immutable `Configuration` with typed
optional accessors, retained source provenance, and redacted presentation. Candidate bytes never
enter configuration diagnostics. Native tests execute ordering, text normalization, atomic failure,
duplicate rejection, required fields, modifier composition, type mismatches, provenance, and secret
redaction through the complete target session.

### Phase 5 — JSON, Environment, and CLI Sources

**Status: planned.** Adapt existing JSON values, process environment snapshots, and structured CLI
arguments to the common builder while preserving caller-authored overlay order.

### Phase 6 — Reloadable Service Lifecycle

**Status: planned.** Add a distinct reload observation, Darwin `SIGHUP` integration, candidate
validation and atomic publication, and prior-value retention on failure.

### Phase 7 — Complete Operational Service

**Status: planned.** Rework the HTTP service example into one installed-home application proving the
complete configuration, exclusive storage, reload, shutdown, redaction, and restart workflow.

### Phase 8 — Qualification and Review

**Status: planned.** Run cross-process contention, crash-tail, migration, reload-race, installed-home,
compiler, LSP, native, documentation, example, deterministic packaging, and responsibility-boundary
gates. Review specifically for duplicate authority, repeated interpretation, reverse dependency,
and contracts that rely on callers preserving hidden invariants.

## Non-goals

v0.67.0 does not add reflection, derive-based configuration, a new configuration language, an ORM,
SQL, distributed storage, multiple concurrent store writers, transparent background retries,
automatic schema migration, a multithreaded executor, or hot replacement of executable code.
