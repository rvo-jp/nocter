# v0.53.0: Structured Services and Streaming Codecs

## Goal

Make a complete network service practical without adding format-specific compiler behavior: codecs
must separate pure incremental transformation from I/O, dynamic task groups must own cancellation
and cleanup, and HTTP server operations must compose those foundations through ordinary standard
library contracts.

## Completion Definition

v0.53.0 is complete when all of the following are true:

- JSON compact generation has one effect-neutral incremental encoder shared by owning String and
  BlockingWriter output;
- streaming codec state never owns a second semantic tree or duplicates its exact spelling rules in
  an I/O adapter;
- structured task groups support a runtime-sized set of child futures with explicit result,
  cancellation, and destruction behavior;
- the HTTP module can accept, decode, respond to, and close server connections with documented
  framing limits and failure policy;
- server orchestration composes asynchronous network I/O, timeouts, task ownership, and codecs
  without a compiler-recognized service abstraction;
- one runnable application exercises the complete public path;
- compiler, editor, standard-library, native, documentation, installation, and packaging gates pass;
- review finds no duplicate codec authority, detached child task, hidden unbounded buffer, or
  destination effect leaking into an effect-neutral transform.

## Phases

### Phase 0 — Codec and Service Boundary

Status: complete.

- identify the concrete effect leak in JSON generation;
- define pure incremental transformation, destination driving, and failure classification as
  separate responsibilities;
- record dynamic task ownership and HTTP connection lifecycle as the next dependent boundaries.

JSON previously expressed compact traversal through a generic package-internal sink whose required
operation was `blocking`. This made in-memory `stringify` conservatively blocking even though it
performed no I/O. The adopted boundary is a pull encoder: it owns traversal and spelling, while
String and BlockingWriter drivers own allocation and destination effects.

### Phase 1 — Effect-Neutral JSON Generation

Status: complete.

- replace the blocking sink abstraction with one explicit nonrecursive encoder;
- keep borrowed chunks behind encoder state so allocation failures do not acquire input provenance;
- keep String generation nonblocking and writer generation explicitly blocking;
- buffer small writer chunks while writing large borrowed chunks directly;
- preserve exact compact spelling, allocator selection, destination failures, and deep traversal.

The encoder publishes state transitions rather than a destination callback. `EncodingFrame` is the
only traversal authority, and the current byte projection stays inside `Encoder`. Construction and
advance results carry only semantic state or allocation failure, preventing a borrowed chunk and a
recoverable error from being merged into one provenance contract. Both public drivers consume the
same chunk sequence.

### Phase 2 — Dynamic Structured Task Groups

Status: planned.

- derive the runtime-sized group contract from concrete concurrent service needs;
- make group ownership, child completion, cancellation, and drop behavior explicit;
- retain fixed-arity combinators as convenience operations only when they remain useful.

### Phase 3 — HTTP Server Lifecycle

Status: planned.

- add bounded request decoding and response encoding over asynchronous byte streams;
- define listener, connection, request-body, response-body, timeout, and close responsibilities;
- keep HTTP parsing and framing in `std/http`, outside compiler and transport internals.

### Phase 4 — Operational Safety

Status: planned.

- enforce explicit limits for headers, body buffering, connections, and outstanding tasks;
- preserve cancellation and cleanup across timeout, peer failure, codec failure, and handler failure;
- expose stable failure identities without leaking transport or parser representation.

### Phase 5 — Application and Qualification

Status: planned.

- build one complete service using only public APIs;
- verify editor presentation and navigation for the new contracts;
- perform whole-repository review and release qualification.

## Deferred Work

Effect-polymorphic callables, automatic serialization derivation, canonical JSON, borrowed JSON DOM
values, HTTP/2, HTTP/3, and a general application framework remain outside this milestone. A later
need may justify them, but none is required to establish the service foundation above.
