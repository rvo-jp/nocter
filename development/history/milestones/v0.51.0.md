# v0.51.0: Unified Execution Contracts

## Goal

Give every callable operation one explicit, time-aware execution contract so allocation,
synchronous waiting, deferred execution, and destruction are decided once and consumed without
reinterpretation. This milestone preserves the released `noalloc`, `blocking`, `async`, and
`future T` source behavior. It prepares one sound semantic foundation for later composite
guarantees such as `realtime`; it does not add those modifiers prematurely.

## Completion Definition

v0.51.0 is complete when all of the following are true:

- authored guarantees, inferred execution facts, and implementation scheduling are distinct
  semantic concepts with names that state their authority;
- an asynchronous callable distinguishes invocation-time future construction from later future
  drive and cancellation;
- one checking-owned fixed-point analysis computes allocation and synchronous-wait facts for
  callables, closures, and destruction roots;
- checked call operations carry the exact invocation plan needed by relation analysis rather than
  requiring a consumer to reconstruct temporal behavior from declaration fields;
- primitive roles provide closed execution facts which target validation compares with authored
  source contracts without name-based inference;
- implicit destruction participates through the same execution-fact graph and has no parallel
  effect classifier;
- `CheckedProgram` exposes one sealed execution-fact authority, while target, MIR, machine, and
  editor stages cannot rerun body analysis;
- declaration presentation renders authored syntax only and never publishes inferred facts as a
  source contract;
- compiler, editor, formatter, standard-library, conformance, and installed-toolchain gates pass;
- a repository-wide review finds no old effect table, temporal-scope guess, duplicate primitive
  classification, or caller-correctness precondition in this area.

## Design Boundaries

### Contracts and Facts

An authored callable contract states what callers may rely on. An inferred execution fact records
what one closed implementation root can do. The two are compared during validation but never
stored as interchangeable values. Forgetting a callable guarantee remains an explicit checked
conversion; successful body inference cannot synthesize a source-visible promise.

### Temporal Scope

Immediate callables execute their body during invocation. Invoking an asynchronous callable instead
constructs an owning `future T`; its body executes only while that future is driven. Invocation,
drive, cancellation, and destruction therefore remain distinct execution scopes even when they
currently share individual facts. No consumer may infer one scope from the presence of `future T`
or from an `async` spelling.

### One Relation Authority

Checking collects edges only from checked operations, selected dispatch, and ownership-frozen
cleanup plans. One least fixed point closes those edges across callable, closure, and drop roots.
Source syntax, names, target instructions, and editor projection are not analysis inputs.

## Phases

### Phase 0 — Execution-Domain Audit and Model

Status: complete.

- inventory every allocation, blocking, async, primitive, and destruction authority;
- define authored contracts separately from inferred execution facts;
- define invocation and deferred-drive scopes without flattening them into unrelated flags;
- record the cross-stage ownership and migration invariants.

The audit established four distinct questions—authored promise, invocation, deferred drive, and
destruction—and rejected a flat modifier record that would erase their temporal scope. The current
compiler already froze immediate versus deferred invocation in `CheckedCallExecution`; that sound
boundary remains. The new execution-contract design is the sole current cross-crate authority, and
the superseded blocking-only design document has been removed.

### Phase 1 — Checking Authority Replacement

Status: complete.

- replace the ambiguously named effect products with one execution-fact vocabulary;
- make invocation behavior an explicit checked-call input to relation collection;
- close callable, closure, and destruction facts in one fixed-point graph;
- remove conservative fallback values from identity lookups that must be total.

Checking now publishes an `ExecutionFactTable` whose vocabulary cannot be mistaken for authored
callable promises. Direct facts and execution edges share one monotonic join, asynchronous future
construction enters as an explicit direct allocation fact from the checked invocation plan, and
missing semantic identities are integrity failures. Conservative behavior exists only as an
explicit external-contract edge. The implementation review is recorded in
[`development/history/reviews/v0.51.0-phases-0-1.md`](../reviews/v0.51.0-phases-0-1.md).

### Phase 2 — Primitive and Boundary Integration

Status: complete.

- expose primitive implementation facts through one closed runtime contract;
- validate authored primitive declarations against that contract once at the target boundary;
- prove future construction and drive-safety facts without reconstructing them from result types;
- prevent target and backend stages from maintaining parallel classifications.

Primitive roles now expose typed `PrimitiveExecutionFacts`. Invocation allocation and synchronous
waiting remain independent, while `PrimitiveProducedComputation` distinguishes no deferred result
from a certified drive-safe future. Target validation compares that closed role fact with the
source declaration and signature once; checking remains target-independent, and downstream stages
receive only selected role identities. The implementation review is recorded in
[`development/history/reviews/v0.51.0-phase-2.md`](../reviews/v0.51.0-phase-2.md).

### Phase 3 — Semantic Consumers and Tooling

Status: complete.

- publish the sealed execution-fact authority through `CheckedProgram`;
- migrate semantic presentation, diagnostics, and editor queries to authored-contract inputs;
- verify that executable, MIR, machine, and native stages consume only already selected plans;
- remove superseded wrappers and helper predicates.

Semantic consumers now use the smallest authoritative input for their responsibility. Provenance
and loans reuse the checked call's executed-result mapping instead of reopening the temporal plan;
declaration body-result mapping likewise has one owner. Structural execution explicitly enumerates
callable, equality, ordering, indexing, coercion, and expansion evidence; non-executable evidence is
an integrity failure rather than a wildcard fallback. Presentation continues to render authored
guarantees only, while target and lowering stages consume frozen execution plans. The implementation review is recorded in
[`development/history/reviews/v0.51.0-phase-3.md`](../reviews/v0.51.0-phase-3.md).

### Phase 4 — Cross-Area Conformance

Status: complete.

- cover direct, generic, interface, structural-callable, closure, async, await, and drop paths;
- exercise filesystem, networking, process, buffering, streams, and `async-file-report`;
- add negative proofs for allocation, synchronous waiting, bodyless declarations, cancellation,
  and implicit destruction;
- verify deterministic fixed-point results under declaration and body-order variation.

Cross-area conformance now includes a positive allocation fact propagated through a mutually
recursive group under reversed declaration order, paired with the existing allocation-free
recursive proof. Editor coverage proves inferred allocation freedom does not synthesize authored
`noalloc`. The complete workspace suite passes across compiler, editor, standard-library, native,
runtime, and public application paths, including its loopback-dependent examples. The review is
recorded in [`development/history/reviews/v0.51.0-phase-4.md`](../reviews/v0.51.0-phase-4.md).

### Phase 5 — Review and Qualification

Status: in progress.

- review the repository for duplicate authority, recomputation, reverse dependencies, and temporal
  scope inference;
- run complete compiler and documentation verification;
- qualify a fresh installed toolchain before release preparation.

`realtime`, `noabort`, `const func`, and a general effect-list syntax are outside this milestone.
Their semantics must be expressible by the completed model before any new surface spelling is
accepted.
