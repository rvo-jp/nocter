# v0.42.0: Asynchronous HTTP Client

**Status: Phase 2 complete; Phase 3 is next.**

## Outcome

v0.42.0 will make the existing HTTP/1.1 client usable inside structured asynchronous programs. It
will preserve one HTTP protocol authority and one response owner while async TCP drives connection,
request transmission, response-head reception, and body consumption without blocking the executor.

HTTPS remains outside this release. It requires a secure transport with an explicit ownership and
cancellation contract; mixing that work into the first async HTTP client would obscure both
boundaries.

## Phase 0: Protocol and Transport Boundary

**Status: complete.**

Request normalization, reserved-field policy, and final response-head selection now live in one
transport-independent exchange layer. The synchronous client consumes this authority instead of
owning the policy itself. A native standard-library test proves that ordinary informational
responses select the final head and status 101 remains rejected without any socket orchestration.

The [Asynchronous HTTP Client Boundary](../../design/asynchronous-http-client-design.md) fixes the
immediate/deferred split, unique response ownership, cancellation direction, and the decision not
to introduce an empty transport abstraction around the only current implementation.

## Phase 1: Async Request and Response Lifecycle

**Status: complete.**

`Client.send_async` now validates and encodes the request and resolves its host before returning a
lazy computation. The computation owns connection establishment, complete request transmission,
and final-response-head reception through async TCP. `Response.read_async` advances the same unique
decoder and connection state as synchronous reads; transport-independent body progression lives in
one shared authority.

The protocol corpus continues to qualify fixed, chunked, close-delimited, informational, and
premature-EOF behavior independently of transport. A local native async fixture proves complete
request transmission, informational-head selection, fragmented chunked reception, and decoded body
reads across reactor suspensions. Implementing that fixture exposed an ARM64 code-generation defect:
large async output staging could overwrite the retained child-consume entry with a stack offset.
The backend now forms staging addresses before loading indirect branch targets, and an independent
large-frame native regression guards the corrected contract.

## Phase 2: Timeout and Cancellation Qualification

**Status: complete.**

`Client.send_async_with_timeout` delegates the existing async TCP connection deadline, complete
write timeout, and response-head idle timeout without introducing HTTP timer state.
`Response.read_async_with_timeout` adds an explicit body-input idle timeout and does not inherit
mutable synchronous socket configuration. Neither operation claims a whole-response deadline.

Local native fixtures qualify lazy send destruction before connection, abandoned body-read
computations that release their borrow without consuming the response, response-head and body idle
timeouts, request-body write backpressure, and premature peer closure. The existing reactor and
async TCP qualifications remain the sole authority for readiness/deadline races and state-specific
cancellation; HTTP owns no scheduler or registration mechanism.

## Phase 3: Practical Client APIs

**Status: planned.**

Complete the request ergonomics needed by real applications while preserving explicit replay and
connection ownership. Convenience operations may be added only when they derive from the same
request and response contracts rather than reimplementing protocol policy.

## Phase 4: Integration and Examples

**Status: planned.**

Add a complete asynchronous local HTTP example, editor coverage, public documentation, and package
qualification. Fixtures remain deterministic and local; external Internet availability is never a
test prerequisite.

## Phase 5: Review and Release

**Status: planned.**

Review the full compiler, runtime, and standard-library change for duplicate state machines,
ownership gaps, blocking executor work, stale synchronous-only wording, and obsolete helpers. Then
run the complete release qualification without weakening any gate.
