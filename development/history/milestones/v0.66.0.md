## Goal

Let a Nocter application retain bounded local state across orderly shutdown, interrupted writes,
and process restart without importing an external database or weakening the existing ownership and
executor contracts. Durability must be explicit: completing an ordinary write is not a durable
commit, and a durable commit cannot be reported before both file content and the containing
directory entry have crossed their target persistence boundaries.

The milestone builds one byte-oriented storage authority from the existing filesystem, binary
record, checksum, and structured-service foundations. It does not add compiler-recognized database
types, hidden process-global storage, or a second blocking executor.

## Completion Definition

v0.66.0 is complete when all of the following are true:

- executor-safe and explicitly blocking file owners expose the same target-independent durable
  synchronization meaning without duplicating target rules;
- a destination can be replaced through an exclusively created sibling file, synchronized content,
  one atomic rename, and synchronized parent-directory metadata;
- an append-only journal uses one versioned, length-delimited, checksummed record format and
  distinguishes an incomplete final record from corruption before that record;
- journal recovery has explicit record, per-value, and aggregate byte limits and never trusts
  unbounded lengths from storage;
- a public byte-oriented store has one owning writer, explicit commit, deterministic replay,
  removal, reopen recovery, and bounded compaction;
- cancellation and failure preserve exactly one owner for every open file and do not publish an
  uncommitted mutation as durable;
- one complete stateful-service example persists application data, performs graceful final commit,
  restarts, and observes the same committed state; and
- compiler, editor, native, standard-library, documentation, example, and packaging gates pass.

## Responsibility Boundaries

`std/io` owns file descriptor ownership and the portable meaning of synchronizing one already-open
file or directory. The generated file service owns executor-safe admission, target execution,
completion facts, cancellation, and retirement. Neither layer owns temporary-path selection,
replacement policy, journal framing, or key/value semantics.

`std/fs` owns path-oriented durable replacement. It creates an exclusive sibling, writes and
synchronizes its complete content, renames it once, and synchronizes the containing directory. It
does not define a record format or retain application state.

`std/store` owns the journal format, recovery limits, current key/value state, commit sequence, and
compaction policy. It consumes public filesystem and codec contracts and cannot inspect file-service
jobs, descriptors, target errno values, or collection internals.

Application code owns serialization above byte keys and values, synchronization between concurrent
tasks, schema evolution, and when a transaction should commit.

## Core Invariants

- A successful ordinary write means that every byte reached the operating-system file interface;
  only explicit synchronization participates in a durable commit.
- Temporary files are created exclusively in the destination directory. A conflicting name is
  retried with a new cryptographic token and is never truncated or reused.
- Rename is attempted at most once. An indeterminate rename failure is returned and never replayed
  internally.
- A successful durable replacement means synchronized temporary content, successful rename, and
  successful synchronization of the destination parent directory, in that order.
- Recovery accepts complete checksummed records in order. Only an incomplete final record may be
  ignored; malformed headers, impossible lengths, checksum mismatches, and corruption before the
  physical end are failures.
- The public store has one authoritative in-memory state and one authoritative committed sequence.
  Compaction produces a replacement snapshot from that state rather than reparsing its own journal.

## Phases

### Phase 0 — Durable Filesystem Authority

**Status: complete.** The closed file-access contract now includes exclusive creation, directory
owners remain package-visible filesystem policy, both execution surfaces expose explicit durable
synchronization, and `std/fs` performs bounded exclusive sibling replacement without duplicating
target ABI or file-service lifecycle rules.

### Phase 1 — Recoverable Journal

**Status: complete.** One package-private journal owns bounded versioned framing, monotonically
sequenced append, synchronized commit, complete replay, incomplete-tail truncation, and corruption
diagnostics over the existing binary and checksum authorities.

### Phase 2 — Byte-Oriented Store

**Status: complete.** `Store` owns one deterministic byte-keyed state with lookup, replacement,
removal, explicit commit, terminal close, configured bounds, and deterministic reopen behavior.

### Phase 3 — Bounded Compaction and Lifecycle

**Status: complete.** Every commit records one complete snapshot. Journal record and byte bounds
trigger durable replacement with the next sequence, explicit clean-state compaction preserves its
sequence, and cancellation leaves both journal and store owners terminal until reopen.

### Phase 4 — Persistent Stateful Service

**Status: complete.** The complete HTTP service publishes its structured event only after the
handler group drains, commits it through `Store`, closes the owner, reopens the journal to simulate
restart, verifies exact bytes and sequence, and removes its example-owned state file.

### Phase 5 — Tooling, Qualification, and Review

**Status: complete.** Editor coverage, documentation, native interruption/reopen probes, the
installed-standard-library execution boundary, and an adversarial authority review are complete.
The [Phase 5 review](../reviews/v0.66.0-phase-5.md) records the authority trace, corrected recovery
work, and complete compiler evidence. Deterministic archive construction is owned by the separate
[release-preparation record](v0.66.0-release-preparation.md).

## Non-goals

v0.66.0 does not add SQL, an ORM, automatic serialization, automatic schema migration,
multi-process writers, distributed storage, a compiler-recognized persistence type, an external
database dependency, or a multithreaded executor.
