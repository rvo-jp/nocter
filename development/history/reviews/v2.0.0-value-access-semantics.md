# Value Access Model: Semantic Closure

## Status and Authority

These are v2.0.0 design decisions made under the user's delegation of the
[Value Access Model](v2.0.0-values-and-access-operations.md#design-responsibility-and-closure).
They refine its adopted input/update/transfer rules. They are not implemented compiler behavior
or a substitute for migration into the owning `spec/` chapters. Surface syntax is separated in
the [source-design review](v2.0.0-source-design-decisions.md). S1 and S3 now select declaration-driven
calls and the owned-capture/callable-type forms; S5 selects implementation mapping and mandatory
interface disambiguation. S4 selects `throw` failure exit and S6 explicit construction entries.
The user rejects result-side `view`/`&view` and `yield`. S2 adopts callable-name result prefixes and
uniform contract-derived calls/bindings, retaining provided ownership rather than making ordinary
bindings I-only. Full result-role specification remains work. The separately adopted `throw reason`
spelling derives ownership transfer from the failure exit without an extra `^` marker.
These surface choices do not change the abstract I/U/X
operations below until a coherent replacement is specified.

`I`, `U`, and `X` below are specification metalanguage for input, update, and transfer. They are
not new keywords. `call(U a, I b)` denotes already selected operand modes, regardless of the final
call spelling. Decisions below do not adopt optional implicit copies, runtime reference counting,
garbage collection, last-use consumption, or automatic extension of resource lifetimes.

## 1. Values, Places, and Dependencies

A place has a semantic root and a path of fields, indices, or ranges. Place identity is not a
numeric address. Distinct zero-sized fields remain distinct places. Evaluating an index or range
selects its components once; later use does not reevaluate them. Bounds validation retains its
ordinary failure/trap semantics.

Track separately:

- **Ownership:** which live slot owns a value and its destruction obligation.
- **Initialization:** initialized, uninitialized, or path-dependent state for each relevant place.
- **Access:** permission to inspect or modify a place, including reservations and delegated access.
- **Dependencies:** outside owners/storage that must remain valid for a value or computation.
- **Effects:** operations on external resources, callbacks, allocation, failure, and termination.

An owned slot is not necessarily dependency-free. A future or closure can own its computation
while retaining access to an outside value. Such dependencies remain explicit in its checked
contract/evidence and propagate through enclosing aggregates; wrapping a future does not hide
them. An ordinary independent owned result cannot acquire such access merely from its use site.
Explicit shared-resource handles may share external identity; owning or copying their headers
does not prove deep independence of the represented resource.

No ordinary `&T`/`&+T` type or freely storable pointer-like projection is introduced. A projection
is an access relationship. A dependent closure or future is a computation with tracked access,
not an implicit conversion from a projection into an independent `T`.

## 2. Permissions and Writable Bindings

| Contract | Read contents | Update contents / replace whole value | Transfer ownership | Obligation on outward recoverable exit |
| --- | --- | --- | --- | --- |
| I | Yes | No | No | Leave caller ownership intact |
| U | Yes | Yes | No unfilled extraction | Leave the caller's complete value initialized |
| X | Yes | Yes | Yes | Dispose of or transfer every live owned component once |

Permissions refer to the supplied place. They do not imply purity, termination, or immunity from
changes to a file, shared service, or explicitly shared handle. Immutable input cannot be used to
launder update permission through a callback or nested field.

`let` remains immutable and cannot be reinitialized after transfer. `var` permits update,
replacement, and valid reinitialization. A parameter is governed by its mode rather than an
implicit `let`: a U parameter denotes a caller-owned writable place, while an X parameter owns a
callee-local writable slot. Both permit whole-value replacement; X additionally permits transfer
and subsequent reinitialization. No extra mutable local is required. Merely supplying a `let`
value to X does not mutate its old place; it ends that place's ownership.

A U parameter may delegate access to a nested operation but cannot move the caller's value out
and leave a hole on any recoverable return or cancellation edge. Use an ownership-preserving
exchange operation: evaluate a replacement first, exchange it with the initialized target without
user callbacks or a fallible gap, and return the old owned value. This is a library/compiler
operation, not a fourth public parameter mode. Ordinary replacement keeps the defined assignment
evaluation and destruction order; exchange must not be silently substituted when effects differ.

Whole replacement of an X slot is permitted even for a type with a destructor: the old complete
value is destroyed exactly once. Partial extraction cannot allow that destructor to receive an
incomplete `Self`. Structural partial extraction is permitted only with proved initialization,
disjointness, and complete remaining cleanup; unproved indexed extraction needs a safe
exchange/removal API. There is no hidden clone or automatic occupancy map used to repair a
rejected extraction. Conditional cleanup flags for accepted control flow remain valid machinery.

## 3. Copy Policy

Retain nominal opt-in using the existing `copy struct` design. An ordinary nominal struct remains
move-only even if its current private fields happen to be copyable. This makes public copyability
a deliberate contract rather than a property that changes when a private field changes.

Implicit copying is structural and has no user-defined hook, allocation, resource acquisition, or
destructor. It is permitted for numeric/boolean/scalar primitives, the unit value, payloadless
enums, and supported raw boundary values; tuples, fixed arrays, and optionals compose the property
from all component types. Aliases preserve it. An opted-in generic nominal family carries the
conjunction of its field requirements, independently of the active runtime state or array length.
No copyable family acquires its own destructor. A generic parameter is potentially move-only
unless its checked requirements prove copyability. Opaque results expose only declared capabilities.

`error`, every fallible outcome, and every future remain move-only. Closure environments compose
copyability from captures: owned captures require copyability, read-access captures can duplicate
their tracked read dependency, and update-access captures prohibit copying. Duplicating a read
dependency does not duplicate its owner or use reference counting. The dependency remains live
through every copy. Copying such a dependent closure is not an independent copy of the captured T.

Reading a Copy value as an I argument still accesses the supplied place; it does not select a
different passing meaning. An owned initializer/assignment/return may make a permitted structural
copy. An arithmetic expression or explicit independent construction can create a snapshot.

Explicit transfer always invalidates its source, including Copy sources. Existing owned returns
and stored initializers use the selected transfer operator; fresh owned temporaries transfer
directly. Standalone transfer targets an existing owned place, not a fresh call result requiring
no additional ownership operation. Optimization may eliminate physical copies without changing
source availability.

## 4. Calls: Preparation, Invocation, and Exit

Resolve one callable identity, substitutions, receiver mode, parameter modes, and execution kind
before applying access rules. Access failure cannot choose another overload or strengthen the
wrapper's signature. Callable values also have an environment invocation mode and are evaluated
before their arguments; receivers precede ordinary arguments.

### Preparation

Evaluate operands exactly once, left to right. A direct existing place supplied to I, U, or X
creates a reservation tied to that evaluated place. A reservation protects the place like a read:
it forbids overlapping writes, replacement, transfer, destruction, and storage invalidation by
intervening expressions. It permits temporary reads. An already active incompatible U access
prevents reservation. The compiler must account for calls and cleanup reached while preparing
later operands, not only explicit assignments.

A reservation of a projected element protects its path and required owner structure against
invalidation, not every unrelated field of the owner. Proof of disjoint fields/ranges permits
independent work. An unknown overlap is not treated as disjoint. A dynamic inequality or successful
checked split may establish disjointness without adding a language-level lifetime annotation.

Fresh expression results are owned temporaries. They are not retroactively treated as aliases to
an earlier input. Preparatory reservations within one call may overlap while being formed; the
complete access bundle must be compatible before invocation. Duplicate X operands are invalid.

### Invocation

Check the whole operand bundle against outside live access and other calls' reservations:

| Two simultaneously live accesses to overlapping places | Allowed |
| --- | --- |
| I and I | Yes |
| I and U, U and U, or X and any other access | No |
| A nested read ending before an outer U/X activation | Yes |
| A nested U/X activation conflicting with an outer reservation | No |

Reborrowing/delegation is not a second independent overlapping access: the parent permission is
suspended or restricted for the delegated subplace until the child ends. A parent U can supply
child I or U access; I cannot supply U, and neither can supply X ownership of the caller's place.
Transitive dependencies are checked, including closures that capture an otherwise separate-looking
operand. Top-level operand names alone do not prove independence.

After successful preparation, activate U and perform X transfers as one non-fallible invocation
transition. There is no user code, allocation, destructor, or callback between transferring the
first and last source. The sources become unavailable; the recipient owns their cleanup. Runtime
checks needed to locate/validate argument places execute during preparation, before that transition.

For an immediate call, the recipient is its invocation frame. For a deferred call, it is the newly
constructed pending computation. Allocate/validate any required frame and prepare its storage
before committing X transfers. An allocation failure therefore cannot expose a half-transferred
argument bundle. Aborting allocation still follows the non-unwinding termination contract.

### Exit and Suspension

If preparation exits recoverably, cancel its reservations and destroy constructed temporaries in
defined reverse construction order. Existing reserved owners are still owned by the caller.
Earlier expression side effects and separate explicit transfers are not rolled back. This is a
preparation rule, not a transaction over arbitrary argument expressions.
If that failure then exits the caller's scope, ordinary caller cleanup still destroys its live
owners. Retaining ownership at the failed call boundary does not suppress that cleanup.

If invocation fails recoverably, ownership is not returned automatically. U leaves a valid value
with any completed changes; X values are disposed of or forwarded by the recipient. Source-level
cleanup order is fixed even when a later optimizer removes its empty physical implementation.
Unrecoverable trap/termination does not invent unwinding or cleanup.

Suspension during later-operand evaluation retains earlier reservations in the parent computation.
They cannot be used for conflicting work while suspended. Cancelling that computation cancels the
current child and cleans its temporaries before releasing reservations or destroying their owners.

## 5. Projections and Persistent Relationships

A projection contract names the owners it can depend on, the accessible part's type/shape, and
read/update capability. It does not produce independent owned T. Built-in fields and indices
use the same access semantics as declared projections. An update projection requires writable
authority; obtaining a read projection cannot manufacture it.

Projection operations may have preparation and cleanup. Their cleanup is an implicit use at the
specified enclosing access boundary. Access cannot end early if that cleanup still requires the
owner. Pure built-in projections can use source-level last-use analysis; user cleanup timing is
not moved to an optimizer-selected last use. This prevents an apparently unused access from
silently releasing a lock or running a callback earlier.

A named projection is scope-bounded access, not an ordinary T initializer. It can be passed to I
or U as permitted, or captured with tracked dependencies. It cannot be put into an independent
field, returned as owned T, or converted into an owning copy according to later use. A declared
dependent projection result may forward caller-owned access; a local owner cannot be made to
outlive its scope to permit escape. An ordinary stored element instead requires permitted copying
or explicit extraction/construction.

For an independent persistent window, use an owned container plus an index/range, with bounds and
invalidation checked by its API. A borrowed iterator retains access to its owner; a consuming
iterator owns the source. Explicit sharing is a separate resource API. None is a universal fallback.
Pointers into a growable container cannot survive a potentially relocating update without a proof
or an API that maintains a stable relationship. Immutable indices do not alone prove stable identity.

Text and sequence shapes `str` and `[T]` can be accessed as unsized I/U inputs and projections
without becoming independently stored unsized values. Owned `String`/`Vec<T>` remain distinct.
Any text update must preserve UTF-8 and owner invariants; this does not authorize unrestricted
byte mutation of a `str` projection.
Storage-to-shape adaptation must select one declared checked operation; comparison does not inherit
a view's operators. No comparison, indexing, or method lookup may retry with a hidden copy.

## 6. Capture Inference and Deferred Computations

Infer capture demand from all potentially reachable checked uses, with I < U < X demand. This
order combines demands on one captured place; it is not a callable-subtyping rule. A later
optimization deleting a use does not change the source operation into a different mode.
Merge overlapping paths at the necessary common prefix and keep proved-disjoint static paths
separate. Dynamic index expressions are not executed at capture construction merely because
they occur in the body: capture their required roots/index inputs and evaluate the index when
the body executes. Explicit capture expressions retain their authored evaluation timing.

Initialize inferred captures in first textual occurrence order of the retained capture paths,
using enclosing occurrences for a nested closure's free dependencies. Own-capture transfer occurs
at closure construction, not first invocation. Cleanup reverses initialization order, with
conditional cleanup for components already transferred. A read capture is not silently upgraded
to an owned copy because the closure escapes. An explicit owned-capture request can force X when
the body itself only reads; the adopted spelling is `^name` in the capture segment before `;`.

Compute environment invocation permission from use: reads permit I invocation, updates require U,
and extraction of an owned capture requires X. Owning a capture and consuming it on invocation
are distinct; an owning, read-only closure can be invoked repeatedly. Environment copyability
is separate from invocation permission. No body inspection at an indirect call reconstructs
missing contract facts.

For async producers, required I/U dependencies begin at successful construction, and X inputs are
owned by the future from that point. Laziness does not postpone ownership or exclusivity. Moving
the future transports the same access identities; it does not release/reacquire its inputs.
An existing-place I/U argument is retained by the public async contract even when transport copies
its bits or omits an unused physical capture; optimization does not change caller availability.
Completion releases only dependencies absent from the result and required remaining cleanup.
An explicitly dependent result keeps its dependencies. A result cannot refer to a future-owned
local that is being destroyed.

Cancellation first cancels the current awaited child, then destroys initialized parent locals in
reverse ownership order, then remaining captures/parameters, releasing access only after its last
required cleanup use. A completed unconsumed future destroys its output once. Composition-owned
children follow their declared task API order; inference does not rewrite that order. Cancellation
is not successful flush, finish, commit, or durable output.

Storage referenced across suspension must remain stable. Internal frames may use embedded storage,
stable handles, or relocation-safe descriptors only when all live accesses remain valid. There is
no blanket heap-frame requirement and no source-level pinning obligation for this internal choice.
Returning a child dependent on a local parent remains invalid; a frame-placement trick cannot
prolong the parent's resource lifetime. User-defined movable self-references are not added.

## 7. Contracts and Compiler Evidence

Each checked callable carries ordered parameter/receiver modes, environment invocation permission,
execution kind, result dependency relations, initialization obligations, and conditional effects.
Parameter identities are reserved before dependency clauses are resolved. Names are source
projections, not the identities used for conformance or forwarding.

Interface conformance preserves exact operation modes, execution kind, associated identities,
and declared result dependencies. No silent I/U/X substitution is added as callable subtyping.
An X-owned local may explicitly supply temporary I/U access inside a wrapper without changing
the wrapper's signature. Erasure preserves access/dependency contracts; allocation of an erased
environment is an independent representation choice.

Public independent result contracts cannot acquire hidden input dependencies from a body. A
dependent result uses an explicit projection/computation relationship; one eligible owner may be
elided mechanically, while multiple candidates require a stable public relationship. Callers
never inspect private bodies to guess ownership meaning. Existing allocator origins remain
separate from access leases: independently owned region-backed data still cannot outlive its region.

Specialization can discharge conditional facts, remove transport, and reuse storage. It cannot
change parameter modes, capture demand, dependency meaning, or destructor order. Runtime safety
checks may be removed by later proofs tied to selected operations, never by a false semantic-law
claim or fresh source/name resolution.

Required evidence comprises canonical places and dependency roots, initialization states, access
identities with begin/reserve/activate/end edges, owned transfer destinations, cleanup order, and
proof obligations for potentially conflicting access. Control-flow joins union dependencies and
require definite initialization at uses; loops reach a conservative fixed point. A failed proof
of non-conflict is a diagnostic, not hidden sharing or unchecked access.

## 8. Distinguishing Cases

These are design cases, not current-language compiler fixtures. Source spellings are intentionally
abstract where the source-design review is pending.

| Case | Required result |
| --- | --- |
| I of one move-only owner twice in sequence | Accept; no ownership copy or refcount operation |
| I of a Copy place with later overlapping mutation during preparation | Reject; Copy does not turn input into a snapshot |
| Explicit independent scalar snapshot followed by source update | Accept when its dependencies are empty |
| Implicit owned initializer from move-only place | Reject |
| X of an integer followed by source read | Reject the read, just as for a resource |
| Generic X-return specialized to Copy and non-Copy | Same transfer rule in both specializations |
| Update contents or replace an X parameter directly | Accept without an intermediate `var` |
| Reinitialize a transferred local `let` | Reject; a parameter's X permission does not change `let` |
| U operation changes a field and returns failure | Accept with changed but valid value; no rollback |
| U operation leaves a hole on recoverable exit | Reject |
| Exchange a move-only field after constructing replacement | Accept; old value has one new owner |
| Partial extraction exposing incomplete Self to its destructor | Reject |
| Outer U reservation; nested I computes independent length; outer activation | Accept |
| Outer U reservation; nested U updates same owner | Reject nested activation |
| X owner plus later I computation of an independent scalar from it | Accept; read ends before transfer |
| Two X operands naming one owner | Reject before invocation |
| Simultaneous U and retained I of overlapping storage | Reject |
| Simultaneous U of proved-disjoint fields/ranges | Accept |
| Two dynamic indices without non-overlap evidence | Reject conflicting access; no address guess |
| Later argument fails before X invocation | Source remains owned; earlier side effects remain |
| Callee fails after X invocation | Source stays unavailable; callee cleans its ownership |
| Preparation suspends, then parent is cancelled | Cancel child/temporaries before releasing reserved owners |
| Store a projected element as independent noncopyable T | Reject without explicit extraction/construction |
| Grow container while an invalidated projection remains live | Reject |
| Projection epilogue still accesses owner after last explicit read | Retain access until epilogue boundary |
| Read-capturing closure escapes a local owner's scope | Reject; no inferred owning copy |
| Own-capture closure reads repeatedly | Repeated invocation allowed; copyability still separately checked |
| Closure captures a dynamic index expression | Preserve body-time evaluation; do not hoist effects |
| Update outside data while a future retains I to it | Reject, even before first await |
| Move an unfinished future, then complete/cancel it | Keep access identity; release/cancel once |
| Cancel parent while child accesses its local | Cancel child before destroying the local |
| Return result retaining a future-owned local destroyed at completion | Reject |
| Wrap a dependent future in a nominal aggregate | Preserve dependencies; no escape laundering |
| I-only generic wrapper forwards to X callee | Reject rather than strengthen wrapper mode |
| Same headers, different private bodies | Preserve public modes/result meaning; inferred effects may differ |

## 9. Research and Limits of Evidence

Reviewed on 2026-11-07. These sources motivate distinctions; the rules above are Nocter decisions.

| Primary source | Design use and limit |
| --- | --- |
| [Mutable Value Semantics, 2022](https://www.jot.fm/issues/issue_2022_02/article2.pdf) | Supports restricting first-class references and exploiting independent values. Its container copy-on-write strategy is not adopted. |
| [Hylo parameter conventions](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#parameter-passing-conventions) | Separates read, update, and owning input. Nocter's exact modes and Copy transfer semantics remain independent decisions. |
| [Hylo subscripts](https://hylo-lang.org/docs/user/language-tour/subscripts/) | Demonstrates projection with suspended accessor cleanup. Nocter's access mode cannot change to consumption merely because of caller last use. |
| [Rust two-phase access implementation](https://rustc-dev-guide.rust-lang.org/borrow-check/two-phase-borrows.html) | Provides a reservation/activation precedent. Nocter applies its explicit call-preparation rule uniformly and also defines delayed transfer; Rust's source-form exceptions are not copied. |
| [Swift Ownership SSA](https://github.com/swiftlang/swift/blob/main/docs/SIL/Ownership.md) | Motivates retaining owned uses, lifetime-ending edges, and verifier obligations in IR. It does not justify adopting Swift reference counting or dynamic exclusivity checks. |
| [Region inference, PLDI 1995](https://www.microsoft.com/en-us/research/publication/better-static-memory-management-improving-region-based-analysis-of-higher-order-languages/) | Supports investigating constraint-based storage placement. It does not allow moving observable resource cleanup or promise optimal placement for arbitrary programs. |

The [bounded model check](v2.0.0-value-access-model-check.py) exercises root-place reservations,
activation, transfer, and cleanup against ownership/exclusivity invariants. It is not a compiler,
an executable language specification, or a proof of projections, generic analysis, suspension,
effect soundness, or the full language. Those require specification migration, checked-operation
validation, and implementation conformance. See the [readiness plan](v2.0.0-implementation-readiness.md).
