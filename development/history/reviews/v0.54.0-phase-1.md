# v0.54.0 Phase 1 Canonical Body-cursor Review

## Scope

This review covers the shared client/server body cursor, incoming-request ownership, consuming body
finalization, terminal failure, retained overread, public examples, and editor projections. It also
searches current HTTP sources and active design documents for the removed collecting path, mirrored
completion state, obsolete one-request overread rejection, and old tuple-return API.

## Findings and Resolution

### Body completion had to remain distinct from terminal failure

The first extraction reused `BodyState.complete` after a decoder or transport failure. That kept
later client reads terminal, but it would also have allowed `IncomingRequest.finish_body` to produce
a responder over a failed, closed stream. `BodyState.failed` now records terminal failure in the
same state authority as decoding and completion. Repeated reads return `std.http.body_failed`, and
consuming finalization cannot cross the failed state.

### Cursor progress cannot require a non-empty caller buffer

The decoder cannot advance a fixed or chunked body into an empty destination. Leaving that fact as
a driver precondition would make a direct cursor caller capable of entering a non-progress loop.
The cursor now returns zero progress without consuming input when output storage is empty. A cursor
test fixes that contract independently of the client and server adapters.

### Source visibility and allocation guarantees must follow the owning source

Moving `IncomingRequest` representation from message storage to server storage exposed two useful
checks: `server_values.nct` must see the representation source directly, and it must import its own
`Vec` dependency instead of relying on a neighboring file. Consuming `close` for owners that contain
generic `Vec` storage no longer claims `noalloc`, because the current generic drop contract cannot
prove that guarantee. No private-field bypass or false effect annotation was introduced.

### The previous response wrapper no longer owns information

`response_progress.nct`, the response-local decoder fields, and the mirrored completion Boolean
were deleted. Both synchronous and asynchronous client drivers, plus the server request driver,
consume `BodyCursorAttempt`. Search found no current `ResponseBodyAttempt`, collecting server body,
tuple-return request API, or unsupported-pipelining failure path. Finalizing an already complete
body also avoids allocating drain storage.

### Overread must transfer as one cursor, not as loose fields

The initial responder representation unpacked the completed cursor into `pending` and
`pending_start`. That would have made a later reusable-connection transition capable of
reconstructing mismatched input state. `Responder` now owns the completed request cursor intact;
the pending allocation, unread offset, completion state, and framing history cross the ownership
transition as one value.

### Documentation had retained pre-streaming statements

The HTTP behavior guide still described a complete request body and simultaneous responder, and the
asynchronous-client design still referred to a separate completion flag and future TLS work. Both
now describe the canonical cursor and the existing plain/TLS transport sum. Examples document the
consuming body-finalization transition.

  across all 53 compiler workspace packages.

  consumption, drain, and response authority on native loopback.

- `cargo test -p nocter-command every_public_package_example_runs_with_its_process_contract` —
  passed for every public package and process contract.

## Result

No open Phase 1 finding remains. One cursor owns body progress and terminal state, incoming requests
stream without body-sized storage, response authority follows consuming finalization, and safe
overread survives in the responder for the later persistence transition. Phase 2 can add response
output planning without reopening request decoding.
