# v0.54.0 Phase 4 Graceful Service-lifecycle Review

## Scope

This review covers listener retirement, accepted connection independence, application-owned
handler draining, fixed shutdown deadlines, timeout cancellation, every public server typestate,
the bounded service example, and the temptation to add HTTP-owned task or connection tracking.

## Findings and Resolution

### Listener admission and accepted work already have distinct owners

`Server` owns only `TcpListener` plus immutable limits. `accept` transfers a new `TcpStream` into a
`ServerConnection`; no accepted typestate retains a reference to the listener. Consuming
`Server.close` therefore stops admission without invalidating accepted work. Adding a separate
`shutdown` state or shared listener flag would duplicate an ownership fact already represented by
the type graph.

### The deadline must enclose the complete drain

Timing each borrowed `TaskGroup.next` would restart the budget and, on expiry, deliberately leave
the group's children alive. The service instead moves the whole group into a drain future that
consumes every output, then applies `task.with_timeout` once to that future. Completion publishes
all handler outcomes. Expiry cancels the owning drain future, destroys its group, and cancels every
remaining child under one fixed deadline.

### Cancellation needs no HTTP cleanup registry

`ServerConnection`, `IncomingRequest`, `Responder`, and `ResponseWriter` each own exactly one
stream through ordinary fields. A handler future owns exactly one of these states at a time.
Destroying that future recursively destroys the state and the stream; no HTTP callback, task ID,
connection table, close flag, or reconciliation pass is needed. A native fixture constructs each
state before suspending its handler, expires the owning group drain, and observes peer EOF in all
four cases.

### Graceful completion and forced cancellation share one orchestration

The successful native case accepts one connection, transfers its lazy handler into the
application group, closes the listener, and only then drives the drain. The handler still sends its
terminal response and the drain observes its result. Forced cases differ only in the deadline
winning; they do not enter a second cleanup path.

### A process signal is a trigger, not a lifecycle primitive

The bounded example can initiate the complete transition after its application-selected final
admission. A future signal API could initiate the same transition, but HTTP does not require or
benefit from knowing that trigger. Phase 4 therefore adds no signal-specific API or compiler
primitive.

## Result

No open Phase 4 finding remains. Admission has one owner, the application has one handler group,
the complete drain has one deadline, and normal structural cancellation is the only forced cleanup
path. Phase 5 can qualify the complete service without adding another lifecycle authority.
