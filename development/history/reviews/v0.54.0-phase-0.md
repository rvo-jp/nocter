# v0.54.0 Phase 0 HTTP Streaming-model Review

## Scope

This review traces body framing, pending transport bytes, completion, timeout, cancellation, and
stream ownership through the synchronous client, asynchronous client, and one-request server. It
reviews the adopted streaming and persistent-connection model before public declarations or
implementation storage make that model expensive to change.

## Findings and Resolution

### Server collection is a driver difference, not a second protocol

The server already uses the shared `BodyDecoder`, but `collect_server_request_body` drives it into
a complete `Vec` before returning request metadata and a responder. The client response path drives
the same decoder one caller buffer at a time. Phase 1 will extract the shared cursor instead of
adding a second streaming decoder or wrapping the collecting server operation.

### Completion currently has two authorities

Client `Response` stores `complete: bool` beside `BodyDecoder.state`. Driver branches update both,
and direct tests inspect decoder state separately. This duplication can drift when another body
owner is added. The canonical cursor will expose terminal progress solely from its decoder; public
owners will not retain another completion bit.

### Response authority cannot coexist with an unfinished body

Returning `(IncomingRequest, Responder)` works only because the current request body is already
complete. Retaining that shape for streaming would split one TCP stream between two unique public
owners or require hidden shared state. The new transition returns one incoming request owner;
consuming body finalization drains unread input and is the only operation that can produce a
responder.

### Safe overread is not unsupported execution

The current server rejects every byte after the current body as unsupported pipelining. TCP does
not preserve message boundaries, so a valid peer may send the next head before the server finishes
the prior exchange. Sequential persistence must retain those bytes while forbidding their parsing
and execution until response completion. The pending range therefore transfers through request,
responder, writer, and reusable connection states.

### Persistence is a completed-exchange fact

Request fields alone cannot authorize reuse. The request body, response framing, and complete
transport write must also succeed. The response-finalization transition is the first authority
that knows all required facts, so it alone may return a reusable connection. Error and cancellation
paths destroy the owner rather than publishing a partially valid continuation.

## Result

No open Phase 0 model finding remains. The design has one body-progress authority, one linear server
stream owner, one persistence publication point, and application-owned concurrency. Phase 1 may now
change internal and public request-body representation without preserving the collecting path as a
compatibility implementation.
