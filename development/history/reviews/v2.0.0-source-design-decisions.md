# v2.0.0 Source Design Decisions Requiring Human Review

## Scope and Status

S1 (declaration-driven calls) and S3 (owned capture and callable types) are adopted for v2.0.0.
S2, S4, S5, and S6 remain under review; the revisions below respond to the user's questions and
are not new adoptions. Examples are proposed Nocter, not runnable current-language packages.
The [milestone](../milestones/v2.0.0.md) owns adoption status; detailed internal rules belong to
[value-access semantics](v2.0.0-value-access-semantics.md).

Decisions need not approve analysis algorithms, proof data structures, frame placement, effect
fixed points, or evaluator dependencies. Those are agent-owned closure work. A selected source
direction still needs precise grammar, tooling rules, and valid/invalid cases before implementation.

## S1. Derive All Call Modes from Declarations

**Adopted.** Uniformly omit receiver and ordinary argument markers at invocation:

```text
func resize(&buffer: Buffer, size: usize): void
func enqueue(^job: Job): void

resize(buffer, 64)
enqueue(job)
buffer.append(42)
let product = buffer.finish()?
```

The rejected alternative was uniform explicit calls: `resize(&buffer, 64)`, `enqueue(^job)`,
`buffer.&append(42)`, and `buffer.^finish()`. Do not retain both as interchangeable styles.

Omission reduces repetition and marker mismatches, but a call alone no longer tells the reader
which operands it consumes. Modes stay explicit in `index.nct`, definitions, callable types, and
editor information. Selection precedes access checking; lack of ownership does not select another
operation. Strengthening a mode is an API contract change even if a caller still compiles.

Standalone transfers, such as `let next = ^previous` and `return ^value`, remain explicit. This
does not adopt the previously deferred omission of ownership transfer in returns or storage.

## S2. Reconsider the Extra Projection Binding Keyword

**Not adopted; revised recommendation.** The earlier `view bytes = ...` changed the binding's
ownership/access category, not the meaning of the `=` punctuation. The initializer still evaluates
once. An owned result and access to existing storage differ in validity, independence, and what
can be retained, but a distinct local binding keyword is not necessary for that distinction.

The declaration-driven design supports considering ordinary bindings instead:

```text
impl Buffer {
    method self.copy_bytes(): Vec<u8>
    view self.bytes(): [u8]
    view &self.edit_bytes(): [u8]
}

let copy = buffer.copy_bytes()   // owns independent bytes
let bytes = buffer.bytes()      // access to existing bytes
var writable = buffer.edit_bytes()
```

`view` on the accessor remains a provisional declaration spelling, not an adopted keyword.
The selected accessor/result category determines whether a name binds owned data or dependent
access. `let` would restrict local update, while `var` could expose update only when the selected
accessor actually supplies it. No ordinary binding can manufacture update authority or silently
turn a projection into a stored copy. Assignment through a writable projected name would update
the original part, not retarget a pointer-like value.

This would revise the earlier local-binding proposal; do not retain `view name` as an optional
alias. It also requires explicit specification of projection-result category propagation and
initialization from existing projected names. Do not infer alias versus copy from later use or
from a failed ownership check. Those semantics are not adopted by answering the user's question.

A retained projection still prevents invalidation while it is used. For example, keeping `bytes`
live while clearing/reallocating its owner is invalid; `copy` can remain usable independently.
The benefit of another keyword was making that distinction visible locally. The cost is another
source form even when the selected contract already states it. The revised preference is one
binding mechanism if the declaration/category rules can keep that meaning understandable.

## S3. Keep Ownership Requests Local in Closures and Callable Types

**Adopted.** Retain the existing closure capture segment only for explicit owned captures,
using the adopted `^` symbol; infer all other necessary captures:

```text
let predicate = (value: i32) { value >= threshold }
var owned = (^buffer; value: u8) {
    buffer.append(value)
    buffer.len()
}
```

The second closure owns `buffer` even though its body does not consume it. Its invocation requires
update permission because the body updates that owned capture. Captures inferred as X because
the body consumes them need no redundant list entry. Do not retain read/update lists as optional
restatements of inference. An explicit entry must express ownership intent that inference would
otherwise not supply.

The alternative is a whole-closure ownership prefix. It is shorter when every capture is owned,
but makes mixed owned and retained-access captures less precise. The selected form is the existing
per-capture segment; retire `move` as an equivalent spelling.

For structural callable types, adopt the following compact mode vocabulary:

```text
func(Item): bool          // input-invocable environment
&func(&Item): void        // update-invocable environment; update parameter
^func(^Job): Product      // consuming environment; transfer parameter
```

The markers inside parameter slots are passing conventions, not ordinary `&T` reference types.
The environment's invocation mode and the mode by which a function receives a callback are
separate: an I parameter holding an update-only callback does not supply permission to invoke it.
An owning callback parameter can update its environment; an updating callback parameter delegates
that permission from its caller. Retain this distinction in examples and diagnostics.

The competing type spelling writes an explicit anonymous receiver, such as
`func &self(&Item): void`. It is not retained as an optional spelling. The selected prefix vocabulary
must be taught with the environment/parameter distinction and reflected consistently in tooling.

## S4. Construct Outcomes Explicitly without Type-Selected Failure

The single `error` failure payload is retained. Separating success from failure selection was
already adopted; this section's constructor names and unit spelling remain proposals.

Recommend ordinary prelude constructor functions for exceptional branch construction, rather
than a new failure-return statement. The names here are proposed API names, not new keywords:

```text
func inspect_error(): error! {
    return error.new("app.sample", "successful error data")
}

func load(): Config! {
    return failure(error.new("app.invalid", "configuration is invalid"))
}

let outer_absent: i32?? = none
let inner_absent: i32?? = some(none)
let present: i32?? = some(some(7))
let done: void = ()
```

`failure` constructs a complete `T!` failure with the one built-in error payload. `some` constructs
exactly one optional layer. Their generic substitutions use ordinary expected-type inference
or explicit arguments; their identities come from checked standard declarations, not magic name
matching. Owned arguments follow the selected call policy. Ordinary `return value` keeps success
injection and never treats type `error` as a failure instruction. Exact-type whole-outcome
forwarding preserves existing tags and requires explicit transfer for existing move-only places.

The reason is compositional behavior, not a preference for another language's errors. For example:

```text
func succeed<T>(^value: T): T! {
    return ^value
}
```

This operation should succeed with the supplied T, including when T is `error`. Type-selected
failure would either make that substitution fail unexpectedly or exclude `error` from an otherwise
general operation. Reading an error record can likewise return `error` successfully while the
read itself fails through the same unified failure channel. Explicit branch construction avoids
per-API failure types and avoids forcing a wrapper merely to return error information as data.

The competing failure form is `fail error_value`, a new control-flow statement. It is concise for
early exits but also needs an expression-level way to store/return a complete failure outcome.
Recommend the ordinary constructor so one mechanism serves those contexts. Propagation with `?`
and handling with `catch` retain their roles. Do not add independently chosen failure payload types.

For unit, recommend `()` as the sole literal of type `void`; it is not a distinct tuple type.
The alternative is the value spelling `void`. This is a human-facing choice about recognizing a
value versus a type name. Nested optional injection, constructor typing, propagation target
selection, and unit contexts require exact specification after this source choice. Repeated
fallible layers are not adopted by this proposal.

## S5. Separate Implementation Binding from Call Disambiguation

**Not adopted; clarification and narrower recommendation.** These two mechanisms have different
semantic roles. A mapping chooses the body for an interface operation; it does not rename that
operation in the interface or export a new inherent name:

```text
impl Buffer {
    impl Reader { read = read_bytes }
    impl OtherReader { read = read_record }
}
```

The helpers may be private in implementation sources. Their names are then not public ways to
call the same operation. Exposing one as an additional inherent API is a separate declaration,
not a language requirement.

A generic caller illustrates why implementation-local naming cannot solve every call collision:

```text
func inspect<T>(value: T): void
where T impl Reader, T impl OtherReader {
    value.read()   // Reader.read or OtherReader.read?
}
```

The generic contract knows those two interface identities, not the private helper names of every
concrete T. Independent libraries may both publish `read`; renaming a local body cannot change
those contracts. The proposed selector chooses the operation identity:

```text
value.(Reader.read)()
value.(OtherReader.read)()
```

Recommend ordinary member calls for unique lookup and mandatory qualification only for an
unresolved interface-operation collision. Do not offer redundant qualified/unqualified spellings
as optional styles when lookup is unique. Exact grammar and eligibility still need approval.

Likewise, allow an implementation map only to bind a genuinely different local body name, resolve
an implementation collision, or explicitly replace a default. Do not add a redundant map as an
optional restatement of already unique same-name conformance. Mapping and qualification are not
substitutes: one defines conformance; the other selects a capability at a call. Explicit source
mapping remains under review, not a reason to require two public names for every operation.

## S6. Withdraw the Representation-Remainder Ellipsis

**Not adopted; the earlier `...` marker recommendation is withdrawn.** The current grammar already
uses `...` for argument packs, literal packs, and spread. A lone marker in a field-contract list
could be parsed in its own context, so this is not an unavoidable parse ambiguity. It nevertheless
adds another concept to the same symbol without establishing that callers need the information.

The original purpose was to distinguish a complete field-initializable record from a contract
that exposes only selected fields. That matters if callers automatically acquire field-literal
construction from the listed fields. It is construction availability, not the existence or count
of hidden fields, that belongs in the public contract.

Prefer evaluating a field contract without a hidden-remainder marker:

```text
// index.nct: proposed direction, not adopted
struct Session {
    id: u64
}

impl Session {
    func new(id: u64): Self!
}
```

The contract exposes the field and supported construction operation. A private representation
may contain additional state without requiring a notice in the public field list. Crucially,
this direction cannot also infer public field-literal construction by inspecting hidden fields:
adding a private field must not silently invalidate previously contract-valid construction.

Before adopting the successor, close how complete public records publish field-literal
construction, versus factory/literal contracts for private representations. Reuse existing
construction/literal contracts where adequate; do not replace `...` with another keyword merely
to announce hidden storage. The internal representation matcher is agent-owned; the caller-facing
construction syntax is the remaining source-design question.

## Root Placement Derived from the Adopted Contract-Only Rule

| Item | Root contract | Ordinary implementation source |
| --- | --- | --- |
| Public callable operation | Signature/default status and interface facts | Matched body |
| Public type and selected field contract | Yes; exact forms follow S6 | Complete private representation where required |
| Private helper / implementation dependency | No | Yes; `use` stays local |
| Authored `use` in root | Always re-export | Not an implementation-only import |
| `see` | Contract/body link, not helper export | Direct private dependency |
| `main` | Declaration when it is the package entry contract | Matched executable body |
| Test body / destructor body / executable statements | No | Yes, subject to ordinary test/lifecycle rules |
| Package metadata / documentation / target directives | Permitted in their established roles; not API exports themselves | Only where their existing item/file role permits |

Do not ask the user to approve declaration-joining algorithms or repeat the decisions that follow
from this table. Constant/static value definitions and interface default bodies must be assigned
their precise contract-versus-body forms during specification migration; a syntax difference
requiring another human decision must be presented concretely rather than guessed during lowering.

Existing generic headers, `where` requirements, grouped directives, and visibility paths should
retain their adopted forms unless a concrete contradiction is found. This review does not reopen
them, the single-error policy, or the `func`/`method` distinction.
