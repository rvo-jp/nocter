# v2.0.0 Source Design Decisions

## Scope and Status

All six principal source directions are adopted for v2.0.0: S1 declaration-driven input calls,
S2 callable-name result prefixes with contract-derived use sites, S3 owned captures/callable modes,
S4 `throw`, S5 interface mapping/disambiguation, and S6 explicit construction entries. This is not
complete grammar or compiler implementation. Result-side `view`/`&view` and `yield` remain rejected.
The follow-ups also adopt `throw reason` without an extra transfer marker, ordinary `some(...)`
for explicit optional presence, and `()` as the `void` literal. Examples are design examples,
not current compiler support. The [milestone](../milestones/v2.0.0.md) owns adoption status;
internal rules belong to [value-access semantics](v2.0.0-value-access-semantics.md).
The three follow-up decisions are recorded under
[outcome and unit source decisions](#outcome-and-unit-source-decisions); R1–R3 are adopted.
The remaining [structural callable result-mode spelling](#structural-callable-result-modes-source-decision-required)
is proposed separately; it is not covered by S3's environment invocation prefixes.

Decisions need not approve analysis algorithms, proof data structures, frame placement, effect
fixed points, or evaluator dependencies. Those are agent-owned closure work. A selected source
direction still needs precise grammar, tooling rules, and valid/invalid cases before implementation.

## S1. Derive All Call Modes from Declarations

**Adopted.** Uniformly omit receiver and ordinary argument markers at invocation:

```text
func resize(&buffer: Buffer, size: usize): void
func enqueue(^job: Job): void

resize(buffer, 64)
enqueue(job)
buffer.append(42)
let product = buffer.finish()?
```

The rejected alternative was uniform explicit calls: `resize(&buffer, 64)`, `enqueue(^job)`,
`buffer.&append(42)`, and `buffer.^finish()`. Do not retain both as interchangeable styles.

Omission reduces repetition and marker mismatches, but a call alone no longer tells the reader
which operands it consumes. Modes stay explicit in `index.nct`, definitions, callable types, and
editor information. Selection precedes access checking; lack of ownership does not select another
operation. Strengthening a mode is an API contract change even if a caller still compiles.

Standalone transfers, such as `let next = ^previous` and `return ^value`, remain explicit. This
does not adopt the previously deferred omission of ownership transfer in returns or storage.

## S2. Declare Result Permission before the Callable Name

**Adopted.** Put the provided result mode before the callable's
identifier. The declaration is authoritative; the marker is metadata, not part of its lookup name:

```text
impl File {
    func ^open(id: u64): Self!
}

impl Buffer {
    method self.bytes(): [u8]
    method &self.&edit_bytes(): [u8]
    method self.^copy_bytes(): Vec<u8>
    method ^self.^move_bytes(): Vec<u8>
}
```

| Position | Meaning |
| --- | --- |
| Before a parameter / `self` | Permission supplied to the operation |
| Before the callable identifier | Permission provided by its result contract |
| No result marker | Read/input result |
| `&` result marker | Update access to existing storage |
| `^` result marker | Owned result delivered to the recipient |

Receiver and result modes are independent. An operation can update its receiver and return owned
data, or consume its receiver and produce owned data. Both `copy_bytes` and `move_bytes` above
provide owned `Vec<u8>` results; copying versus reusing storage does not determine result ownership.
Their receiver contracts distinguish retained versus transferred source ownership.

The declaration and matched body must agree. A binding cannot manufacture ownership or writable
access absent from the result contract, and a private body cannot strengthen or change the public
mode. Reject same-name declarations that differ only in result mode; a destination marker must
not become an overload selector. Interface requirements and callable values must preserve the
mode after the named declaration is no longer directly available.

### Selected Use-Site Policy and Rejected Alternatives

Policy C is adopted. A and B below are rejected alternatives, not available source styles. The
selected rule derives permission from the declaration rather than requesting a different mode:

| Policy | Example for `^open` | Tradeoff |
| --- | --- | --- |
| A. Mandatory binding assertion | `let ^file = open(...)` | Mode is visible beside the name across statements; every binding repeats and must match the expression's result contract. |
| B. Mandatory callee assertion | `let file = ^open(...)` | Mode is visible at invocation; looks like an operation on the callable/receiver and requires extra rules for qualified, method, chained, and indirect calls. |
| C. Derive from contract, adopted | `let file = open(...)` | Least repetition and consistent with S1; readers use the signature or editor information to identify result permission. |

Do not offer these as optional spellings of the same program. Reject redundant result assertions
at both the binding and callee positions. A would have added a local intent check after result-mode
changes, but repeated every result contract. B would have resembled callable or receiver transfer
and the retired `buffer.^finish()` spelling. Neither alternative is part of the selected policy.
Actual transfers from existing owned places remain separate operations; this adoption does not
silently change their source spelling.

If a binding marker instead requests weaker access to an owned result, that is a different
semantic operation, not a readability-only assertion. Do not combine those interpretations or
infer a conversion according to future uses. This review compares fixed contract-derived modes.

### Adopted Rule and Its Consequences

Adopt C together with the callable-name declaration prefix. It completes the public-contract
information missing from the previous binding-only proposal and follows S1's declaration-driven
receiver/argument policy. Named helpers, function values, interfaces, and generics need one checked
result mode; the caller does not inspect a private implementation.

With the selected rule, `let file = open(...)` receives the owned result of `^open`. It is not an input-only binding
that loses transfer rights because no `^` was written locally. For example, a consuming parameter
can receive that owned file through an ordinary unmarked call. Local binding mutability and
reassignment remain separate from ownership; `let` need not be redefined as universal nonownership.
This supersedes the earlier preference to make every unmarked local an I-only binding. That
preference was never adopted and must not impose new restrictions on ordinary code.

A result-mode change is an API contract change even if an unchanged unmarked caller still
compiles. Editor signature/help/hover should expose the selected result mode. Do not count on
method names, inferred last use, or optional source annotations to convey it.

### Remaining Specification Work

The delegated [result-contract decisions](v2.0.0-result-access-contracts.md) now select the
authority, origin, ordinary-return, outcome, and future-output rules. The obligations below
remain precise typing, source grammar where needed, specification migration, and conformance;
do not treat already selected internal alternatives as new approval requests.

The mode alone does not identify the storage owner. Retain the adopted public dependency/origin
rules and their sound zero/one-owner elision. Update access cannot outlive its owner or be returned
from an already-destroyed local. Fresh owned values are returned by an owning contract; a read
result can supply an independent permitted Copy value without authorizing an owning clone.

Specify result-mode notation in structural callable types, interface/default matching, and
qualification independently from the already adopted invocation-environment markers
`func`/`&func`/`^func`. Those describe the callable environment, not its returned value. The name
prefix does not reintroduce `view`, `yield`, mode-based overload selection, or a first-class
storable reference type.

Close optional/fallible result layers, forwarding, async output versus the owned outer future,
multiple-component results, and source operands at return before implementation. In `^open: Self!`,
the successful Self is supplied owned and failure still carries the one owned error. Carrier
ownership must not be erased or confused with access to a produced payload. These are agent-owned
semantic obligations; any materially different additional source form still needs a concrete
human-facing review. Source adoption alone is not a general proof or implementation-readiness claim.

The separate follow-up decision R1 adopts `throw reason` without a redundant transfer marker.
Neither S2 nor R1 restores the deferred implicit-return-transfer proposal.

## S3. Keep Ownership Requests Local in Closures and Callable Types

**Adopted.** Retain the existing closure capture segment only for explicit owned captures,
using the adopted `^` symbol; infer all other necessary captures:

```text
let predicate = (value: i32) { value >= threshold }
var owned = (^buffer; value: u8) {
    buffer.append(value)
    buffer.len()
}
```

The second closure owns `buffer` even though its body does not consume it. Its invocation requires
update permission because the body updates that owned capture. Captures inferred as X because
the body consumes them need no redundant list entry. Do not retain read/update lists as optional
restatements of inference. An explicit entry must express ownership intent that inference would
otherwise not supply.

The alternative is a whole-closure ownership prefix. It is shorter when every capture is owned,
but makes mixed owned and retained-access captures less precise. The selected form is the existing
per-capture segment; retire `move` as an equivalent spelling.

For structural callable types, adopt the following compact mode vocabulary:

```text
func(Item): bool          // input-invocable environment
&func(&Item): void        // update-invocable environment; update parameter
^func(^Job): Product      // consuming environment; transfer parameter
```

The markers inside parameter slots are passing conventions, not ordinary `&T` reference types.
The environment's invocation mode and the mode by which a function receives a callback are
separate: an I parameter holding an update-only callback does not supply permission to invoke it.
An owning callback parameter can update its environment; an updating callback parameter delegates
that permission from its caller. Retain this distinction in examples and diagnostics.

The competing type spelling writes an explicit anonymous receiver, such as
`func &self(&Item): void`. It is not retained as an optional spelling. The selected prefix vocabulary
must be taught with the environment/parameter distinction and reflected consistently in tooling.

## S4. Separate Success Return from Failure Exit

The single `error` failure payload and type-independent success/failure selection remain adopted.
**Adopted:** use `return` for success or exact whole-outcome
forwarding, and `throw` for an explicit failure exit:

```text
func ^load(bytes: [u8]): Config! {
    if bytes.len() == 0 {
        throw error.new("app.empty", "configuration is empty")
    }
    return Config.decode(bytes)?
}

func ^read_error_record(): error! {
    return error.new("app.recorded", "error information returned successfully")
}
```

Define `throw expression` as evaluating and transferring one owned built-in `error` into the
current callable's declared failure layer, then completing that callable with ordinary recoverable
exit cleanup. It does not search dynamically for a handler, skip a closure boundary, unwind callers,
or implicitly propagate through a call without `?`. A callable without a declared fallible layer
cannot use it. For an async producer it completes the producer output when driven; it does not
execute the producer body at future construction.

Throwing transfers an owned error into the failure result. An input-only error parameter cannot
satisfy that ownership requirement. **The separately adopted operand spelling is `throw reason`:**
the failure exit supplies the transfer meaning. Do not retain `throw ^reason` as an alternative
style. See R1 for the rationale and rejection cases.

This does not adopt omission of explicit transfer in ordinary existing-owned success returns.
Standalone transfers remain explicit under S1; call-result bindings follow the adopted S2 choice.

Ordinary success return never interprets type `error` as a failure instruction. Thus a generic
`func ^succeed<T>(^value: T): T! { return ^value }` also succeeds for T = error. Existing complete
outcomes keep their tags when forwarded. The unique declared fallible layer determines propagation/
throw placement within supported mixed outcomes; no repeated fallible layers or per-API failure
types are added.

A stored failure can be produced by an ordinary fallible helper whose body uses `throw`.
Its name is an ordinary API choice, not a required prelude constructor or a second failure syntax.
A helper accepting an existing owned error uses `throw reason`.
Whole-outcome forwarding remains a general operation, not another keyword alias for `throw`.
Catch recovery/rethrow preserves the owned error; suppression remains explicit `catch _`.

This supersedes the earlier preference for a constructor-only failure mechanism. The merits are a
short, recognizable early-failure exit and clear success-return meaning. The teaching cost is that
`throw` is often associated with exception mechanisms elsewhere; Nocter's definition must state its
current-callable boundary and explicit propagation clearly.

The separate follow-up decisions R2 and R3 adopt ordinary `some(...)` for explicit optional
presence and `()` for the unit value. No implicit flattening or new pattern language is adopted.
Exact grammar and nested-outcome cases remain required.

## Outcome and Unit Source Decisions

These three adopted follow-ups resolve spellings previously reserved separately from S1–S6.
They do not change the current released specification or claim implementation. Detailed grammar,
type/access rules, and migration into the owning chapters remain required.

### R1. Use `throw reason` without a Redundant Transfer Marker

**Adopted.** Use one canonical failure exit:

```text
func ^fail(^reason: error): void! {
    throw reason
}
```

`throw` always evaluates and consumes one owned `error`. It has no read-only, update, or copying
variant, so `^` would repeat information fixed by the operation. The owned source becomes
unavailable; an input-only error cannot be thrown, and no implicit clone supplies missing
ownership. Reject `throw ^reason` as an alternative spelling of that same transfer. Fresh
constructor expressions continue to work as in S4.

Requiring `throw ^reason` would expose transfer consistently with ordinary standalone returns
and storage, but adds a marker whose meaning cannot vary in this context. Prefer the shorter
form for the same reason S1 derives argument modes from a fixed contract. The current `await`
contract also consumes its future without an extra transfer marker. This decision does
not omit `^` from general existing-owned success returns or storage transfers: their broader
expression rules remain separately adopted or deferred. Preserve S4's current-callable boundary,
ordinary exit cleanup, and explicit caller propagation with `?`.

### R2. Construct Exactly One Presence Layer with Ordinary `some(...)`

**Adopted.** Use an ordinary generic prelude function, exposed through the ordinary standard-library
contract mechanism, with this v2.0.0 declaration:

```text
func ^some<T>(^value: T): T?
```

It takes ownership of its argument and returns an owned optional with exactly one new present
layer. S1 omits the argument marker at calls. Do not introduce a new keyword, magic lookup by
the identifier `some`, an `Option<T>` replacement, or automatic flattening. `some` remains an
ordinary expression identifier; its contextual use in opaque result types is independent.

```text
let absent: i32?? = none
let present_absent: i32?? = some<i32?>(none)
let present_value: i32?? = some(some(42))
```

These represent three different states: no outer item, an outer item containing absence, and
an outer item containing a present integer. `some(none)` requires enough expected-type or
explicit type-argument information to determine the absent payload type; the explicit argument
above makes that dependency visible without relying on unfinished inference rules.

Retain unambiguous contextual presence injection in bindings as well as returns:

```text
let a: i32? = 10
```

The initializer above is present with payload 10; it does not require `some(10)`.
Returning a plain payload from an optional-returning callable likewise remains supported.
The explicit function is needed to choose and preserve a layer when the payload is itself
optional. It is not a second keyword spelling
for `none` or a requirement to wrap every ordinary optional return. An ordinary library
implementation can use the adopted return/presence rules; no allocation, runtime wrapper call,
or special representation is inherently required. Exact generic injection/forwarding rules
remain an internal closure obligation before implementation.

### R3. Use `()` as the Sole Explicit Value of Type `void`

**Adopted.** Use the literal `()` for the already adopted storable unit type:

```text
let complete: void = ()
let present_completion: void? = some(())
let no_completion: void? = none
```

`some(())` and `none` are distinct even though the present payload carries no information.
Keep `void` as the type name; do not add a separate zero-element tuple type, `Unit` type,
`void()` constructor, or `unit()` alias. Normal completion and bare `return` still supply the
unit value without a written literal. Its zero-byte payload does not remove evaluation effects
or the need for an initialized logical value.

The reason to give `void` one value is generic composition, not a runtime payload or a speed
claim. A generic task can use its result type uniformly for both a calculation returning an
integer and an operation reporting only completion. A generic key/value container can use
`void` as its value type when only key membership matters, without a dummy integer or Boolean.
Those replacement values would introduce irrelevant distinctions. Ordinary applications do not
need a local unit binding simply because their operation returns `void`.

The need for an explicit literal is a separate convenience decision: a unit value could instead
be obtained by calling a `void`-returning function. The literal makes unit data available in
generic arguments, initializers, and present optionals without an otherwise unnecessary helper
call. It is not required by memory safety, optimization, or every `void`-returning operation.

The grammar must distinguish the unit expression `()` from a zero-parameter closure such as
`() { work() }` using source syntax alone. Record recognition and formatting cases during
grammar closure; do not use type inference to choose between the parses. A named unit constant
or constructor would avoid punctuation but introduce a name and lookup for a value with no
variable content; the single literal keeps value construction independent of library scope.

## S5. Separate Implementation Binding from Call Disambiguation

**Adopted.** These two mechanisms have different
semantic roles. A mapping chooses the body for an interface operation; it does not rename that
operation in the interface or export a new inherent name:

```text
impl Buffer {
    impl Reader { read = read_bytes }
    impl OtherReader { read = read_record }
}
```

The helpers may be private in implementation sources. Their names are then not public ways to
call the same operation. Exposing one as an additional inherent API is a separate declaration,
not a language requirement.
The root can publish the conformance fact and associated bindings while a directly seen
implementation source supplies the mapping. Both fragments contribute to one conformance
identity; private helper names need not be added to the outward contract or re-exported.

A generic caller illustrates why implementation-local naming cannot solve every call collision:

```text
func inspect<T>(value: T): void
where T impl Reader, T impl OtherReader {
    value.read()   // Reader.read or OtherReader.read?
}
```

The generic contract knows those two interface identities, not the private helper names of every
concrete T. Independent libraries may both publish `read`; renaming a local body cannot change
those contracts. The adopted selector chooses the operation identity:

```text
value.(Reader.read)()
value.(OtherReader.read)()
```

Use ordinary member calls for unique lookup and mandatory qualification only for an unresolved
interface-operation collision. Do not offer redundant qualified/unqualified spellings as optional
styles when lookup is unique. Complete recognition/tooling grammar remains specification work,
not another approval request for the selected policy.

Likewise, allow an implementation map only to bind a genuinely different local body name, resolve
an implementation collision, or explicitly replace a default. Do not add a redundant map as an
optional restatement of already unique same-name conformance. Mapping and qualification are not
substitutes: one defines conformance; the other selects a capability at a call. The selected source mapping
form does not require two public names for every operation.

## S6. Publish Construction Entries, Not Hidden-Storage Notices

**Adopted.** Use the `impl` container
and existing `func` / `literal` vocabulary. A public field list describes accessible fields; it
neither asserts complete private representation nor automatically grants public raw construction.

A named construction operation needs no additional keyword:

```text
// index.nct
struct Session {
    id: u64
}
impl Session {
    func ^open(id: u64): Self!
}

// Caller
let session = Session.open(42)?
```

The private representation may also hold a socket or other state. The implementation initializes
it and satisfies the published operation. `Session { id: 42 }` is not a public entry merely because
`id` is visible. Callers need no `...` notice or inspection of private fields to know this.

For a simple field-constructed record, publish an explicit structural literal grant:

```text
// index.nct
struct Point {
    x: i32
    y: i32
}
impl Point {
    literal { x, y }
}

// Caller
let point = Point { x: 1, y: 2 }
```

`literal { x, y }` is an adopted v2.0.0 record shape of the literal declaration family,
not current compiler syntax. Its names refer to the already declared public fields and obtain their types
from those identities; do not duplicate type annotations or introduce a variadic marker. It grants
one synthesized structural initialization entry, not an arbitrary user body that recursively calls
itself through `Self { ... }`. Visibility, generic substitution, exactly-once field evaluation,
explicit transfer into owned field initializers, and failure/partial-initialization cleanup remain
checked normally. Public callable invocation still follows S1.

The complete representation must satisfy that structural initialization contract: all required
semantic fields must be covered, with no unknown or silently uninitialized remainder. A private
change that violates the published construction promise is diagnosed at the type implementation,
not by silently removing the entry from callers. Named factories are the existing mechanism for
invariants or hidden state requiring additional initialization. More general custom record-literal
bodies/defaults are not adopted by this decision.

Do not automatically generate both a named `new` and a field literal as equivalent public styles.
Publish the entry that expresses the intended construction; deliberately different named factories
or supported literal shapes may have different purposes. No construction entry is inferred from
an implementation-only helper or from absence of hidden fields.

The short public literal grant keeps construction availability stable and visible in `index.nct`
while preserving public `Point { ... }` convenience. The alternative of named construction only
is not the selected policy. No `pub`, `construct` container, or hidden-representation marker is
reintroduced. Complete grammar, initializer ownership rules, generic field matching, and
implementation conformance remain specification work, not another approval of the selected form.

## Root Placement Derived from the Adopted Contract-Only Rule

| Item | Root contract | Ordinary implementation source |
| --- | --- | --- |
| Public callable operation | Signature/default status and interface facts | Matched body |
| Public type and selected field contract | Yes; exact forms follow S6 | Complete private representation where required |
| Private helper / implementation dependency | No | Yes; `use` stays local |
| Authored `use` in root | Always re-export | Not an implementation-only import |
| `see` | Contract/body link, not helper export | Direct private dependency |
| `main` | Declaration when it is the package entry contract | Matched executable body |
| Test body / destructor body / executable statements | No | Yes, subject to ordinary test/lifecycle rules |
| Package metadata / documentation / target directives | Permitted in their established roles; not API exports themselves | Only where their existing item/file role permits |

Do not ask the user to approve declaration-joining algorithms or repeat the decisions that follow
from this table. Constant/static value definitions and interface default bodies must be assigned
their precise contract-versus-body forms during specification migration; a syntax difference
requiring another human decision must be presented concretely rather than guessed during lowering.

Existing generic headers, `where` requirements, grouped directives, and visibility paths should
retain their adopted forms unless a concrete contradiction is found. This review does not reopen
them, the single-error policy, or the `func`/`method` distinction.

## Structural Callable Result Modes: Source Decision Required

**Proposed, not adopted.** S3 fixes `func`, `&func`, and `^func` for environment invocation;
S2 fixes the result prefix on a named declaration. A structural callable has no identifier on
which to place that result prefix, so an exact human-facing spelling is still needed.

Recommend keeping the result marker in the omitted-name position, immediately before the
parameter list, independently of any environment prefix:

```text
func(): usize                 // read invocation, read/Copy answer
func ^(u64): File!            // read invocation, owned successful result
&func ^(u64): File!           // update invocation, owned successful result
^func ^(u64): File!           // consuming invocation, owned successful result
func &(&buffer: Buffer): [u8] // read invocation, update result from buffer
```

Compare `func ^open(id: u64): File!` with `func ^(u64): File!`: removing the name leaves the
result marker in one stable location. No result marker means I, `&` means U, and `^` means X.
This adds no call-site assertion or first-class reference type. Parameter modes remain independent.

The main alternative is to mark the result beside its type, such as `func(u64): ^File!` and
`&func(u64): ^File!`. That groups output information together but uses a different position from
named declarations, and the marker can look like part of a data type. The recommended position
instead requires learning the distinction between `^func` (consume the callable environment)
and `func ^` (receive an owned result). This distinction already exists semantically and must
remain visible; do not collapse it into one marker or offer both placements as styles.

Both alternatives can encode the same checked contract. Human reading/learning, rather than
implementation effort or optimization, decides between them. Internal origin/cleanup/forwarding
work proceeds independently while this source choice is pending.
