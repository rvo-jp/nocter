# v0.42.0 Phase 5 Asynchronous HTTP Client Final Review

**Result: implementation and source-tree qualification complete with no open practical v0.42.0
finding (2026-09-09).** The asynchronous HTTP client composes the existing URL, resolver, TCP,
HTTP framing, error, and structured-computation contracts without adding another protocol or
scheduler authority.

## Authority and Ownership Audit

The final implementation has these single authorities:

1. `std/url` owns parsed destination components. HTTP reads the retained host, port, authority, and
   request target and never reparses URL text.
2. The private HTTP exchange layer owns request normalization, generated fields, encoded-head
   preparation, informational-response handling, status-101 rejection, and final-head selection.
   Both transport adapters consume its closed attempts.
3. The existing codec and response-body decoder own syntax, finite limits, framing selection, EOF,
   and decoded-byte progression. The shared response-progress operation is the only adapter from
   that decoder to the response cursor.
4. The synchronous and asynchronous client adapters own only transport progress, timeout
   delegation, failure context, and terminal stream closure. Their separate control flow reflects
   different blocking and suspension contracts; it does not repeat a protocol decision.
5. One private `Response` representation uniquely owns its stream, final head, decoder, unread
   bytes, scratch storage, cursor, and terminal flag. Synchronous reads, asynchronous reads,
   explicit close, failure, and destruction all mutate that same owner.
6. Request conveniences use only the public general constructor and mutation contracts. Whole-body
   collectors use only public asynchronous response reads and cannot inspect transport, framing,
   pending input, or completion state.
7. Async TCP and the structured-computation runtime remain the sole authorities for readiness,
   deadlines, suspension, and cancellation. HTTP stores no task, reactor, timer, or descriptor
   registration identity.

Request validation, encoding, and synchronous host resolution finish before an async send
computation is returned. The computation then owns exactly one pending connector or connected
stream. A response-read computation borrows the response exclusively, so destroying it releases
the borrow without creating a second stream owner. Whole-body collection consumes the cursor as it
progresses; cancellation discards its independently owned prefix and cannot rewind the response.

## Findings Corrected During Review

The final review corrected three concrete boundary defects:

- A byte-prefix helper introduced with the exchange split lived beside request and final-head
  policy even though synchronous transport, asynchronous transport, and native fixtures all used
  it. Bounded transport-buffer construction and append operations now have one independent source
  file, leaving the exchange layer transport-neutral and the client-storage file responsible only
  for ownership layout.
- The earlier Internet-client design still described asynchronous I/O as excluded and attributed
  all connection progress to the synchronous client. It now records the shared foundation and
  delegates the asynchronous extension to its own current boundary document.
- Milestone wording claimed the public example validated an exact private serialization. The
  fixture actually and correctly waits for a bounded complete head plus its expected body without
  depending on generated-field order; the historical record now states that contract.

The public response declarations now state the maximum write extent of asynchronous reads. The
behavior guide also records partial collector cancellation and terminal UTF-8 validation, so
callers do not need implementation knowledge to understand cursor advancement.

The complete gate also rejected two qualification-code defects before closure. The first async
HTTP editor test combined too many independently observable features in one 118-line function; it
now shares only its source fixture and separates complete-source hover, navigation, and hints from
incomplete-source completion. The new example also used a noncanonical multiline sequence layout;
the Nocter formatter rewrote it, and the complete runnable-example corpus now accepts it unchanged.

Searches across the release diff found no second request normalizer, final-head selector, body
decoder, timeout state, scheduler state, response owner, HTTP-specific editor inference, source
compatibility path, or obsolete synchronous-only error text. No wrapper remains whose only role is
to preserve a superseded API. Sync and async orchestration deliberately remain separate because a
shared control-flow abstraction would need to expose blocking-versus-suspending transport details
and would weaken rather than strengthen the protocol boundary.
