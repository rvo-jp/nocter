# v0.50.0 Phase 4 Streaming-adapter Review

Date: 2026-09-14

## Result

Phase 4 is complete. Asynchronous item transformation, bounded byte chunks, bounded text lines,
single-directory entries, and recursive directory entries now share one `AsyncIterator` contract.
The review found and removed one initially proposed unbounded line-iterator surface before closure:
`BufReader` itself remains a convenience reader, while `Lines<R>` requires a maximum encoded-line
byte count.

## Contract and Authority Boundaries

- `AsyncMapIter`, `AsyncFilterIter`, `AsyncTakeIter`, and `AsyncEnumerateIter` depend only on the
  compiler-checked `AsyncIterator` associated-item and `next` contract. They do not reconstruct
  method selection or future result shape.
- `ByteChunks<R>` depends only on `Reader` and the package-owned read-count validator. It has no
  branches for files, pipes, sockets, TLS, or HTTP bodies.
- `Lines<R>` owns a `BufReader<R>` and calls one package-visible bounded-line operation. Newline
  removal, partial-line retention, UTF-8 validation, failure termination, and cancellation recovery
  therefore remain in the existing buffered-reader state machine rather than being copied into the
  adapter.
- `ReadDir` and `WalkDir` implement the same asynchronous item contract through their already
  authoritative `next` methods. Filesystem code does not know loop lowering or adapter state.
- The executor, blocking-job service, target ABI, and transport implementations received no
  framing, decoding, or iteration policy.

## Boundedness and Lifecycle

`ByteChunks` normalizes a zero requested size to one, allocates one initialized chunk per requested
step, performs no read-ahead, validates the implementation-reported count, and yields only the
initialized prefix. EOF and failure make it terminal. Cancellation destroys the unpublished chunk;
subsequent source usability remains exactly the selected `Reader` contract.

`Lines` requires an encoded-line bound. Bytes before LF count toward the bound, including a CR that
would be removed from a CR/LF result. Exceeding the bound reports `std.io.line_too_long` and
terminates the producer. Its read-buffer capacity and accepted incomplete-line length are bounded,
and it retains no completed item after yielding it.

All transformation adapters are lazy. `filter` may request multiple upstream items for one accepted
item, but it retains only the current item. `take` stops upstream acquisition at its limit. No
adapter collects the complete source.

## Composition Evidence

The native streaming fixture constructs `ByteChunks` at concrete `File`, `ChildStdout`,
`ChildStderr`, `TcpStream`, `TlsStream`, and HTTP `Response` types. These type-check through their
existing `Reader` conformances. Runtime coverage proves byte boundaries, zero-size normalization,
EOF stability, invalid-count failure, line normalization, line-limit failure, and terminal replay.
The directory-stream native test consumes `ReadDir` with `for await`, including early return and
owner cleanup; recursive traversal already covers `WalkDir` through the same syntax.

## Validation

- all 544 `nocter-checking` library tests;
- all 49 `nocter-lsp` library tests;
- all 76 `nocter-native-session` library tests, including localhost network/TLS/HTTP fixtures;
- `cargo clippy --all-targets -- -D warnings` for the affected compiler workspace;
- `cargo fmt --check` and `git diff --check`;
- deterministic generation and validation of 287 documentation pages.

No retained endpoint-specific streaming loop, duplicated line decoder, unbounded streaming adapter,
or reverse dependency into runtime services remains in the Phase 4 scope.
