# v0.49.0 Structured Process I/O Final Review

**Result: implementation and pre-identity qualification complete with no open practical v0.49.0
finding (2026-09-13).** Public streaming and closed process operations now share one launch,
endpoint, observation, and abandonment model across blocking and executor-safe execution.

## Reviewed Authority Model

The review followed command preparation through target execution, child ownership, ordinary byte
interfaces, structured cancellation, editor queries, examples, and installed artifacts.

1. `fork_spawn_command` is the only standard-library transition that creates a child. Blocking and
   asynchronous launch differ only in how they await the same close-on-exec report.
2. One private `ChildOwner` contains the unreaped PID. Explicit observation consumes or updates
   that owner, while destruction transfers the still-pending identity to the target abandonment
   service. Public `Child` never exposes a PID or asks its caller to reap one.
3. One wait classifier owns interruption, pending state, exact-PID validation, exit decoding,
   signal decoding, syscall failure, and invalid native state. Blocking, nonwaiting, and
   asynchronous observation consume its closed result instead of decoding status independently.
4. One pipe constructor performs close-on-exec normalization. Spawn configuration transfers each
   endpoint into either the child or one public owner exactly once; untaken owners close during
   destruction.
5. Generic `Reader`, `Writer`, `BlockingReader`, and `BlockingWriter` contracts are the only byte
   boundary visible to buffering and transfer. Neither compiler nor editor code recognizes
   `Command`, `Child`, `Stdio`, `ProcessIo`, or pipe wrapper names.
6. `ReactorInterest::ProcessExit` is target-independent semantic vocabulary. The Darwin event
   adapter and generated root map that value to the one runtime-owned event ABI; semantic layers do
   not import native event records or constants.

## Findings Corrected During Review

Nonwaiting child observation treated an interrupted `wait4` as an absent status. That violated the
documented contract that `none` means only "still running" and left pending-state interpretation
outside the shared decoder. The decoder now owns pending state and validates the returned PID
against the exact owner. `try_wait` retries interruption and returns `none` only for a successful
nonwaiting pending observation. Blocking observation rejects the impossible pending result.

The standard self-test still contained a million-iteration process-liveness probe superseded by
the Phase 6 exact-PID cancellation test. It was removed. Production asynchronous observation waits
on process-exit events; it performs no periodic PID probe. A bounded native integration loop remains
only to exercise the deliberately nonblocking `try_wait` API until a requested termination becomes
observable.

A fresh warnings-denied Clippy run exposed repeated Rust match arms for identical primitive ABI
shapes and standard-fixture dependencies. Those tables now group equal contracts without merging
their distinct semantic roles. The pipeline language-server test was divided into focused
assertion responsibilities while retaining one server, package, and semantic analysis. Two native
tests retain narrow line-count allowances because each embeds one complete executable lifecycle
scenario; no product warning or correctness rule is suppressed.

The review catalog omitted the existing Phase 5 and Phase 6 records. Their entries were restored
with this final record so the historical evidence remains discoverable from its owning catalog.

## Legacy, Duplication, and Dependency Audit

Searches and dependency inspection found no remaining terminal `CommandIoSession`, generated
`pollfd` process wait, compatibility alias, duplicate launch authority, second wait-status decoder,
public raw-PID ownership, hidden pipe duplication path, process-specific buffer, compiler/editor
source-name branch, or reverse dependency from runtime adapters into standard source or frontend
semantics.

The blocking pipe coordinator still uses `poll` for descriptor readiness. It neither observes
process completion nor launches or reaps a child, so it is not a second process wait model. The
Darwin reactor depends only on the event adapter and task/runtime contracts. ARM64 selection
depends on closed machine and runtime contracts rather than public standard-library declarations.
