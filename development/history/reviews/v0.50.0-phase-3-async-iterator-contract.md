# v0.50.0 Phase 3 Async-iterator Contract Review

Date: 2026-09-14

## Result

Phase 3 now has one compiler-recognized `AsyncIterator` contract without yet introducing a second
loop implementation. The standard interface owns `Item` and one executor-safe readwrite `next`
whose body output is `Item?!`. `WalkDir` conforms directly through its existing step method.

## Identity and Validation

- Three closed standard roles select the interface, associated item, and method. Consumers do not
  infer them from the `AsyncIterator`, `Item`, or `next` spellings.
- The declaration lives in `iter/asynchronous`, where its common member names cannot collide with
  the synchronous iterator role locators. `std/iter` re-exports only the public type name.
- Standard semantic preparation validates the synchronous and asynchronous contracts through one
  parameterized relationship checker. The asynchronous variant requires deferred execution and a
  fallible optional associated projection; an immediate or infallible near miss is rejected before
  body checking.
- The filesystem implementation imports the declaring module directly when stating conformance.
  Public callers may use the shorter re-export without making implementation identity depend on an
  import wrapper.

## Dependency Review

`std/fs` depends on the asynchronous iteration declaration, while the interface has no filesystem,
executor, or target dependency. `WalkDir` supplies policy and ownership; `AsyncIterator` supplies
only the item-consumption contract. No target ABI, scheduler state, or directory representation
enters the interface.

The next change must make `for await` retain the checker-selected method and outcome plan. MIR must
consume that plan and may not search the standard library or reconstruct the `next` signature.
