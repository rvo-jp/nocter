# v0.37.0 Phase 1 Bottleneck Attribution

**Result: complete (2026-09-06).** External timing, compiler-owned query accounting, a ten-second
sample of the released persistent LSP workload, and direct code review identify one structural
incremental bottleneck. No production instrumentation or behavior change was required.

## Evidence

The Phase 0 baseline records a 188.280 ms median for one body edit followed by checked hover. The
profile sampled 7,843 main-thread stacks while the released compiler processed the same repeated
body edit. Of the 7,756 samples below `LanguageServer::receive`, 7,602 were in workspace analysis,
6,319 reached `CompilerComputation::analyze`, and 5,046 reached `ProgramFinalizationQuery`. Whole-
program finalization therefore occupied about 65 percent of the observed request path and about 80
percent of compiler-computation samples.

The largest finalization branches included:

| Work repeated after one body edit | Inclusive samples | Share of analyzed request |
| --- | ---: | ---: |
| loan analysis for every body | 1,240 | 16.0% |
| provenance analysis and fixed-point inference | 1,157 | 14.9% |
| replay of reusable checked bodies | 834 | 10.8% |
| source-index reconstruction | 637 | 8.2% |
| allocation-effect analysis | 86 | 1.1% |

These inclusive branches overlap only at their finalization parent; percentages are descriptive
sampling evidence, not exact accounting. Top-of-stack samples also show substantial hashing,
sorting, allocation, and cloning distributed across reconstruction rather than one isolated slow
function.

The deterministic query tests independently establish the invalidation shape. A body-only edit
reuses declarations and program preparation, executes name and type checking only for the changed
body, then necessarily executes `ProgramFinalizationQuery` and the complete analysis query again.
The profiler confirms that the final step, not repeated parsing or sibling body type checking,
dominates the warm editor path.

Cold process sampling could not reliably attach before the short-lived command exited. No claim is
derived from that empty sample. Direct process timing independently reproduced the stored package
baseline, so the Phase 0 values remain valid.

## Root Cause

The incremental boundary ends one stage too early. `ReusableCheckedBody` gives each typed body a
source-neutral query product, but body-local structural types and closures use private identities.
`BodyTypeRecipe` and `BodyClosureRecipe` must replay every body in canonical order before the
compiler can publish one `CheckedProgram`. After replay, provenance, effects, loans, and source
projection are represented only as whole-program tables. A change to one typed body therefore
invalidates the one monolithic finalization product and reconstructs every unchanged body relation.

This is not duplicate semantic logic in the LSP and not a defect in dependency validation. CLI and
LSP reach the same compiler query entry, and the query engine correctly follows the dependencies it
has been given. The defect is the mismatch between body-granular inputs and a scope-granular final
query with no reusable intermediate relation products.

Three smaller contract problems amplify the same path:

- provenance, effect, and loan passes each receive a separate slice carrying identical body facts;
- those passes repeatedly recover `BodyId` membership with linear searches instead of consuming an
  indexed catalog that proves canonical coverage once;
- source projection is rebuilt from every body's projections even when only one body changed.

The slice APIs rely on the caller to supply a complete unique body set and then rediscover that
property independently. This is both unnecessary work and a weaker contract.

## Selected Change Boundary

Phase 2 will first introduce one canonical indexed body-relation catalog owned by checking. It will
validate exact graph coverage once and supply the same body/source/origin fact to provenance,
effects, and loans without three copied vectors or repeated linear lookup. This removes an actual
cold and warm cost while creating the input boundary required for further decomposition.

Phase 3 will move reusable finalization facts across the query boundary. The target model separates:

1. source-neutral facts produced once per typed body;
2. program summary facts whose fixed point depends only on relevant callable edges;
3. body-local provenance, loan, cleanup, and source-projection products keyed by the exact summary
   facts they consume;
4. cheap canonical assembly of the final checked program.

Stable identity must be solved at that boundary; caching already-materialized values whose
`TypeId` or `ClosureId` belongs to an earlier replay branch is forbidden. The implementation must
not bypass full diagnostics, add an editor-only checker, seed a fixed point from unchecked stale
state, or make query order observable.

Phase 2 is measured independently. If indexed input alone does not reach the milestone performance
target, that result is evidence to continue the Phase 3 decomposition, not a reason to broaden a
local optimization.
