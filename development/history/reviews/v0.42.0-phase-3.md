# v0.42.0 Phase 3 Practical HTTP Client API Review

**Result: complete with no open Phase 3 finding (2026-09-09).** The practical operations derive
from existing request values and the unique response cursor. They add no HTTP policy, replay,
framing authority, timeout mechanism, or transport owner.

## Reviewed Boundary

The review covered the public HTTP declarations, the new request-convenience and response-
collection implementation files, the synchronous and asynchronous client adapters, standard HTTP
tests, and local native async fixtures. It asked whether an operation could be removed without
changing the underlying protocol contract, and whether any implementation needed private state
owned by another responsibility.

## Authority Findings

- Named GET, HEAD, and POST construction delegates `Request.new`; there is no second target or URL
  validation path.
- Text header mutation completes both validated value constructions before calling the existing
  append operation. An invalid name or value leaves the request unchanged.
- Text body mutation copies exact UTF-8 bytes through the existing complete-body setter. It does not
  add a content header or create another body representation.
- Whole-body async collection invokes `Response.read_async` or
  `Response.read_async_with_timeout`. It cannot access or reinterpret body framing, pending input,
  completion state, or the owned stream.
- Byte and UTF-8 collectors share one byte-collection implementation. UTF-8 validation occurs only
  after transport completion.
- Timeout collection preserves a fresh idle timeout for each transport fragment needed by the
  existing read operation. It does not claim or compute a whole-body deadline.

No obsolete compatibility spelling, duplicate cursor, partial-mutation fallback, or wrapper that
re-exposes private transport state was found in this scope.
