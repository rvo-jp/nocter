# v0.67.0 Phase 6 Reloadable Lifecycle Review

**Result: complete with no open Phase 6 finding (2026-09-23).** Process lifecycle observation and
validated configuration publication now meet at application code without sharing representation or
creating process-global mutable configuration.

## Event Authority

The runtime contract owns one process-context layout for the lifecycle descriptor, original
`SIGHUP`, `SIGINT`, and `SIGTERM` dispositions, and the sticky termination value. The ARM64 Darwin
helper is the only owner of `kqueue` signal registration, event decoding, disposition restoration,
and native signal numbers. Runtime primitive roles select its descriptor and observation entries;
the standard-library target adapter sees only a two-word classified result.

`LifecycleRequest.reload` is consumed, so a service can wait for later reloads. Interrupt and
termination are sticky because shutdown cannot be withdrawn and concurrent waiters must not lose
it. Multiple waiters may wake for one descriptor event, but only one consumes a reload; after a
termination is consumed, every later observation reads the process-context value without touching
the queue.

## Publication Authority

`PublishedConfiguration` owns one `Mutex<SharedValue<Configuration>>`. Its public constructor and
`publish` method accept only the result of `Builder.finish`; neither a builder nor an unvalidated
source has the required type. `current` retains the selected immutable shared owner and releases the
mutex before returning its `ConfigurationView`. Existing views can continue reading an old
generation without blocking publication or later readers. Candidate input reading, overlay,
normalization, constraints, and required field checks occur before acquiring the publication
mutex. A failure therefore has no published mutation to undo.

Atomic replacement uses the general `MutexGuard.replace` ownership operation. This keeps raw
pointer replacement inside `std/sync` and prevents `std/config` from knowing the mutex
representation. The previous shared owner is released after replacement; its configuration is
destroyed only after the last existing view ends. No process-global configuration slot, reload
callback, hidden source precedence, or signal-to-configuration dependency was added.

## Adversarial Review

- Reload and termination do not have parallel descriptors or competing consumers.
- Standard source does not reproduce native event layout, signal registration, or process-context
  offsets.
- The backend cannot derive lifecycle helper presence from declaration names; closed primitive
  roles remain the sole selector.
- Failed candidate validation cannot reach publication, including when a later source contains an
  invalid typed value.
- A handler cannot retain a borrowed configuration beyond `ConfigurationView`; the view owns the
  exact immutable generation rather than holding the publication mutex.
- Phase 6 adds no configuration reader, filesystem watcher, retry loop, or logging policy. Those
  remain application decisions.

## Qualification

Focused runtime-contract and ARM64 suites cover the changed ABI and helper selection. A native
process receives repeated `SIGHUP`, `SIGINT`, and `SIGTERM` deliveries and observes two reloads plus
both termination variants through the public service contract. The complete configuration-source
application retains its initial published value after a rejected candidate, observes one successful
atomic replacement through a shared reader, and proves that a view acquired before replacement
still owns the previous immutable generation. Standard-package discovery and native configuration
contracts verify the new dependency edges and checked declarations.
