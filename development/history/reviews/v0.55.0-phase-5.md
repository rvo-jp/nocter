# v0.55.0 Phase 5 Practical HTTP Application and Qualification Review

## Scope

This review closes the erased-callable and practical HTTP application milestone. It covers checked
callable erasure, executable closure specialization, MIR ownership and cleanup, Machine and ARM64
indirect dispatch, parsed request targets, deterministic routing, the complete public application,
editor behavior, and repository-wide qualification.

## Findings and Resolution

### Consuming erased calls have one ownership transition

The first native implementation invoked an owning erased environment through its concrete closure
body, but the caller still scheduled ordinary value cleanup. The ownership analysis had projected
static call targets individually and omitted the new erased-callable target. The correction is not
an erased-call exception: every call target now exposes its callable operand through one common
projection, and ownership, loans, provenance, and closure-capability analysis consume that
projection. A consuming erased call transfers the staged callable exactly once; its generated
adapter invokes the body, preserves the result, completes retained capture destruction, and
releases the environment mapping.

### Operand staging follows the existing call-order contract

Static consuming closures were staged before later arguments, while the initial erased path left
the callable in its source place until invocation. A later fallible argument could therefore exit
before the transfer represented by the checked call. MIR lowering now stages and deactivates every
consuming callable operand before lowering later arguments. Native tests cover direct and retained
environments, moved captures, fallible results, deferred results, cancellation, and argument
failure; each path destroys or transfers the environment once.

### Runtime erasure remains an explicit closed operation

Checked semantics select erasure only when the expected type is an authored `any func`,
`any &func`, or `any &+func` contract. `ExecutableProgram` closes each reached concrete closure and
owning adapter before MIR. MIR records a typed environment, invocation signature, capability, and
destruction plan. Machine assigns dense adapter and destruction identities, while ARM64 consumes
only those closed identities and layouts. No backend performs source-name lookup, type inference,
or callable selection, and ordinary statically specialized `func` calls retain their existing
path.

### Request targets have one parsing authority

The HTTP codec constructs one `RequestTarget` from the already validated request-target spelling.
It retains the original text together with path boundaries, decoded path segments, and query
iteration. Routing and applications consume that value rather than splitting or decoding the raw
target again. Malformed percent encoding has one public failure boundary, and decoded owned values
are created only when requested by the caller.

### Routing owns selection, not execution

`Router` validates route patterns and ambiguity during construction, preserves declaration order,
and selects one method/path match with typed parameters. `Handler` is a readonly erased callable,
so heterogeneous handlers share one explicit representation without acquiring connection, task,
or allocator authority. A successful dispatch consumes the request into the selected handler; an
unmatched dispatch returns the request for explicit not-found or method-not-allowed policy.

### The application keeps lifecycle policy at its owner

The public HTTP service example covers exact and parameter routes, query decoding, handler failure,
malformed input, request timeout, a 32 KiB streamed body and response, sequential keep-alive, and
graceful shutdown. The application owns a bounded `TaskGroup` and its drain deadline. HTTP owns
framing and responder typestate, TCP owns transport progress, and the router owns only deterministic
selection. There is no hidden handler task registry or second connection lifecycle.

### Qualification findings were contract drift, not compatibility work

Warnings-denied Clippy exposed oversized assembly functions after the new operation crossed MIR,
Machine, and ARM64. Those functions were separated by existing responsibilities: operation-use
collection, call-target validation, closure specialization, destruction-site collection, ABI
planning, and instruction selection. The standard dependency audit also identified the Router's
new `http -> iter` edge, and the formatter audit identified one continuation-indent difference in
the application. Both audit authorities now describe the final authored graph and canonical source.
No warning suppression, wrapper, or legacy path was added.

## Whole-Repository Review

The final implementation was reviewed for implicit callable boxing, duplicated target selection,
caller-maintained ownership state, backend semantic reinterpretation, raw request-target reparsing,
ambiguous route order, hidden task ownership, and response framing outside the established writer.
The review also followed erased callable data through checked execution, ownership, loans,
provenance, executable specialization, MIR validation and async-frame liveness, Machine dataflow,
ARM64 selection, native cleanup, and semantic presentation.

Each downstream responsibility consumes a closed contract from the preceding layer. The concrete
closure body, generated owning adapter, destruction plan, call ABI, and code address each have one
identity authority. The only repeated work is representation-specific projection required by the
next layer; no later layer repeats source selection or semantic inference. No compatibility
fallback, source-text runtime lookup, second HTTP parser, hidden service registry, or open
caller-correctness precondition remains.
