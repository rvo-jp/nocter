# v0.68.0 Phase 5 Optimization-boundary Review

**Result: complete with no open Phase 5 finding (2026-09-24).** The complete optimized-machine
boundary, ARM64 consumption path, and native measurement harness were reviewed after the workload
comparison. Two concrete contract defects were corrected before the complete gate ran.

## Frozen-body and Dataflow Authority

Ordinary MIR bodies, generated destruction, and generated erased-callable adapters are the only
three `MachineBodyDraft` producers. All three submit the complete draft to `MachineBody::freeze`.
That method invokes the sole target-independent optimization entry before constructing any
immutable identity table. `MachineFunction::new` constructs `MachineFunctionDataflow` only from
the resulting frozen body. No producer builds liveness, call-crossing facts, or a target plan from
the draft, and no later stage can retain a pre-optimization identity.

Reachability starts from the frozen entry candidate and closes over control-flow targets,
operations, values, addresses, stack objects, drop flags, packs, and reachable deferred execution
state. One `DenseRemap` then rewrites every surviving cross-domain reference before the vectors
become immutable `MachineTable`s. Operation kinds, terminators, address steps, packs, cancellation
actions, and deferred fields are remapped with closed enum matches. ARM64 additionally rejects a
non-dense Machine table at each target-plan boundary rather than accepting a sparse identity.

## Legality and Target Consumption

`MachineOperationKind::effect` remains the sole conservative removal classification. The review
found that the separate call-boundary fact used a positive `matches!` list. Adding a new operation
or terminator could therefore have silently inherited `false`, making local storage forwarding,
drop-flag coalescing, and register allocation depend on the contributor remembering every
consumer. Phase 5 replaced both operation and terminator classifiers with exhaustive matches. A
new enum member now fails compilation until its boundary behavior is classified. The storage pass
then no longer needs its redundant special case for `DriveComputation`; it consumes only the shared
classification.

Constant-index resolution remains Machine-owned. Each checked address step and structural index
borrow freezes `Required`, `ProvenInBounds`, or `ProvenTrap`. ARM64 copies that disposition into its
selected address or cancellation plan. It emits a comparison for `Required`, direct fixed-offset
formation for the exact in-bounds proof shape, and an unconditional bounds trap for
`ProvenTrap`. It does not compare constants or ranges again. Machine's exact stack-address proof
also checks complete extent, checked offset arithmetic, and alignment before marking address
evaluation removable; pointer, view, dynamic, and unresolved paths remain trapping.

ARM64 performs target planning rather than target-independent rewriting. Its value plan consumes
post-optimization dataflow, Machine-proven physical-storage aliases, and the single pre-frame
direct-aggregate plan. No ARM64 pass folds Machine constants, removes Machine operations, computes
reachability, or reclassifies ownership and trap behavior.

## Measurement Isolation

No compiler workspace manifest or production crate references `development/benchmarks`, and the
optimizer does not branch on measurement state. The immutable optimization report is observation
evidence retained on each frozen body; production lowering never consumes it to alter behavior.

The review found one implicit JavaScript calling convention in the new native runner. The
subprocess workload read its source through `this.source`, although every other workload depended
only on explicit invocation arguments. Extracting or wrapping that method would have changed the
working directory. The runner now passes each workload's already normalized `sourceRoot`
explicitly, and its helper test calls the detached function to prove that receiver binding is not
part of the contract.

## Qualification

The complete compiler gate ran in one disposable external Cargo target after both corrections. It
passed repository metadata verification, benchmark-helper tests, pinned Unicode reproduction,
formatting, warnings-denied workspace Clippy, all enabled locked workspace tests,
no-default-features checking, and warnings-denied Rust documentation. The run included 54 Machine
tests, 117 ARM64 tests, 61 analysis tests, 38 CLI tests, 62 command tests, 126 native-session tests,
and 118 language-server tests. Native suites exercised safety traps, cleanup, deferred
cancellation, standard-library applications, process, filesystem, network, TLS, HTTP, and every
public example through the same optimized body path.

Phase 5 found no stale pre-optimization dataflow, duplicate target-independent ARM64 optimization,
sparse identity leakage, lost safety or ownership barrier, or benchmark-only production behavior.
v0.68.0 implementation is ready for release preparation; this review does not assign release
identity or publish an artifact.
