# v0.66.0 Phase 5 Durable Local-state Review

**Result: implementation complete with no open Phase 5 finding (2026-09-21).** Durable file
replacement, recoverable journal framing, current-state reconstruction, compaction, the HTTP
service application, and editor projection form one directional authority chain. Release identity
and deterministic archive qualification remain the separate release-preparation boundary.

## Authority Trace

| Responsibility | Sole authority | Consumers |
| --- | --- | --- |
| Open descriptor ownership, synchronization, and executor retirement | `std/io.File` and the generated file service | `std/fs` and `std/store` |
| Exclusive sibling selection, atomic rename, and parent-directory synchronization | `std/fs` | `std/store` and applications |
| Record magic, version, sequence, length, CRC-32, and incomplete-tail classification | `std/store` journal | `std/store.Store` |
| Snapshot shape, configured limits, current byte-keyed state, and compaction policy | `std/store.Store` | applications |
| Serialization, schema evolution, transaction timing, and concurrent-task synchronization | application code | application behavior |

The journal consumes byte order, CRC-32, file I/O, and durable replacement through their public
standard-library contracts. It does not inspect target descriptors, errno values, file-service
jobs, or collection placement. `Store` consumes one journal recovery result and does not reopen or
reinterpret filesystem persistence. The HTTP service serializes its own event, commits it, closes
the owner, reopens the store, and compares exact application bytes; no persistence-specific path
exists in the compiler or language server.

## Corrected Findings

The first recovery shape retained every complete snapshot body and `Store.open` decoded each one
only to discard all but the final state. Since every record is a complete snapshot, this repeated
obsolete application-state reconstruction. Recovery now validates every record header, sequence,
bound, and checksum while scanning, copies only the final complete body, and decodes exactly that
one authoritative snapshot.

Duplicate-key validation initially scanned all previously decoded entries. A maximum-size valid
snapshot could therefore require quadratic comparisons. Decoding now builds one temporary seeded
hash-to-position index. It retains no second key copy, resolves collisions with exact byte
comparison, and is discarded after the insertion-ordered state is reconstructed. The persisted
format and public lookup semantics remain independent of hash-table placement.

The record-count guard initially ran before incomplete-body classification. A journal already at
its configured complete-record bound could reject a valid interrupted next commit instead of
discarding its incomplete tail. The guard now counts only complete records, while sequence
continuity is still checked as soon as a complete final header is available. A dedicated test
covers this boundary.

Snapshot decoding also accepted a configured entry bound before proving that the declared number
of entry headers could fit in the observed payload. It now derives the physical maximum from the
payload before reserving entry storage. The review also removed four test-only recovery wrappers
and an unreachable empty-compaction branch; neither represented an independent contract.

## Failure and Ownership Review

Commit and replacement make their store and journal owners terminal before the first suspension.
A failed or cancelled operation cannot be retried through an owner whose durable outcome is
unknown. Reopen is the only operation that resolves the stored sequence. Successful append waits
for file synchronization; successful replacement additionally waits for parent-directory
synchronization. Recovery publishes no state until the final snapshot has passed all structural
checks.

Configured limits bound the physical journal read, one record, one snapshot, entry count, and each
key and value. Lengths read from storage are checked before allocation or arithmetic. The one
remaining full-journal input buffer is an intentional bounded implementation choice: streaming the
same format can replace it later without changing the journal or store contract.
