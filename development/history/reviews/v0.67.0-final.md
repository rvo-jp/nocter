# v0.67.0 Final Operational-application Review

**Result: complete with no open release-blocking finding (2026-09-23).** This review covers the
whole v0.67.0 change range rather than treating the store, configuration, lifecycle, and example as
independent features.

## Authority Review

`StoreState` is the sole authoritative in-memory application state. Its hash index contains only
transient hashes and slot positions, while insertion links own deterministic traversal and
persistence order. Journal recovery applies versioned records into that same state and migration
uses the ordinary durable replacement path. No consumer reparses the journal to answer an ordinary
lookup or serializes hash placement.

Configuration has one owned representation for schema fields, source candidates, prepared input,
and immutable finalized slots. `Builder.apply` prepares and validates a complete source before
publishing any replacement, so adapters cannot choose precedence or partially mutate retained
configuration. JSON, environment, and command-line modules only project existing typed values into
the source-neutral vocabulary. `PublishedConfiguration` accepts only a completed `Configuration`
and cannot observe candidate construction.

The lifecycle runtime reports reload or termination requests but has no access to configuration,
listener, handler, or store state. The HTTP service example alone owns startup-only policy,
candidate acceptance, bounded admission, shutdown order, and its durable event schema. This keeps
application policy out of standard modules and keeps the example from interpreting runtime ABI or
journal bytes.

## Failure and Ownership Review

- Store ownership is tied to a stable lock sibling rather than a replaceable journal inode. Failed
  open and migration paths retire their acquired owners, while a failed commit makes the public
  store terminal until reopen.
- Recovery validates lengths before allocation, accepts only an incomplete final frame as a crash
  tail, and never guesses a format. A complete invalid record remains corruption.
- Configuration errors retain field and source identity but never candidate bytes. Secret values
  cannot enter display, diagnostics, provenance, or the example's structured events.
- Reload validates an isolated candidate before acquiring the publication lock. Rejected or
  startup-incompatible candidates require no rollback and leave the preceding generation live.
- Shutdown closes admission, drains the owned handler group, commits a dedicated lifecycle event,
  closes the store, and verifies reopen recovery even when no request was accepted.

## Compiler and Editor Review

The complete LSP gate found one checker defect rather than an application exception: member-call
disambiguation performed speculative semantic checking before method fallback. The checker now
resolves the receiver once and keeps callable-field mutation in a private `PlaceDraft` clone.
Checked nodes and source projections therefore come from only the selected interpretation. A
focused nested-index regression and the complete HTTP-service editor scenario cover the repaired
boundary.

No new compiler special case recognizes configuration names, store paths, lifecycle policy, or the
HTTP example. Target-specific file locking and lifecycle delivery remain selected through the
runtime contracts that already separate standard declarations, target selection, generated code,
and host conformance.

## Closure

The review found no obsolete compatibility path, duplicate state authority, reverse dependency, or
public contract whose correctness relies on a caller preserving an undocumented invariant. The
remaining limits—single writer, explicit source order, Darwin lifecycle signals, and application-
owned reload policy—are documented product boundaries rather than hidden implementation
assumptions.
