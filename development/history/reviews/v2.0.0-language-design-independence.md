# v2.0.0 Language Design Independence Review

## Scope and Status

This review evaluates the current language contracts against Nocter's goals: simple application
code, explicit public contracts, safe deterministic ownership, and faster generated programs through
compile-time evaluation and optimization. Similarity to Rust is neither evidence for a rule nor a
reason to reject it. The specification can establish what a rule does; it cannot establish that
its author adopted it uncritically.

The evidence is the current `spec/` and checked standard-library contracts and behavior guides.
The [v2.0.0 plan](../milestones/v2.0.0.md) is used only to distinguish adopted direction from current
behavior. Archived implementations and historical qualification reports are not language evidence.
This is a specification review, not an implementation qualification or a measured performance
comparison. Recommendations below are not adopted changes to the language or release candidate.

The main concern is not wholesale imitation of Rust. Several restrictions instead expose the
current evaluator, representation, or proof boundary as rules application authors must learn.
Those restrictions need independent justification before they become v2.0.0 contracts.

## Priority Findings

### 1. Compile-Time Evaluation Is Much Narrower Than the Optimization Goal

**Priority: high. Recommendation: expand the evaluator before adding syntax. Not yet adopted.**

[Compile-Time Constants](../../../spec/language/constants.md#compile-time-callables) admits immutable
scalar, text, tuple, and array values and conditionals, but not mutable local computation or loops.
Constant declarations cannot hold nominal or aggregate values. Immutable statics admit tuples and
enumerated arrays, but exclude nominal values, floating-point storage, and even array repetition.
These are different restrictions from rejecting I/O, escaping temporary storage, or nondeterministic
evaluation.

A checksum table generated by a loop, a parser table built from records, or a repeated static array
therefore encounters restrictions unrelated to its final value's safety. Runtime construction or
externally generated source becomes necessary where ordinary compile-time computation should be
the natural operation. The adopted rule allowing closed `usize` results in structural positions
fixes one inconsistency; it does not close this larger gap.

Keep `const` as an explicit capability promise, with the ordinary checked body as its source.
Extend evaluation to local mutation, bounded-by-evaluation-work loops, array repetition, and
serializable aggregate results. Define separately which temporary operations can execute and which
values may survive in the emitted result. Deterministic work limits, target arithmetic, dependency
cycles, and rejection of runtime-only effects remain necessary. This does not require every
function to become `const`, arbitrary compile-time I/O, or a new metaprogramming language.

Qualification examples should include a generated checksum table, a floating-point static table,
and a nominal table entry. Compare generated code and startup work rather than counting accepted
constant-expression forms.

### 2. Opaque Results Cannot Be Separated from Their Implementation Bodies

**Priority: high. Recommendation: close this interaction before implementing contract-only roots.
Not yet adopted.**

[Static Opaque Results](../../../spec/language/generics-and-interfaces.md#static-opaque-results)
allows `some Interface` only on a body-bearing callable, and explicitly excludes bodyless interface
requirements and several other declaration positions. In particular, an ordinary bodyless public
function cannot currently publish the opaque return contract of its separately authored body.

The desired v2.0.0 arrangement is conceptually:

```nct
// index.nct: proposed contract; invalid under the current opaque-result rule.
func values(): some Source { .Item = i32 }

// A directly seen implementation source supplies the body and concrete witness.
```

Without closing this rule, an author must expose the concrete adapter type or keep the opaque
factory body in the public contract. This conflicts with the adopted separation of API and
implementation. Inferring the hidden witness from the implementation is a compiler responsibility;
the caller needs the public capability and storage relationships.

Permit a bodyless contract and its matched implementation to share one opaque declaration identity.
Check the witness in the implementation and keep it hidden from callers. Retain one witness per
specialization unless a separate representation design supports heterogeneous returns. Do not infer
public copyability or extra methods from the witness: changing private implementation must not
silently change the API's ownership contract. Whether interfaces may themselves require opaque
results is a separate decision, not a consequence of ordinary contract/body separation.

Rust's return-position `impl Trait` also selects one concrete return type, but that property alone
does not determine Nocter's source-file organization. See the
[Rust Reference](https://doc.rust-lang.org/reference/types/impl-trait.html#abstract-return-types).

### 3. Generic Cleanup Effects Cannot Be Expressed Independently of Copyability

**Priority: high. Recommendation: infer conditional cleanup effects; expose advanced requirements
only where an abstract boundary needs them. Not yet adopted.**

[No-allocation contracts](../../../spec/language/memory-and-regions.md#no-allocation-callable-contracts)
include implicit destruction. An unknown generic destructor is conservatively allocating, and
there is no authored drop-effect requirement. `copy T` establishes trivial destruction, but excludes
move-only values whose destructors allocate nothing. The
[fixed-capacity collection guide](../../../std/fixed/README.md) consequently cannot promise
`noalloc` for `clear`, despite requiring no backing allocation.

This restriction makes two different facts appear connected: whether a value may be duplicated and
whether releasing it requests storage. A move-only handle with allocation-free destruction is a
valid and useful counterexample. Adding more `copy` bounds would obscure ownership and reject
legitimate programs.

Track destructor effects independently, including their dependence on element types and captured
values. A source-backed generic helper should be provable allocation-free for an appropriate
specialization without the author adding an unrelated copy requirement. Preserve the distinction
between that implementation proof and an unconditional public guarantee. If a bodyless abstract
contract needs a cleanup guarantee, provide a precise capability there; do not require ordinary
application APIs to spell a general effect algebra. Include nonblocking cleanup and immediate trap
freedom in the design audit rather than solving allocation alone.

Validate this with an inline collection of move-only handles whose destruction does not allocate,
and a contrasting element type whose destructor does allocate. Both ordinary cleanup and early
failure paths must satisfy the selected guarantee.

### 4. noalloc Does Not Exclude Runtime-Owned Error Storage Allocation

**Priority: high for contract meaning. Recommendation: strengthen the managed-storage guarantee,
with a migration audit. Not yet adopted.**

The current [definition](../../../spec/language/memory-and-regions.md#no-allocation-callable-contracts)
excludes requests through a Nocter allocator, not every dynamic storage request. The
[`error` declarations](../../../std/error/index.nct) mark `new` and `context` as `noalloc`, while
the [error guide](../../../std/error/README.md) explicitly permits private error-storage allocation
and termination if it fails. This is consistent with the narrow definition, but a reader cannot
treat `noalloc` as a guarantee that the Nocter runtime requests no new memory.

This matters for both predictability and optimization. A guaranteed callable is not thereby pure,
infallible, free from termination, or free from operating-system work. Similarly,
[`notrap`](../../../spec/language/callables.md#callable-types) admits explicit process
termination and allocation-failure termination. Neither modifier justifies eliminating calls.

Prefer a `noalloc` contract that also covers dynamic storage managed privately by the Nocter
runtime, including error nodes. Dynamic error construction would then need an allocation-capable
contract unless its complete operation is proven allocation-free. Static prebuilt failures and
forwarding an existing error can remain allocation-free. This does not change the single failure
payload or require typed error families. Audit registered primitive guarantees and all transitively
affected public signatures before adopting this change.

The alternative is to retain the narrow allocator-capability guarantee and consistently describe
that scope, including the error-storage exception. That is easier to migrate but less useful to
an author asking whether a callable requests managed memory. Neither alternative promises zero
allocation inside arbitrary operating-system services or real-time execution.

### 5. Storage Provenance Makes Some Mutable Borrowed Collections Require Ownership Rebinding

**Priority: medium to high for learning cost. Recommendation: investigate bounded provenance
inference with concrete collection tasks. Not yet adopted.**

[Value Storage Contracts](../../../spec/language/memory-and-regions.md#value-storage-contracts)
explicitly forbids adding an unrelated origin to an existing mutable owner in place. Its example
requires a consuming `push` that returns a new `Self from self | value`.

This has a sound purpose: a container must not retain a view after its source dies. But avoiding
named lifetime parameters does not itself remove the conceptual burden. Collecting views from
several long-lived inputs can still require understanding why an ordinary mutable append is
rejected and why ownership must be returned and rebound. This is a Nocter-specific cost, not proof
that adopting Rust lifetime syntax would improve it.

Investigate inferring a stable storage upper bound when the collection is created, allowing later
mutation only with values proven to fit that bound. A complementary design may track origin changes
for an exclusively owned local when no outstanding loan can observe the old state. These are
different designs and require branch, alias, call-boundary, and cleanup rules before adoption.
Keep the current safe rejection until a replacement is proven; do not repair it with hidden
cloning, reference counting, or unconstrained origin widening.

Use a collection of views from two enclosing strings, a view into an inner-scope string, and a
collection with an outstanding element borrow as distinguishing cases. The first should measure
ergonomic cost; the latter two must remain safely constrained.

### 6. Some Runtime Costs Are Mandated by Representation Contracts

**Priority: high for speed; already listed for further evaluation, not adopted.**

[Erased callables](../../../spec/language/callables.md#erased-callable-types) always allocate an
environment. [Async producers](../../../spec/language/asynchronous-computations.md#structured-ownership)
use an allocation-backed representation and cannot satisfy `noalloc`.
[ABI and Layout](../../../spec/platform/abi-and-layout.md) fixes declaration-order fields,
byte-tagged outcomes without niche representations, and a mapped four-word erased callable.
Every enum is limited to 256 variants by its fixed byte tag.

These contracts make implementation straightforward, but they are not all inherent consequences
of ownership, erasure, or asynchronous computation. A nonescaping callback, a statically selected
future frame, or an optional non-null borrow are useful workloads for evaluating alternatives.
Do not assume all erasure can be allocation-free or that every future can be stored in a fixed-size
stack slot: heterogeneous environments and escaping lifetimes still require a representation.

Prioritize escape analysis, specialization, frame placement, and compact layout where the external
contract permits them. Reconsider the universal byte-tag/256-variant restriction independently of
the source enum concept. Keep fixed representation only where a documented observable or platform
boundary requires it. Explicitly settle allocation-failure observability, address identity, and
cleanup order before permitting allocation elimination. No additional application annotation is
needed merely to select a better internal representation.

Rust syntax is not the relevant benchmark. Measure allocation counts, live memory, code size, and
execution time against equivalent optimized programs. Existing fixed-layout promises cannot be
silently ignored by an optimizer.

## Restrictions to Keep Unless Concrete Evidence Justifies a Change

- **One failure payload.** Preserve `error`, codes, context, and direct propagation. Per-API failure
  type parameters would restore the reconciliation work Nocter intentionally removes. This is not
  changed by admitting an error as successful data.
- **Exclusive writable access and deterministic cleanup.** Preventing use after move and conflicting
  live borrows protects safety without a tracing collector. Infer proofs where possible; do not
  substitute hidden copying or shared ownership. The current field/index sensitivity boundary is
  an analysis limit, not proof that disjoint indexed access is inherently unsafe.
- **Copyability as a public capability.** A hidden representation or one currently empty outcome
  must not determine whether caller code can duplicate a value. Permission to copy is not a
  guarantee that copying is cheap; large copies still need optimization and cost visibility.
- **Explicit interface conformance and unique static selection.** Accidental shape matching and
  import-order selection make contracts fragile. The adopted identity-based operation mapping
  addresses name collisions without requiring Rust-style general UFCS.
- **Restricted extension ownership.** Nocter permits type behavior only in its defining module,
  even for a locally declared interface. This is stricter than Rust's trait-implementation rules,
  which admit a local trait or certain local-type cases. The restriction reduces coherence and
  encapsulation complexity, but requires adapters for external types. Keep it pending real adapter
  use cases rather than copying Rust's orphan rules wholesale. See the
  [Rust Reference](https://doc.rust-lang.org/reference/items/implementations.html#trait-implementation-coherence).
- **One-step borrowed views and lossless numeric conversion.** Their limits prevent a hidden
  conversion graph and silent numeric loss. The adopted removal of comparison fallback correctly
  separates a view capability from domain equality.
- **Always-on safety semantics.** Optimize away checks with valid proofs while preserving failure,
  evaluation, and cleanup behavior. Do not gain a benchmark result by silently weakening checks.
- **Separate ordinary functions and receiver methods.** No UFCS is needed merely because another
  language uses it. Receiverless interface requirements remain type-generation operations under
  the adopted design.

## Already Adopted v2.0.0 Corrections

The plan already addresses explicit capture-list repetition, missing callable type arguments,
`pub` duplication in contract roots, separate `construct`/`instance` surfaces, name-based interface
matching and default replacement, error-versus-success ambiguity, optional nesting limits,
non-storable `void`, comparison through borrowed views, and silent failure disposal. These remain
current-specification costs until implementation; they are not new recommendations in this review.

The new findings above should be evaluated with those decisions, especially opaque results with
contract-only roots and cleanup effects with unified type behavior. Do not count plan text as
evidence that the compiler accepts the proposed programs.

## Separate Specification Consistency Findings

These need focused conformance audits; they do not establish that Rust influenced the design or
that a released executable is wrong:

- The ordering selection/derivation discrepancy is already recorded in the
  [v2.0.0 plan](../milestones/v2.0.0.md#follow-up-audit-derived-ordering-selection).
- [Construction Surfaces](../../../spec/language/construction.md#construct-declarations) shows an
  `async` construction function, while
  [Producer Declarations](../../../spec/language/asynchronous-computations.md#producer-declarations)
  excludes constructors. Determine whether that term excludes construction functions or denotes a
  narrower construct; remove the contradictory or ambiguous guidance with a distinguishing case.
- [Formatting](../../../spec/tooling/formatting.md#direction) says style violations are not compile
  errors, but [constant naming](../../../spec/language/constants.md#declaration) is a semantic
  `UPPER_SNAKE_CASE` requirement with diagnostic `E0243`. Either document this as an explicit
  identifier rule rather than a style preference or move it to style checking. This is a small
  consistency issue, not a runtime-speed priority.

## Recommended Decision Order

1. Close opaque contract/body separation and the meaning of managed allocation guarantees.
2. Expand compile-time evaluation with realistic generated-data workloads.
3. Model cleanup effects independently of copyability and verify generic container use.
4. Evaluate representation freedom and borrowed-collection ergonomics using measured examples.

For every proposed rule, record the operation the user wants to perform, the invalid behavior to
prevent, why inference or an ordinary API is insufficient, and the code and runtime cost. A rule
should remain because it serves Nocter's contracts, not because Rust accepts or rejects it.
