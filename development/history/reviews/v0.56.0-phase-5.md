# v0.56.0 Phase 5 Editor, Application, and Qualification Review

## Scope

This review closes the unified value-provenance and lending-API milestone. It covers canonical
formatting, semantic presentation, navigation, semantic highlighting, inferred-contract hints,
the lending HTTP query path in the public service application, and the compiler authorities that
normalize, prove, and project value-provenance contracts.

## Findings and Resolution

### Structural callable parameter names are presentation names, not hidden source state

Structural callable types retain parameter positions and resolved provenance edges, but parameter
spellings do not participate in type identity. Their semantic presentation therefore uses stable
`p0`, `p1`, and later positional names. For example, an authored relationship from `value` to
`owner` is rendered canonically as `p0 ... from p1`; it is not reconstructed from a source slice.
The editor regression matrix now fixes both the normalized names and the preserved relationship.

### Inferred value provenance must not be presented as an authored local contract

The HTTP service receives a `QueryParameter` lent from its `QueryIter`. That runtime provenance is
used by checking and loan exclusion, but the local declaration did not author `from query`.
Hover therefore presents `let parameter: QueryParameter`, while hover on `query_pairs` presents the
public `QueryIter from self` contract. This keeps semantic facts available without inventing source
syntax that the user did not write.

### Every authored contract position crosses a canonical tooling boundary

Formatter coverage now includes callable results, parameters, receivers, annotated locals, and
structural callable types in one idempotent source. Analysis coverage renders declaration inputs,
receivers, local annotations, results, and normalized structural contracts. The protocol test
then crosses hover, signature help, definition navigation, semantic highlighting, and inferred
result inlay hints from one checked generation. Provenance-origin tokens resolve to parameter
identities; editor features do not look up their spellings independently.

### The practical HTTP path retains lending rather than adapting it back to ownership

The service compares the first decoded query parameter before advancing its decoder. Unescaped
text remains borrowed from the retained request target and encoded text may use the iterator's
reusable scratch storage. The application does not call `to_owned`, keep the item across another
advance, or maintain a parallel query parser. The reference-application test projects the public
`from self` contract and the borrowed local through the same installed standard-library graph.

## Authority Review

The repository has one recursive containment operation,
`nocter_model::provenance_is_bounded_by`, used by declaration compatibility, invocation checking,
interface implementation, and body validation. Declaration lowering resolves authored receiver
and parameter spellings once into parameter identities. Structural callable normalization stores
position-based `InputProvenance`; checking consumes those edges and never reparses a clause.
Analysis renders declarations and structural contracts from the checked graph and type store.
Source text is used only for source-owned edits, ranges, formatter input, and lexical recovery—not
to select semantic provenance.

Result-specific names that remain describe the result dimension of the unified value contract;
they do not implement a second result-only compatibility or inference path. Search and call-site
review found no order-dependent origin resolution, downstream source-spelling lookup, duplicate
containment solver, compatibility wrapper, or caller-maintained lending state.
