# v2.0.0 Syntax Coherence under Four Design Goals

## Status and Scope

Subsequent [S8](v2.0.0-source-design-decisions.md#s8-place-access-qualifiers-on-types) adopts type-side
access qualifiers. Identifier-side examples below now record the proposal's earlier notation,
not an optional style. The other C1–C6 proposals remain unadopted. In particular S8 alone does
not adopt destination-directed transfer, inherited implementation heads, or future output grammar.

The later [S9 decision](v2.0.0-source-design-decisions.md#s9-infer-local-permission-from-the-initialization-operation)
selects explicit standalone transfer and operation-directed inference instead of C2. Receiver
abbreviations and `func`/`mut`/`once` are now adopted separately. S10 adopts qualifier scope and
rejects C1's inherited implementation heads, retaining complete signatures for implementation
readability. The original C1–C6 package is not adopted together.

This is a new proposal, not an adopted replacement for S1–S7 or the owning future specification.
The user permits reconsidering earlier decisions to reduce repeated specifications, make operation
meaning readable from declarations, infer lifetimes/conflicts, and explain failures locally.
Permission to reconsider does not select the source forms below. The current
[source decisions](v2.0.0-source-design-decisions.md) and
[future Value Access Model](../../../spec/language/value-access.md) remain the selected design.

The main proposed replacements are implementation signature inheritance and destination-directed
ownership at all owning boundaries. The latter would replace explicit standalone source-transfer
expressions, including S7's `let ^next = ^previous`; do not silently mix the two policies.
Future output-type notation and conservative default origin bounds are also proposals. No
compiler implementation, usability improvement, speedup, or full safety proof is claimed.

## Information Policy

Write each fact at the boundary where its author chooses it. Derive other occurrences from that
authority. Do not remove two declarations merely because their glyphs happen to match:

| Fact | Authority | Derived occurrences |
| --- | --- | --- |
| Public inputs, result permissions, types, generic requirements | Contract-only `index.nct` | Matched implementation's parameter/result bindings and calls |
| New private operation's signature | Its one private declaration | Its body and calls |
| Local read/update/ownership intent | `let`, `let &`, or `let ^` | Assignment and operand availability |
| Owning destination's receipt of an existing owner | The destination contract | Source transfer without a second expression marker |
| Deliberate duplicate value | Ordinary explicit Copy/construction API | No automatic clone or type-dependent move fallback |
| Outside result-origin upper bound | Contract defaults or a genuinely narrower explicit bound | Call/forwarding/escape checking |
| Actual access ranges, captures, storage placement, and effects | Checked operations and dependencies | Diagnostics, validation, and optimization evidence |

A callable offering ownership and a local choosing ownership are different facts: the first
defines the API; the second declares how the local is to be used. A local reading an existing
owner, obtaining update access, or requesting an independent Copy must remain distinguishable.
This is why three local forms remain, even though a fresh factory result requires the X form.

## C1. Inherit an Implementation from One Exact Contract

**Rejected by the user.** Omitting the body signature forces implementation readers to open the
contract to recover inputs and permissions. This increases reading work despite reducing text.
The following preserves the original proposal for history; complete signatures remain required.

The original proposal recommended writing a public signature once. A matched implementation has a mandatory short head,
not an optional full-signature alternative. Illustrative proposed syntax:

```text
// index.nct
impl Buffer {
    func ^create(capacity: usize): Self!
    method self.len(): usize
    method &self.append(value: u8): void
    method self.bytes(): [u8]
    method &self.&edit_bytes(): [u8]
    method ^self.^finish(): Product!
}
```

```text
// A directly seen implementation source; bodies are illustrative.
impl Buffer {
    method append {
        self.storage.append(value)
    }

    method finish {
        return Product.from_buffer(self)
    }
}
```

The contract introduces the receiver/parameter names and types, generic bindings, modes, result
shape, and requirements into the matched body. A body cannot restate different modes or select a
different overload by its contents. `func` and `method` remain distinct and UFCS is not added.

Match by one declaration owner, callable kind, and member identity through the existing direct
`see` boundary. No matching by inferred body type, search order, result destination, or unrelated
implementation files. A missing/ambiguous/duplicate contract is an error at the short head. If
multiple candidate declarations exist, require their already meaningful owner/interface scope or
distinct operation identity; do not invent signature guesses to make short heads work.

A new private helper still declares its own signature once. That is a different task from
implementing an existing operation, not a second optional spelling of the matched implementation.
Direct interface bodies can inherit their exact interface operation; helper mappings remain for
real naming/default/collision decisions rather than mandatory signature duplication.

Tradeoff: a short body needs the linked contract to read its full input/result meaning. The editor
must show that inherited signature and its source. This uses Nocter's intentional root-plus-direct-
implementation working set; it does not make private files semantically self-contained. Parameter
renames must update body uses, and contract/body identity and invalidation need executable checks.

## C2. Let Owning Destinations Perform Ownership Handoff

Retain `let name` for I, `let &name` for U, `let ^name` for X, and no `var`. Replace the current
extra source-transfer marker with one operation rule for all owning destinations:

| Supplied expression | Operation at an X destination |
| --- | --- |
| Existing owned place | Transfer it, including for Copy T |
| Fresh owned result | Receive its ownership |
| Non-owning readable value/access | Materialize an independent value only with checked Copy evidence; otherwise reject |

Apply this rule at a selected X parameter, X binding, owning result, owned field/element
initialization, and replacement of an owned value. Use the full result/shape contract at outcome
boundaries, rather than confusing a carrier's ownership with its successful payload's permission.

```text
let ^first = File.open(42)?
let ^next = first             // transfer; first is unavailable

let ^a = 10
let ^b = a                    // transfer even though the integer is Copy
let ^c = copy(b)              // explicit structural Copy; b remains available
```

`copy` here is a proposed ordinary generic library operation requiring Copy capability, not a new
keyword or a name recognized by the compiler. An allocating/deep copy remains a separately chosen
ordinary API. No owning destination silently clones a move-only non-owner.

An owning result therefore uses `return value`, with transfer of an existing owner determined by
the result contract. A generic owning identity has the same behavior for Copy and move-only T.
Likewise, an assignment to an X local already knows it replaces an owned value, so it needs no
additional source-transfer annotation. U assignment replaces the caller's value and must leave
it valid; it does not retarget the local access or take an unfilled extraction.

Under this proposal reject standalone `^source` transfer expressions, rather than retaining
`let ^next = ^first` or `return ^value` as alternate styles. Declaration/capture/type-slot markers
remain; they state destination contracts. `throw reason` and `await pending` continue to consume
their fixed owned operands without another marker. Ownership is selected by source contracts,
never by last-use optimization or a private callee body.

Tradeoff: a return or assignment's transfer meaning needs its destination contract. The benefit
is one source-disposition rule across calls, initialization, assignment, and return, rather than
separate binding and call rules. This deliberately revises the previously deferred implicit
return/storage-transfer decision; it is not already authorized by adopting S7.

Keep left-to-right evaluation and the selected reservation/commit rules. Failure during argument
preparation must not consume merely reserved sources; failure after invocation does not restore
them. Construction, partial initialization, assignment, cleanup, and outcome forwarding need
the same complete accounting before this replacement can be adopted or implemented. It does not
make all earlier side effects transactional.

## C3. Infer Internal Facts, Keep Boundary Promises Explicit

Infer local data types, closure parameter/result information from expected contracts, capture
demand, last required access use, proved-disjoint places, effect summaries, and representation.
Expected destination modes can flow into `if`/`match` branches before checking them. Do not choose
their mode retrospectively from later uses or silently change an already checked generic body.

A new private operation can infer its result data type when its one mode-declared body determines
that type uniquely; unresolved recursion or an intentionally different expected type needs an
annotation. This is distinct from C1's implementation head inheriting an already complete
contract. Do not make an omitted permission mean "infer the greatest authority from the body".

Public result mode and input mode remain explicit in the root contract. They express allowed
behavior, not merely what one private implementation happens to do. A getter that updates a cache
can intentionally return only read access; inferring the greatest available authority would
publish a different API. A matched body inherits the chosen promise under C1.

Keep removed `noalloc`, `notrap`, and `blocking` modifiers removed. Infer their relevant facts and
retain ordinary runtime checks where the language allows them. Unknown memory safety or future
drive safety cannot be accepted by adding an unrelated check. Keep `const` for its deliberate
staging promise; ordinary proven folding does not need that promise restated at every use.

Local type annotations should add a constraint or resolve missing information, such as an integer
width, empty/absent payload type, generic argument, or callable requirement. They need not repeat
an already determined type merely to make an operation compile. An annotation cannot be another
way to select a permission or overload when the selected source contract already fixes it.

## C4. Preserve Permissions Where Values Are Abstracted

Do not make source dissimilarity to Rust an acceptance criterion. Data type, authority, and
outside dependencies are real facts; hiding them in an interface instead of a type constructor
does not remove their obligations.

Recommend the following future-output slots when an explicit type is needed:

```text
future T
future &T
future ^T
```

Their output modes are I, U, and X respectively; each future itself is owned. An async
`func ^load(...): Config!` produces `future ^Config!`. Ordinary application bindings infer this:

```text
let ^pending = load(42)
let ^config = await pending?
```

An explicit type is needed at an abstraction/storage boundary when the whole contract cannot be
inferred there. It must retain output mode and origins through generics and erasure, without
inspecting a private producer body to recover missing information. Do not add a second callee or
binding assertion spelling, and do not restrict future outputs to owned data solely to avoid a
permission-qualified type spelling.

This does not by itself decide arbitrary first-class reference containers. General mode
polymorphism, mixed-result task composition, dependent computation storage, nested futures,
outcome tags, and ABI witnesses remain explicit closure obligations. Those are reasons to test
the abstraction model, not to claim the three example spellings already form a complete type system.

## C5. Default Origin Bounds Conservatively

For result types capable of retaining outside access, consider a default bound over all eligible
receiver/parameter origins rather than requiring an annotation merely because there are several.
Known independent data results need no new source-place dependency; carried payload/region
dependencies remain separate. With one eligible origin this preserves ordinary elision.

A narrower `from left` is then a meaningful stronger public promise, not decorative repetition of
an inferred clause. Callers may rely on that narrower relationship, and the body must prove it.
Do not present an explicitly written full default union as a second canonical style.

Tradeoff: a broad default can conservatively prevent updates that would be safe with a narrower
bound. Compiler/editor explanations must identify both the retaining operation and the particular
origin bound. This proposal changes the current ambiguous-bodyless-contract rule; prototype
selectors, two-input parsers, and dependent callback factories before selecting it.

Do not infer a public permission/origin promise from a private body and then silently let a body
edit change what the root declaration means. Private effect summaries and physical optimization
can still change with bodies under their already selected rules.

## C6. Explain One Conflict with Its Local Evidence

Use a primary failure location plus the smallest relevant dependency chain, not a dump of the
whole inferred graph. For example:

```text
let bytes = buffer.bytes()
buffer.append(42)
inspect(bytes)
```

The diagnostic should identify the attempted update, where `bytes` acquired read access, and the
later use that keeps it active. When the last use precedes the update, accept without another
block or explicit release, provided no cleanup/capture retains it. For futures, identify the
retaining task and its completion/cancellation use. For returned access into a local, identify
the return and the owner's cleanup boundary.

Do not ask users for lifetime equations or internal mode variables. Explain inferred versus
declared facts separately. An unproved relationship is uncertainty, not a claim that overlap
definitely occurs. Suggest ownership, explicit Copy, a narrower public origin, or an API change
only when that corresponds to the actual missing capability. Reordering, copying, and moving can
change effects, so do not apply them as automatic fixes without an equivalence proof.

## Limits and Review Gate

The four goals can substantially reduce repeated annotations and interpretation choices. They
cannot simultaneously make every call locally reveal its complete contract, omit that contract
at every use, infer human ownership intent, and accept arbitrary sharing without a defined
management strategy. Conflicts and unsupported escapes still exist.

The original recommendation paired C1 and C2. C1 is now rejected, and S9 chose explicit transfers
instead of C2; do not implement either recommendation as the selected policy. C3 and
C6 largely advance already selected inference and diagnostics. C4/C5 need explicit type/origin
case validation; source spelling and public-default changes remain unadopted. Current examples
must not be rewritten as if this candidate has been accepted.

Before selection, compare API implementation, signature change, numeric copying, a buffer view,
generic owning identity, fallible argument preparation, closure escape, and async cancellation.
Count authored facts, places requiring edits, files read, and explanations needed. Then validate
source availability, cleanup, origin bounds, and generated operations in an implementation.
No measured learning or performance improvement is claimed by this prose review.
