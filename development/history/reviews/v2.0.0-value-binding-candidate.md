# v2.0.0 Value Binding Candidate: Adoption Audit

## Status and Authority

This reviews the user's requested clean-slate source candidate after the first private-unit
checkpoint, `83ec05fd4`. It is **not adopted source syntax**, a normative specification, or a
compiler implementation. The adopted future rules still belong to
[Value Access Model](../../../spec/language/value-access.md); the implemented subset remains
bounded by the [first access slice](v2.0.0-first-access-slice.md).

The candidate uses `let`/`var` for fixed/mutable value bindings, `read`/`edit` for scoped aliases,
and unmarked/read, `edit`, or `take` input contracts. Ordinary `T` results deliver values.
Value-producing boundaries copy when source-level evidence permits Copy and otherwise move an
eligible owner. They never silently create an alias or insert a clone. The user requested that
previous source choices may be reconsidered; this review does not infer adoption from tentative
agreement. `View<T>`, `EditView<T>`, factories and members below are illustrative capability APIs,
not standard-library declarations. Code blocks are candidate examples, not runnable packages or
fixtures accepted by the current parser.

The audit asks whether view results, dependency-bearing records and callbacks can use one
coherent safety contract. Verdicts below are design obligations derived from the proposed rules,
not compiler test results or a general soundness proof. No new finite model is presented as
validation of the new source language.

## Conclusion

No contradiction was found in the reviewed cases if the candidate retains complete dependency
and operation evidence. Recommend the candidate with these qualifications:

1. Separate ordinary data type `T` from an input's binding operation. Do not claim that permission
   information disappears from the type system. Function types preserve input operations and
   invocation contracts; capability types expose their allowed operations.
2. A returned value can depend on outside owners. Moving/copying its descriptor cannot erase those
   dependencies. Public/erased contracts bound result origins without inspecting hidden bodies.
3. Copy of an update capability is forbidden even when its element type is Copy. A read view can
   be Copy while continuing to restrict the original storage.
4. `let` does not permit ordinary edit access to its value or owned fields. Writing through an
   ordinary edit-view value or invoking a mutable environment needs `var`/edit authority. Moving a
   `let` value is allowed; its recipient acquires its own value slot. Read is not purity, and
   explicit synchronized/shared-state APIs need their own safe effect/access contracts.
5. Callback argument operations, environment invocation, retained result origins and dependency
   changes to edited inputs/environments are independent facts. All survive generic forwarding,
   interface matching and erasure, including a `void` return.

This closes a counterexample/design audit only. It identifies necessary contracts and compatible
case verdicts rather than completing the full calculus. Full grammar, dependent-type summaries,
algorithmic correspondence, compiler conformance, ABI and performance evidence remain work.

## 1. Value Bindings and Copy Evidence

An initializer, assignment or ordinary value return constructs a destination value. Copy requires
evidence available at that source boundary; otherwise the source must be an initialized owner
eligible for transfer. A read-only non-Copy input cannot be moved merely because the destination
is a value binding. Copy preserves carried access/storage dependencies. No layout-size threshold,
later use or specialization selects a different checked operation.

`let` and `var` affect updates to the destination, not whether a value can leave it. Both may be
transferred. A read input remains read-only even for a concrete scalar; a local snapshot can be
mutable without increasing authority over the input. A `take` parameter receives a local value
and its cleanup obligation; a known-Copy caller can supply a copy without invalidating its source.
An unconstrained generic body cannot assume that ability. Consuming callable invocation similarly
requires a value; Copy permits a distinct instance, never repeated consumption of one instance.

| Case | Proposed verdict | Reason |
| --- | --- | --- |
| V01: `let b = a` for known `i32`; later update `a` and read `b` | Accept | Snapshot, not an alias |
| V02: `let next = file` for an owned non-Copy file; later use `file` | Reject later use | Initialization moved the owner |
| V03: move a non-Copy `let` value into a `take` input | Accept | Fixed contents do not forbid transfer |
| V04: initialize a value from an unbounded, read-only generic `T` | Reject without Copy evidence | Neither duplication nor extraction is authorized |
| V05: the same generic input under a declared Copy requirement | Accept snapshot | Evidence is present when checking the body |
| V06: instantiate V04 with `i32` afterward | Preserve the original verdict | Specialization cannot repair missing source evidence |
| V07: direct `take` inputs use the same known-Copy scalar twice | Accept two snapshots | No duplicate ownership of the original place |
| V08: direct `take` inputs use the same non-Copy owner twice | Reject | One invocation cannot transfer an owner twice |

This changes the adopted S9 plain-binding rule and the existing-Copy-X invocation rule. In
particular the old duplicate-X scalar rejection cannot be carried unchanged into candidate
conformance. A passing old corpus does not validate the new candidate.

During left-to-right preparation, snapshot a Copy value when its `take` operand is prepared.
Later operands cannot change that prepared answer; contained dependencies remain protected.
A direct non-Copy owning place remains reserved until the full invocation commits. Interruption
releases its reservation. An earlier completed move in a nested initializer/call is not rolled
back; any constructed prepared owner is cleaned in reverse order. No user code or fallible gap
occurs between the individual transfers of one validated invocation bundle.

## 2. View Results

```text
func bytes(buffer: Buffer): View<[u8]>
func edit_bytes(edit buffer: Buffer): EditView<[u8]>
func snapshot(buffer: Buffer): Bytes
```

These return value descriptors with different capabilities. `View` carries shared read access;
`EditView` carries unique update access and is non-Copy. `Bytes` denotes an actual copied/constructed
value only when its checked implementation establishes that contract; the name does not supply
independence. Do not infer allocation, cheap copying or an independent payload from any name.

| Case | Proposed verdict | Required evidence |
| --- | --- | --- |
| R01: return a view into the surviving read input | Accept | Result depends on the caller's original root |
| R02: return an edit view from an edit input | Accept | Exclusive authority survives handoff without duplication |
| R03: return a view into a local buffer destroyed at exit | Reject | The descriptor does not own the buffer |
| R04: return a view into a `take` parameter's local payload | Reject | Consumed parameter storage ends at return |
| R05: forward a taken view descriptor whose dependency is an outside buffer | Accept | Transfer its existing dependency; do not depend on the dying descriptor slot |
| R06: copy a read view, end the original descriptor, then read the copy | Accept if the outside owner survives | Copy retains the outside dependency |
| R07: copy an edit view of `i32` | Reject | Copy of the element does not duplicate update authority |
| R08: modify/relocate/destroy the referent while a view is still needed | Reject overlap or unknown invalidation | An owned descriptor is still dependent |
| R09: write via an edit view held by `let` | Reject ordinary edit invocation | Use a mutable holder; moving it into a taking operation is a separate action |
| R10: return a view obtained through a local guard whose destruction revokes access | Reject | Cleanup-dependent authority must survive, not only the bytes |
| R11: return the guard as an explicit owning capability | Accept when its full dependency contract is satisfied | Caller visibly receives the completion/cleanup obligation |

R04 applies even if the taken value is Copy and the caller still has its original. The callee's
copy is a distinct value/place; a view into it cannot be redirected to the original by guessing.
R05 is the contrasting legal case: a descriptor's carried dependency can survive destruction of
the descriptor's old slot. Distinguish referent R, payload D and storage S at that boundary.

One eligible direct source permits origin elision. Multiple possible sources need a stable
contract. For this audit, retain the existing `from` relation as candidate notation rather than
inventing lifetime names:

```text
func choose(first: Buffer, second: Buffer): View<[u8]> from first | second
```

The bound permits either result, not simultaneous update access to both. A caller must protect
every possible live result dependency. A narrower `from first` contract must be established by
the body/witness; an indirect consumer cannot recover it by searching private source. New spelling
or a broader default for multi-origin elision is not selected by this audit.

Ordinary return still stages the result, preserves its dependencies through normal callee cleanup,
and then hands it off. No hidden coroutine, guard lifetime extension, GC or automatic owner capture
rescues R03/R04/R10. A plain view destructor that only releases access differs from user cleanup
that reads an outside object or revokes a lease; the latter extends the corresponding obligation.

## 3. Records Containing Views

```text
struct Window {
    bytes: View<[u8]>
}

func make_window(buffer: Buffer): Window
```

The compiler derives a dependency schema from the selected fields and their contracts; a concrete
value carries the instantiated outside roots. Private fields cannot hide this from callers.
Public functions expose the retained bound, with the same elision/explicit relation rules as view
results. This does not require a source lifetime argument on every `Window` use.

| Case | Proposed verdict | Reason |
| --- | --- | --- |
| S01: return a window over a surviving caller input | Accept | Aggregate preserves its field's outside dependency |
| S02: return a window over a local buffer | Reject | Wrapping does not erase the dead root |
| S03: move the window; then destroy the outside buffer before using it | Reject destruction | Move transfers the dependency |
| S04: copy a Copy window containing a read view | Accept; retain dependencies for both copies | Copy duplicates a descriptor, not its backing owner |
| S05: infer Copy for a window containing an edit view | Reject | Unique update capability is non-Copy |
| S06: wrap the window in an optional, tuple or generic container and escape | Apply the same dependency bound | Containers cannot launder D/S |
| S07: user destruction reads the window's backing data after its last ordinary use | Keep the owner valid through destruction | Last ordinary use is not the last cleanup use |
| S08: generic forwarding or opaque return conceals private view fields | Preserve declared dependencies | Representation privacy is not independence |
| S09: a record owns a buffer and a raw view into its own movable inline storage | Reject without a stability/relative-reference proof | External dependency tracking alone does not solve self-reference |

S09 is distinct from an ordinary window over another owner's storage. A stable backing certificate
or an explicit owning-container-plus-range design can support suitable APIs. Mere co-location in
one record, numeric address equality or moving the record does not prove safety. Range-based access
still needs bounds/invalidation checks; no unchecked or automatically pinned fallback is adopted.

A generic or erased aggregate must preserve its dependency schema. The owning data constructor,
not consumer-side name inspection, supplies that evidence. A region constraint remains even if
an optimizer elides the current bytes. Unknown dependencies require a conservative bound or a
source-local failure, not a hidden clone or lifetime repair.

## 4. Callbacks: Three Independent Contracts

Retain the independently selected environment protocols as candidate notation:

| Environment protocol | Authority needed to invoke |
| --- | --- |
| `func(...)` | Read environment, repeatable |
| `mut(...)` | Update environment, repeatable |
| `once(...)` | Consume the supplied callable instance |

Each protocol separately specifies ordinary argument operations. For example:

```text
func update(action: func(edit Buffer): void, edit buffer: Buffer): void {
    action(buffer)
}

func repeat(edit action: mut(i32): void, value: i32): void {
    action(value)
    action(value)
}

func finish(take action: once(take Job): void, take job: Job): void {
    action(job)
}
```

The function-type spelling above is a candidate extension of the named input syntax, not adopted
grammar. `func(edit Buffer)` reads its environment but updates its explicit Buffer argument.
`edit action` supplies access to the caller's callable value; `mut(i32)` says invoking that value
can update its environment and reads its explicit i32 argument. Those are separate objects and
facts. Receiving a callable by value does not determine whether invocation consumes its captures.
Read invocation does not promise purity or absence of effects through explicit edit arguments,
registered resources or deliberately shared capabilities.

| Case | Proposed verdict | Reason |
| --- | --- | --- |
| C01: read-environment callback updates an explicit edit argument | Accept | Environment and argument permissions are independent |
| C02: pass a read-only argument to that update contract | Reject | Function type cannot manufacture writable authority |
| C03: invoke `mut` through an unmarked read input or fixed local | Reject | Need edit authority / a mutable holder |
| C04: invoke `mut` twice through a valid edit input | Accept sequential calls | Preserve valid environment state after each call |
| C05: invoke a once-only value without Copy evidence twice | Reject second use | The first invocation consumes its instance |
| C06: discard an uninvoked owned once-only value | Clean it normally | At most once is not exactly once |
| C07: Copy is separately proved for a callable | Permit separate instances; each has its own consumption | Invocation kind alone does not imply or forbid Copy |
| C08: callback captures update access to a root also passed as live input | Reject overlap unless the required accesses are proven compatible | Check captured dependencies as well as explicit argument names |
| C09: store/return a closure capturing a dead local owner by access | Reject escape | Owning the closure header does not own the captured object |
| C10: once invocation returns a view into an owned capture destroyed by invocation exit | Reject | The consumed environment cannot remain as an invisible owner |
| C11: return a moved capture value, or a descriptor already dependent on a surviving outside owner | Accept under its result bound | Ownership/contained dependencies can be forwarded |
| C12: callback receives a fresh access on every invocation, then stores one for later | Reject without a compatible retained bound | Each invocation has its own access extent |
| C13: erase or forward the callback through an interface/generic | Preserve all contracts | Names and concrete bodies are not part of the consumer proof |
| C14: cancel a deferred computation owning a callback and dependent inputs | Clean children/temporaries before releasing required outside dependencies | No pending capability or owned capture may be lost |
| C15: a mutating callback stores an input view in its environment | Accept only under a compatible retained postcondition | The environment acquires the view's dependencies |
| C16: a void-returning operation stores a view into an edited record, then its caller destroys the backing owner | Reject destruction while that record still needs it | Result origins alone do not describe changed state |

Function types additionally preserve result origin relations. A projector that returns access into
its explicit argument and one that returns access into its own captured storage cannot be treated
as having the same origin promise merely because both print `func(T): View<U>`. Instantiate a
fresh invocation extent for each call; abstract consumers must prove their uses for any valid
extent. This is the internal obligation analogous to higher-ranked lifetime checking, without
requiring lifetime names in ordinary source.

The full contract records environment-storage and carried-capture origins separately from each
argument's place and contained dependencies. An unresolved contract cannot silently omit the
environment. Require the existing explicit origin relation when the sources are not uniquely
elidable; inference for concrete closures can prove an expected library contract. Recommend using
the callable's implicit `self` for its environment in this advanced candidate notation:

```text
func(input: Buffer): View<[u8]> from input
func(input: Buffer): View<[u8]> from self
```

The first excludes environment-backed output; the second permits it and conservatively keeps the
required environment storage/dependencies valid. Source input names bind semantic positions, not
name-based type equality. This spelling remains a human-facing recommendation, not an adopted
extension. It cannot replace the internal distinction between environment storage and carried
capture dependencies, or promise that every `from self` result is independent of its descriptor.

Mutation needs a post-state dependency contract as well as a result-origin contract. For example,
`remember(edit holder: Holder, buffer: Buffer): void` can store a new view in `holder` even though
it returns no value. Likewise a `mut(View<T>): void` callback can retain a copied view inside its
environment. The caller must then preserve the newly retained outside owners through later use
and dependent cleanup of the edited value. Copying the incoming descriptor does not avoid this.

Preserve a source-neutral relation from the old edited state, each permitted input dependency and
the environment to each resulting edited value. Validate the body's actual transition against
that relation. A retention-free interface rejects fresh invocation-local escape; a retention-capable
interface makes its permitted dependencies part of the caller's post-state. Hidden bodies cannot
silently choose between those promises. Unknown nonempty behavior needs a conservative permitted
bound and caller validity proof, or rejection; an omitted result is never an empty post-state.
The exact surface spelling for a narrowed retained-state contract belongs to later library/source
design, not to a claim that `edit` alone supplies complete escape information. The internal
postcondition is mandatory even when the compiler derives it without another source annotation.

Invocation adapters must preserve the complete origin, parameter, post-state and cleanup contract. Readable
implementations can supply a stronger invocation context only with checked adaptation; adaptation
to consuming invocation cannot return access into an environment that the adapter destroys.
Do not implicitly strengthen a mutating callback into a read callback or reselect a body when
permission fails. Mutable/update captures prohibit Copy; erasure cannot invent Copy evidence.

Capture inference selects required read/update/value capabilities from checked operations. Keeping
a non-Copy owner inside an escaping closure when its body merely reads it is a distinct semantic
choice: private escape use must not silently change destruction timing or choose a clone.
Recommend a candidate value-capture list, such as `(file; args) { ... }`: a listed name uses the
same value construction as `let next = file` (Copy when proved, otherwise move). Unlisted ordinary
captures remain inferred from checked body operations. No separate transfer marker repeats the
value-capture operation. This is a proposed replacement for the currently adopted explicit
capture form, not an optional alias or an implemented grammar extension. Source readability still
needs human evaluation.

## 5. Adoption and Migration Gates

The three main patterns are conditionally coherent. They require dependency-carrying value
contracts and complete callable types, rather than literal removal of all permission information.
Before candidate adoption, confirm the human-facing source package, including the fixed/mutable
bindings, local alias forms, implicit value-boundary transfer, parameter operation names, capability
type vocabulary, callable input-mode spelling, advanced result-origin spelling and deliberate
owned-capture form. Existing source choices are not replaced piecemeal during this review.

After adoption:

1. Migrate owning bindings, ownership, callable, generic/interface, outcome/async, origin,
   construction/module, grammar, formatting and diagnostic contracts coherently.
2. Derive valid/boundary/rejection fixtures from V/R/S/C cases, including a changed public
   contract, hidden callback captures, preparation interruption and return cleanup.
3. Reuse the current source-neutral control/identity/ownership principles where they still match.
   Replace incompatible local/result/Copy rules and qualify one accepted authority, without a
   released-borrow adapter or parallel accepted path for the same source program.
4. Establish type-preservation and dependency/cleanup obligations, then compiler conformance and
   native lifecycle tests. Documentation consistency is not executable validation.
5. Measure source-reading/writing tasks and generated operations. This syntax does not by itself
   prove a speedup, allocate a view, insert reference counting or require a physical copy.

## Research Evidence and Limits

These primary sources informed the counterexamples; none specifies Nocter semantics:

- [Hylo bindings](https://docs.hylo-lang.org/language-tour/bindings) separates fixed/mutable
  bindings from update projections. Its explicit-copy policy is not the candidate's implicit
  Copy policy.
- [Swift SE-0456](https://github.com/swiftlang/swift-evolution/blob/main/proposals/0456-stdlib-span-properties.md)
  distinguishes a view's descriptor from the parent storage and preserves inherited dependencies
  through copyable views. It covers selected Span-providing properties, not arbitrary Nocter records.
- [Rust FnMut](https://doc.rust-lang.org/std/ops/trait.FnMut.html) and
  [FnOnce](https://doc.rust-lang.org/std/ops/trait.FnOnce.html) distinguish repeated mutable and
  consuming invocation. Their existence is evidence for separating invocation from explicit inputs,
  not authority to import Rust's spelling or all of its conversions.
- [Rust higher-ranked bounds](https://doc.rust-lang.org/reference/trait-bounds.html#higher-ranked-trait-bounds)
  provides a concrete counterexample to treating a callback's invocation lifetime as one persistent
  lifetime owned by the surrounding caller. No Nocter proof follows from the Rust rule.

The audit registers 44 distinguishing cases: eight value, eleven view-result, nine aggregate and
sixteen callback cases. They are reviewed requirements, not 44 compiled tests. The case identifier
counts/uniqueness and local review links were checked. Documentation generator tests, an explicit
external 377-page build and `git diff --check` passed. No compiler, source fixture or normative
specification was changed; no compiler conformance, runtime or speed claim follows from this audit.
