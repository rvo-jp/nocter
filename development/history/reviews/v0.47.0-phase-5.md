# v0.47.0 Phase 5 Canonical Asynchronous Byte I/O Final Review

**Result: implementation and source-tree qualification complete with no open practical v0.47.0
finding (2026-09-11).** Generic asynchronous byte algorithms now depend on one ordinary interface
contract, while blocking access, transport deadlines, HTTP framing, and native readiness retain
separate explicit owners.

## Authority and Dependency Audit

The completed area has these single authorities:

1. The language callable contract owns `async`, receiver access, failure, capture, and result
   identity. Neither `Reader` nor any method spelling receives compiler-defined meaning.
2. `std/io.Reader` and `std/io.Writer` own executor-safe byte requirements and their portable
   collection, UTF-8, text, line, and flush defaults. `BlockingReader` and `BlockingWriter` own the
   separate synchronous surface without aliases.
3. One `std/io` validator owns the recoverable impossible-read-count policy used by blocking,
   asynchronous, file, and HTTP timeout paths. Generic defaults do not inspect concrete streams.
4. TCP and TLS own transport progress and fixed operation deadlines. Their interface witnesses
   delegate to the same inherent read and write implementations rather than adding adapter loops.
5. HTTP owns one response cursor, framing limit, and decoder for both execution surfaces. Ordinary
   whole-body collection dispatches to the generic `Reader` default; HTTP retains only its explicit
   per-input timeout collector.
6. Checker preparation selects interface evidence once. Target-program specialization consumes
   that frozen evidence and MIR lowering consumes the selected executable item; no later layer
   searches for an implementation again.
7. The task runtime and reactor remain the only suspension, readiness, timeout, and cancellation
   authorities. File I/O is not given a false asynchronous witness backed by a blocking call.
8. Semantic editor queries consume checked interface identities and source locations. Hover,
   completion, signature help, navigation, tokens, and hints contain no I/O-name or concrete-type
   interpretation.

The blocking and asynchronous collectors retain distinct orchestration because their operations
have different execution kinds. They share byte-buffer construction and read-count validation,
which are the only effect-independent decisions. The HTTP timeout collector and public example
retain separate loops because each introduces an explicit timeout policy absent from `Reader`;
neither duplicates HTTP decoding or transport progress.

## Finding Corrected During Review

The complete warnings-denied gate found that the new LSP integration test had grown beyond the
repository's 100-line responsibility limit. Adding an allow attribute or splitting it into tests
would either hide the structural issue or repeat package analysis. The feature assertions now live
in a narrow helper that receives the existing server and source. One test still creates exactly one
semantic generation, while navigation, presentation, tokens, and hints remain independently
readable.

Searches across active standard source, examples, compiler code, tests, and current documentation
found no `AsyncReader` or `AsyncWriter` compatibility alias, old unqualified synchronous meaning,
compiler recognition of the standard names, concrete-type branch in a generic default, second
ordinary HTTP collector, blocking operation reachable through an async witness, or source-level
dispatch recomputation.
