# v0.62.0 Phase 5 Structured Command-Line Application Review

## Scope

This review closes the structured command-line application milestone. It covers schema
construction, option and positional recognition, nested commands, owned parsed results, usage and
help rendering, the process adapter, public examples, native execution, and documentation. It also
checks that the feature added no compiler-known declarations or source-language exceptions.

## Findings and Resolution

### The option terminator could still select a subcommand

The initial parser disabled option recognition after `--` but still allowed the next token to enter
subcommand selection. That gave the terminator two meanings depending on the schema. Command
selection now occurs only while recognition is enabled. Every token after `--` follows the one
documented positional-data path, and a command-only schema rejects such data as a surplus
positional. A regression test covers command-shaped data after the terminator.

### Repeated-value help omitted the repetition policy

The parser retained every value for a repeated option, while its help spelling was identical to a
single-use value option. Help now renders `<VALUE>...` for the repeated form. A native test proves
that presentation and parsing retain the same repetition policy.

### Impossible slice failures needed one stable internal category

The parser and process adapter each require a range only after proving its bounds. Their first
formulations could have assigned unrelated public errors if that invariant failed. Both now use
`std.cli.internal_invariant`, owned by the CLI error responsibility. The ordinary argument and
schema categories remain reserved for user-controlled failures.

### One schema test could pass after accepting an invalid definition

The first invalid-input test nested duplicate-option, unknown-option, and positional-order checks.
If duplicate registration had been accepted, a later unknown-option failure could still make the
test pass. Each rejection now has an independent helper that fails when the operation succeeds and
accepts only its exact stable error code.

### Authored sources had formatter drift

The first application migration preserved behavior but did not leave every changed Nocter source
in canonical formatter output. Every changed example and `std/cli` source was formatted. The
repository formatter contract and public application execution tests pass from that state.

## Authority Review

`std/process` remains the sole authority for raw operating-system argument order and UTF-8
decoding. `Application.parse_process` calls that authority once, removes only argument zero, and
passes the resulting text sequence into the ordinary parser. Neither schema construction nor
presentation can access process state.

`Application` is the sole retained grammar authority. Construction validates and copies every
name, description, option policy, positional policy, and child command. Parsing and presentation
read that representation directly; there is no generated parser table, help-only schema, or
second declaration registry. Recognition is deterministic: option and command names are unique,
positional order is explicit, and one schema level cannot mix commands with positionals.

The parser classifies each token once. A selected child receives only the untouched suffix after
its command token. `ParsedArguments` owns copied values and lookup names, so it does not retain a
process buffer or an `Application` borrow. Its queries scan the derived match collection but never
inspect original token syntax, repeat validation, or consult schema state. The copied names are
result-local lookup keys, not a competing grammar authority.

Usage and help traverse the same `Application` that parsing consumes. They return an owned
`String`; they do not print, inspect a terminal, select help or version flags implicitly, or choose
an exit status. Public applications own those policies. The CLI parser likewise does not convert
application values, open files, perform network I/O, or know any example-specific rule.

The files under `std/cli` divide implementation work inside one language module. Their reciprocal
`see` edges do not form public namespaces or duplicate representations: `storage.nct` contains the
only structs, `schema.nct` the only mutation and validation rules, `parsing.nct` the only token
classifier, `presentation.nct` the only renderer, and `process.nct` the only operating-system
adapter. Search found no raw process-index use in public examples and no CLI-specific branch in the
compiler or language server.

  `cli -> string`, and `cli -> vec` edges; and

## Result

No implementation or architecture finding remains open in the v0.62.0 scope. The milestone is
ready for a separate release-preparation change. This work did not change release identity, create
an archive, tag a commit, push commits, or publish an asset.
