# v0.72.0 Phase 3 Review

## Scope

Phase 3 closes the pre-existing gap between Nocter's always-on integer trap specification and
native ARM64 execution. It also makes value-sensitive arithmetic proof a checking-owned product.

## Authority Review

- Checking is the only layer that derives `Required`, `ProvenSafe`, or `ProvenTrap` from constants
  and path intervals.
- Execution analysis consumes that recorded decision for `notrap`; it no longer repeats an
  operation-and-type trap table.
- MIR and Machine preserve the decision. Compiler-generated range-loop, pack-length, and
  destruction arithmetic uses a distinct `InternalInvariant` state.
- Machine optimization treats required and proven-trap arithmetic as observable. It can remove an
  unused result only after checking proved the operation safe or classified it as non-trapping.
- ARM64 consumes the closed Machine state. It performs no source range analysis and never upgrades
  `Required` to a proof.

## Runtime Review

ARM64 now checks:

- signed and unsigned add/subtract overflow at the declared width;
- signed and unsigned multiplication overflow, including full-width 64-bit products;
- signed negation of the minimum value;
- zero division and remainder;
- signed minimum divided or reduced by negative one; and
- negative or width-exceeding shift counts.

Narrow integer results are sign- or zero-normalized before later operations. A third reserved
compiler scratch register lets multiplication retain both spilled operands, the full product, and
the destination without borrowing an allocatable register.

## Evidence

- checking tests cover constant and flow-proven dispositions and `notrap` consumption;
- MIR and Machine tests verify lossless disposition transport;
- ARM64 encoding and allocation tests cover the expanded closed instruction/register contract;
- native ARM64 execution accepts safe boundary cases and reaches `SIGTRAP` for dynamic add,
  subtract, multiply, negation, division, remainder, and shift failures; and
- the affected checking, MIR, Machine, ARM64, and native-session gates pass.

## Findings

No backend-owned proof, unchecked source arithmetic fallback, or duplicate execution trap table
remains in the reviewed path. Phase 4 may adopt `notrap` only where these checking facts already
prove the complete implementation.
