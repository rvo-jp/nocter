# v0.60.0 Release-candidate Safety Review

## Scope

This adversarial review reopened the qualified v0.60.0 candidate before publication. It followed
the complete `archive-inspect` path from compressed input through gzip, tar completion, retained
report state, ARM64 value transport, editor projection, documentation claims, and release records.
The review considered current observable defects and direct structural causes; it did not add
speculative facilities for hypothetical later requirements.

## Findings and Root Causes

### The application bounded declared bodies rather than all decoded bytes

The application rejected a sum of declared entry sizes above its output limit. Tar headers,
padding, terminal blocks, and decoded bytes after the in-band tar marker did not contribute to that
sum. `TarStream` correctly drained those bytes to validate its outer gzip reader, but the
application had placed no policy boundary between gzip and tar. A small compressed stream could
therefore force unbounded decompression work even though every declared entry passed policy.

The defect came from assigning one `output_bytes` name to a declaration precheck rather than
defining which stream boundary the resource policy owned. The corrected pipeline has two explicit
application-owned readers: one bounds accepted compressed bytes before gzip, and one bounds every
decoded byte between gzip and tar. Declared body accounting remains a separate early rejection for
hostile sizes. Exact-limit EOF succeeds only after a one-byte sentinel probe; any later decoded
byte fails before a report is returned.

### Large indirect aggregate construction corrupted its input after 32 KiB

Wrapping `BlockingGzipReader<R>` in another owning generic reader failed during native execution.
The failure was not gzip state, interface dispatch, or field projection: direct field forwarding
worked until a constructor accepted the large reader indirectly and returned a larger aggregate
indirectly.

ARM64 non-overlapping copy expansion retained the incoming indirect pointer in `x17`. Once a
destination stack offset exceeded the scaled load/store range, stack-address materialization also
used `x17`. It silently replaced the source root midway through the copy. Earlier tests covered a
large stack store and a large value classification independently, but did not compose a retained
register root with a copy crossing that encoding boundary.

The single memory-copy emitter now resolves both complete addresses once into distinct
boundary-only registers before expanding chunks. The allocator and address materializer cannot use
those registers as scratch. Every aggregate, call, return, pack, primitive, and edge copy already
uses this emitter, so the correction adds no caller convention or parallel large-value path. A
native regression wraps the 32 KiB-history gzip reader in `BlockingBufReader` and exercises the
same indirect-argument and indirect-result path that exposed the defect.

### Archive documentation overstated publication finality

The tar parser necessarily exposes provisional entry and body events before later framing and
outer integrity can be known. Its behavior guide said it did not publish partial state, which
confused parser observation with an application's trusted publication decision. The guide now
states the provisional contract and requires consumers to wait for tar completion and validated
outer EOF before publishing trusted state. The application follows that rule.

## Authority Review

`std/compress` still owns gzip representation and integrity. `std/archive` still owns tar framing,
entry interpretation, and path normalization. The two application readers own only resource
policy and consume the common `BlockingReader` contract; neither reinterprets gzip or tar state.
ARM64 owns physical address lifetime during materialization and receives only Machine-selected
copy operations. No later stage, standard-library module, or application now knows its scratch
register choices.

Search and call-site review found one native non-overlapping-copy materializer and no second
decoded-byte counter in gzip or tar. Public and milestone descriptions now distinguish compressed
bytes, complete decoded transport bytes, and declared body bytes. The obsolete qualified candidate
is explicitly superseded in the release-preparation record and handoff.

## Focused Evidence

- all 114 `nocter-arm64` library tests pass, including the fixed-base exclusion contract;
- native gzip execution passes direct and buffered-reader composition across the large aggregate;
- all three declared `archive-inspect` tests pass, including exact decoded-limit EOF, post-marker
  decoded data, gzip truncation, integrity damage, and every application limit;
- the real application passes hover, completion, definition, implementation, semantic-token, and
  inlay-hint coverage from one checked editor generation;
- deterministic documentation tests and the 332-page out-of-tree build pass; and
- Rust formatting and repository whitespace checks pass.

## Result

The identified implementation and documentation defects are resolved without a compatibility
path or feature-local workaround. The previous archive remains invalid for publication. Full
compiler verification and deterministic replacement-candidate qualification remain required
before v0.60.0 can return to publication-ready status.
