# v2.0.0 Result Access Contracts

## Status and Scope

This records internal Value Access Model decisions under the user's delegation, following the
adopted S1–S6 and R1–R3 [source decisions](v2.0.0-source-design-decisions.md). It refines
[semantic closure](v2.0.0-value-access-semantics.md); the
[milestone](../milestones/v2.0.0.md) owns adoption status. It is not current compiler behavior,
a normative specification, a full soundness proof, or evidence of a speed improvement.

The decisions below fix result authority, origin retention, handoff, outcome composition, and
deferred cleanup. Structural callable result-mode spelling is now adopted separately:
`func ^(...)` supplies an owned result, while `^func` describes consuming environment invocation.
Those independent positions encode the contracts below.

The subsequent [typing/migration review](v2.0.0-access-typing.md) refines Copy materialization,
generic evidence, and binding/return validation. Migrated language rules now belong to the
explicitly future [Value Access Model](../../../spec/language/value-access.md) and its linked
owning sections. This review remains a design record; it is not a parallel normative authority.

## 1. One Contract, Several Independent Facts

Every checked callable has a result contract with:

| Fact | Meaning |
| --- | --- |
| Payload mode I / U / X | Read, update existing storage, or receive ownership |
| Result shape | Exact ordinary, tuple, optional, and fallible nesting; async adds a distinct future boundary |
| Access-origin relation | Which caller-owned places can supply a retained I/U access, including transitive dependencies |
| Carried dependencies | Outside access retained by a returned computation or other explicitly dependent value |
| Storage constraints | Allocator/region validity requirements, separate from exclusive or shared access |

Ordered parameters, receiver permission, environment invocation mode, execution kind, and effects
remain separate contract facts. In particular, owning a closure/future does not mean it is free
of outside dependencies. An allocator constraint alone does not borrow an entire allocator
exclusively for every operation on its allocated value.

Contracts use declaration and parameter identities, not source names. A result prefix is metadata,
not a second callable name. A body, specialization, or caller's later uses cannot change its mode.
Representation and transport may change once all these facts remain preserved.

## 2. Meaning of the Three Result Modes

### Owned Results

X supplies one owned initialized value. A fresh construction or transferred existing owned place
can supply it. `return ^value` transfers an existing owner even when its type is Copy. Returning
an existing Copy place without transfer can instead make the already permitted structural copy;
an input-only move-only place cannot be turned into X by an implicit clone.

An ordinary binding of an X result owns it, as adopted by S2. An independently owned result has
no new access to the callee's input slots. An explicitly dependent owned result, such as a closure
retaining read access, still carries that dependency. Wrapping it in another owned aggregate does
not erase the relationship. Region constraints remain checked in either case.

### Read Results

I supplies read authority, not ownership of a move-only referent. It can expose a caller-owned
place or produce a permitted Copy value. A concrete scalar result such as `len(): usize` copies
its answer into result transport; it does not retain an access to an internal counter merely
because the answer was read there. A Copy computation that carries external access retains those
dependencies when copied; Copy does not imply storage independence.

An unconstrained generic I result cannot promise a new owned T. Returning an I parameter can
forward access to it under the result-origin contract; proving Copy permits the separate
structural-copy operation. Generic origin bounds are not discarded merely because specialization
chooses a Copy type. A destination performing a permitted Copy initialization can establish an
independent copy of that payload; it must preserve any dependencies contained inside the value.

An unmarked binding initialized by an I projection retains read access unless ordinary Copy
initialization supplies a separate owned value. It never silently clones a move-only referent.
This is contract-derived access binding, not an owned initializer secretly converted to an alias.

### Update Results

U supplies delegated exclusive access to initialized caller-owned storage. It requires writable
authority at its origin and must preserve initialization on ordinary return, failure, and
cancellation. It does not transfer ownership of the referent or permit leaving an extraction hole.

A U result binding retains its update authority. `let` fixes that binding; it does not erase the
update authority supplied by the accessor. This differs from an owned `let`, whose own storage
remains immutable under the ordinary binding rule. Rebinding either requires the appropriate
binding form; writing through a U access is an operation on its caller-owned referent.

There is no I-to-U, I-to-X, or U-to-X strengthening. Temporary I/U delegation from X and I
delegation from U remain ordinary checked operations, not new result modes or implicit clones.
The later typing account permits a proved structural Copy to create a new owned value at an X
destination. It never transfers ownership of an I/U referent or substitutes copying for transfer
of an existing owned X actual; the distinction is recorded as a materialization operation.

## 3. Origins without Private-Body Lookup

Public contracts must determine possible result origins. Preserve the existing `from` upper-bound
model and zero/one-origin elision, adapted to value access rather than first-class borrow types:

1. Fresh independent owned results and ordinary independent Copy answers need no new caller-place
   origin. Carried dependencies and lexical region requirements remain tracked separately.
2. A retained I/U result needs eligible outside storage. A U result additionally needs update
   authority to that storage. Static read-only storage can supply I, never arbitrary U access.
3. One eligible origin can be elided. Multiple eligible origins need an explicit stable public
   relation unless the contract already establishes independence. A private body cannot narrow an
   ambiguous bodyless contract on the caller's behalf.
4. X parameters and locally owned captures are callee-owned storage. They are not eligible
   outside roots for an escaping I/U result. An already-carried dependency on a genuinely outside
   owner can be forwarded without pretending the consumed parameter itself survives.
5. A `from` upper bound permits fewer actual dependencies; it does not create authority or turn
   an unrelated owner into a source. For an abstract associated result explicitly tied to a
   receiver, retain the invocation dependency until a checked copy/independence operation discharges
   it. Generic substitution alone does not erase the relationship.

No new source lifetime parameters or body search at an indirect call are added. Origin relations
compose through forwarding, parameter containment, associated types, and environment captures.
Unknown field/range overlap stays conservative. A body must prove its actual returned access and
carried dependencies fit the declared upper bound on every return path.

## 4. Ordinary `return` Finishes the Callable

An I/U-returning callable selects existing storage with ordinary `return`; it does not suspend its
body or acquire an implicit continuation. For a move-only `Item`, these are projection bodies:

```text
impl Pair {
    method self.first(): Item { return self.left }
    method &self.&edit_first(): Item { return self.left }
}
```

No `view`, `yield`, new return keyword, or call/binding assertion is required. The selected result
contract determines whether `return self.left` exposes read or update access. Ordinary field
selection supplies a place; it is not an owned extraction in these examples.

Return processing is a checked sequence:

1. Evaluate the result once. Stage its owned payload or delegated access and exact dependencies.
2. Protect the selected referent/dependencies during all remaining ordinary exit cleanup. A
   destructor or deferred cleanup cannot invalidate the staged result or use conflicting access.
3. Perform normal callee cleanup, skipping ownership already transferred into the staged result.
   Local regions and owned parameters end at their specified boundaries.
4. Hand the result to its caller. Reparent escaping access from the invocation permission into
   the returned access as one transition; end the invocation's remaining permissions.

The caller cannot observe a U handoff as two independent overlapping updates. Delegating to a
child access restricts/suspends the parent's permission; releasing the child restores only rights
that its still-live parent is entitled to regain. Returning a child does not restore a parent
permission that would conflict with it.

Selecting a local/temporary/consumed-parameter place for I/U is rejected if ordinary cleanup ends
its storage. Protecting it does not make it eligible to escape. The compiler must not postpone
cleanup, heap-promote an owner to extend its resource lifetime, or insert shared ownership.

### Guards and Access Epilogues

Do not reinterpret `return` as retaining arbitrary local guards until the caller finishes using
the result. If an accessor acquires a local lock guard and the returned access requires that
guard to remain live, an ordinary access return cannot discharge normal cleanup and is rejected.
An API can instead return an explicitly owned guard/capability with its checked outside
dependencies, and expose access through that live owner. This uses ordinary X and I/U contracts.

The earlier general discussion of projection epilogues does not authorize synthesized suspension
of an ordinary callable. Cleanup for a separately specified live access/guard remains a use at
its own semantic boundary. A future explicit accessor-continuation facility would be a separate
source/semantic decision; it is not smuggled in by deleting `yield` from the spelling.

## 5. Tags, Payloads, and Outcome Construction

The callable's result mode applies to its successful data payload, recursively through the
selected optional/fallible shape. Carrier tags are initialized control data, not ownership of the
referent. A fallible result always owns its active failure `error`, even when its success result
is I or U. For example, a U-returning fallible accessor can produce either an update access or an
owned failure; it never makes an error into writable caller storage.

| Active branch | Result contents and retained success access |
| --- | --- |
| Ordinary success | I/U access or X ownership according to the result contract |
| Present optional | One preserved layer containing its recursively checked payload |
| Absent optional | No payload and no dependency arising only from an inactive success payload |
| Failure | One owned `error`; no dependency arising only from an inactive success payload |

Actual error storage constraints remain part of escape analysis; failure does not erase them.
Before a tag is known, analysis conservatively retains the union of possible dependencies. A
checked branch that proves absence/failure can remove dependencies of the impossible successful
payload. This requires a tag proof, not a guess based on customary API behavior.

Exact whole-outcome forwarding preserves the tag, mode, and dependencies. A stored owned outcome
requires explicit transfer when forwarded from an existing owner. No flattening, automatic
success extraction, or reinterpretation of type `error` as failure is allowed.

After exact forwarding, unambiguous contextual injection constructs the required present/success
layers. `none` selects the applicable outer absent layer, rather than guessing an inner absence.
`some<T>(value)` constructs exactly one present layer with T as its payload, even when T is itself
optional. Its ordinary implementation can return the owned T into T?; exact forwarding cannot
confuse the finite types T and T?. `let a: i32? = 10` remains valid without `some`.

`throw reason` moves one owned error into the declared unique fallible layer. It constructs the
enclosing branch path required by that shape, performs ordinary cleanup, and exits this callable.
Repeated fallible layers are not added. An `error!` success remains ordinary owned data.

`void` has the single value `()`, including as a stored or optional payload. Bare `return` and
normal unit completion remain implicit success. `never` supplies no normal result; it is not a
second unit value and does not enable arbitrary outcome payload positions.

### Multiple Components

A single result prefix covers the result's data components uniformly: an X tuple owns its
components, a U tuple projection must identify real caller-owned component places, and I exposes
read authority or permitted Copy answers. Do not silently mix an owned noncopyable component and
a non-owning component into an ordinary tuple merely because their displayed T types fit.
An explicitly dependent owned aggregate may carry relationships supported by its checked API;
it is not a general tuple of freely storable references. No new per-component permission syntax
is adopted in this pass.

## 6. Futures and Consuming Environments

For an async declaration, the prefix describes the eventual successful output. The immediate
result is an owned pending computation. Checked expression information must carry both facts:
ownership of the future and its output contract. `await` consumes the future and exposes the
output under that contract; it does not promote an I/U output to X.

I/U argument dependencies begin at successful future construction. X parameters become future-owned
then, not at first drive. Result transfer follows these boundaries:

- On success, validate the output against ordinary producer cleanup. Outside dependencies used by
  the output move from producer access into output access without an unprotected interval.
- A completed, unconsumed future owns/retains its active output and dependencies. Completing it
  does not release a dependency still needed by that output.
- `await` transfers that output and dependencies to the awaiting context once. Future-frame
  cleanup must not destroy an owner on which the output depends.
- On failure or absence, release unused successful-output dependencies after required producer
  cleanup. Retain only the active branch's actual storage/dependencies.
- Cancelling pending work cancels its child before destroying child-accessed parent locals.
  Dropping a completed, unconsumed future destroys its owned output, or ends its non-owning output
  access, once. Owned output cleanup runs before releasing dependencies its destructor needs.

Returning access to a producer-owned parameter/local remains invalid: caller storage placement
or an embedded frame cannot change that semantic cleanup boundary. Returning an owned child future
that depends on such a disappearing parent local is invalid for the same reason.

Environment invocation mode is orthogonal. A consuming closure may return X from an owned capture,
but cannot return I/U into that destroyed capture. A closure retaining access to outside storage
can forward that outside dependency if its contract permits it. A repeatedly invoked mutable
closure cannot be invoked again incompatibly while its previous U output remains live.

## 7. Forwarding and Compiler Obligations

Generic and interface matching preserves parameter modes, environment invocation permission,
execution kind, result mode/shape, and origin relations after identity-based substitution. No
matching only on the displayed return type, no permission strengthening, and no new per-call
body lookup are permitted. Copy initialization is a checked operation, not an excuse to forget
dependencies. Opaque witnesses and erased callable evidence must carry the same facts.

Inference joins possible dependencies across control flow and keeps definite initialization
separate. A path that returns X and another that returns I do not acquire a common contract by
choosing whatever the caller needs. A wrapper forwarding X must own the forwarded value; an I
wrapper cannot discover ownership from a particular specialization's implementation.

An expected callable contract can provide a closure's result mode before checking its body,
as it provides parameter/result types. Without that context, accept inference only when the
checked return expressions establish a unique result protocol; otherwise require an existing
callable annotation or named declaration. Later uses must not retroactively change the closure's
mode. This does not introduce a new closure-result keyword or make environment invocation mode
stand in for output mode.

The checked graph must record staged results, branch tags, delegated access parent/child edges,
ownership destinations, dependent outputs, region constraints, and cleanup-before-handoff edges.
Before lowering, validate that each continuing path has exactly one owner for each live owned
value, that all active accesses have initialized live roots, that overlapping U is exclusive
apart from explicit restricted delegation, and that all exits preserve U initialization.

Optimizers may remove transport, propagate tags, scalarize owned carriers, fuse calls, and shorten
unobservable storage use. They must preserve these edges or discharge a proof obligation. A
semantic X transfer need not move bytes; an I/U result need not allocate a descriptor. Native
results and performance measurements are still required before claiming those benefits.

## 8. Distinguishing Cases and Evidence

| Case | Decision |
| --- | --- |
| `let file = open(...)` from `^open` then an X call | Accept; binding owns the result |
| I of a move-only caller field, then consume its owner while access remains live | Reject the consumption |
| U of a caller field, then overlapping parent update | Reject until child access ends |
| Return I/U into a consumed parameter or local | Reject; no lifetime repair |
| Return I/U into caller storage, but local destructor invalidates it | Reject the cleanup conflict |
| Local guard must survive an ordinary access return | Reject; use an owned guard API |
| Independent scalar result of reading an internal field | Accept a Copy answer without retaining that field |
| Copy of a read-capturing closure | Keep dependencies of every copy |
| Generic owning identity specialized to Copy and move-only | X in both; existing source unavailable after transfer |
| Generic/interface forwarding drops the result origin or changes U to X | Reject the contract mismatch |
| Fallible U accessor fails after valid mutation | Owned error, no U result, valid changed caller value |
| Optional U accessor proves absent | No retained success access on that branch |
| Whole `error!` success is forwarded | Preserve success tag; do not throw it |
| Nested optional contains an absent payload | Preserve both independent tags |
| Async I/U output refers to outside caller storage | Retain through ready future and onward through await |
| Async I/U output refers to its own frame local | Reject before code generation |
| Owned async output carries an outside dependency | Keep it despite X output ownership |
| Ready future is dropped without await | Clean active output once before releasing its dependencies |
| Consuming closure returns access into its owned capture | Reject |
| Consuming closure transfers its owned capture as X | Accept with exact cleanup ownership |
| U-returning callback is invoked twice with a still-live conflicting first output | Reject |

The separate [result handoff model check](v2.0.0-result-access-model-check.py) explores a finite
post-invocation abstraction, including outside/inside ownership, result dependencies, absence,
failure, forwarding, read-access duplication, completion, cancellation, and discarded ready outputs.
It does not parse Nocter, verify this entire chapter, or replace compiler conformance.

## 9. Primary Evidence and Limits

Reviewed on 2026-11-07; these are independently selected Nocter rules:

- [Swift Ownership SSA](https://github.com/swiftlang/swift/blob/main/docs/SIL/Ownership.md)
  distinguishes lifetime-ending uses from ordinary uses and states path-wise ownership
  invariants. It motivates explicit ownership edges and validation, not adopting Swift ARC.
- [Hylo subscripts](https://hylo-lang.org/docs/user/language-tour/subscripts/)
  retain accessor execution across a yielded access and can run code afterward. This is a
  meaningful semantic difference: Nocter does not reproduce that behavior behind ordinary `return`.
- [Oxide, revised 2021](https://arxiv.org/abs/1903.00982v4)
  formalizes provenance approximations and proves properties of its own type system. It motivates
  explicit origin reasoning; it is not a proof of Nocter's model or authority for its syntax.

Remaining work includes exact grammar and owning specification migration for the selected forms,
a precise declarative/algorithmic typing account for general projections and Copy,
loop/join and reborrow proofs, effects, region escape, and executable implementation conformance.
The selected result rules are not a claim that those obligations are already discharged.
