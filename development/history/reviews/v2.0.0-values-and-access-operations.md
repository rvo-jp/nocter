# Value Access Model

## Status and Purpose

The adopted name is **Value Access Model**. It names Nocter's value-oriented input, update, and
transfer model; it does not claim identity with Mutable Value Semantics or another research model.
Naming the model does not adopt the pending declaration-driven call policy below.

The six semantic decisions below are also adopted: independent owned storage, uniform explicit
transfer, owned-parameter permissions, preparation before call access activation, explicit
projection dependencies, deferred-access duration, and preservation of modes through abstraction.
Their remaining closure questions do not reopen these decisions or imply compiler support.

The conceptual input/update/transfer model and its symbols are adopted for v2.0.0: unmarked input,
`&` update, and `^` transfer. Implementation, receiver-marker placement, and complete grammar
remain pending. Examples illustrate adopted mode distinctions and the explicitly identified
placement alternatives, not current compiler support. The [v2.0.0 plan](../milestones/v2.0.0.md) owns adopted
decisions. This model replaces borrow terminology and `&` type notation without treating
implementation effort, short-term delivery, or Rust comparisons as constraints.

The earlier adopted call-marker baseline is illustrated first. The latest recommended revision is
uniform declaration-driven calls for receivers and ordinary arguments, documented below; that
revision has not been adopted. It is not an optional second spelling of the baseline.

Explain ordinary programs through values and the operations permitted on them:
input, update, and transfer. Separate these operations from the physical decision to pass an
address, copy bits, allocate storage, or reuse a location. Preserve defined behavior and sound
access information without requiring a first-class reference type in ordinary source.

This is an adopted replacement model, not permission to implement the deferred type-driven
automatic-borrowing or implicit-return-transfer proposals in the existing model. Its detailed
closure requires coherent semantics for projections, stored data, closures, asynchronous work,
and resources; a keyword
substitution alone would not achieve the objective.

## Design Responsibility and Closure

Completion of the model's semantics, static analysis, and optimization design is delegated to the
agent. Remaining model questions are work to resolve, not an approval queue. This includes
copy eligibility within the selected source design, permission composition, nested argument
reservation/activation, projection dependencies, retained access, initialization and cleanup,
cancellation, generic evidence, and the soundness of storage reuse. These decisions may affect
accepted programs and observable execution; that alone does not require user approval within
this delegated scope. Preserve the adopted operation model and safety/resource requirements.

Reserve user consultation for language-design choices requiring human judgment about writing,
reading, or learning code. Call-marker omission/placement, projection source forms, and
callable-type spelling remain such questions when materially different alternatives survive.
Present concrete programs and a recommendation rather than asking the user to design the
underlying analysis. Delegation itself does not select the pending call-marker policy.

For each autonomous decision, record its exact rule, primary research where relevant, alternatives
and counterexamples, interaction with adopted contracts, proof obligations, and distinguishing
valid/conflicting/failure/cancellation cases. Research supports reasoning; it does not establish
Nocter semantics or prove a performance benefit by analogy. Record remaining uncertainty and
measure generated operations before claiming a runtime improvement.

Resolve internal details independently of unsettled spelling where possible, using explicitly
identified conceptual notation. Record resolved rules as model decisions, and keep genuine
syntax alternatives visibly pending. Design resolution is distinct from implementation and
qualification: the current specification remains authoritative until coherent v2.0.0 migration.
Implementation effort, short-term delivery, and Rust comparisons remain outside the acceptance
criteria for a better model.

## Adopted Operation Model

| Operation | Caller-visible meaning |
| --- | --- |
| Input | Supplies read access; retains ownership of the supplied value. |
| Update | Grants temporary exclusive access to update the original writable place. |
| Transfer | Transfers an owned value; its previous owned place is unavailable until valid reinitialization. |

An unmarked parameter consistently means input. An existing owned argument is not silently consumed
because a callee happens to need ownership. Updating and transferring require matching explicit
operations at the call and contract under the retained explicit-call baseline. Explicit transfer
invalidates the source for both copyable and noncopyable values. The implicit-copy type policy and
newly constructed values still need detailed rules.

This differs from eliding `&` according to a selected parameter type while leaving plain `T`
parameters consuming. Here the unmarked operation has one meaning across contracts. The price is a
major change to parameter semantics, which must be evaluated as a complete model.

Update permission is an observable contract, not an optimization guarantee like the removed
`noalloc` modifier. Avoid reusing `var` for it: a mutable local binding and access to the caller's
original place are different operations. Keep transfer explicit in calls and existing owned
returns. Initial `edit` and `move` sketches name those operations; the adopted symbols replace
those keyword spellings rather than adding equivalent aliases.

## Adopted Single-Symbol Spelling

Use no marker for input, `&` for update, and `^` for transfer. Use matching markers before
parameter names and arguments; full expression grammar still needs closure:

```text
func inspect(value: Config): void
func reset(&value: Config): void
func submit(^value: Job): void

inspect(config)
reset(&config)
submit(^job)
```

These markers describe an operation on a value or place, not a pointer type. In the adopted model,
`&T` and `&+T` do not remain ordinary borrow types, `&value` does not create a storable reference,
and `let alias = &value` is not an escape hatch for shared mutable identity. Input remains
unmarked; update and transfer remain explicit irrespective of hidden implementation facts.

Transfers into owned bindings, stored fields, and results use the transfer
marker, for example `let next = ^previous` and `return ^value`. Transfer has the same meaning for
generic substitutions regardless of copyability. Constructor temporaries, partial extraction,
repeated markers, and statement boundaries need precise
closure. The marker must never request a hidden deep copy. A transfer of a newly created value
can directly forward its storage; it must not require a redundant physical move merely because
the programmer supplied an explicit operation marker.

Keep one canonical source spelling per operation rather than
retaining `edit`/`move` as equivalent keyword aliases. Diagnostic text and documentation should
continue to name input, update, and transfer in words.

### Receiver and Invocation Placement

The earlier method proposal places the call-side mode after the member-selection dot so it
clearly applies to the receiver operation. Its position is now under review; it is not a settled
precedence rule merely because the mode symbols are adopted:

```text
impl Buffer {
    method self.len(): usize
    method &self.append(value: u8): void
    method ^self.finish(): Product!
}

buffer.len()
buffer.&append(42)
let result = buffer.^finish()?
```

The ordinary call reads its receiver, `.&` updates it, and `.^` transfers it. Method declarations
use the same mode before `self` as parameter declarations use before a name. These remain methods;
the spelling does not introduce UFCS or a second top-level-function call form.

The earlier proposal defines prefix `^` to transfer the selected value after its call/member/index chain, before an
outcome suffix. Thus `^make()` forwards the newly produced owned result, `^result?` means
`(^result)?`, and `^buffer.finish()` applies to the result rather than the receiver. Selecting
the receiver mode at `.` makes `buffer.^finish()` a distinct, readable operation. Selection of an
indexed place does not by itself authorize ownership extraction; the operation must preserve the
container's initialization and cleanup contract. Complete precedence, generic method arguments,
computed receivers, callback invocation, operator contracts, and forwarding
still require grammar decisions. This method-selector shape is a proposal, not permission to
implement a special receiver exception before the complete invocation model is closed.

Access activation during argument evaluation also needs closure. For example,
`buffer.&append(buffer.len())` must be evaluated against a defined input/update sequencing rule,
not rejected or accepted accidentally because a prefix happened to be visited first. Preserve
exactly-once evaluation and reject genuinely overlapping retained accesses.

### Receiver Placement Review

The current preferred candidate is declaration-driven access for all call operands, described next. It is not
adopted yet. The earlier marker-position alternatives remain below to explain their tradeoffs.

The original reason for `buffer.^finish()` was to make the receiver mode explicit at invocation,
separately from transferring a returned value. It is a design choice, not a requirement imposed
by ownership or by an existing language's operator precedence.

| Candidate | Intended interpretation | Remaining issue |
| --- | --- | --- |
| `buffer.^finish()` | Invoke `finish` with transfer of `buffer`. | Adds a mode position inside member selection. |
| `(^buffer).finish()` | Put the explicit transfer on the grouped receiver, then invoke its method in that mode. | Requires an explicit mode-forwarding rule for grouped receivers; more grouping is written. |
| `^buffer.finish()` with call/member selection tighter than prefix | Transfer the result of `buffer.finish()`, not its receiver. | Does not express the requested receiver transfer. |
| `^buffer.finish()` with prefix tighter than member selection, or a dedicated receiver-prefix rule | Transfer the receiver before invocation. | Must also define fields, indexes, callable values, and multi-call chains consistently. |

Under the earlier result-prefix interpretation, the bare prefix does not satisfy a `^self` receiver
contract merely by appearing before the expression. An input method returning an owned result,
such as `buffer.snapshot()`, would instead demonstrate result transfer as `^buffer.snapshot()`.
Do not silently reinterpret the same syntax as receiver transfer because `finish` requires it.

Before selecting a prefix alternative, distinguish transferring `holder.buffer` from transferring
`holder` and accessing its field, and distinguish the first and later receivers in
`buffer.prepare().finish()`. Also distinguish invocation mode from transferring the returned value
for a callable variable. Grouping may make the target explicit, but it must have one defined role.
All choices must preserve exactly-once evaluation and the access activation/cleanup rules.

These explicit-marker placement alternatives did not establish a final receiver spelling. Do not
reinterpret an explicit prefix's operand as receiver or result merely to satisfy the selected
method. The declaration-driven candidate below is a separate rule for unmarked calls.

### Preferred Candidate: Declaration-Driven Calls

**Recommended revision, not adopted.** Use one policy for both receivers and ordinary arguments:
the selected callable contract determines input, update, and transfer, and call syntax has no
access-mode markers. This revises the earlier receiver-only recommendation. It would supersede
the previously adopted requirement for matching argument markers if separately adopted.

Keep `&` and `^` on declarations and use ordinary calls:

```text
func resize(&buffer: Buffer, size: usize): void
func enqueue(^job: Job): void

impl Buffer {
    method self.len(): usize
    method &self.append(value: u8): void
    method ^self.finish(): Product!
}

resize(buffer, 64)
enqueue(job)
buffer.len()
buffer.append(42)
let product = buffer.finish()?
```

An unmarked parameter declaration still means input. An unmarked call argument instead supplies
the operand to the already selected parameter; it no longer independently asserts input access.
This change must be explicit in the model and teaching materials. Public modes remain authored
contracts, not summaries inferred from the current body or guesses based on a caller's last use.

Select one callable identity, then apply its declared receiver and parameter modes. Validate read
access, a writable exclusive update target, or ownership available for transfer as appropriate.
An unavailable mode is a diagnostic; do not insert a clone, change a binding's mutability, or choose
a different callable to repair the call. Do not overload or rank same-name operations solely by
mode or choose a consuming alternative because a writable operand is unavailable.

Generic bounds, interface conformance, function-value types, invocation capabilities, and erased
callable contracts must preserve modes. An indirect call cannot recover missing modes by inspecting
the selected implementation body. A wrapper's input parameter cannot be forwarded to a consuming
parameter unless the wrapper owns a suitable value; the compiler must not silently strengthen the
wrapper's public contract to transfer. Concrete specialization does not change a declared input
into update or transfer merely because a particular type or call site would allow it.

An update call requires a writable place: an ordinary immutable local does not supply that
permission, while a transferred parameter has the adopted owned-parameter permissions below.
After a consuming call actually transfers an argument or receiver, that previous owned place is
unavailable even if the operation fails. Apply the adopted preparation/activation timing and
deferred-access duration below. Partial initialization, nested preparation, and exact cancellation
cleanup still need closure; omitting a marker does not omit those checks.

The declaration is the authoritative contract under either policy. A repeated call-side marker
was an assertion of the caller's intent, not a second authority capable of changing the callable's
meaning. Omitting it reduces repetition and marker mismatches, while giving up that visible intent
assertion. The call expression alone no longer states which operands are read, updated, or
consumed. This is a readability tradeoff rather than proof that all duplicate-looking syntax is
semantically unnecessary.

For Nocter's contract-centered modules, the uniform policy is the preferred tradeoff. Keep all
modes visible in `index.nct`, callable signatures, and editor navigation. A
change requiring stronger operand access, such as input to update or transfer, is an API contract
change even when some callers still compile unchanged. Document receiver consumption, including
failure behavior, on operations such as `finish`; names are explanatory, never dispatch authority.

The update in `resize(buffer, buffer.len())` begins only according to the specified call activation
rules; the computed length is different from retaining a read access during an update. A call
holding overlapping update/input operands must still be rejected when they conflict. Operand
evaluation, access activation, and failure before or after transfer need explicit conformance cases.
In particular, a later argument's preparation failure does not consume an earlier reserved
transfer source. Apply that adopted timing consistently; marker omission must not make initialization
state depend on an optimizer or an ad hoc attempt to keep the program valid.

### One Canonical Call Policy

There are two coherent uniform policies:

| Policy | Receiver call | Ordinary arguments | Benefit and cost |
| --- | --- | --- | --- |
| All explicit | `buffer.&append(42)` / `buffer.^finish()` | `resize(&buffer, n)` / `enqueue(^job)` | Makes access intent local and forces call edits after mode changes; repeats the declared mode at every use. |
| Declaration-driven, recommended | `buffer.append(42)` / `buffer.finish()` | `resize(buffer, n)` / `enqueue(job)` | Reduces writing and teaches one call rule; requires the contract to understand mutation and consumption. |

A fixed receiver-only omission policy is not optional spelling freedom: it is one rule for each
syntactic role. However, it adds a distinction that needs justification. In Nocter's current design
direction, a uniform declaration-driven policy is preferable to that split. Both uniform policies
can carry the same checked operation and safety facts; there is no inherent runtime-speed choice
between them when the selected contract is the same.

Do not support explicit and omitted access markers as interchangeable spellings for the same call.
If declaration-driven calls are selected, remove `.&`/`.^` and direct argument-mode prefixes rather
than keeping them as optional intent checks. Transparent grouping must not restore a redundant
mode annotation. If all-explicit calls are selected instead, missing required markers are errors
for both ordinary arguments and receivers. Source cannot choose a local style.

Standalone ownership operations such as `let next = ^previous`, `return ^value`, and owned field
initialization are outside this call policy and are not proposed for omission here. Close their
expression grammar without allowing a standalone transfer to become a disguised alternate
call-mode spelling. Separate preparation of an owned local remains an actual source operation,
not an optional annotation on a call. This distinction also keeps the previously deferred
implicit-return-transfer proposal separate.

The user requested evaluation of the two uniform policies; no adoption of this revision is
recorded. Receiver placement and call-argument grammar remain open until that decision.

### Symbol Rationale and Migration

- **`&` for update:** compact and compatible with the idea of operating on the supplied place.
  Its old Nocter meaning was readonly borrowing. Migration therefore requires retiring that old
  meaning coherently, not leaving two interpretations in the language. The symbol by itself does
  not eliminate the need to teach the new update operation.
- **`^` for transfer:** no existing expression-operator meaning in the current Nocter grammar.
  Keep it dedicated to ownership transfer rather than introducing another use for `!`, `?`, or
  comparison/generic delimiters. It is a learned notation, not a universally obvious glyph for
  transfer. The existing bitwise APIs do not require a binary `^` operator.
- **`~` for update:** considered but not selected. It avoids reusing the old borrow marker and has
  no existing Nocter expression meaning, but has a weaker association with updating the supplied
  place. This historical alternative does not reopen the adopted `&`/`^` symbol decision.
- **`!` for update:** rejected because prefix logical negation and postfix forced
  unwrap already use it. Argument types must not decide whether one written operator means a
  boolean expression or an update request.
- **`>` for transfer:** a directional glyph is attractive, but the token already participates in
  comparison and generic closing syntax. Prefer a dedicated marker for a common source operation.

The existing grammar uses `^` only in explanatory mathematical notation and `~` in its meta-grammar
or path examples, not as Nocter expression operations. Verify token recognition and newline rules
against [Lexical Grammar](../../../spec/language/lexical-grammar.md) and
[Expression Precedence](../../../spec/language/syntactic-grammar.md#expression-precedence) when
closing the selected spelling. The compiler must resolve modes from syntax, not reinterpret a
marker after type checking. In the proposed model, `&&` need not split into nested borrow prefixes.

## Inputs

An input may be inspected for the duration of the operation. Through that input the callee cannot
update the supplied place, transfer its ownership, or retain a non-owning access beyond the
allowed operation duration. Returning or storing an independent scalar copy remains distinct from
retaining access to the original storage. Returning an independent owned result requires
construction, an explicitly permitted copy, or a transferred input; the compiler must not insert
an owning clone to make an invalid return work.

Input permission does not imply purity. The operation may have other effects through explicit
capabilities or external services. Define the treatment of shared handles and external resource
identity rather than pretending a readonly argument makes the outside world immutable.

The compiler may transport a small value in registers, pass a larger value's address, inline the
operation, or specialize it. These choices must preserve source identity observations, validation,
and destruction. No source-level object copy or allocation is required solely to spell an input.

Text and slice inputs are important cases, not an afterthought. Investigate `text: str` and,
using the adopted symbol, `&elements: [T]` as access to text or an element sequence without making
`&str` or `&+[T]` ordinary value types. Owned storage such as `String` or `Vec<T>` remains a separate question from
the shape being accessed. Close adaptation from storage to an input/projection and the distinction
between accessible unsized data and independent stored results. Removing `&` cannot silently turn
a view into an allocating copy or leave generic position rules unexplained.

For immediate calls the input access normally ends when the operation returns. Deferred operations
retain required access from construction through completion or cancellation and required cleanup;
an explicitly dependent result may retain it longer. Call construction must not be confused with
completion. A pending operation can therefore prevent a conflicting update even though ownership
remains with the caller. Exact cancellation and returned-dependency contracts remain to be closed.

## Updates

An update targets a writable place. During the access, overlapping conflicting access is invalid;
provably disjoint places may be used independently. Updating a field, assigning a replacement, or
passing a temporary update onward must retain one access identity and correct initialization and
cleanup. The callee cannot extract the caller's owned value and leave an uninitialized place on
return, failure, or cancellation. Replacement needs a defined safe operation, not a loophole in
the transfer rules.

Failure does not imply rollback. An update must preserve a valid initialized value, but may leave
completed changes visible. Transactional restoration is a separate API contract.

The compiler selects layout and passing strategy while preserving the caller-visible update. A
signature change from input to update requires a corresponding call change; it cannot silently
make an ordinary unmarked call mutate its argument.

Temporary values, method receivers, compound operations, and forwarding through callbacks need
the same operation model. Exact receiver and forwarding syntax remains open; do not invent a
different ownership rule for each callable kind.

## Transfers

Transfer authorizes the callee to store, return, or destroy the owned value. After transfer, the
caller cannot use the previous owned place without valid reinitialization. Keep the distinction
between semantic transfer and physical movement of bytes. Direct result construction and storage
reuse are implementation choices.

A transferred parameter grants read, update, and further-transfer permission without requiring an
intermediate mutable local. The recipient owns cleanup responsibility even on failure. Explicit
transfer invalidates the source uniformly, including when the type permits implicit copying.

The model keeps explicit owned returns, initially illustrated as `return move value` and proposed
symbolically as `return ^value`. It does not use optional last-use optimization to decide whether
a source expression transfers ownership. The implicit-copy type policy, partial moves, and uniform
type-family cleanup must be closed before generalizing the examples into grammar.

## Parts of Values Instead of Freely Stored References

The main conceptual reduction comes from not treating every temporary access as an ordinary
storable value of type `&T` or `&+T`. A field, collection element, or projected subrange can instead
identify a place on which an input or update operation acts. A projection exposes a part of an
existing value; it is not an ordinary function returning an independent owned result.

Investigate structured access to such projections. The owner must remain valid during use, and an
operation that could invalidate the selected storage must be rejected unless non-conflict is
proven. Passing an element directly to an input operation need not manufacture an owned element.
Binding or storing an independent owned element must not quietly become a stored alias instead.

Do not merely rename `&T` to `View<T>` and keep all the same general storage/lifetime obligations.
Determine which long-lived relationships the language actually needs, and give them explicit
semantics. Options include owned results, structured projections, an owner plus an index/range,
and deliberate shared ownership through a specified API. They have different identity,
invalidation, retention, and runtime-cost consequences; none is an adopted universal fallback.

Closures and futures are essential distinguishing cases. An escaping closure may need owned
captures; an operation retaining read access needs a proved duration and storage relationship.
Moving a container must not invalidate an internal reference by accident. A future must release
retained access in the defined cancellation order. The compiler cannot silently prolong a file,
lock, or user destructor's lifetime to make the model convenient.

## Adopted Semantic Decisions

The following six decisions are adopted for the v2.0.0 redesign, not implemented behavior. Complete
their remaining grammar and boundary cases before implementation. Examples using unmarked
update/transfer calls assume the pending declaration-driven candidate solely to discuss behavior;
adopting these decisions does not select that call policy.

### 1. Independent Storage, Copying, and Transfer

Distinguish reading an existing value from initializing another owned value:

```text
let second = first
let second = ^first
```

An ordinary owned binding always contains an independent value, never a hidden
alias to `first`. The first form requires permitted implicit copying; a noncopyable value needs
transfer or an explicit construction/copy operation. Do not silently introduce cloning,
copy-on-write, or shared ownership. Decide which types permit implicit copies and what their
observable copy semantics are; copyability must not mean that every copy is cheap.

Allow explicit transfer uniformly for copyable and noncopyable types, with the
source unavailable afterward in both cases. This makes `return ^value` in an owning generic
operation independent of a substitution's copyability. Do not reject transfer for copyable types
or silently change it to a non-invalidating copy. Physical
copy/move elimination remains possible when it preserves these meanings and observable cleanup.

### 2. Permissions after Receiving Ownership

A transferred parameter grants read, update, and further-transfer permission:

```text
func normalize(^value: Data): Data {
    value.normalize_in_place()
    return ^value
}
```

Do not require an extra mutable local solely to update an exclusively owned parameter. Ownership
already prevents the caller from continuing to access the transferred place. Distinguish this
permission to update owned contents from local binding reassignment, and define how each interacts
with `let`/`var`. Resource-specific restrictions and explicitly shared external state still apply.
An input cannot be strengthened to update or transfer; an update cannot take ownership and leave
the caller's place uninitialized. Define a safe replacement/exchange operation where necessary.

An update must leave a valid initialized value on failure, but need not restore the previous
value. There is no automatic rollback: an operation may update part of a valid structure before
returning an error. Transactional behavior requires its own API contract. A transferred parameter,
by contrast, remains the callee's responsibility even when the operation fails.

### 3. Argument Preparation and Access Activation

Consider a consuming first parameter and a fallible later argument:

```text
func send(^packet: Packet, stamp: Stamp): void
send(packet, make_stamp()?)
```

Use exactly-once, left-to-right operand evaluation, reservation of existing source places
during preparation, and activation of transfers/exclusive updates only after all arguments are
ready, at invocation. If `make_stamp()` fails during preparation, the planned transfer of `packet`
has not occurred. If `send` begins and then fails, ownership has transferred. This is not rollback
of earlier expression side effects, owned temporary construction, or separate ownership operations.
Their cleanup and effects remain defined by evaluation order.

Reservations must prevent an intervening move, destruction, replacement, or storage invalidation
of a prepared place. They may allow temporary reads that finish before exclusive activation:

```text
buffer.append(buffer.len())
```

By contrast, retaining overlapping input and update access throughout one invocation must be
rejected unless their independence is proved. Define snapshots for copied operands, nested calls,
two transfers of one place, disjoint fields/elements, partial initialization, and temporary cleanup.
Do not promise that every expression mentioning the same owner twice is accepted. These rules
must also work for receivers, indirect calls, and asynchronous operation construction.

### 4. Independent Results versus Access to Parts

Determine what binding a window into existing storage means, rather than merely selecting its
type spelling. An ordinary owned result is independent of its input's storage.
An operation exposing a field, element, or range instead has a distinct projection contract;
creating, passing, and retaining that access must have a defined owner dependency. Do not choose
between a projection and an owning copy according to whether the caller later stores the result.

Close indexing, iteration, text/slice adaptation, and a stored window using the same distinction.
For persistent relationships, compare an owner plus a checked range, an explicit independent copy,
and deliberate sharing. State which owner operations invalidate each relationship and whether
ownership transfer preserves it. A new name for unrestricted stored references is insufficient.
Exact projection syntax and the permitted forms of persistent access remain open.

### 5. Deferred Access and Cancellation

For an asynchronous input, distinguish constructing pending work from executing it:

```text
let task = analyze(data)
update_data(data)
await task
```

Retained input/update dependencies begin when the pending operation is constructed,
not at its first execution or `await`. Transfer parameters become owned by that pending operation
at construction under the same preparation rules as immediate calls. A conflicting update while
the task retains input access is invalid; moving or dropping the task must not lose the dependency.
Completion or cancellation releases retained access after required cleanup, unless a returned
projection or other result explicitly retains the dependency. Define cancellation order, early
drop, returned dependencies, and escaping captures together.

Apply the adopted capture inference to the same rights and retention rules. Do not silently copy,
share, or extend a resource lifetime to make an escaping closure or future valid. Diagnose the
conflicting operation and the retaining task/capture rather than exposing internal lifetime
equations as the ordinary explanation.

### 6. Contracts through Abstraction

Specify the mode of every parameter and receiver in interface requirements, generic forwarding,
function values, and erased callbacks, together with the invocation permission of captured state.
Preserve these contracts without inspecting bodies to decide a call's meaning.
An input-only wrapper cannot forward its input to a consuming operation. An owned value can supply
temporary input or update access without surrendering ownership unless the selected contract
requires transfer. Close callable-type syntax and conformance using that same permission model.

Concrete specialization may optimize transport and cleanup; it must not change the public mode
because a type is copyable or a caller has no later use. Treat mode strengthening as an API
contract change. Shared resource handles also need explicit identity/effect contracts: reading a
handle does not by itself imply that files, locks, or remote services cannot change.

Prioritize detailed closure of decisions 1–3: they determine ordinary bindings, owning functions,
and the state visible after failure. Then use windows, iterators, escaping closures, futures,
resource handles, and generic callbacks to qualify decisions 4–6. For every rule, compare a valid
program, a conflicting program, failure/cancellation behavior, and the runtime work actually required. The objective is
fewer user decisions with stable semantics, not fewer visible markers at the expense of hidden
ownership choices.

Still open are the set and declaration of implicitly copyable types; binding reassignment versus
owned-content update; safe replacement/exchange syntax; nested reservations, snapshots, partial
initialization, and temporary cleanup; projection syntax and persistent-access forms; cancellation
order and dependent-result contracts; and callable-type syntax and conformance details. These are
closure work within the adopted decisions, not permission to select hidden copies, delayed
ownership transfer until first `await`, automatic rollback, or body-dependent public modes.

## Research Context and Independent Evaluation

[Implementation Strategies for Mutable Value Semantics](https://www.jot.fm/issues/issue_2022_02/article2.pdf)
studies a model restricting first-class references while allowing independent mutable values and
efficient native compilation. Its strategies include copy-on-write for dynamic containers; that
cost model is not automatically adopted here.

Hylo describes explicit
[parameter passing conventions](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#parameter-passing-conventions)
for input, mutation, and consumption, and emphasizes
[independent values and exclusive mutable access](https://docs.hylo-lang.org/language-tour/bindings).
These are evidence that operation-oriented models deserve evaluation, not authorities for
Nocter's syntax. In particular, Nocter's adopted model keeps caller-side transfer explicit.

The model still needs lifetime and access-validity analysis internally. It seeks to reduce the
number of concepts exposed as ordinary source types, not eliminate the underlying safety facts.
If ordinary programs still require reasoning about hidden captured accesses and invalidation as
often as before, the terminology change has not met the objective.

## Cases That Must Decide the Model

- Calling a reader repeatedly with one move-only value retains the original owner, without an
  owning clone or reference-count adjustment inserted just to pass the argument.
- A call that updates the caller's configuration states that permission visibly. A contract change
  cannot silently add mutation or consumption to an unchanged call.
- A transferred job can be queued or returned; the original owned place is unavailable afterward.
- Owned binding initialization never silently creates an alias. Implicit copies require a permitted
  type; explicit transfer invalidates both copyable and noncopyable sources, including in generics.
- An owned parameter can be updated without an intermediate mutable local. An update that fails
  leaves a valid value but need not undo completed changes; a consuming operation owns cleanup.
- Failure while preparing a later argument leaves an earlier reserved transfer source owned by the
  caller. Failure after invocation does not return transferred ownership. Earlier side effects and
  constructed temporaries follow their defined evaluation and cleanup rules without rollback.
- A factory cannot return a dangling input-dependent access as an independent owned result.
- Two disjoint element updates can coexist when proved safe; overlapping or invalidated
  projections cannot. Evaluation order and failure behavior remain specified.
- A long-lived text window, iterator, and stored callback each have an understandable policy for
  owner retention and invalidation, without requiring arbitrary lifetime equations in ordinary code.
- Deferred calls distinguish construction, active execution, completion, and cancellation. A live
  input dependency is diagnosed at a conflicting operation, not repaired with implicit sharing.
- Unique resources, locks, cleanup callbacks, and observable destructors retain their defined
  completion and release behavior across failure and cancellation.
- Generic APIs, interface operations, receiver methods, closures, and opaque results use one model
  instead of accumulating unrelated exceptions.

Judge these cases by semantic clarity, local reading, source obligations, soundness, and the
execution work the compiler can justify removing. Compiler and standard-library rewrite size is
not an objection to a better model. Proving a universally optimal implementation is not required
to select a coherent model, and Rust comparison is not an acceptance criterion.
