# Values and Access Operations

## Status and Purpose

The conceptual input/update/transfer model is adopted for v2.0.0; implementation and detailed
specification remain pending. The words and declaration shapes below illustrate semantics;
exact spelling is not adopted grammar. The [v2.0.0 plan](../milestones/v2.0.0.md) owns adopted
decisions. This model replaces borrow terminology and `&` type notation without treating
implementation effort, short-term delivery, or Rust comparisons as constraints.

Explain ordinary programs through values and the operations permitted on them:
input, update, and transfer. Separate these operations from the physical decision to pass an
address, copy bits, allocate storage, or reuse a location. Preserve defined behavior and sound
access information without requiring a first-class reference type in ordinary source.

This is an adopted replacement model, not permission to implement the deferred type-driven
automatic-borrowing or implicit-return-transfer proposals in the existing model. Its detailed
closure requires coherent semantics for projections, stored data, closures, asynchronous work,
and resources; a keyword
substitution alone would not achieve the objective.

## Adopted Operation Model

| Operation | Caller-visible meaning |
| --- | --- |
| Input | Supplies read access; retains ownership of the supplied value. |
| Update | Grants temporary exclusive access to update the original writable place. |
| Transfer | Transfers an owned value; its previous owned place is unavailable until valid reinitialization. |

An unmarked parameter consistently means input. An existing owned argument is not silently consumed
because a callee happens to need ownership. Updating and transferring require matching explicit
operations at the call and contract. Existing copyable and newly constructed values need detailed
rules; the transfer example deliberately uses an existing move-only value.

This differs from eliding `&` according to a selected parameter type while leaving plain `T`
parameters consuming. Here the unmarked operation has one meaning across contracts. The price is a
major change to parameter semantics, which must be evaluated as a complete model.

Update permission is an observable contract, not an optimization guarantee like the removed
`noalloc` modifier. Avoid reusing `var` for it: a mutable local binding and access to the caller's
original place are different operations. Keep transfer explicit in calls and existing owned
returns. Initial `edit` and `move` sketches name those operations; their exact source spelling is
now under separate evaluation.

## Recommended Single-Symbol Spelling

**Recommendation only; punctuation is not adopted.** Use no marker for input, `&` for update,
and `^` for transfer. Prefer matching markers before parameter names and arguments:

```text
func inspect(value: Config): void
func reset(&value: Config): void
func submit(^value: Job): void

inspect(config)
reset(&config)
submit(^job)
```

These markers describe an operation on a value or place, not a pointer type. In the proposal,
`&T` and `&+T` do not remain ordinary borrow types, `&value` does not create a storable reference,
and `let alias = &value` is not an escape hatch for shared mutable identity. Input remains
unmarked; update and transfer remain explicit irrespective of hidden implementation facts.

In the same proposal, transfers into owned bindings, stored fields, and results use the transfer
marker, for example `let next = ^previous` and `return ^value`. Constructor temporaries, generic
copyable types, partial extraction, repeated markers, and statement boundaries need precise
closure. The marker must never request a hidden deep copy. A transfer of a newly created value
can directly forward its storage; it must not require a redundant physical move merely because
the programmer supplied an explicit operation marker.

If this symbol set is adopted, prefer one canonical source spelling per operation rather than
retaining `edit`/`move` as equivalent keyword aliases. Diagnostic text and documentation should
continue to name input, update, and transfer in words.

### Receiver and Invocation Placement

For methods, recommend placing the call-side mode after the member-selection dot so it clearly
applies to the receiver operation:

```text
impl Buffer {
    method self.len(): usize
    method &self.append(value: u8): void
    method ^self.finish(): Product!
}

buffer.len()
buffer.&append(42)
let result = buffer.^finish()?
```

The ordinary call reads its receiver, `.&` updates it, and `.^` transfers it. Method declarations
use the same mode before `self` as parameter declarations use before a name. These remain methods;
the spelling does not introduce UFCS or a second top-level-function call form.

Define prefix `^` to transfer the selected value after its call/member/index chain, before an
outcome suffix. Thus `^make()` forwards the newly produced owned result, `^result?` means
`(^result)?`, and `^buffer.finish()` applies to the result rather than the receiver. Selecting
the receiver mode at `.` makes `buffer.^finish()` a distinct, readable operation. Selection of an
indexed place does not by itself authorize ownership extraction; the operation must preserve the
container's initialization and cleanup contract. Complete precedence, generic method arguments,
computed receivers, callback invocation, operator contracts, and forwarding
still require grammar decisions. This method-selector shape is a proposal, not permission to
implement a special receiver exception before the complete invocation model is closed.

Access activation during argument evaluation also needs closure. For example,
`buffer.&append(buffer.len())` must be evaluated against a defined input/update sequencing rule,
not rejected or accepted accidentally because a prefix happened to be visited first. Preserve
exactly-once evaluation and reject genuinely overlapping retained accesses.

### Alternatives and Conflicts

- **`&` for update:** compact and compatible with the idea of operating on the supplied place.
  Its old Nocter meaning was readonly borrowing. Adoption therefore requires retiring that old
  meaning coherently, not leaving two interpretations in the language. The symbol by itself does
  not eliminate the need to teach the new update operation.
- **`^` for transfer:** no existing expression-operator meaning in the current Nocter grammar.
  Keep it dedicated to ownership transfer rather than introducing another use for `!`, `?`, or
  comparison/generic delimiters. It is a learned notation, not a universally obvious glyph for
  transfer. The existing bitwise APIs do not require a binary `^` operator.
- **`~` for update:** avoids reusing the old borrow marker and has no existing Nocter expression
  meaning. It has a weaker association with updating the supplied place. Keep `~/^` as the main
  alternative if old/new `&` confusion outweighs the benefit of the proposed pair.
- **`!` for update:** reject for this proposal because prefix logical negation and postfix forced
  unwrap already use it. Argument types must not decide whether one written operator means a
  boolean expression or an update request.
- **`>` for transfer:** a directional glyph is attractive, but the token already participates in
  comparison and generic closing syntax. Prefer a dedicated marker for a common source operation.

The existing grammar uses `^` only in explanatory mathematical notation and `~` in its meta-grammar
or path examples, not as Nocter expression operations. Verify token recognition and newline rules
against [Lexical Grammar](../../../spec/language/lexical-grammar.md) and
[Expression Precedence](../../../spec/language/syntactic-grammar.md#expression-precedence) when
closing the selected spelling. The compiler must resolve modes from syntax, not reinterpret a
marker after type checking. In the proposed model, `&&` need not split into nested borrow prefixes.

## Inputs

An input may be inspected for the duration of the operation. Through that input the callee cannot
update the supplied place, transfer its ownership, or retain a non-owning access beyond the
allowed operation duration. Returning or storing an independent scalar copy remains distinct from
retaining access to the original storage. Returning an independent owned result requires
construction, an explicitly permitted copy, or a transferred input; the compiler must not insert
an owning clone to make an invalid return work.

Input permission does not imply purity. The operation may have other effects through explicit
capabilities or external services. Define the treatment of shared handles and external resource
identity rather than pretending a readonly argument makes the outside world immutable.

The compiler may transport a small value in registers, pass a larger value's address, inline the
operation, or specialize it. These choices must preserve source identity observations, validation,
and destruction. No source-level object copy or allocation is required solely to spell an input.

Text and slice inputs are important cases, not an afterthought. Investigate `text: str` and,
using the proposed symbol, `&elements: [T]` as access to text or an element sequence without making
`&str` or `&+[T]` ordinary value types. Owned storage such as `String` or `Vec<T>` remains a separate question from
the shape being accessed. Close adaptation from storage to an input/projection and the distinction
between accessible unsized data and independent stored results. Removing `&` cannot silently turn
a view into an allocating copy or leave generic position rules unexplained.

For immediate calls the input access normally ends when the operation returns. For deferred
operations its duration needs a separate precise rule: a candidate is completion or cancellation
of the computation. Call construction must not be confused with completion. A pending operation
can therefore prevent a conflicting update even though ownership remains with the caller.

## Updates

An update targets a writable place. During the access, overlapping conflicting access is invalid;
provably disjoint places may be used independently. Updating a field, assigning a replacement, or
passing a temporary update onward must retain one access identity and correct initialization and
cleanup. The callee cannot extract the caller's owned value and leave an uninitialized place on
return, failure, or cancellation. Replacement needs a defined safe operation, not a loophole in
the transfer rules.

The compiler selects layout and passing strategy while preserving the caller-visible update. A
signature change from input to update requires a corresponding call change; it cannot silently
make an ordinary unmarked call mutate its argument.

Temporary values, method receivers, compound operations, and forwarding through callbacks need
the same operation model. Exact receiver and forwarding syntax remains open; do not invent a
different ownership rule for each callable kind.

## Transfers

Transfer authorizes the callee to store, return, or destroy the owned value. After transfer, the
caller cannot use the previous owned place without valid reinitialization. Keep the distinction
between semantic transfer and physical movement of bytes. Direct result construction and storage
reuse are implementation choices.

The model keeps explicit owned returns, initially illustrated as `return move value` and proposed
symbolically as `return ^value`. It does not use optional last-use optimization to decide whether
a source expression transfers ownership. Generic
substitutions, copyable values, partial moves, and uniform type-family cleanup must be closed
before generalizing the examples into grammar.

## Parts of Values Instead of Freely Stored References

The main conceptual reduction comes from not treating every temporary access as an ordinary
storable value of type `&T` or `&+T`. A field, collection element, or projected subrange can instead
identify a place on which an input or update operation acts. A projection exposes a part of an
existing value; it is not an ordinary function returning an independent owned result.

Investigate structured access to such projections. The owner must remain valid during use, and an
operation that could invalidate the selected storage must be rejected unless non-conflict is
proven. Passing an element directly to an input operation need not manufacture an owned element.
Binding or storing an independent owned element must not quietly become a stored alias instead.

Do not merely rename `&T` to `View<T>` and keep all the same general storage/lifetime obligations.
Determine which long-lived relationships the language actually needs, and give them explicit
semantics. Options include owned results, structured projections, an owner plus an index/range,
and deliberate shared ownership through a specified API. They have different identity,
invalidation, retention, and runtime-cost consequences; none is an adopted universal fallback.

Closures and futures are essential distinguishing cases. An escaping closure may need owned
captures; an operation retaining read access needs a proved duration and storage relationship.
Moving a container must not invalidate an internal reference by accident. A future must release
retained access in the defined cancellation order. The compiler cannot silently prolong a file,
lock, or user destructor's lifetime to make the model convenient.

## Research Context and Independent Evaluation

[Implementation Strategies for Mutable Value Semantics](https://www.jot.fm/issues/issue_2022_02/article2.pdf)
studies a model restricting first-class references while allowing independent mutable values and
efficient native compilation. Its strategies include copy-on-write for dynamic containers; that
cost model is not automatically adopted here.

Hylo describes explicit
[parameter passing conventions](https://hylo-lang.org/docs/user/language-tour/functions-and-methods/#parameter-passing-conventions)
for input, mutation, and consumption, and emphasizes
[independent values and exclusive mutable access](https://docs.hylo-lang.org/language-tour/bindings).
These are evidence that operation-oriented models deserve evaluation, not authorities for
Nocter's syntax. In particular, the illustrated proposal keeps caller-side transfer explicit.

The model still needs lifetime and access-validity analysis internally. It seeks to reduce the
number of concepts exposed as ordinary source types, not eliminate the underlying safety facts.
If ordinary programs still require reasoning about hidden captured accesses and invalidation as
often as before, the terminology change has not met the objective.

## Cases That Must Decide the Model

- Calling a reader repeatedly with one move-only value retains the original owner, without an
  owning clone or reference-count adjustment inserted just to pass the argument.
- A call that updates the caller's configuration states that permission visibly. A contract change
  cannot silently add mutation or consumption to an unchanged call.
- A transferred job can be queued or returned; the original owned place is unavailable afterward.
- A factory cannot return a dangling input-dependent access as an independent owned result.
- Two disjoint element updates can coexist when proved safe; overlapping or invalidated
  projections cannot. Evaluation order and failure behavior remain specified.
- A long-lived text window, iterator, and stored callback each have an understandable policy for
  owner retention and invalidation, without requiring arbitrary lifetime equations in ordinary code.
- Deferred calls distinguish construction, active execution, completion, and cancellation. A live
  input dependency is diagnosed at a conflicting operation, not repaired with implicit sharing.
- Unique resources, locks, cleanup callbacks, and observable destructors retain their defined
  completion and release behavior across failure and cancellation.
- Generic APIs, interface operations, receiver methods, closures, and opaque results use one model
  instead of accumulating unrelated exceptions.

Judge these cases by semantic clarity, local reading, source obligations, soundness, and the
execution work the compiler can justify removing. Compiler and standard-library rewrite size is
not an objection to a better model. Proving a universally optimal implementation is not required
to select a coherent model, and Rust comparison is not an acceptance criterion.
