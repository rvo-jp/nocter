# v0.65.0 Phase 4 Stateful-routing Review

**Result: complete with no open Phase 4 finding (2026-09-21).** One generic router now owns one
explicit application-state value and lends that exact value to the selected handler. The complete
HTTP service exercises this contract through concurrent dispatch without a global, state clone, or
second route-selection path.

## Reviewed Surface

The review followed the public `Router<State>` and `Handler<State>` declarations through route
storage, deterministic selection, erased-callable invocation, future provenance, handler
cancellation, linear request and connection ownership, the complete loopback service, editor
projection, and current behavior guidance. Shared storage and synchronization internals were
checked only at their public boundary; the router does not inspect those representations.

## Authority Trace

| Responsibility | Sole authority | Consumers |
| --- | --- | --- |
| application-state ownership | `Router<State>` | application setup and shutdown |
| shared-mutation policy | the application-selected `State` type | handlers |
| route validation and precedence | `Router<State>` route storage and dispatch | HTTP applications |
| heterogeneous invocation | `Handler<State>` erased callable contract | router dispatch |
| handler lifetime over state | checked `from state | request | route` provenance | ownership, future lowering, cancellation |
| task creation, capacity, and draining | application `TaskGroup` | complete service |

The router borrows its state only after route selection. Unmatched requests therefore retain their
existing ownership without acquiring application-state provenance. A selected handler receives
`&State`, the owned request, and the owned route match in one call. Dispatch awaits that future
directly, ending the state loan before it returns a `RouteDispatch` value.

## Corrected Findings

The first focused compile exposed two contract details rather than runtime workarounds. Generic
constructor inference needed an explicit `Router<usize>.new` receiver in the standard test,
preventing an unrelated default integer type from becoming accidental state. Recovering state
could not honestly be marked `noalloc`: consuming a router also destroys arbitrary erased handler
environments, whose destruction contract is not allocation-free. Removing that guarantee preserves
the stronger rule that effect annotations describe the complete operation, including implicit cleanup.

The public HTTP service previously repeated its request timeout inside handlers and passed another
copy beside the router to connection handling. It now constructs one `ServiceState`, obtains the
connection policy through `Router.state`, and receives the same state borrow in every selected
handler. This is observable evidence that the generic API is useful, not a compile-only container.

## Behavioral Evidence

The standard HTTP target still executes all 57 native cases. Its route-registration case now
constructs `Router<usize>`, erases state-aware handlers, rejects equal-precedence ambiguity, and
recovers the original state after handler destruction. The complete public-package suite executes
the updated seven-connection HTTP service, including concurrent handler tasks, request reuse,
failure, malformed input, timeout, 404, and 405 outcomes.

The HTTP-service editor test resolves generic `Router<State>.dispatch`, the generic handler alias,
its implementation source, and capability-filtered `dispatch` and `state` completions. Consuming
and mutable methods remain absent from a readonly router borrow.

## Conclusion

No compiler or editor special case was introduced. Routing knows only the handler contract and a
borrow of its own state field; handlers know neither route storage nor selection internals. The
application remains the sole owner of task concurrency and synchronization choices. Replacing
route storage, state representation, handler implementation, or executor internals independently
does not require another responsibility to inspect that implementation.
