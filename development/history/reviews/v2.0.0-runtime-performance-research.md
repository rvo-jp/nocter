# v2.0.0 Runtime Performance: Research and Feasibility

## Scope and Conclusion

The subsequent design decision makes Nocter's own semantic and execution quality the objective.
Rust comparisons, relative-speed thresholds, implementation effort, and short-term delivery are
not roadmap gates. Earlier comparison-oriented recommendations below are optional context for
interpreting research, not current requirements. The milestone owns this revised direction.

Research reviewed as of 2026-11-07. Recent results from 2024–2026 are considered alongside the
foundational value-semantics work relevant to Nocter's ownership discussion. This is a selected
primary-source review, not an exhaustive literature survey. It concerns execution of generated
programs, not speed of the compiler executable.

Large gains over particular optimized Rust programs are a plausible research objective. A broad
promise of several-fold improvement over carefully optimized Rust is not supported by the evidence.
The strongest opportunity is to remove work or memory traffic using high-level semantics and
whole-program knowledge. Independent instruction encoding alone does not create that advantage.

These judgments are inferences for Nocter, not measured Nocter results. No Rust comparison or
research artifact was executed for this review. Its recommendations do not adopt new source
semantics, an optimizer implementation, mutable value semantics, automatic copying, ARC, or GC.
They do not reactivate the deferred call-site automatic borrowing or return-`move` omission.
The [v2.0.0 plan](../milestones/v2.0.0.md) owns adopted direction.

## What the Research Actually Demonstrates

Results below use different baselines, machines, workloads, and correctness conditions. Their
percentages cannot be multiplied, pooled into one average, or presented as speedups over Rust.

| Work | Reported evidence | Relevance and limit for Nocter |
| --- | --- | --- |
| [Partial Evaluation, Whole-Program Compilation, PLDI 2025](https://pldi25.sigplan.org/details/pldi-2025-papers/14/Partial-Evaluation-Whole-Program-Compilation) | Specializing existing interpreters yields reported 2.17x and 1.84x speedups for SpiderMonkey and Lua respectively. | Supports specializing a general evaluator against known programs or configuration. These are interpreter comparisons, not improvements over optimized native Rust or a top-tier JIT. |
| [MEMOIR, CGO 2024](https://users.cs.northwestern.edu/~simonec/files/Research/papers/MEMORY_CGO_2024.pdf) | Reports a 26.6% speedup from dead-element elimination on SPECINT 2017 `mcf`, and 20.8% lower peak memory through layout-related transformations. | Shows why keeping collection semantics above raw memory matters. The performance study manually applies the described transformations and uses older native compiler baselines; it is not a general automatic-optimizer or Rust result. |
| [Minotaur, OOPSLA 2024](https://arxiv.org/abs/2306.00229) | Verified SIMD superoptimization reports average speedups of 1.5% on SPEC CPU 2017 and 7.3% on GMP on Intel Cascade Lake. | Demonstrates remaining opportunities beyond LLVM, but modest suite averages and an x86 SIMD target do not establish an ARM64 or several-fold application advantage. |
| [Mind the Abstraction Gap, OOPSLA 2025](https://2025.splashcon.org/details/OOPSLA/42/Mind-the-Abstraction-Gap-Bringing-Equality-Saturation-to-Real-World-ML-Compilers) | Equality saturation integrated into XLA reports an average 3.45% speedup across its suite and a maximum 56.26% for NasRNN on CPU. | Supports searching combinations of fusion and layout choices. It still needs a global cost model and concerns ML graphs, not arbitrary imperative programs. |
| [CIRBench, ICML 2026](https://proceedings.mlr.press/v306/yang26m.html) | Across 800 IR instances and six evaluated LLMs, the study reports many analysis/rewrite failures and median performance below the compiler baseline, despite a maximum 4.96x speedup over `-O3`. | Supports investigating missed opportunities with validation. A best case is not evidence that an LLM optimizer reliably improves ordinary builds. |
| [Implementation Strategies for Mutable Value Semantics, 2022](https://www.jot.fm/issues/issue_2022_02/article2.pdf) | Explores efficient native implementation of independent mutable values, restricting first-class references and using stack storage and copy-on-write strategies. | Supports examining a simpler user model with strong optimization facts. It does not prove that arbitrary sharing is free, eliminate every runtime ownership operation, or establish a Rust speedup. |

The [MEMOIR evaluation](https://users.cs.northwestern.edu/~simonec/files/Research/papers/MEMORY_CGO_2024.pdf)
also reports a 5.1% execution-time increase for `deepsjeng` despite reduced memory use. A smaller
representation is therefore not automatically a faster representation. Preserve the complete
measurement, including regressions and the manual-transformation methodology.

The pattern is important: improvements to an already mature optimizer often have small averages
and larger outliers. Removing interpretation, unnecessary collection elements, intermediate data,
or other structural work can produce a different scale of improvement. No single result proves
that a new general-purpose compiler will routinely surpass tuned Rust by the same factor.

## Interpreting Rust Comparisons When They Are Requested

Rust already supports [constant evaluation](https://doc.rust-lang.org/reference/const_eval.html),
[LTO, target selection, and other code-generation options](https://doc.rust-lang.org/rustc/codegen-options/index.html),
and [profile-guided optimization](https://doc.rust-lang.org/rustc/profile-guided-optimization.html).
Adding constant evaluation, cross-function optimization, or target-aware generation to Nocter is
necessary capability, not by itself evidence of an advantage.

The [ownership rules](https://doc.rust-lang.org/book/ch04-01-what-is-ownership.html) are checked at
compile time. Removing their surface syntax does not remove an existing runtime borrow-checking
tax. A different source model can simplify programming and improve available facts, but it must
retain sufficiently strong lifetime, alias, and mutation guarantees to exploit them.

If a Rust comparison is separately requested, distinguish these three questions:

1. Equivalent ordinary optimized implementations, with normal usage patterns and libraries.
2. Matched algorithm, input knowledge, safety/failure behavior, target features, and execution model.
3. A carefully tuned Rust implementation, allowing an expert to exploit the same domain knowledge,
   layout, specialization, and suitable libraries. Record extra implementation effort separately.

Winning the first comparison can be a meaningful product advantage even if the third narrows the
gap. Do not describe a generic-library versus specialized-kernel comparison as a fundamental
language limit. Rust can often express a specialized algorithm or layout manually; Nocter's
opportunity is to obtain it automatically from simpler ordinary code.

## Most Promising Sources of a Large Advantage

The following priorities are recommendations, not predictions of a numerical speedup.

### 1. Specialize Away Runtime Generality

Use known schemas, route tables, formats, callback witnesses, and configuration to eliminate
interpretation, repeated lookup, generic branches, and unnecessary intermediate objects. A
schema-aware decoder can be a better experiment than another scalar arithmetic benchmark.
Keep the actual input data dynamic; do not replace the measured task with a precomputed answer.

Distinguish evaluating an entirely known expression from partial evaluation, where known inputs
simplify the computation that remains for unknown inputs. The latter is important for meaningful
application speedups. Cross-function effect and origin summaries are prerequisites. Bound code
growth and compilation work; excessive specialization can harm instruction-cache behavior.

### 2. Keep Collections and Data Relationships Visible Longer

Represent operations on collections, fields, slices, and ownership explicitly before committing
to raw addresses and fixed storage. Investigate eliminating unused fields/elements, fusing
producer/consumer chains, avoiding temporary materialization, removing indirections, and selecting
array-of-records versus column-like layouts where semantics permit.

This is particularly compatible with Nocter's whole-program model and adopted representation
freedom. Public contract boundaries and direct `see` remain human visibility boundaries, not
optimization barriers. Keep one selected semantic operation and explicit effect dependencies;
later optimization must not reinterpret names or assume an arbitrary ordinary library method
implements a familiar collection operation merely because of its spelling.

Do not make new unsafe assumptions about observable addresses, views, external layouts, user
destructors, callbacks, or error timing. A collection operation must have a proved summary or
verified contract before an optimizer reasons about it abstractly.

### 3. Eliminate Managed Work through Lifetime and Uniqueness Proofs

Investigate frame/environment placement, removal of nonescaping allocations, reuse of dead
storage, destination construction, and elimination of redundant copies. This can reduce both
allocator overhead and cache/memory traffic.

The critical facts are validity, identity, uniqueness, access conflicts, and cleanup obligations;
they need not be spelled using Rust's syntax. A value-oriented model may make them easier to
derive. But automatic sharing, copy-on-write, and reference counting have costs when uniqueness
cannot be proven. Compare ordinary data processing separately from long-lived borrowed views,
shared mutation, and file/lock protocols before changing the source model.

### 4. Combine Safety Proofs with Loop and Target Optimization

Permit proofs after specialization and inlining, then use proven ranges and disjointness for
check elimination, loop transformations, and SIMD where valid. Preserve exact trapping and
floating-point behavior. Reassociation or vector execution is not legal merely because it is
faster; scalar failure ordering and observable effects still matter.

For a large end-to-end win, target a measured memory or computation bottleneck. Once an
implementation already approaches the relevant throughput or memory-bandwidth bound, instruction
selection alone has little room to produce a several-fold improvement. Runtime specialization or
guarded fast paths may help when inputs vary, but they still need a correct general path.

### 5. Use Search and Synthesis Selectively

Equality saturation and verified superoptimization are promising for hot loops and specific
operation families after the ordinary optimizer is competent. Cost models must include downstream
layout, register pressure, code size, and the actual ARM64 target. Cap search time and retain
validated results with their exact semantic and target assumptions.

LLMs can propose optimization candidates or help investigate missed opportunities. A production
pipeline still needs deterministic validation and a reliable fallback. Do not make correctness or
ordinary-build performance depend on an unvalidated generated rewrite.

## Current Nocter Constraints Relevant to Feasibility

The inspected current sources establish a development gap, not measured performance ratios:

- The [Machine optimizer](../../compiler/crates/nocter-machine/src/optimization.rs) performs local
  folding, control-flow pruning, storage forwarding/proofs, drop-flag processing, and storage alias
  work. Its [contract](../../compiler/crates/nocter-machine/README.md) documents conservative call
  barriers and same-block whole-storage forwarding. This inspection is not an exhaustive proof
  that every advanced transformation is absent elsewhere.
- [MIR](../../compiler/crates/nocter-mir/README.md) and Machine preserve checking-owned bounds and
  arithmetic dispositions. Current rules do not permit a later stage to strengthen them. The
  adopted v2.0.0 later-proof direction must become a concrete obligation/evidence protocol.
- The [erased-callable ABI](../../../spec/platform/abi-and-layout.md#erased-callable-layout) owns a
  mapped environment, and [async producers](../../../spec/language/asynchronous-computations.md#structured-ownership)
  use an allocation-backed representation. Removing avoidable costs can improve Nocter, but
  removing one's own overhead does not automatically beat a Rust implementation that avoided it.
- [Regions](../../../spec/language/memory-and-regions.md#lexical-regions) currently release a list
  of individually mapped allocations. A region is therefore not currently synonymous with a
  bump allocator or a proof of fewer allocation system calls.
- The [native benchmark runner](../../benchmarks/README.md#native-product-measurements) compares
  Nocter compiler variants and validates representative application outputs. This review has not
  established a retained, controlled Rust comparison or executed a new benchmark.

Nocter needs strong ARM64 instruction selection, register allocation, loop optimization, and
appropriate SIMD generation as a foundation. LLVM independence provides control and deployment
benefits, while also leaving this engineering work to Nocter. High-level transformations cannot
compensate for poor generated code on every workload.

## Execution Experiments

Assess Nocter execution and individual transformations with representative dynamic inputs,
correctness evidence, generated-operation inspection, and measurements. The earlier suggested
2x Rust-relative research threshold is superseded; no external language comparison is required.

Start with:

- static-schema decoding of dynamic input, with and without specialization;
- collection pipelines and graph/record processing with measured intermediate data and cache costs;
- asynchronous pipelines and callbacks, measuring frame/environment allocations and cancellation;
- numeric and byte-processing controls, to expose backend quality.

Use the existing [measurement boundary](../../benchmarks/methodology.md). Record source and binary
identities, compiler versions/options, CPU and OS, dynamic inputs, outputs, algorithms, core/thread
counts, allocations, peak memory, copied bytes where measurable, code size, compilation resources,
and repeated timing distributions. Measure startup and steady execution separately where relevant.
Match supported instructions and do not compare a parallel program with a single-threaded one
under the same claim.

Nocter's [always-on safety rules](../../../spec/language/control-flow.md#safety-checks-and-build-modes)
include integer overflow and bounds checks. Rust's
[options](https://doc.rust-lang.org/rustc/codegen-options/index.html) permit different overflow and
panic policies; if such a comparison is requested, record them and match safety conditions. Do not imply that one option
makes all fault reporting and cleanup semantics identical. Test observable errors and cancellation
as well as successful results. Do not change floating-point accuracy, input validation, durability,
or error handling to win a timing comparison.

Attribute improvements with ablations: disable specialization, layout changes, allocation reuse,
and later safety proofs separately. Do not multiply each pass's isolated gain into a hypothetical
total. Use representative training inputs and distinct evaluation inputs if using PGO or tuning.

Whole-program speedup depends on how much execution is improved. If an optimized fraction `p` runs
`s` times as fast and the rest is unchanged, the idealized total speedup is
`1 / ((1 - p) + p / s)`. For example, making 80% of execution four times faster yields 2.5x overall.
If only 20% can improve, the ceiling under these assumptions is 1.25x even with that fraction removed.
These are illustrative arithmetic, not observations of Nocter or Rust.

## Recommendation

Prioritize high-level partial evaluation, collection/data representation, and ownership-aware
storage optimization, supported by a competent ARM64 backend and explicit correctness evidence.
Treat syntax reduction and fewer ownership concepts as usability goals whose performance effects
must be measured, rather than assuming a shorter language or absent borrow notation is faster.

The current objective is coherent source semantics and justified removal of unnecessary execution
work while preserving concise source and checked behavior. Evaluate models independently of
implementation burden or near-term delivery. Published comparisons can inform techniques, but
relative superiority over Rust is neither the definition of a good model nor a required milestone.
