# v2.0.0 Partial Payload Resource Checkpoint

Date: 2026-11-09. Scope: selected logical places and sparse partial payloads in the existing
checking-owned resource ledger. This is implementation evidence, not nominal source acceptance.

## Contract and Authority

[Value Access](../../../spec/language/value-access.md#return-replacement-and-cleanup) owns partial
moves, restoration and cleanup. [Nominal value payloads](../../../spec/language/structs-and-enums.md#future-direction-v2-0-0-nominal-value-payloads)
own the closed record shapes. The crate READMEs own the model, declaration-projection and resource
implementation contracts; the [private handoff](../../architecture/pipeline/value-access-declarations.md)
owns their cross-stage authority boundary.

Model field paths identify logical containment independently of names, offsets or access rights.
Declaration projection checks every field against its exact containing record. The same resource
ledger used by ordinary body checking now owns complete builtin/record payloads and sparse moved
selections. There is no second record owner store or alternate scalar cleanup implementation.
Existing value moves, argument transfers, evaluation cleanup and assignments use this ledger;
whole-owner replacement now uses its unified replacement operation.

## Selected Invariants

A partially moved record retains its containing slot. Availability is queried for the selected
place: a containing value becomes incomplete, but initialized disjoint fields remain available.
Missing siblings do not merge into a missing parent, because a writable containing slot still
permits restoring an individual field. A genuinely moved parent must be restored as a complete
value before a deeper child can be written.

Only complete selected values transfer or reach invocation/return. Replacement consumes an
already-evaluated complete value, cleans the destination's initialized remainder, then installs
it. A rejected internal transition publishes neither half a transfer nor a partial cleanup/frame
change. This is integrity rejection, not rollback of user effects after recoverable failure.
Local writability, access permission and source evaluation remain separate checking obligations.

Cleanup emits maximal initialized regions in reverse field declaration order. Intact nested
records retain one schema operation; only branches around moved selections expand. When all
fields have moved, releasing the surviving container emits no duplicate field disposal. A partial
container's ownership ends explicitly after its surviving regions; this operation carries no
second payload destruction or implied physical deallocation policy. Partial evaluation temporaries stay registered in their original frame until cleanup or complete transfer.
Source-neutral reports distinguish complete initialization from mere container presence.

The source contract now explicitly lets `drop name` clean a definitely present partial record
without a user destructor. Requiring a complete value here would force pointless restoration
before ending ownership, even though lexical cleanup already knows every remaining part. This
intrinsic performs cleanup rather than supplying a value to an ordinary callable. Wholly moved
containers and alias referents remain ineligible; user-destructor prerequisites still apply.
The current builtin-only source goal is unchanged. Projected initialization must use the distinct
container-presence requirement for this operation when nominal source admission is implemented.

Empty external D/S for these records composes only the four exact builtin leaf contracts. Neither
Copy evidence, record identity, ownership nor an absent outside referent proves arbitrary value
independence. No dependent/container/callable/generic/outcome/user-destructor schema is admitted.

## Verification

Resource tests cover sibling survival, incomplete parent rejection, field/parent restoration,
partial/whole replacement, cleanup order, empty remainders, field ownership, logical overlap,
rejected transition atomicity, invocation/return completeness, partial evaluation temporaries,
report initialization, and all sixteen subsets of four moved fields in both traversal orders.

A shared 128-level record graph has two occurrences of the previous record per level. Moving
one deepest field produces one sparse missing path; cleanup produces only 127 intact sibling
regions and 127 container-end operations, without recursively expanding the conceptual payload
tree or host stack.

Verification completed on 2026-11-09:

- focused model (40), declaration (45) and checking (674) tests passed; the resource group has
  fifteen tests, including fourteen nominal partial-payload cases
- warnings-denied Clippy passed for the affected crates and all their targets
- the complete disposable-target compiler gate passed, including CLI (38), command (62),
  native-session (132), language-server (118), no-default-features and Rust documentation checks
- documentation generator tests, the explicit external site build (377 pages) and diff checks passed

The long CLI/native/editor suites are existing-product regression evidence. Their active pipeline
does not consume this future product; passing them does not prove partial nominal source behavior.
Running them at every small internal checkpoint spends time without closing that gap. Subsequent
work follows the [verification selection policy](../../verification/README.md#selecting-evidence-for-a-change)
and uses actual source acceptance/rejection as its feature integration criterion.

## Remaining Admission Work

The `V2CoreUnit` grammar, callable headers and typed bodies still admit only bool/i32/void/error.
The thirty source-corpus cases retain their scope. These Rust resource tests do not count as
nominal source conformance, full-language safety, native execution or performance evidence.

Next connect selected field places to typed operations, control flow, initialization, permission
demand, delegation/reservations and diagnostics together. Then admit nominal source headers and
operations. Indexing, dependent payloads, user destructors and native lifecycle realization require
their own further contracts and validation. The ledger does not grant permissions merely because
it can represent an operation, or authorize passing an incomplete value to a user destructor.
