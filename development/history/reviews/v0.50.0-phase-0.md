# v0.50.0 Phase 0 Blocking-job Model Review

**Result: complete with no open Phase 0 defect.** The model closes admission, execution,
completion, cancellation, abandonment, worker loss, and shutdown before filesystem policy enters
the service.

## Findings Corrected During Implementation

### Counters and completion queues initially duplicated lifecycle authority

The first implementation retained a running counter beside job state and a completion-event queue
beside completed outcomes. Either copy could disagree with the actual owner after cancellation or
shutdown. The final model gives queued inputs to one FIFO and all running or completed states to one
active-job map. Counts are derived under the same lock, and exact completion is observed by
`JobId`; there is no second completion index.

### Adapter follow-up notification made correctness depend on its caller

An adapter originally had to mutate lifecycle state and then remember a separate wake call. A
missed call could strand a valid waiter. Notification now belongs to the lifecycle transition and
runs after the state lock is released. The Darwin descriptor transports only a coalescible wake;
it cannot identify or consume a result.

### Worker failure needed a closed ownership transition

Requiring every worker path to call either `complete` or an error callback would make capacity
safety depend on control-flow discipline. A claimed input is now owned by `RunningJob`. Dropping
that owner publishes `WorkerLost` to an attached waiter or retires abandoned work, so panic and
early worker exit cannot strand a slot.

### Phase 1 integration exposed service-local identity aliasing

The initial model made `JobId` and `CapacityEpoch` monotonic only within one service. Two service
instances could therefore issue equal observations, and a consumer that accidentally queried the
wrong service could observe an unrelated job or a false capacity transition. Both identities now
carry an opaque process-local service qualification. Job queries cannot alias, and capacity queries
reject foreign observations explicitly. A deterministic two-service test fixes this boundary.

## Authority Review

- `nocter-blocking-runtime` alone owns job identity, queue order, capacity, result state,
  cancellation, abandonment, and shutdown. Its production dependency set is empty.
- `nocter-darwin-blocking-service` owns fixed host workers, synchronization, unwind containment,
  and the nonblocking wake descriptor. Its only production dependency is the lifecycle contract.
- The existing Darwin reactor observes ordinary readable-descriptor readiness. It receives no job
  variant, job identity, operation kind, or outcome representation.
- A future retains either its exact service-qualified monotonic `JobId` or `CapacityEpoch`, polls
  the issuing lifecycle authority after a wake, and tolerates coalesced or unrelated wakes.
- Filesystem paths, descriptors, errno classification, standard-library errors, compiler IR, task
  identities, and source declarations are absent from both lifecycle state and its public contract.
- Submission and cancellation transfer or return exact owned values. No blocking operation may
  retain storage borrowed from an abandonable computation frame.

The conformance architecture suite fixes both new production dependency sets. A later phase cannot
add compiler, task, reactor, filesystem, or standard-library knowledge without changing a reviewed
test expectation.

## Lifecycle Evidence

Deterministic model tests cover FIFO claim, saturation and epoch retry, queued cancellation,
running abandonment, completion without a waiter, stale identity rejection, shutdown extraction,
worker loss, notifier re-entry, coalesced wake delivery, operation panic, fixed worker capacity,
and join-before-release shutdown. No public operation exposes lifecycle fields for a caller to
repair.
