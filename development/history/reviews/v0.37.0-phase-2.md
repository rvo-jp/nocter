# v0.37.0 Phase 2 Body-Relation Input Review

**Result: complete (2026-09-06).** Provenance, allocation-effect, and loan analysis now consume one
checking-owned exact-coverage body catalog. The change removes three parallel input types, three
caller-built vectors, repeated linear `BodyId` discovery, and the implicit requirement that the
caller keep three independently expressible collections identical.

## Design Result

`BodyRelationCatalog` accepts checked bodies, the declaration graph, and the canonical source
catalog once. Construction rejects missing, duplicate, and unknown body identities, then stores
each immutable `(source, checked body, origin map)` relation in a dense `BodyId` arena. Consumers
can retrieve only a complete relation by semantic identity; they cannot pair one body's checked
graph with another body's source evidence.

`BodySourceCatalog` now uses the same dense arena representation. Its previous sorted slice made
every lookup repeat a binary search even though `BodyId` already defines a dense canonical domain.
The source catalog still owns construction and exact projection validation.

The resulting implementation removes 262 lines while adding 200 lines, including the new shared
contract and its documentation. No source semantics, diagnostic classification, editor behavior,
or checked-program representation changed.

## Comparison Measurement

The candidate at repository revision `13194d3da2f7c70f41a8adde3c36a85ed3ab1b51` was packaged as a
complete integrity-checked installed home and compared in one alternating run with the released
v0.36.0 home. The host and scenario inputs match the Phase 0 Apple M1 baseline. The released
compiler digest was `2314f369c9596f28563822fffa0dfa64f3b9899744e654adf8fd82dba542c8f1`; the
candidate digest was `6937582c653a8589fb2c6be01511db199be9678fd1e73d9e83ff3b18b5ce704c`.

| Scenario | v0.36.0 median | Phase 2 median | Change |
| --- | ---: | ---: | ---: |
| Single-file cold check | 674.952 ms | 677.558 ms | +0.4% |
| Representative package cold check | 737.323 ms | 733.037 ms | -0.6% |
| LSP initialize | 125.233 ms | 135.997 ms | +8.6% |
| LSP open plus first checked hover | 541.123 ms | 533.725 ms | -1.4% |
| Body edit plus checked hover | 188.412 ms | 185.716 ms | -1.4% |
| Fifty-edit session total | 9,477.003 ms | 9,279.875 ms | -2.1% |

Process measurements used two warmups and seven samples. Editor measurements used five persistent
sessions, two warmup edits per session, and fifty measured edits per session. The isolated
initialize increase is not treated as a regression: it has only five short samples, does not
contain the changed path, and the complete session improved. Cold latency and peak resident memory
were effectively unchanged.

The result confirms a small real reduction in repeated relation-input overhead, but it cannot meet
the milestone's 15 percent target. Phase 3 must decompose finalization itself; adding micro-
optimizations around this catalog would optimize noise rather than the attributed dominant cost.

## Review Conclusion

No legacy input wrapper remains in provenance, effects, or loans. No pass re-scans a body input
slice to recover membership. The catalog is crate-private and exposes immutable relation access,
so it does not widen the public semantic model. Phase 2 is complete; the measured evidence requires
Phase 3 rather than further work in this boundary.
