# v0.69.0 Canonical Declaration-contract Review

**Result: complete with no open implementation finding (2026-09-25).** The existing callable
modifier surface now has one vocabulary and order, one syntax recognizer, one syntax-to-semantic
projection, one declaration compatibility policy, and one checked execution-fact authority. This
review also evaluates possible additions; it does not adopt another source modifier.

## Closed Findings

The review found five concrete defects, all closed before qualification:

- the normative grammar omitted the already implemented `const` callable modifier;
- declaration contexts independently scanned optional modifiers and could drift from declaration
  classification;
- asynchronous modifier compatibility was partly implemented as a type-position validity rule;
- `const async` and `const primitive func` promised compile-time execution that the evaluator could
  not provide; and
- editor completion maintained its own modifier-order matrix and incorrectly withheld `async` from
  supported construction functions.

`nocter-language::CallableModifier` now owns the closed vocabulary, spelling, canonical order, and
context-independent compatibility relation. `CallablePrefixGrammar` owns which vocabulary subset a
syntax production admits. Syntax maps each admitted modifier to one lossless node and does not
interpret effects. Declaration lowering projects those nodes once into `CallableGuarantees` and
`CallableExecution`. `nocter-declarations` combines the shared compatibility relation with
declaration-kind policy. Checking owns only source projection and body-proof comparison.

Semantic presentation iterates the language-owned order over authored semantic facts. Completion
uses the same order, grammar category, and compatibility relation. Formatting preserves accepted
syntax and semantic highlighting classifies reserved tokens, so neither owns another callable
contract. The standard library and examples already used the canonical order.

## New-modifier Evaluation

A modifier earns language syntax only when callers need the promise, the compiler can prove it
transitively, and existing type or execution syntax does not already express it.

| Candidate | Decision | Reason |
| --- | --- | --- |
| `noblock` | reject | Absence of `blocking` is already the structural nonblocking guarantee; a second spelling would create two source forms for one fact. |
| `nothrow` | reject | `T` versus `T!` already exposes recoverable failure in the result type. A modifier would duplicate the type contract and still say nothing about process aborts. |
| `nosuspend` | reject | Immediate versus `async` declaration execution already owns this distinction. Returning an existing `future T` does not suspend the current call. |
| `alloc` | reject | Possible allocation is an inferred implementation fact. It neither describes result provenance nor gives callers a useful guarantee, and it encourages blanket annotation. |
| `pure` | defer | The word ambiguously combines allocation, mutation, ambient reads, I/O, blocking, failure, determinism, and destruction. `const` already owns compile-time availability. |
| `unsafe` | reject | Ordinary source has no unsafe escape mode; trusted low-level authority remains restricted to the selected Nocter home. |
| `total` or `notrap` | defer | This could support high-assurance code, but Nocter does not yet have a closed abort/trap fact domain covering bounds, arithmetic, assertions, allocation failure, primitives, and destruction. |
| `realtime` | preferred future profile | It can provide a caller-relevant admission guarantee, but only as a proved profile over independent facts rather than a synonym for `noalloc` plus nonblocking. |

The next modifier should therefore not be another atomic negative guarantee. If a concrete
latency-sensitive application is selected, a `realtime` feasibility phase should first define
bounded work, bounded synchronization, primitive cost authority, destruction cost, recursion and
dynamic-dispatch rules, and the relationship to abort behavior. Syntax should be added only after
that proof model accepts representative standard APIs and rejects an unbounded implementation.

## Qualification

The complete compiler gate passed in a disposable target after the changes. It covered repository
metadata, benchmark helpers, pinned Unicode reproduction, formatting, warnings-denied Clippy, all
workspace tests, installed-standard-library CLI and command paths, every public example, native
conformance, 126 native-session tests, 118 language-server tests, no-default-features checking, and
warnings-denied Rust documentation. The first sandboxed run reached one TCP loopback test and was
denied permission to create its socket; the identical full gate passed outside that sandbox.

Documentation generation remained deterministic and produced 372 pages outside the repository.
The repository worktree contained no generated-site output or verification target after the gate.
