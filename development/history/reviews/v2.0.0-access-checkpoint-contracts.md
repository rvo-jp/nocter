# Pre-S12 Private Access Checkpoint Contracts

## Status and Use

This preserves the explicitly future source contracts used by the `83ec05fd4` private-unit
checkpoint before S12. The current released specification is unchanged. The user subsequently
adopted a different value-binding foundation; these are **superseded source rules**, not S12
syntax, an implementation oracle, or a compatibility language. The [first-slice review](v2.0.0-first-access-slice.md)
retains the measured implementation evidence. The [source decisions](v2.0.0-source-design-decisions.md#s12-separate-values-binding-operations-and-capabilities)
and owning future chapters govern replacement work. Raw Markdown is preserved below solely to
identify the checkpoint's former contracts; its links and examples are archival text.

# Value Access Model

## Future Direction: v2.0.0

This chapter defines the adopted v2.0.0 value-access rules. They are not part of the current
released contract. Current ownership rules remain in [Ownership, Borrowing, and Drop](ownership.md).
This future chapter owns operation permissions, Copy materialization, access bindings, and result
handoff; it does not introduce a second current-language borrowing syntax.

Ordinary parameter/result placement, receiver abbreviations, callable invocation, and local
read/transfer inference are defined here and in the linked future callable section. The
[type-scope rules](values-and-types.md#future-direction-v2-0-0-access-qualifier-scope) distinguish
outcomes of access from access to stored outcomes. Complete implementation signatures are
retained under the [future module contract](modules.md#future-direction-v2-0-0-complete-implementation-signatures).
Full composition and module migration remain work. This does not reopen the selected lifetime,
initialization, reservation, or cleanup obligations. No complete compiler implementation or
soundness proof is claimed.

### Type-Side Declarations and Inferred Locals

An ordinary declaration writes its permission with its type:

```text
func open(id: u64): ^File!
func append(buffer: &Buffer, value: u8): void
```

Unqualified T provides input/read, `&T` update, and `^T` ownership. `&T` does not regain its
released readonly meaning. Declarations and interface contracts remain authoritative; calls
repeat neither parameter nor result permission markers.

An unannotated local infers the qualified result of the initialization operation, not the stored
permission of a named source variable:

```text
let first = Buffer.create(64)? // ^Buffer, supplied by the factory's successful result
let next = ^first             // ^Buffer, explicitly transferred; first is unavailable
let inspect = next            // Buffer, read access; next remains the owner
```

An explicit update-access expression supplies U:

```text
let editable = &next          // &Buffer, delegates update access to next
```

This is a separate example from keeping `inspect` live. `&place` requires definitely initialized
writable owned storage or an existing U access. It cannot upgrade I, target a fresh temporary,
copy a capability, or transfer ownership. Grouping preserves the operation. Reading the resulting
`editable` into another unannotated local still supplies I. Type-side `&T` declares a contract;
expression-side `&place` performs delegation. `let &editable` is not another spelling.

Reading an existing place supplies I, even when the place is owned, writable, or Copy. This
includes an identifier, field, element, or range selected without an explicit transfer. `^place`
instead supplies X by transferring an initialized owner. A call supplies its selected result
permission; binding a U-returning call therefore infers U without another marker. Parentheses
preserve the operation rather than turning a read into a transfer. Successful `?` extraction and
`await` preserve the selected payload/output permission, not ownership of the outer carrier.

An explicit `: T`, `: &T`, or `: ^T` annotation requests that permission and data type, subject to
source eligibility. It cannot manufacture authority or replace a missing source-transfer operation.
No `: ^_` placeholder is mandatory for inferred owned results. Independent I answers supplied by
a declared read-result contract retain I unless an explicit destination requests a checked Copy.
Numeric, Boolean, and unit literals and newly computed primitive scalar values construct fresh
X values; they do not access an existing place. A literal denoting static storage instead follows
that storage contract without introducing an allocation. Inference does not inspect later uses,
Copy specialization, or an optimizer's storage choice to change an already checked binding. `var` remains removed.

The distinction is between initialization operations, not two interchangeable styles of the
same operation. The type qualifier `^T` states an ownership contract; the expression `^place`
performs a transfer. There is no alternative inferred move spelling `let next = first`.

### Ownership, Access, and Dependencies

An owned value has one initialized owning place responsible for its eventual transfer or cleanup.
Access to that value does not itself create another owner. A place includes a binding, field,
element, or range selected by an expression; distinct places need not have distinct numeric
addresses, particularly for zero-sized values.

The compiler tracks three different relationships:

- Access to a particular existing place, which prevents conflicting operations while that access
  is live.
- Dependencies contained inside a value, such as a closure's access to captured outside data.
- Storage requirements, such as an allocation region that must remain valid.

Owning a value does not imply that the last two sets are empty. Copying a closure does not copy
the data it accesses. Storage requirements do not by themselves grant read or update permission.
The [future storage rules](memory-and-regions.md#future-direction-v2-0-0-value-access-origins)
define the public origin bounds.

### Input, Update, and Ownership Transfer

Parameter and receiver declarations select one permission:

| Declaration | Permission | Responsibility |
| --- | --- | --- |
| `value: T` | Input/read | Leave caller ownership intact; do not update through this access |
| `value: &T` | Update | Update the original writable place; leave it initialized on recoverable exits |
| `value: ^T` | Ownership transfer | Receive ownership and dispose of or forward each live owned part once |

These permissions are called I, U, and X in descriptions of the model. Those letters are not
language keywords. A type T is not rewritten into a freely storable `&T` or `&+T` value type.

Inputs may overlap inputs. Overlapping input/update, update/update, and transfer/access cannot
be simultaneously active. Proved-disjoint fields or ranges can be accessed independently.
Delegation is different from two independent accesses: the parent is restricted or suspended
while its child access is live. A parent update can delegate input or update; an input cannot
delegate update. Neither transfers ownership of the caller's place.

U must leave a valid initialized value on success, failure, and cancellation. It need not undo
completed changes. An exchange operation must prepare a replacement before removing the old
owned value; it cannot expose a fallible uninitialized gap. An X parameter instead owns a
writable local slot, including the right to replace or transfer its contents, without another
mutable local declaration.

Calls uniformly derive receiver and argument permissions from the selected declaration:

```text
func append(buffer: &Buffer, value: u8): void
func enqueue(job: ^Job): void

append(buffer, 42)
enqueue(job)
```

Do not retain direct argument-mode prefixes or method `.&`/`.^` markers as alternate call styles.
An unavailable permission is an error; it does not select another overload, silently clone a
value, or change the declaration.

### Copying Is a Separate Operation

Implicit copying requires a checked Copy capability. Nominal structs opt in with `copy struct`;
private copyable fields alone do not make an ordinary nominal type Copy. Copying is structural,
has no custom hook or resource acquisition, and does not allocate. Copy does not promise that a
large value is cheap to copy.

Scalar primitives, unit, payloadless enums, and supported raw boundary values permit Copy.
Tuples, fixed arrays, and optionals require Copy for every component type, independently of the
active branch or array length. Generic code needs declared Copy evidence. `error`, fallible
outcomes, and futures remain move-only. A Copy type cannot have a destructor.

A closure can be Copy when its owned captures are Copy and its remaining captures only retain
input access. Every copied closure retains those outside dependencies. Update captures prohibit
Copy. Opaque values expose only capabilities promised by their contracts.

Copy materialization creates a separate owned value. It removes the new value's need to access
the old value's containing place, but preserves dependencies inside the copied payload and its
storage requirements. For example, copying a read-capturing closure can allow the old closure
header to be discarded; it cannot allow the captured outside data to be destroyed.

An ordinary owned initializer, assignment, or owned success return can perform a permitted
Copy. An I call argument still accesses the original place even for Copy T; it does not acquire
snapshot semantics merely because bits could be copied. An X call with an existing owned place
transfers it uniformly for Copy and move-only types. It does not choose a non-invalidating copy.
An I/U access is not ownership of its referent. Supplying it to X requires checked Copy evidence:
preparation materializes a separate owned snapshot and the invocation receives that snapshot.
Without Copy evidence the call is invalid; it cannot extract the caller's original value or
insert a clone. This rule does not require an otherwise unnecessary intermediate local.

```text
let read = first        // read access, including when first is Copy
let second: ^T = first  // explicit Copy request; requires Copy evidence for T
let third = ^first      // transfer; first is unavailable even when T is Copy
```

`^place` transfers an existing owned place into standalone storage/return expressions. A fresh
owned result already supplies ownership and needs no transfer prefix. General transfers do not
become implicit because the source has no later use.

### Result Contracts and Local Bindings

A callable declares result permission beside the result type, independently of its input modes:

```text
func bytes(buffer: Buffer): [u8]
func edit_bytes(buffer: &Buffer): &[u8]
func copy_bytes(buffer: Buffer): ^Vec<u8>
```

Permission is part of the contract, not the lookup name or an overload discriminator. Changing it
changes the API contract. Calls omit result assertions. Locals infer what their initialization
operation supplies:

```text
let input = bytes(buffer)
let editable = edit_bytes(buffer)
let owned = copy_bytes(buffer)
```

These are separate examples; simultaneous overlapping input/update access is still invalid.
The resulting permission determines assignment and transfer:

| Resulting local permission | Assignment and ownership |
| --- | --- |
| I: read | No update, replacement, or transfer of the referent |
| U: update original storage | Update/replace the original; no unfilled ownership extraction or retargeting |
| X: own a writable value | Update, replace, transfer, and valid reinitialization of its own slot |

An I binding to an existing place/access retains a read relationship regardless of Copy. An
independent read/Copy answer has no outside referent of its own. An explicitly I/U destination
cannot retain a fresh X temporary as an invisible owner; an unannotated binding instead receives
that X value openly as its own owner. An explicit I destination can materialize a separate Copy
answer from a fresh Copy value when proved, preserving its D/S dependencies and finishing the
source temporary's cleanup. This retains no hidden owning parent and does not promote I to X.
Fresh noncopyable X cannot satisfy that I binding.

A U binding requires an existing writable owned place or supplied U access. Its original place
and required structure stay protected for the access's live range. A bare name naming a U binding
still supplies a read when used to initialize another unannotated local; it does not duplicate an
exclusive capability. An explicit U destination or U-result handoff delegates access, restricting
the parent while the child is live.

`&place` establishes that delegated access when the expression is evaluated, rather than reserving
it until a surrounding operation completes. Its target and carried dependencies remain protected
through its live uses and dependent cleanup. An active U child excludes overlapping access through
its parent; an I child permits compatible reads but prevents parent update/transfer. Ending a child
restores only the surviving parent's rights, subject to its other live children. No lexical block,
explicit lifetime name, or separate release statement is needed for an ordinary access whose last
use and required cleanup have ended. This does not move a resource destructor earlier.

Infer the permission still required by later uses and cleanup. After an access's last update
requirement, compatible read access may suffice for its remaining reads. This does not change its
declared type or reselect operations: a later U argument, U result, explicit update delegation or
write keeps the update requirement live. Explicit `&place` still requires exclusive eligibility
at its evaluation point, even if its answer will only be read. No runtime upgrade is introduced.

When an intermediate access has no remaining use or cleanup obligation, reparent its live children
to the surviving authority for the same root. Preserve each child's permission and dependencies.
An unused U intermediary does not keep exclusive access merely because a live I child was created
through it: that child still prevents update/transfer, while compatible reads can resume. A U child
continues to exclude overlapping reads after reparenting. Retain an intermediary needed by a later
operation or prepared call at the permission that call requires. A pending I request does not
retain an otherwise unused U intermediary: preserve its identity reservation and read authority
without activating an input early. Never upgrade I, duplicate U, or keep a destroyed root alive.

An X binding receives a fresh owned result or an explicitly transferred owner. An explicitly X
destination may also materialize a permitted Copy from a readable value, retaining payload and
storage dependencies. Thus `let next = ^previous` transfers an existing owner, while
`let snapshot: ^T = previous` requests a checked Copy. A move-only source in the latter form is
an error. Destination ownership never supplies an omitted source-transfer operation.

```text
let limit: i32 = 100
let count = 0
count += 1
count = 10
```

I bindings cannot be assigned. Assignment to U updates its identified caller-owned place, even
for whole-value replacement; it never retargets the access. Assignment to X replaces its own value
and performs required old-value cleanup. After transfer or explicit drop, X can be reinitialized
by assigning a complete replacement; failure before that replacement is ready leaves the slot
uninitialized. Maybe initialized slots still require definite-initialization checks and conditional
cleanup. A failed replacement does not itself clean or install a destination value, but it does
not undo explicit moves or other side effects already performed by the right-hand expression.
U must remain valid on every outward recoverable edge.

There is no separate immutable-but-transferable owned local form. Update permission follows X
ownership, as it does for X parameters. Passing temporary I access still restricts the called
operation without freezing every future operation on its owner.

Binding I/U access does not manufacture a freely storable reference. Access remains bounded
by its owners and cannot be stored as an independent T. Persistent relationships require an
explicitly owned dependent computation/capability
or an owned container with a checked index/range, rather than an implicit clone or lifetime repair.

### Generic Evidence and Origin Preservation

A generic body uses its declared capabilities. An unconstrained T is potentially move-only.
Specializing that body with a Copy type does not reselect a checked transfer, convert an I
binding to X, erase an origin, or change a public result mode. The caller can
perform a separate permitted Copy operation when its own checking context proves Copy.

For example, a generic I accessor can return access to an I parameter. Its checked body remains
an accessor when specialized with an integer. A caller whose initializer knows the integer type
can request an X binding and materialize an independent integer answer. An owning generic identity instead always uses
ownership transfer:

```text
func identity<T>(value: ^T): ^T {
    return ^value
}
```

Copy removes only the access needed to read the source value, not dependencies already carried
inside T. An explicit receiver-origin bound on an abstract associated result remains authoritative
until a checked materialization or other independence operation discharges the particular access.

### Preparation and Invocation

Select one callable and its complete contract before checking operand permissions. Evaluate the
callable/receiver and arguments exactly once, left to right. Preparing an existing place reserves
that place against destruction, transfer, replacement, and conflicting update while later operands
are evaluated. Temporary reads that finish before invocation can remain valid:

```text
buffer.append(buffer.len())
```

When a non-owning Copy argument is materialized for X, take that snapshot during its left-to-right
preparation, preserving payload dependencies and storage requirements. It becomes a prepared
owned temporary; later operands do not change its copied answer. Other live uses of the original
access still retain their normal restrictions. An existing owned X source instead remains
reserved for invocation-time transfer, with no Copy fallback.

After all preparation succeeds, check the complete access bundle and activate updates/transfers
as one non-fallible transition. Reservations are protections, not already-active I/U permissions.
A source's active children must permit the requested operation at commit; a child that finishes
during operand preparation need not prevent reserving the address. Actual replacement, transfer
and conflicting writes remain forbidden while reserved. An already-active computed access keeps
its own restrictions during preparation. No user callback, allocation, or destructor occurs between the
first and last committed ownership transfer. Required allocation and place validation precede
that transition.

Failure during later argument preparation releases reservations and cleans constructed temporaries;
it does not consume an earlier merely reserved owned place. Earlier side effects and separate
ownership operations are not rolled back. Failure after invocation leaves transferred ownership
with the callee and leaves U inputs valid with their completed changes.

### Evaluation Temporaries

An I call input may read a fresh X value without requiring Copy. Keep that explicitly evaluated
temporary alive through the enclosing statement, loop condition, or block-result evaluation,
including use of the call's answer. This is temporary storage, not an invisible owning local.
After the destination is installed or the result staged, release remaining evaluation temporaries
in reverse construction order, before leaving the containing block. A retained result cannot
outlive a temporary it accesses. Copying a scalar answer can remove that referent; binding access
cannot extend the temporary's lifetime.

Moving a temporary into a local, returned owner, or X call input transfers its cleanup obligation.
Preparing an I input does not transfer that obligation to the callee. Cancellation destroys only
the successfully prepared owned arguments, in reverse preparation order, then releases other
temporaries in the exited evaluation frames. A merely reserved named owner remains intact.
Nested evaluation, call, and lexical frames unwind in their actual nesting order. Traps that
terminate without unwinding do not acquire source cleanup from these rules.

For the bounded first fragment, `bool`, `i32`, and `void` have no contained access or external
storage requirements and need no resource destructor. The opaque built-in `error` follows its
[owned snapshot contract](../../std/error/README.md): it owns its private immutable failure graph,
has no access into input views or caller-managed region dependency, and releases that graph when
destroyed. It remains move-only. These are exact data contracts, not consequences of Copy or X;
no such independence is inferred for a future aggregate, closure, future, or generic value.

### Return and Cleanup

An X result returns a fresh owned value, a permitted Copy, or an explicitly transferred existing
owner. An I result exposes eligible surviving storage or a permitted Copy answer; a U result
exposes writable surviving caller storage. A scalar answer such as `len(): usize` can be copied
before cleanup, without retaining access to the source counter.

Ordinary `return` evaluates the result once, protects its referent and dependencies during exit
cleanup, performs normal callee cleanup, and hands the result to the caller. Escaping delegated
access is reparented without an interval that permits conflicting access or creates two exclusive
authorities. A cleanup operation conflicting with the staged result is invalid.

Returning access into an owned local, temporary, or consumed parameter that is destroyed on exit
is invalid. The compiler must not suspend the ordinary callable, delay a local guard's destructor,
extend a region, or insert reference counting to make that return valid. Return an owned guard or
capability when its resource must survive; access through that live owner remains separately checked.
Neither `yield` nor a `view` return form is introduced.

Control-flow joins require definite initialization for every use and conservatively retain all
possible live dependencies. Mutually exclusive branch accesses are alternatives, not simultaneously
active updates; a use after the join must nevertheless be safe for every incoming alternative.
Loops preserve these obligations on every backedge. Conditional cleanup disposes only initialized
owned parts and never grants source permissions to a maybe initialized value.

Moving an owned field also changes the parent's initialization state. A user destructor that
requires the complete parent may run only with that state restored on every path reaching it,
including failure and cancellation. Do not silently skip that destructor or call it with missing
fields. This is a path-sensitive obligation, not a blanket prohibition on moving fields from
every type with a destructor: a verified reinitialization before all affected exits can satisfy
it. Without a user destructor, ordinary partial cleanup disposes only the remaining initialized
parts. A complete-value transfer cannot carry an uninitialized required field.

### Boundaries with Other Contracts

Result modes survive generic forwarding, interface matching, and callable abstraction. Environment
invocation and output permission are distinct; see the
[future callable contract](callables.md#future-direction-v2-0-0-value-access-callables).

Optional/fallible result tags and future ownership do not turn a non-owning success payload into
an owner. Their complete v2.0.0 composition must preserve the result access and carried
dependencies defined here. This chapter does not silently replace current outcome/future syntax,
standard-library contracts, or target ABI rules. Those owning contracts must be migrated coherently
before the complete v2.0.0 language boundary takes effect.

## Future Direction: v2.0.0 Assignment and Flow

These rules refine the future [Value Access Model](value-access.md), separately from the released
`let`/`var` rules above. A local has one inferred or annotated I/U/X permission. No subsequent
assignment, branch, use, or specialization changes it.

`let _ = expression` evaluates once and introduces no binding. Dispose of an owned result at that
point; an I/U result releases only that temporary access and does not destroy its outside referent.
`drop name` requires a definitely initialized X place without conflicting live access, disposes
of its value, and leaves that owning slot uninitialized. It cannot extract/destroy a referent
through I/U. Implicit exit cleanup follows the same ownership obligations but is conditional on
the actual initialized parts. Neither discard nor drop supplies an implicit clone or move of a
bare existing source.

### Assignment Order and Reinitialization

Evaluate the entire right-hand expression first. Only after success, evaluate dynamic destination
components once, check the destination's state after those right-hand actions, dispose of its
initialized old value when required, and install the complete replacement. Protect a prepared
replacement and its dependencies through target evaluation and cleanup. Reject a replacement
that would destroy storage needed by its own retained I/U access or D/S dependencies. Do not
reserve or read the assignment destination before the right-hand side merely to simplify checking.

An X destination stores a fresh owned value, explicit transfer, or proved Copy; an expected X
assignment does not silently move an existing move-only source. A U destination replaces its
original referent under the same complete-value requirements. I is not writable. U does not
become an uninitialized owning slot and cannot be retargeted to another access.

If the right-hand side fails or terminates, perform no target evaluation, replacement cleanup,
or store. Previously performed right-hand moves, calls, and effects remain performed. Successful
reinitialization of an uninitialized X slot performs no old-value destruction. Replacing a maybe
initialized X slot conditionally cleans only the old value actually present on that path.

```text
func refresh(value: ^error): ^error {
    value = ^value
    return ^value
}
```

Here the right-hand transfer leaves `value` uninitialized; assignment installs that same owned
value without destroying a nonexistent old value. Similarly `value = replace(value)` can consume
then restore an owner if the selected call returns a compatible X result. An incompatible live
access still prevents the transfer. A failed call does not restore an owner it has consumed.

Compound assignment also evaluates the right-hand side first, then identifies the target once,
reads its definitely initialized value, computes the primitive numeric result, and writes it.
`value += consume(value)` is invalid if preparing/invoking `consume` moved `value` and did not
restore it. It is not a textual rewrite that reads the old value before the right-hand side.
Numeric type, overflow, division, and checked-operation rules continue to apply; no arithmetic
reassociation or effect reordering follows from X permission.

### Conditional Results and Access Duration

For an unannotated conditional result, all normally producing branches must supply the same
natural permission and compatible data types. A terminating branch supplies no result. A plain
place supplies I, an explicit `&place` supplies U, and a fresh result or explicit transfer supplies
X. Do not choose a common mode by inspecting later uses or Copy specialization. An explicit
expected binding/result contract instead checks each producing branch at that boundary, including
its permitted Copy materialization. It never supplies an omitted standalone move.

```text
let source = 10
let answer = if flag { ^source } else { 20 } // X on both paths
```

`source` is maybe initialized afterward; its old cleanup is conditional, and an unguarded read
is invalid. Replacing `^source` with `source` produces I versus X and cannot infer a common mode.
An explicit `: ^i32` answer could instead copy the I branch under available Copy evidence.

At a join, keep initialization and alternative access dependencies separately. Every operation
must be safe on every still-possible incoming path. Two branches delegating U to different places
create alternatives, rather than two simultaneously active U accesses. A use that cannot establish
which place is accessed must respect both possibilities. Do not assume a branch correlation that
has not been proved. Assignment to a whole maybe initialized X slot can restore definite state.

End an ordinary scalar access after its last required use, including any dependent cleanup;
propagate that requirement backward through branches and loop edges. Creating `&place` activates
U immediately. A selected call's U operand instead uses the separately defined preparation and
invocation protocol. These have different timing, even when both eventually update the same place.
A child read restricts update/transfer through its parent while live. An exclusive child update
also restricts overlapping parent reads. The compiler explains a conflict at the attempted
operation and identifies the retained access and its later use or cleanup.

### Loops and Exits

Compute a conservative fixed point at each loop header over initialization, live accesses, and
carried dependencies. Include the zero-iteration path of `while`, every continuing backedge and
`continue`, and each `break`/return edge at its actual destination. A transfer followed by
reinitialization only on an exiting path does not make the next iteration safe. A transfer on
all continuing paths followed by valid reinitialization before the backedge can be safe.

Owned parts are cleaned exactly once on their actual exits; missing or maybe initialized parts
are not read or destroyed as complete values. U remains initialized on every outward recoverable
edge. These obligations do not require unrestricted path reasoning or acceptance of every safe
program. When conservative checking fails, report the specific unproved initialization/access
relationship locally; do not insert copying, runtime sharing, or a lifetime extension.

## Future Direction: v2.0.0 Value Access Callables

The v2.0.0 [Value Access Model](value-access.md) separates access to the callable value,
environment invocation permission, explicit parameter permissions, and result permission.
These are adopted future contracts, not current released syntax.

| Structural callable type | Environment invocation |
| --- | --- |
| `func(T): R` | Repeated input/read invocation |
| `mut(T): R` | Repeated update invocation |
| `once(T): R` | Consuming invocation, at most once per owned callable instance |

`mut` describes access to the environment, not purity or the modes of explicit arguments.
`once` does not require an invocation: an uninvoked owned callable can be dropped normally.
Invocation consumes its owned instance even when that particular body only reads captures.
Copying, when separately permitted, creates another instance; it does not let one instance be
consumed twice. A move-only environment cannot acquire Copy from an invocation type.

Type-side qualifiers independently describe how the callable value is supplied:

```text
^func(i32): ^Product // own the callable; read invocation; owned result
&mut(i32): ^Product // update caller's callable; update invocation; owned result
^once(i32): ^Product // own the callable; consume it on invocation; owned result
func(&Buffer): &[u8] // read invocation; update argument; update result
```

The return qualifier is beside the result type. Unqualified T offers I, `&T` U, and `^T` X.
No marker appears in the callable-name position. The three invocation kinds admit all nine
invocation/result mode pairs; origin and cleanup checks may still reject a particular type/body.
For example, consuming an environment cannot return access into a capture destroyed by that exit.

`^func(...)` now means ownership of a read-invoked callable, not consuming invocation;
`&func(...)` means update access to that callable value, not an update-invocation contract.
The latter access can permit replacing the caller's callable value while calls themselves only
read its environment. There is no optional old invocation-prefix interpretation.

A call has no receiver/argument mode assertions. Read invocation requires readable environment
access, update invocation requires writable environment access, and consuming invocation follows
the selected X-operand preparation/commit rules. In particular an existing Copy owner still
transfers; a non-owning actual can only supply a separate snapshot when checked Copy evidence
permits it. Environment preparation precedes explicit arguments. Direct `^callback(...)` is not
an invocation-mode assertion or an alternative spelling of the selected callable type.

An annotation, interface witness, generic forwarding operation, or erased callable preserves
invocation kind, parameter modes, result mode/shape, and result-origin bounds. It cannot infer
new authority from a private body, remove carried dependencies, or choose a mode from later use.
Static specialization does not change the selected source contract. No implicit conversion among
`func`, `mut`, and `once` contracts is introduced by naming them; exact matching and the separately
checked Copy-answer adaptation remain the basis.

For matching I-result callables with the same result data type, a receiving boundary with Copy
evidence can materialize the returned read access as an independent Copy answer. This is a checked
copy operation, not permission substitution: invocation/parameter/result modes stay unchanged,
and dependencies carried inside the copied payload and its storage requirements must still fit
the receiving contract. A U result cannot be detached this way, and an X result cannot be silently
reclassified as I. The original callable's generic body and origin contract remain unchanged.

An expected callable contract supplies a closure's result mode before checking its body. Without
that context, inference must establish one result protocol from its checked returns; later uses
cannot retroactively select another. A conflicting or underdetermined body needs an ordinary
callable annotation or named declaration, not a new result keyword.

Ordinary captures are inferred. Retain `(^buffer; value: u8) { ... }` for deliberately moving an
owner into the environment when body use alone would only require reading/updating it. Here
`^buffer` is the existing source-transfer operation, not an identifier-side type annotation.
No `buffer: ^_` capture alias is added. Owned capture does not itself select `once`: an owning
closure that only reads its captures can retain a `func` invocation contract.

A fresh closure expression supplies X to an inferred local, for example `let callback = ...`.
Binding another existing callable variable with plain `let alias = callback` instead creates I
access, regardless of whether the environment is Copy. Capture and output dependencies still
restrict both callable aliases and owners through invocation, destruction, or escape.

The [future storage rules](memory-and-regions.md#future-direction-v2-0-0-storage-optimization)
allow environment scalarization/reuse only while preserving capture transfers, dependency bounds,
observable identity, and cleanup. They do not reschedule explicit capture evaluation or roll back
earlier transfers after later formation effects fail. Opaque/foreign use may require backing by
its contract deadline; invocation kind alone is not an allocation-elision certificate.

Do not restore retired `&+func`, result markers before callable names, or call-site permission
assertions as aliases. Source recognition belongs to the
[future syntax rules](syntactic-grammar.md#future-direction-v2-0-0-access-syntax).

## Future Direction: v2.0.0 Access Qualifier Scope

The future [Value Access Model](value-access.md) uses unqualified T for input/read, `&T` for
update, and `^T` for ownership. A qualifier applies to the following type atom. An optional or
fallible suffix outside that atom wraps the qualified type. Parentheses put a complete inner
type, including its outcomes, inside the qualifier's scope.

| Type | Contract |
| --- | --- |
| `&File?` | Optional update access to File; absence supplies no File access |
| `&(File?)` | Update access to an existing optional slot, including when that slot is absent |
| `^File!` | Owned successful File, or the one owned error failure |

These are scope distinctions, not permission conversions. For example, a successful call returning
`&(File?)` retains access to the slot even when its stored tag is absent. Inspecting that tag must
not release the slot's lease. A call returning `&File?` may instead produce absence with no File
lease. Replacing a slot through U must still leave it initialized; the qualifier does not authorize
an unfilled extraction or an owning clone.

Preserve the constructor order when resolving aliases, substituting generic arguments, comparing
contracts, or displaying types. An alias naming `File?` is a complete atom: applying `&` to that
alias qualifies the optional object, not just File. Alias expansion cannot move an access qualifier
through an optional/fallible wrapper. Parentheses may be removed by formatting only when doing so
preserves the type's constructor tree.

For callable types the result consumes its complete type, including outcome suffixes. Thus
`^func(i32): ^File!` owns a read-invoked callable whose call can fail and whose successful File is
owned. An outcome on the callable value itself requires grouping, such as `(func(i32): ^File)!`.
Invocation kind, value permission, and output permission remain independent under the
[future callable rules](callables.md#future-direction-v2-0-0-value-access-callables).

Repeated optional layers retain their separate tags; they do not flatten. The existing selected
single-failure rules, permitted type positions, origin obligations, and carrier/payload distinctions
still apply. Recognizing a type does not authorize propagating a move-only error out of non-owning
storage. Nor does this scope rule alone admit general stored access-qualified components such as
an owned aggregate containing update accesses; that extension needs its own dependency, duplication, and
cleanup validation. Full compound-value checking remains a migration gate.

## Snapshot: spec/language/lexical-grammar.md

## Future Direction: v2.0.0 Access Tokens

For v2.0.0, `^` is punctuation for type-side ownership qualifiers and explicit source transfer.
`&` denotes update in a type qualifier, the `&place` delegation expression, or the special
`&self` receiver abbreviation; it does not introduce an ordinary readonly borrow type. Neither `&T` nor `^T` is a compound lexical token.
The selected receiver forms tokenize as optional punctuation followed by `self`.

`mut` and `once` introduce future structural callable invocation kinds alongside `func`.
They are contextual type heads when followed by a callable parameter list; elsewhere ordinary
identifier rules apply. Recognition does not depend on whether a nominal type with that name exists.
In `^func(...)`, the punctuation qualifies the callable value; it no longer selects consuming
invocation. Invocation meaning comes from the callable word, not token adjacency or lookup.

Local declarations begin with `let` and an undecorated identifier/pattern. Type qualifiers occur
after a type-annotation colon when written; `^place` in an initializer is a transfer expression.
`&place` in an initializer creates update access. Neither expression prefix is an optional direct
call-argument assertion. In the future access expression grammar a unary position containing the
lexical `&&` token supplies two update prefixes; it does not retain the released readonly meaning.
Its inner expression is not an existing writable place, so `&&value` fails place checking. Binary
`left && right` remains logical conjunction. Spacing does not select a different access model.
`var` is not a v2.0.0 binding declaration. Its rejection must not fall back to the released
`let`/`var` grammar. The forced-capture prefix uses the same punctuation as source transfer.

`()` consists of the ordinary `(` and `)` tokens. Unit versus closure recognition is syntactic.
No type lookup changes tokenization. The current lexical rules above continue to describe the
released language; this future section does not admit a general binary `^` operation or restore
retired `&+` borrow syntax by splitting it into tokens. Full recognition belongs to the
[future syntax fragments](syntactic-grammar.md#future-direction-v2-0-0-access-syntax).

````markdown
## Future Direction: v2.0.0 Access Syntax

These fragments record the adopted ordinary access, receiver, callable, and local-binding
positions, separately from the complete released grammar above. They are not a complete v2.0.0
type, expression-precedence, outcome, module, or implementation-body grammar.

```text
V2AccessQualifier = "&" | "^"
V2InvocationKind = "func" | "mut" | "once"

V2Type = V2QualifiedAtom V2OutcomeSuffix?
V2QualifiedAtom = V2AccessQualifier? V2TypeAtom
V2OutcomeSuffix = "?" "?"* "!"? | "!"
V2GroupedType = "(" V2Type ")"

V2NamedFunctionHead = "func" Name
V2MethodHead = "method" V2AccessQualifier? "self" "." Name
V2Parameter = "..."? Name ":" V2Type ProvenanceClause?

V2CallableType = CompileTimeModifier? V2InvocationKind
                 "(" List(V2CallableParameter) ")" ":" V2Type ProvenanceClause?
V2ErasedCallableType = "any" V2CallableType
V2CallableParameter = "..."? (Name ":" V2Type | V2Type) ProvenanceClause?

V2BindingStatement = "let" V2BindingPattern V2TypeAnnotation? "=" Expression
V2BindingPattern = V2BindingLeaf
                 | "(" V2BindingPattern "," V2BindingPattern ("," V2BindingPattern)* ","? ")"
V2BindingLeaf = Name | "_"
V2TypeAnnotation = ":" V2Type ProvenanceClause?

V2UnitExpression = "(" ")"
V2UpdateExpression = "&" V2UpdatePlace
V2TransferExpression = "^" V2TransferPlace
V2ForcedCapture = "^" Name
```

`V2TypeAtom` covers the future named/built-in, bracket/tuple, grouped, and callable atoms; their
complete productions and permitted positions remain a migration gate. It is not the released
`Type` grammar with old borrow types silently admitted. `V2UpdatePlace` and `V2TransferPlace` denote a
place under its future contract. No `pub`, `noalloc`, `notrap`, or `blocking` modifier is restored
by reusing a released enclosing production.

A qualifier binds to the following atom before outcome suffixes. Thus `&File?` wraps an update
access in optionality, while `&(File?)` updates an optional object. `^File!` supplies an owned
successful File. Repeated `?` retains distinct optional layers. `T!?` and `T!!` do not acquire an
ungrouped production; grouping and existing single-failure validity checks govern other nesting.
Do not flatten the type tree while expanding aliases or checking contract headers. The
[future type-scope rules](values-and-types.md#future-direction-v2-0-0-access-qualifier-scope)
own these meanings and their storage/cleanup limits.

A callable's result consumes its full `V2Type`, including outcomes, before an enclosing type can
finish. An outcome on the callable value itself therefore needs a grouped callable atom, as in
`(func(i32): ^File)!`; `func(i32): ^File!` instead has a fallible call result. The full
provenance and remaining constructor grammar must preserve this distinction.

An ordinary parameter puts its access qualifier beside its type, as in `buffer: &Buffer` or
`job: ^Job`. A result does likewise: `func open(id: u64): ^File!`. No result marker occurs before
the callable name or before an anonymous parameter list. Function heads take their ordinary
generic/parameter/result tail. Receiver abbreviations are solely `self`, `&self`, and `^self`;
expanded typed receiver aliases are not added. A method head has no result-name prefix.
Matched implementations repeat that complete head and tail before their block; no
`method append { ... }` or `func name { ... }` implementation shortcut is added. Header agreement
follows the [future contract/body rules](modules.md#future-direction-v2-0-0-complete-implementation-signatures).

The structural invocation word is `func`, `mut`, or `once`. An outer type-side qualifier describes
access to that entire callable value. For example `^func(i32): ^Product` owns a read-invoked
callable with an owned result; `^once(i32): ^Product` independently adds consuming invocation.
Retired `^func`/`&func` invocation meanings cannot be recovered from name or type lookup.

Local binding identifiers have no permission prefix. An annotation states the expected type and
permission; without it the initialization operation supplies them. In particular `let next = ^first`
infers X, while `let inspect = next` infers I. Copy does not change either decision. A U-returning
call or explicit `&place` supplies U; a bare existing U variable instead supplies I. The explicit
update expression activates delegation during its evaluation, not at invocation commit.
Tuple shape, component ownership,
partial extraction, and discard cleanup still require the corresponding future pattern/type rules.
`_` introduces no binding or access assertion. `var` is not a future binding declaration.

Calls have neither receiver `.&`/`.^` nor direct argument-mode assertions. Direct call/argument
prefix assertions remain invalid under transparent grouping; ordinary update/transfer expressions
remain available in initialization, storage, and return operations. They transfer existing owned
places, not fresh call results. Earlier explicit ownership operations during operand computation
are not rolled back by a later preparation failure.

The existing capture segment accepts `V2ForcedCapture`: `(^buffer; value: u8) { ... }` explicitly
moves the source into the inferred environment. That entry is a transfer operation, not a
name-side access annotation or a second typed-capture style.

For parentheses, a closure head followed by its optional result annotation and a block selects
the closure. Otherwise empty `()` selects unit, a single parenthesized expression selects grouping,
and a comma-separated list selects a tuple. Delimiter and statement-boundary recognition decides
these forms before type checking. Unit introduces no zero-element tuple type.

Permission, initialization, Copy, dependency, and cleanup checks follow recognition under the
[Value Access Model](value-access.md). Remaining constructor, expression-precedence, and full
module contracts must be migrated coherently before implementing the complete v2.0.0 boundary.


### First Access Validation Fragment

The following closes a bounded v2.0.0 function/body fragment for initial front-end conformance.
It is a subset of the future language, not a new package format, source version switch, or a
claim that the complete v2.0.0 grammar is closed. `V2CoreUnit` is a test parse goal containing
private function definitions in one supplied module; it does not authorize executable bodies
in a contract-only `index.nct`. Module discovery, root/body matching, nominal declarations,
generics, callable values, outcomes, and async have their separate owning contracts.

This fragment imports only lexical `Name`, `integer_literal`, tokens/trivia/newline rules, and
the structural `List`/`LineSequence` notation above. It does not inherit the released `Type`,
`Expression`, callable modifiers, or binding productions.

```text
V2CoreUnit = LineSequence(V2CoreFunction)
V2CoreFunction = "func" Name "(" List(V2CoreParameter) ")" ":" V2CoreType V2CoreBlock
V2CoreParameter = Name ":" V2CoreType
V2CoreType = V2AccessQualifier? ("bool" | "i32" | "void" | "error")

V2CoreBlock = "{" LineSequence(V2CoreEntry) "}"
V2CoreEntry = V2CoreStatement | V2CoreExpression
V2CoreStatement = "let" (Name | "_") (":" V2CoreType)? "=" V2CoreExpression
                | V2CorePostfix V2CoreAssignmentOperator V2CoreExpression
                | "return" V2CoreExpression?
                | "drop" Name
                | "break" | "continue"
                | "while" V2CoreExpression V2CoreBlock
                | "loop" V2CoreBlock
V2CoreAssignmentOperator = "=" | "+=" | "-=" | "*=" | "/=" | "%="

V2CoreExpression = V2CoreOr
V2CoreOr = V2CoreAnd ("||" V2CoreAnd)*
V2CoreAnd = V2CoreEquality ("&&" V2CoreEquality)*
V2CoreEquality = V2CoreOrdering (("==" | "!=") V2CoreOrdering)?
V2CoreOrdering = V2CoreAdd (("<" | "<=" | ">" | ">=") V2CoreAdd)?
V2CoreAdd = V2CoreMultiply (("+" | "-") V2CoreMultiply)*
V2CoreMultiply = V2CorePrefix (("*" | "/" | "%") V2CorePrefix)*
V2CorePrefix = ("!" | "-" | "&" | "^") V2CorePrefix | V2CorePostfix
V2CorePostfix = V2CorePrimary ("(" List(V2CoreExpression) ")")*
V2CorePrimary = Name | integer_literal | "true" | "false" | "(" ")"
              | "(" V2CoreExpression ")" | V2CoreIf
V2CoreIf = "if" V2CoreExpression V2CoreBlock
           ("else" (V2CoreBlock | V2CoreIf))?
```

Calls bind before prefix operations: `^make()` transfers a call result and fails the existing-place
check; it does not mark the call's return contract. `&` has the same prefix precedence as `^`.
Only grouping is transparent to a direct call operand's marker restriction: strip outer grouping
from the callee and each argument and reject a root `&`/`^` expression. Thus `take((^value))`
does not bypass the single call spelling. An explicit operation inside a genuinely computed
operand, such as an `if` branch, executes at its authored evaluation point and is not rolled back
by a later operand failure. No context-dependent alternate parse removes the operation.

The parser retains a prefix with a non-place operand and an assignment with a non-place target;
the checker rejects their place/permission/initialization violations. In this fragment a place
is a local or parameter name, including grouping; function names are not storage places. Direct
calls resolve one named function (possibly grouped) before checking arguments. Indirect callable
values and postfix member/index access are outside this initial fragment, not forbidden by v2.0.0.
In unary position, lexical `&&` is subdivided into two update prefixes; the resulting inner access
is not an existing place. After a left operand it remains logical conjunction.

All repeated binary levels associate left. Equality/ordering have at most one ungrouped operator.
Short-circuit right operands are conditional flow edges. Newlines separate entries, with ordinary
lexical continuation inside delimiters; call openers stay on the callee's logical line. `return`
without a same-line operand is bare return. A final expression supplies the block's result; an
expression before another entry must complete with `void`. A block without a final expression
supplies normal unit completion. `if` without `else` normally produces unit and requires unit-producing branches.
The checker verifies return types, conditions, numeric operands, loop exits, and name uniqueness;
recognition cannot use their types to select a grammar path.

The built-in `error` is available as an opaque move-only data type in this fragment; no error
constructor, `throw`, or fallible result is introduced here. `void` has the one value `()` and is
Copy. Primitive numeric/Boolean/unit construction supplies fresh X; a declared I Copy result
still supplies an independent I answer. U output needs surviving eligible caller storage, with
one eligible source elided under the future origin rule. The initial corpus uses no ambiguous
multi-source output contract. Unsupported constructs must not produce an accepted core product
or fall back to the released language grammar. This development parse goal is not exposed as an
alternate user language or compatibility mode.

Within this private-function fragment, resolve every header before checking bodies. Function
names must be unique in the supplied module and parameter names unique in their own header.
Parameter/result data types and I/U/X modes never depend on a body or declaration order.
Concrete I results of `bool`, `i32`, and `void` normalize to independent Copy answers. This
normalization does not change their declared I permission. X results need no outside referent
for the result itself; neither fact erases dependencies carried inside a value.

For a retained I `error` result, the header's possible caller referents are its I/U `error`
parameters. For U results, they are its U parameters of exactly the result's data type. Consumed
X parameters are not eligible referents. Record these resolved parameter identities as an upper
bound, retaining zero, one, or several candidates. An empty bound does not create independent U
or make a local eligible: no normally producing return can satisfy that access in this fragment.
A body that never produces a result can still satisfy its result contract. Multiple private
candidates are alternatives; body checking must prove each actual return and can establish a
narrower private summary. Do not treat every candidate as simultaneously active U.

This private bound is not an inferred public `from` contract. A future public root/header still
requires the stable explicit bound specified by the origin rules when more than one source is
eligible. Do not export a private inferred union as a bodyless public contract, consult a callee
body to select a result mode, or flatten later outcome/access constructor trees into these simple
built-in contracts.

#### Core Body Typing Boundaries

The fragment's primitive arithmetic and ordering require `i32` operands, and logical operators
require `bool`. Equality requires the same admitted data type on both sides; its primitive domain
is defined in [Equality](equality-and-indexing.md#future-direction-v2-0-0-core-primitive-equality).
Integer literals default to `i32`. Decode their complete lexical magnitude before range checking;
a minus applied directly through grouping to an integer literal admits `-2147483648`. Arithmetic
retains checked overflow, division, and remainder semantics; an X operand is not a safety proof.

Primitive scalar operands are read once in left-to-right order. Preserve each prepared scalar
payload before evaluating a later operand; do not reread a changed or transferred place afterward.
For example, `value + consume(value)` can read the left scalar before an X call consumes its owner.
This is the built-in primitive operand rule, not snapshot semantics for an ordinary I call argument.
Explicit transfers still occur at their authored points, even for Copy data. Test a condition before
entering either branch, and evaluate only the selected short-circuit operand. Physical copies may
be elided when the compiler preserves these values, effects and ownership operations.

A local initializer with no normal result cannot infer a data type or access mode. An explicit
annotation can supply that contract; `never` is control interruption, not an inferred stored unit.
The discard statement remains exactly `let _ = expression`, without a type annotation. These
rules do not introduce typed patterns or partial extraction.

An explicit binding, assignment, or result contract can contextualize producing conditional
branches under the access-boundary rules. A selected call instead types each computed operand
with its natural permission, then selects preparation from the argument's place/value category
and the parameter contract. Do not insert a transfer or active update into conditional branches
merely because the parameter requires X or U. For example, passing an `if` of two plain move-only
places to X cannot silently move either source. Direct existing-place arguments retain the
contract-driven reservation/commit rules.

An `if` without `else` completes with unit when it completes normally. Its producing then branch
must have `void` data; without another explicit expected contract, materialize its Copy unit answer
and the absent branch as X unit. This does not retain an access from only one branch. A conditional
with two producing branches still obeys natural permission agreement unless an explicit expected
boundary applies. Unreachable final expressions are checked in their own expression context but
cannot contribute a function/block result after a terminating statement. Explicit `return` still
checks the declared result contract. When a condition itself never completes, do not require its
unexecuted branches to supply the surrounding result; their own operations and explicit contracts
remain checked. A non-breaking `loop`, or a literal-`true` `while` without a
reachable break, supplies no normal completion. Never derive a continuing edge from a dead break.

Typing names, data shapes, structural places, and selected calls is not full program acceptance.
Initialization, source access liveness, escaping referents, short-circuit/loop flow, and cleanup
must also succeed before the fragment supplies accepted checked-program evidence.
````

## Future Direction: v2.0.0 Named-Slot Initialization Diagnostics

The first access fragment uses `E0378` when a reached read, update, transfer, explicit drop,
compound target, or prepared/committed direct-place argument lacks definite named-slot
initialization. A complete X assignment can restore an uninitialized slot; it is not such a use.
Check compound assignment after its complete right-hand evaluation, and check every potentially
continuing loop backedge and zero-iteration edge. Code unreachable after terminating control does
not acquire fictitious initialization obligations, while its structural typing rules still apply.

Point at the attempted operation, relate the slot's declaration, and identify ownership-removal
actions on contributing paths. An earlier loop iteration may contribute the same authored action;
explain that reaching-path/backedge relationship rather than suggesting a missing type annotation.
Distinguish a definitely unavailable slot from one whose initialization is unproved across paths.

This diagnostic proves neither the validity of a retained access's outside root nor the absence of
conflicts. An initialized I/U holder can still refer to invalid or conflicting storage. Those
failures require their own lifetime/access evidence. Initialization conditions for potential cleanup
are not permission to skip required destruction or emit an executable cleanup schedule.
