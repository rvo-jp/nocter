# v0.61.0 Verified Artifact-installation Review

## Scope

This review followed a local release archive from command parsing through digest verification,
bounded extraction, candidate-home validation, publication, replacement rollback, interrupted-state
recovery, process presentation, public specification, and release qualification. It reviewed the
new paths together with the existing installation, integrity, archive-extraction, command, and CLI
responsibilities.

## Findings and Corrections

### Digest verification and extraction initially reopened the archive

The first implementation hashed the archive path, then reopened that path to obtain extraction
bytes. A concurrent replacement could therefore make the trusted digest describe different bytes
from those extracted. The installer now performs one bounded read, hashes that immutable byte
snapshot, and passes the same snapshot to the shared safe extractor. The content-integrity crate
owns byte and physical-file SHA-256 identities; the installer assigns release trust meaning.

### The process adapter initially planned installation paths

The first CLI route resolved authored relative paths, selected the default destination, and built
the installation request itself. That contradicted the established boundary in which
`nocter-command` plans user commands and `nocter-cli` only adapts process inputs and renders typed
results. Installation composition now lives in its own command module. The CLI performs only
exhaustive route selection, error projection, and result rendering.

### Interrupted state had to precede ordinary destination interpretation

Destination inspection initially occurred before recovery of an installer-owned transaction.
That allowed temporary transaction state to be interpreted as an ordinary inactive destination.
The installation authority now recognizes and closes a marked prior transaction before classifying
the destination. It validates a retained old or published new home before restoration or cleanup,
and never removes an unmarked reserved path.

## Resulting Model

- `nocter-command` owns the local path and default-destination plan.
- `nocter-installation` owns candidate interpretation, replacement policy, and recovery state.
- `nocter-content-integrity` owns digest calculation without assigning trust.
- `nocter-archive-extraction` owns bounded physical materialization without knowing release shape.
- `nocter-cli` owns process routing, stable diagnostics, and human output only.

The archive digest is an explicit caller-provided trust input. It proves identity of the one byte
snapshot that is validated; it does not prove publisher authenticity. Candidate contents are
completely validated before destination mutation. Existing destinations are replaceable only when
they are the active validated home. Reported publication failures restore the previous home when
the filesystem permits it, while a double failure retains the exact previous-home path for manual
recovery.

## Evidence

- content-integrity tests prove byte-snapshot and physical-file SHA-256 agreement;
- installation tests cover fresh publication, active replacement, digest and foreign-destination
  rejection, interrupted old-home restoration, stale marked cleanup, and unmarked-path retention;
- command tests cover the exact local archive, digest, and optional-home syntax;
- CLI tests cross the validated installed-command and output boundary; and
- local release qualification installs the generated archive into a fresh home, replaces that
  active home from the same archive, validates it with `doctor`, and compares both materialized
  homes recursively.
