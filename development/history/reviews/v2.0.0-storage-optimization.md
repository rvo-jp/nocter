# v2.0.0 Storage Optimization and Observable Effects

## Status and Authority

This is semantic/optimization closure under the user's delegated Value Access Model scope, not
compiler implementation, a benchmark result, or a complete soundness proof. It refines the
[representation freedom](../milestones/v2.0.0.md#leave-physical-representation-and-proof-placement-open-to-optimization)
already selected for v2.0.0. No new source annotation or alternative syntax is introduced.
The owning future rules are in [Memory, Regions, and Allocators](../../../spec/language/memory-and-regions.md#future-direction-v2-0-0-storage-optimization),
[Allocation and Failure](../../../std/mem/README.md#future-direction-v2-0-0-storage-optimization),
and [Vectors](../../../std/vec/README.md#future-direction-v2-0-0-storage-optimization).
Released contracts and current checked standard-library declarations remain unchanged.

The selected distinction is between a semantic value/resource obligation and its chosen physical
backing. Removing an implementation heap request may remove only its implementation-specific
out-of-memory termination when that request is optional under the owning contract. It does not
remove a promised failure, resource request, callback, budget charge, capacity reservation,
allocator affinity, validation, or destructor. Unknown obligations remain conservative.

## 1. Audit of Existing Contracts

| Authority | Constraint found | v2.0.0 closure |
| --- | --- | --- |
| [Current memory language rules](../../../spec/language/memory-and-regions.md) | Default storage failure terminates without unwinding; origins and region release are tracked | Preserve the failure policy for actual required requests; automatic backing is not a promise of one heap request |
| [Allocation guide](../../../std/mem/README.md) and [declarations](../../../std/mem/index.nct) | Recoverable adapters, layout checks, failure atomicity, backend affinity | Retain those semantic effects; an unused successful buffer alone does not justify deletion |
| [Vector guide](../../../std/vec/README.md) | Capacity reservation, unchanged state on failure, initialized-prefix ownership, construction-time allocator affinity | Keep these facts even for virtualized storage; do not defer a necessary allocation into an already reserved path |
| [Readiness boundary](v2.0.0-implementation-readiness.md#conservative-optimization-boundary) | Observable allocation/failure remains protected; private transport can change | Classify the obligation and materialization deadline rather than treating every temporary as an exact allocator event |

Current source deliberately has no arbitrary user allocator plugins. Observer/budget/unknown-backend
cases below are conservative semantic conditions and future-extension tests, not a claim that such
plugins are implemented. Ordinary API names are not compiler primitives or optimization certificates.

## 2. Values, Requests, and Backing Plans

Keep three distinct records in the checked/optimization model:

1. **Logical value and dependencies:** selected operation, initialization, I/U/X access, referent
   roots R, carried dependencies D, semantic storage/allocator requirements S, cleanup, and outcomes.
2. **Observable obligations:** resource requests, recoverable/required failure, external effects,
   budgets, capacity guarantees, supported address/ABI observations, and resource-completion order.
3. **Physical placement P:** chosen registers, stack slots, frame fields, heap blocks, alignment,
   capacity, and backing lifetimes used by one execution plan.

P is an internal plan, not a fourth source permission or an authored lifetime. Changing P cannot
erase R/D/S. In particular, a vector created with an allocator-affine contract still carries that
semantic origin even if its current bytes are eliminated. Nor can a dependent future escape a
local owner merely because its frame became a register. A placement-only dependence may disappear
when its backing is removed, but must not be confused with an API's semantic affinity or origin.

An allocation effect can be treated as optional backing only with a checked certificate derived
from the owning language/library contract and the selected implementation. A function named `new`,
a fresh X result, or absence of an authored effect modifier is insufficient. Effects of an ordinary
or opaque call remain effects until justified otherwise. Do not add keyword/attribute aliases for
`noalloc`, `notrap`, or `blocking` to express these compiler facts.

## 3. Elision and Materialization Deadlines

Compiler-generated frames, environments, transport, and temporary data need no heap backing when
a valid plan represents them otherwise. Such automatic storage does not guarantee a heap-allocation
count or the out-of-memory termination of a discarded heap plan. This is permitted representation
variation; do not execute a dummy allocator probe merely to reproduce that removed failure.

This permission is narrow. An explicit recoverable operation or a contract exposing a request,
budget, allocator callback, or prescribed failure retains it. Even when physical bytes disappear,
validation and argument evaluation may still fail or perform effects. Preserve those operations.
A known zero-size/inert path may discharge obligations through proof; no API is permanently barred
from optimization just because its general case can allocate or fail.

Before an operation promises usable capacity, exports a concrete address/ABI object, crosses an
opaque consumer boundary, or commits ownership to a computation requiring backing, discharge its
materialization obligations. Either establish that no physical backing will be required on any
relevant path, or provide it by the contract's deadline. Do not relocate a possible allocation
failure or synchronous wait into a getter, reserved append, future drive, cancellation, or destructor
that did not permit it. Unknown future demand may require eager materialization.

Call preparation must complete actual required frame/environment allocation and validation before
the invocation-time X/U commit. Elision may remove an optional physical allocation, but does not
change left-to-right evaluation, reservations, source availability, or the fixed transfer boundary.

Observable failures use ordinary trace preservation for the same environment and resource state.
Optional private backing instead admits multiple valid representations: optimized observations
must refine that abstract contract, rather than reproduce every heap-only reference-plan failure.
Do not use this distinction to erase a recoverable error or change an exact finite-budget result.

## 4. Reuse

A simple backing-block reuse needs compatible size/alignment/domain, and no remaining use of the
old bytes through direct reads, delegated access, captured dependencies, a future, foreign addresses,
or byte-reading cleanup. Source last use alone is insufficient. A user destructor still runs at
its specified semantic point, even if its unused backing is recycled. If cleanup needs the old
payload, retain that payload or postpone reuse; do not skip cleanup or present overwritten fields.

Preserve allocator affinity and backend release ownership. Reusing bytes cannot silently change
which allocator a value uses for later growth. Crossing domains needs an actual contract/proof of
compatibility, not matching pointer sizes. Reinitialization and partial cleanup obey the existing
validity rules; U cannot expose an unfilled extraction on a recoverable edge.

The simple checker below rejects reuse needing saved cleanup data or a domain conversion. That is
a limitation of that overwrite plan, not a prohibition on a stronger plan carrying the necessary
metadata or performing a permitted transfer. Semantic budget reservation can remain independently
of physical storage only when its own contract allows that separation; no fake backend request is
introduced to simulate failure.

## 5. Fusion

Producer/consumer fusion must preserve results, observed callback order, the first failure and its
payload/cause, initialization, cleanup, and dependencies. Read-only access is not purity. Even a
callback with no I/O can fail, read changing shared state, or retain access affecting later work.

For the finite pure-input-only model, simple streaming fusion is safe when intermediates have no
observable cleanup and at least one stage is total and observationally inert with no cross-stage
state dependence. More general fusion needs a checked commutation/trace argument. It is not
justified by two methods being named `map` or by callbacks lacking writes.

A minimal counterexample uses inputs `[0, -1]`. The producer fails on negative input and otherwise
returns `2*x+1`. The consumer fails on the value 1. Producing the complete intermediate first fails
at producer index 1. Streaming consumption instead fails at consumer index 0. Both callbacks have
no I/O, but they select different failures. A single unified error type does not erase that difference.

Observable intermediate cleanup also needs its original schedule. The model's reference explicitly
uses reverse production cleanup while the naive streamed plan drops each intermediate immediately.
It is a chosen source schedule, not an assertion about implicit vector element-drop order. A more
advanced plan may fuse computation while retaining the correct logical cleanup, but must validate
it separately and account for the storage it keeps.

## 6. Compiler Products and Proof Obligations

A storage/effect certificate records the selected operation and public contract identities,
checked body/callee evidence, conditional generic requirements, R/D/S preservation, required
observable effects, permitted backing alternatives, byte-use/cleanup constraints, and materialization
deadlines. A plan witness then maps logical values to P and justifies each eliminated/reused block
or reordered operation. A compound operation can contain both an optional backing event and
required I/O/validation/resource effects; do not classify the entire callable as removable.

Derive these facts from checked operations and applicable contract evidence, not header spelling.
Input-only total behavior excludes changing external reads, escaping access, failure, and cleanup
effects, not merely writes or I/O. Unknown evidence is not the empty effect set. Invalidate evidence
when its body, callee/generic witness, contract, observation policy, target, or backend facts change;
a retained cached proof cannot outlive its premises. Certificate derivation itself still needs
validation and must not become a trusted assertion supplied by an ordinary function name.

Carry selected operation identities, conditional effects, R/D/S, and materialization obligations
forward. A placement change must revalidate its physical dependencies, memory validity, required
resource effects, and async-drive constraints. It cannot reuse a stale allocation/wait summary.
Choose required runtime helpers no later than executable-program graph closure, or account for
all permitted candidates beforehand; later passes cannot discover new source dispatch or call
unlinked helpers. A late proof may remove a physical request without changing source semantics.

Required general work includes path-sensitive storage liveness, delegation/foreign escape,
constructor invariants, materialization deadlines, interprocedural effect/commutation certificates,
loop/cleanup validation, and translation validation against the chosen abstract observations.
None is established by a finite trace exploration alone. Optimization failure retains a valid
conservative plan; safety/drive failure cannot be patched by assuming an unknown operation is pure.

### Measurement Is Not a Source Observation Contract

An external profiler or post-optimization diagnostic counter does not make an otherwise private
request a source-required allocator event. Application-visible budget/callback behavior is a
separate semantic case. Do not introduce such behavior merely to count the requests an optimizer
could have removed. Separate logical resource attempts, static possible materialization sites,
and actual dynamic backend requests; they are not interchangeable counts. Instrumented timing
also includes instrumentation cost. This pass adopts no new reporting keyword or CLI option.

## 7. Finite Exploration and Limits

Run:

```sh
python3 development/history/reviews/v2.0.0-storage-optimization-check.py
```

The script checks three deliberately small models:

- 64 storage profiles, each with a validation-failure and allocation-failure bit. It accepts eight
  elision/environment observations under the narrow private-backing certificate, finds a rejection
  witness for each of 62 other profiles, and rejects eight mutants dropping requests, failure,
  observers, budget, backing validity, origin metadata, cleanup, or validation.
- 768 reuse cases over two capacities, three requested sizes, two alignments, and five Boolean
  liveness/domain/cleanup facts. It accepts 27 simple reuse cases and rejects 741 unsafe overwrite
  cases with changed observations or storage requirements.
- 18 fusion profiles over producer/consumer behaviors and resource cleanup, tested on all 40
  sequences of length zero through three over `{-1, 0, 2}`. It checks 720 trace pairs, accepts 200
  pairs covered by five sufficient streaming certificates, and finds witnesses against each of
  the 13 other unconditional fusion schemas.

The validation step in the storage fixture is explicitly recoverable; it is not a claim that
all aborting allocator validation returns an error. Origin events are proof metadata, not language
introspection. Pure scalar arithmetic in the fixture stays within bounded integer range. The
script does not infer real summaries, parse/compile Nocter, model general loops or aliases, run an
allocator/executor, model arbitrary resource availability, or prove performance/soundness of a real
optimization. The tests exercise assumed certificates and finite trace consequences, not the
soundness of deriving those certificates from library code.

No source choice requiring human writing/reading evaluation was introduced in this pass. Migration
of the selected rules is separate from implementing certificates, an optimizing IR, or native
performance experiments. The research plan's artifact results are still external evidence.
