# v0.67.0 Phase 7 Operational HTTP Service Review

**Result: complete with no open Phase 7 finding (2026-09-23).** The public HTTP service example now
composes configuration, lifecycle, HTTP, structured concurrency, redacted events, and durable local
state without creating a second implementation of any constituent contract.

## Application Authority

`configuration.nct` is the only owner of the example schema, source order, environment mapping,
argument mapping, and startup-value decoding. Standard `config` modules still own typed overlay,
validation, provenance, immutable publication, and secret-safe presentation. `operational.nct`
owns only long-running admission, reload acceptance policy, readiness, and graceful termination.
`service.nct` owns shared HTTP state, routes, event construction, persistence, and the bounded
integration scenario. No standard module knows this application policy.

The service retains one `Store` owner from startup through final shutdown. An event is rendered and
committed while holding only the store mutex, then appended while holding only the event mutex; no
task waits for one application lock while retaining the other. The durable commit therefore
precedes publication to the in-memory event list. Restart verification reads the exact committed
bytes and sequence through the public `Store` contract.

## Operational Concurrency

The operational loop races lifecycle observation with an admission computation. That admission
computation races listener acceptance with completion of an existing handler while capacity is
available, and observes only handler completion at the two-handler limit. Cancellation of
`TaskGroup.next` leaves its children owned by the group. Reload requests can therefore be observed
while handlers run, admission remains bounded, and shutdown closes the listener before draining the
same owned group under the request deadline. Per-connection failure remains connection policy and
does not terminate the service.

Reload builds and validates a separate complete candidate before comparing the startup-only listen
address and journal path. Only an accepted candidate reaches `PublishedConfiguration.publish`.
Existing handlers retain their immutable generation, rejected candidates require no rollback, and
the operating service never mutates its listener or durable owner in place.

Termination records a dedicated `service.shutdown` event after the handler group drains. Final
commit and restart verification therefore do not depend on a request having succeeded earlier in
the process lifetime. The no-request path is exercised separately after the reload scenario.

## Adversarial Review

- The example does not parse JSON, environment values, command-line options, HTTP syntax, journal
  bytes, signals, or configuration provenance itself.
- Readiness is one application-owned file and is removed after successful shutdown; it is not a
  hidden standard-library registry or compiler convention.
- Secrets reach neither structured events nor process output. The event asks the configuration
  contract for its display value rather than reading and redacting the raw token itself.
- The installed-home runner now honors the same declared arguments and environment as the source
  example runner; example execution has one repository-owned contract.
- No handler retains a configuration publication lock, event lock, or store lock across unrelated
  application work.

The complete LSP gate exposed one pre-existing checker defect through the new event-tail expression:
member-call disambiguation first attempted `receiver.member` as a complete callable place and then
rechecked `receiver` as a method receiver after a missing-field result. The failed attempt retained
checked nodes and source references, so nested calls in the receiver acquired duplicate source
projections. The checker now resolves an addressable receiver once. Callable-field lookup mutates a
private clone of that unresolved place draft; method fallback consumes the original receiver.
Neither branch can observe or retain the other's provisional place state. A focused checker test
uses a method call on an indexed value whose index itself contains a method call and validates the
complete `SourceIndex`, while the HTTP-service LSP test exercises the original failure through
hover, navigation, completion, tokens, diagnostics, and inlay hints.

## Qualification

The bounded public example proves JSON → environment → command-line precedence, concurrent
capacity, routing failures, malformed and idle connections, large streaming transfer, redaction,
incremental commit, clean close, and restart recovery. The installed-home operational test proves
exclusive cross-process ownership, two valid `SIGHUP` replacements, retention after an invalid
replacement, live HTTP observation of every published generation, `SIGTERM` drain, artifact
cleanup, clean termination before any accepted request, and absence of secret text from stdout and
stderr. Phase 8 owns whole-workspace and release-level qualification.
