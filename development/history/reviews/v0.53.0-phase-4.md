# v0.53.0 Phase 4 HTTP Operational-safety Review

## Scope

This review covers fixed server-operation deadlines, cancellation and destruction behavior,
stable failure identity, per-message storage limits, and application-owned concurrent connection
capacity.

## Findings and Resolution

### One composition owns every complete deadline

`accept_with_timeout`, `read_request_with_timeout`, and `respond_with_timeout` wrap the ordinary
operation with `task.with_timeout`. The timer therefore begins when the returned future is driven
and applies to the complete named operation. HTTP does not calculate elapsed time, TCP does not
receive a succession of restarted relative timeouts, and the codec remains unaware of clocks.

### Timeout consequences follow ownership

Accept holds an exclusive listener borrow. Expiry cancels that borrowing future and returns the
same `Server` to its caller. Request decoding and response transmission consume their connection
states; expiry destroys the suspended owner and closes its TCP stream. No timeout path returns a
partial request, partial response capability, or retryable write state. The same consequences
already apply to explicit cancellation because both paths destroy the same ordinary computation.

A native loopback case first lets accept expire, then accepts successfully through the same
listener, and finally lets a silent peer expire during request decoding. The successful public HTTP
example uses all three deadline-bearing operations while completing a client/server exchange.

### Failure identity has one layer

Expiry is the operation-level `std.http.timed_out` failure. A completed operation transfers its
original result unchanged, so TCP and codec errors retain their existing stable code. Context is
added only at the byte-operation boundary and does not replace that code. No server code compares
error messages or translates a transport representation.

### Aggregate capacity follows the actual owner

`Server` stops owning a connection when accept transfers it. A hidden connection count in the
listener would therefore be stale unless response destruction called back into server state.
Instead, the application retains each handler future in `TaskGroup` and stops accepting when its
selected count is reached. `TaskGroup.len` and `next` bound child tasks and accepted streams at the
same ownership point. Per-server `Limits` bounds each request and response body, so their product
forms an explicit aggregate storage bound.

## Deferred Boundaries

Phase 5 owns the complete multi-connection application, handler policy, editor checks, installation,
and packaging qualification. No generic server framework, implicit accept loop, connection
semaphore, keep-alive pool, or format-specific compiler operation is required for those tasks.

## Evidence

- authored-standard discovery, dependency review, visibility, and body checking;
- native accept-expiry, listener-reuse, and request-read-expiry execution;
- successful deadline-bearing public HTTP client/server loopback execution;
- existing task timeout cancellation and TCP readiness lifecycle suites;
- complete bundled-standard target-session compilation;
- formatter, metadata, documentation, and diff-integrity checks recorded with the phase commit.

## Result

No open Phase 4 finding remains. Timer ownership, stream ownership, failure identity, message limits,
and concurrent task capacity each have one authority. Timeout behavior is derived from ordinary
operation destruction instead of a parallel recovery path.
