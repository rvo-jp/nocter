# Nocter v0.5.0 Development Plan

## Purpose

v0.5.0 makes an ordinary Nocter package sufficient for sustained application development. The
release adds compiler-owned testing, package-wide editor operations, and the practical standard
library surface needed by small command-line applications. It builds on the exact package graph
and immutable editor snapshots released in v0.4.0; it does not introduce a second project model.

The released baseline is v0.4.0. Every v0.5.0 phase must preserve its source-owned `nocter.nct`,
exact dependency identity, explicit target selection, and CLI/LSP package-graph parity.

## Phase 0 Record: Published-Artifact Audit

Phase 0 completed on 2026-08-06. The published GitHub asset was downloaded into a fresh temporary
installation rather than reused from repository `dist/`. Its SHA-256 digest matched the qualified
release asset. With no `NOCTER_HOME` and a minimal environment, the installed compiler found its

No v0.4.1 blocker was found. v0.4.0 remains an immutable released baseline.

## Phase 1 Record: Explicit Package Test Targets

Phase 1 completed on 2026-08-06. It establishes the package, command, execution, and reporting
boundaries for testing before adding a new test-declaration language form.

### Source Contract

A package declares test targets explicitly in `nocter.nct`:

```nct
#test: {
    name: "unit",
    entry: "./tests/unit",
}
```

- `#test` is repeatable.
- `name` and `entry` are required strings.
- Names are unique across test targets. Test and executable namespaces remain distinct because
  `--test` and `--executable` select different target kinds.
- `entry` uses the same exact logical module resolver as executable entries and cannot escape the
  package, cross a nested package, contain `.nct`, or resolve ambiguously.
- The selected module must contain a process entry with the released `main` signature contract.
  Reusing the process ABI does not turn a test target into an executable target: it is not selected
  by `build` or `run`, produces no persistent package artifact, and is owned by a distinct typed
  target identity.
- The compiler does not scan a conventional `tests/` directory and does not synthesize targets
  from filenames.

### Command Contract

```sh
nocter test
nocter test --test unit
nocter test --locked --offline
nocter test --format json
```

- `test` is package-only. It accepts `--root`, `--test`, `--target`, `--locked`, and `--offline`.
- With no selector, targets execute in declaration order. `--test name` selects exactly one.
- Each target is compiled to a unique temporary executable and run in a separate process. A trap,
  abort, or nonzero status fails that target without preventing later targets from running.
- Status zero passes. A nonzero exit, signal termination, compilation diagnostic, graph diagnostic,
  or runner failure fails the target.
- Human output names every run and ends with passed/failed totals. JSON output uses one stable
  envelope whose `runs` keep `target` and nullable source-level `test` identities separate, plus
  outcomes, exit information, diagnostics, and aggregate process status. Phase 1 target-entry runs
  use `test: null`; Phase 2 fills it without changing the envelope model.
- Temporary artifacts are removed after every outcome. Package sources and declared output paths
  are never modified.

### Compiler Boundaries

- `ast` and `parser` own the source shape, spans, duplicate fields, and AST JSON.
- `package::targets` owns shared logical entry resolution. A new test-target model owns test
  identity and selection; CLI code does not interpret manifest strings.
- `driver::test_command` owns orchestration. A separate report model owns human/JSON presentation.
- The existing pipeline owns semantic checking, buildability, lowering, ABI, and native emission.
  The runner cannot bypass those phases or duplicate executable-entry validation.
- LSP manifest occurrences, semantic ranges, completion, and definition navigation consume the
  same typed test target and resolved module identity.

integration covers passing, nonzero, fallible failure, trap, compile failure, selection, ordering,

## Phase 2 Record: Native Test Declarations and Assertions

Phase 2 completed on 2026-08-06. It adds compiler-recognized test declarations inside test modules,
a trusted runner entry plan, failure-preserving execution, source-backed test names, and a small
`std/testing` assertion surface. It uses the Phase 1 target/report protocol rather than introducing
a second command or result model.

### Adopted Source Model

```nct
test vec_pushes_in_order {
    var values = Vec []
    values.push(1)
    assert_eq_usize(values.len(), 1)?
}
```

- `test name { ... }` is a top-level declaration with an identifier name and a fixed `void!`
  result contract. It has no visibility, parameters, generic parameters, explicit return type, or
  callable value identity.
- Test names are unique within their module. Documentation comments attach normally. A test cannot
  be imported or called by source code; only the compiler-owned test plan can select it.
- Tests can be declared in the module under test or in a separate target entry module. Same-module
  tests naturally see private items. Separate modules cross the ordinary import boundary and see
  only `pub` API; there is no test-only friend access.
- A target module containing native tests does not require or synthesize a source `main`. At Phase
  2 completion, `#test` selects its native test declarations rather than retaining a legacy-main
  compatibility mode.
- Falling through the body succeeds. `return` succeeds explicitly, and `return error` or `?`
  propagation fails with the normal `Error` payload. Assertions are library functions returning
  `void!`; neither equality nor failure formatting becomes compiler magic.

### Execution and Selection Model

- Every native declaration is a separate `TestRunId { target: TestTargetId, test: DeclarationId }`.
  Each run is lowered to a trusted process entry and executed in its own temporary native process.
  A trap cannot prevent later tests from running.
- The backend receives an explicit compiler-owned entry plan. It does not rename declarations,
  rewrite source text, synthesize an AST `main`, or discover functions by spelling after semantic
  analysis.
- `--test target` keeps selecting a package target. `--case name` selects one native declaration
  and requires `--test`; using distinct options preserves typed target and declaration namespaces.
- A target-wide parse, resolution, or type error yields one run with `test: null`. Accepted native
  declarations yield runs with the exact source test name. Human output may render
  `target::test`, but JSON always carries the two identities separately.
- The runner continues in target declaration order and then source declaration order. Summary
  counts describe executed runs, not packages or source modules.

### Assertion Boundary

`std/testing` exports `assert(condition: bool): void!` and bool, `i32`, `usize`, `u8`, and text
equality helpers needed by the standard library's own tests. Failures use stable error codes and
static payload messages, so failure reporting requires no allocation. Assertion helpers remain
ordinary Nocter functions so propagation and cleanup pass through existing language contracts.

### Completion Gate

- parser, AST JSON, formatter, duplicate-name, fixed-contract, and invalid-context coverage
- compiler-owned entry planning with no source rewriting and per-declaration reachability
- passing, assertion failure, propagated error, trap, compile failure, filtering, ordering,
  continuation, output capture, cleanup, human, and JSON integration coverage
- `std/testing` success and error payload coverage from a distributed home; its static failure
  payloads deliberately have no allocation-failure path
- LSP hover, symbols, semantic ranges, completion, definition, and diagnostics for test declarations
- complete repository verification and optimized packaged-home native test execution

### Phase 2 Verification Record

The implementation uses source-backed `TestDeclarationId` and `TestRunId` values from discovery
through runner reporting. Entry lowering receives the selected declaration directly, assigns a
compiler-private IR target, and leaves backend selection identity-based. It never rewrites source,
synthesizes a `main`, or inserts tests into the callable namespace.

Parser, AST JSON, formatter, duplicate-name validation, fixed-contract typechecking, private/public
module boundaries, target and case filtering, declaration order, independent processes, propagated
errors, traps, compile failures, continuation, captured output, cleanup, human/JSON reports,
distributed `std/testing`, hover, semantic ranges, symbols, completion, and definition are covered.
The legacy test-target `main` path was removed at the Phase 2 boundary.

## Phase 3: Package-wide Editor Index and Refactoring

Phase 3 is active.

- index every module reachable through the exact package graph without ambient directory scanning
- package-wide references and compiler-planned rename
- automatic import candidates and source edits
- code actions for missing imports, required interface members, and outcome handling
- optional provenance, allocation-effect, and inferred-type inlay hints

The index is generation-numbered snapshot state. It cannot become a mutable side cache with a
different package graph or declaration identity.

## Phase 4: Practical Standard Library

- owned path and filesystem operations
- buffered file input/output
- string and vector search, split, retain, and conversion operations
- iterator `find`, `any`, `all`, `fold`, and collection operations
- numeric/text conversion
- higher-level process argument and environment APIs

Every allocating or ownership-transferring API requires success, allocation failure, partial
initialization, cleanup, and provenance tests through the Phase 1/Phase 2 test system.

## Phase 5: Package Authoring and Stabilization

- package initialization and CI-oriented test output
- dependency-graph inspection and clearer locked/offline diagnostics
- CLI/LSP parity audit for every package target kind
- applications exercising filesystem, text, collections, dependencies, tests, and editor flows
- fresh packaged-home qualification and release preparation

## v0.5.0 Completion Definition

v0.5.0 is complete when a released-home user can create a package, write and isolate Nocter tests,
run them with stable human and JSON results, safely rename across the package graph, and build a
small filesystem-oriented command-line application using the distributed standard library.

Registries, semantic-version resolution, multi-package workspace membership, async execution,
concurrency, runtime interface dispatch, source-level lifetime parameters, and a stable
cross-version ABI are not v0.5.0 goals.
