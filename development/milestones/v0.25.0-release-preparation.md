# v0.25.0 Release Preparation

**Status: release-content candidate being prepared (2026-09-02).** This record owns the candidate
identity, qualification contract, and final local artifact evidence. Publication requires separate
explicit authorization and will receive an immutable record under `development/releases/`.

## Release Boundary

v0.25.0 adds one source-visible negative callable guarantee: `noalloc`. One checker-owned positive
allocation-effect table proves the guarantee over direct allocation and transitive semantic edges,
including callbacks, closures, interface dispatch, coercions, operators, typed literals, implicit
destruction, recursion, concrete generic substitutions, opaque witnesses, and trusted primitive
metadata. Unqualified callables remain valid and make no allocation guarantee.

The release also closes semantic query and recovery ownership exposed by the final whole-workspace
reviews. Typed failures cross query and session boundaries without reconstruction, exact body
source input is sealed by checking, target validation cannot inspect source projection, and later
stages consume frozen semantic products rather than repeating earlier decisions.

The public release notes are [`../../releases/v0.25.0.md`](../../releases/v0.25.0.md). The root
download link and public release index deliberately remain on v0.24.0 until publication.

## Candidate Identity

The release inputs agree on `0.25.0`:

- `development/packaging/VERSION`, the sole authored release-version input;
- the `#package` version in `development/std/index.nct`;
- the archive name and installed manifest derived from `VERSION` and `RELEASE.json`;
- compiler and language-server reporting derived from the validated installed home.

The exact release-content commit will be recorded after this preparation state is committed.

## Qualification Contract

The clean release-content commit must pass:

1. two independent complete locked workspace test runs in distinct external Cargo targets;
2. warnings-denied all-target Clippy in both external targets;
3. formatter, documentation generation and reproducibility, repository whitespace, and release
   metadata checks;
4. the explicit public-HTTPS dependency-acquisition test;
5. checks and representative native execution for every public example against an isolated
   candidate home;
6. two independent optimized package builds with byte-identical archives and recursively identical
   installed homes;
7. fresh extraction checks for version, doctor, help, initialization, locked/offline check and
   test, deterministic graph, native run, explicit build and execution, and framed LSP analysis;
8. rejection after either the installed compiler or standard-library content is changed, plus
   proof that ordinary qualification commands do not mutate the installed home.

## Publication Boundary

Release preparation may update candidate inputs, create the local archive, and record evidence. It
must not create or push a tag, upload an asset, publish a GitHub release, or advance `README.md` and
`releases/README.md` latest-release links. Those mutations belong to a later explicitly authorized
publication operation, which must reuse the qualified archive without rebuilding it.
